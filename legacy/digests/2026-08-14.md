### [How to Evaluate General-Purpose Robot Policies for Real-World Deployment](https://developer.nvidia.com/blog/how-to-evaluate-general-purpose-robot-policies-for-real-world-deployment/)

`RoboLab` `Robot Foundation Models` `Simulation Benchmark` `Isaac Lab-Arena` `NVIDIA Research` `Robot Policy Evaluation`

> 범용 로봇 정책을 제대로 평가할 시뮬레이션 벤치마크 RoboLab 소개

#### 요약

- 기존 시뮬레이션 벤치마크는 학습·평가 환경 중복, 고정 과제로 인한 성능 포화, 실패 원인 진단 불가, 통계적 신뢰성 부족 등의 한계를 가짐
- NVIDIA Research는 로봇·정책에 독립적인 시뮬레이션 벤치마킹 플랫폼 RoboLab과, 120개 과제로 구성된 초기 벤치마크 RoboLab-120을 공개
- 장면·과제를 몇 분 만에 새로 만들 수 있어 벤치마크 포화를 방지하고, 시각·절차·관계형 역량별로 과제를 태깅해 능력별 평가가 가능
- 성공률 외에 부분 점수, 동작 효율성(SPARC), 실행 속도, 실패 이벤트 로깅, 민감도 분석 등 다각적 진단 도구를 제공

#### 시사점

- 로봇 파운데이션 모델 개발자가 sim2real 격차를 줄이고, 실배포 전에 정책이 진짜 일반화하는지 검증할 수 있음
- 특정 로봇 임베디먼트에 종속되지 않아 다양한 로봇·정책 아키텍처를 동일 기준으로 비교 가능
- 실패가 발생한 정확한 지점과 원인을 진단할 수 있어, 데이터 기반으로 모델 개선 방향을 도출 가능

#### 용어 설명

- **RoboLab**: NVIDIA Research가 개발한 로봇 정책 평가용 시뮬레이션 벤치마킹 플랫폼
- **Real2sim**: 실제 환경 이미지를 바탕으로 시뮬레이션 환경을 재구성하는 기법
- **Gaussian Splatting**: 실사에 가까운 3D 장면을 빠르게 렌더링하는 기법
- **Clopper-Pearson 방법**: 이항 분포 성공률의 신뢰구간을 정확하게 계산하는 통계 기법
- **SPARC (Spectral Arc-Length)**: 속도의 푸리에 스펙트럼을 이용해 로봇 동작의 부드러움을 측정하는 지표
- **Neural Posterior Estimation (NPE)**: 관측된 결과로부터 원인이 되는 변수의 사후 확률분포를 추정하는 기법
- **Isaac Lab-Arena**: RoboLab 연구를 기반으로 한 NVIDIA의 오픈소스 대규모 정책 평가 프레임워크

#### 상세 내용

**기존 벤치마크가 부족한 이유**

실제 환경에서의 로봇 평가는 비용이 크고 재현이 어려워, 시뮬레이션이 대규모 평가의 대안으로 쓰인다. 하지만 기존 벤치마크에는 여러 근본적 문제가 있다.

- 학습과 평가에 같은 시각적 소스(시뮬레이션 환경)를 사용해, 높은 성능이 실제 일반화 능력이 아니라 환경 암기를 반영할 수 있음. Real2sim 방식(Gaussian Splatting 등으로 실사 환경 재구성)은 이를 개선하지만 장면당 1시간 이상 소요돼 대규모 테스트에 부적합
- 고정된 과제 세트를 반복 사용해 모델들이 빠르게 점수를 포화시키므로, 90% 이상 성공률이 흔해져 모델 간 실력 차이를 구분하기 어려움
- 성공/실패라는 이진 점수만으로는 실패 원인(물체 색상 혼동, 지시문 표현, 카메라 위치 변화 등)을 알 수 없음
- 물리 엔진과 정책에는 확률적 요소가 있어, 소수 rollout(시행)만으로는 성공률의 신뢰도를 판단하기 어려움. Clopper-Pearson 방법으로 계산하면, 70회 rollout에서 90% 성공률의 95% 신뢰구간은 80.5%~95.9%(15.4%p 폭)에 달하지만, 1,030회로 늘리면 88.0%~91.8%(±2%p)로 좁아짐. 즉 신뢰구간을 10%p에서 2%p로 좁히려면 약 15배 더 많은 rollout(70→1,030)이 필요

**RoboLab 소개**

RoboLab은 세 가지 원칙으로 설계됐다.

- 로봇에 종속되지 않으면서도 의미 있는 지표를 제공하는 평가
- 벤치마크 포화를 막기 위한 신규 과제의 빠른 생성(에이전틱 AI 워크플로 지원)
- 정책의 성능, 실패 시점, 실패 원인을 종합적으로 보여주는 분석 도구 제공

물체를 배치하고 언어 지시문을 추가한 뒤 정책을 실행하는 실제 셋업 과정을 그대로 모사하며, 전체 과정이 몇 분이면 끝난다. 코딩 에이전트가 활용할 수 있는 "agent skills"도 제공돼, 사용자가 워크플로 안에서 새 과제를 직접 생성할 수 있다.

**로봇 임베디먼트에 무관한 평가(Bring-your-own-robot)**

범용 정책을 만들려면 다양한 로봇 형태(embodiment)에 걸친 데이터가 필요하지만, 한 팀이 모든 로봇에 대해 충분한 데이터를 갖기는 어렵다. RoboLab의 과제는 로봇·정책에 독립적으로 설계돼, 같은 과제 세트를 어떤 로봇 임베디먼트나 정책 아키텍처에도 그대로 적용해 평가할 수 있다.

**역량별 과제 설계**

일반적인 조작 능력은 최소 세 가지 역량으로 구성된다.

- 시각적 역량: 색상, 크기, 의미론적 범주 등 지각 속성 인식 (예: "작은 빨간 컵 놓기")
- 절차적 역량: 쌓기, 재배치 등 행동 지향적 추론 (예: "머그컵을 바로 세우고 빨간 것끼리 선반에 쌓기")
- 관계형 역량: 접속사, 개수 세기, 상대 위치 등 공간·언어 논리 (예: "오렌지 또는 라임을 그릇에 넣기")

초기 벤치마크 RoboLab-120은 120개의 사람이 직접 만든 테이블탑 pick-and-place 과제로 구성되며, 각 과제에 필요한 역량을 태깅해 능력별 균형 잡힌 커버리지를 유지한다.

**정책 평가 방법**

성공률만으로는 로봇이 과제를 "어떻게" 수행했는지 알 수 없다. RoboLab은 다음 세 가지 평가 도구를 추가로 사용한다.

- 등급형 과제 점수: 다단계 지시문 중 일부만 완료해도 부분 점수 부여
- 궤적 품질: 경로 길이와 SPARC(속도의 푸리에 스펙트럼 기반 부드러움 지표)로 동작 효율성 측정
- 실행 속도: 엔드 이펙터(로봇 팔 끝단) 속도를 측정해 사람이 선호하는 빠른 동작을 평가

**실패 시점과 원인 진단**

실패 이벤트 로깅은 잘못된 물체 파지, 물체 낙하, 그리퍼 충돌 등을 자동으로 추적해 실행이 무너진 지점을 정확히 짚어낸다. 예를 들어 "플라스틱 병을 모두 통에 넣기" 과제에서 정책이 병을 모두 넣었지만 오렌지도 함께 넣은 경우, 과제는 기술적으로 성공했지만 중간에 잘못된 물체를 잡는 실패 이벤트가 있었음을 확인할 수 있다.

- 내장 대시보드가 에피소드 중 발생한 이벤트를 실시간으로 보여줘, 실패가 발생한 프레임으로 바로 이동 가능
- "성공했는가?" 대신 "정확히 어디서 실패했고 그 배경은 무엇인가?"를 물을 수 있는 로봇 행동용 디버거 역할

**복잡도 증가에 대한 강건성 평가**

실제 배포 환경은 벤치마크처럼 깔끔하지 않으며, 지시문 표현, 장면 혼잡도, 과제 단계 수가 다양하다.

- 언어 복잡도: RoboLab은 하나의 과제에 모호함(vague), 기본(default), 구체적(specific) 3가지 지시문 변형을 제공. 모호한 지시문일수록 실패가 잦아 현재 모델이 표현 방식에 취약함을 확인했고, 지시문이 지나치게 구체적일 때도 성능이 떨어지는 경우가 있었음
- 장면 복잡도: 방해 물체(distractor)와 시각적 노이즈가 늘어난 환경에서 정책이 목표 물체를 여전히 정확히 골라낼 수 있는지 평가
- 과제(task) 복잡도: 예를 들어 "캐비닛에 머그컵 정리하기"는 캐비닛을 먼저 열어야 하는 다단계 과제다. 대부분의 정책이 장기(long-horizon) 과제에 취약해, 4개를 초과하는 복잡한 하위 과제를 연속으로 성공한 정책은 없었음

**변화(variation)에 대한 민감도 분석**

카메라 위치 등 환경 변수를 하나씩 바꿔가며 개별 테스트하는 방식은 실험 수가 지수적으로 늘어나 비현실적이다. RoboLab은 여러 장면 변형을 동시에 평가한 뒤, Neural Posterior Estimation(NPE)으로 관측 결과 $x$에 대한 변수 $\theta$의 사후 확률분포 $p(\theta \mid x)$를 추정해, 어떤 환경 변수가 성능 저하와 가장 연관돼 있는지 정량적으로 짚어낸다.

### [Reducing High-Bandwidth Memory Bottlenecks in JAX-Based LLM Training with Host Offloading](https://developer.nvidia.com/blog/reducing-high-bandwidth-memory-bottlenecks-in-jax-based-llm-training-with-host-offloading/)

`JAX` `LLM Training` `NVIDIA Blackwell` `Host Offloading` `MaxText` `Mixture-of-Experts`

> JAX 호스트 오프로딩으로 GPU 메모리 병목을 줄여 LLM 학습 처리량을 대폭 향상

#### 요약

- LLM 학습 시 모델 가중치·그래디언트·활성값이 GPU HBM(고대역폭 메모리) 용량을 초과해 병목이 발생하는데, JAX의 호스트 오프로딩은 순전파 중 일부 활성값을 CPU 메모리로 옮겼다가 역전파 시 다시 불러오는 방식으로 이를 완화한다.
- NVIDIA Grace-Blackwell 시스템은 NVLink-C2C(900 GB/s 양방향 대역폭)로 CPU-GPU를 연결해 호스트 오프로딩에 특히 유리하며, Vera Rubin 플랫폼은 이를 1.8 TB/s로 두 배 확장한다.
- MaxText 프레임워크로 GB200 NVL72(128 GPU)에서 실험한 결과, DeepSeek-V3 671B는 오프로딩+지연 은닉 스케줄러(LHS)+파이프라이닝 조합 시 908.2 TFLOPs/s/device로 재계산 대비 57% 향상됐고, Llama 3.1 405B는 QKV 오프로딩+LHS로 2.9% 향상됐다.
- 오프로딩은 처리량 향상뿐 아니라 더 큰 배치 크기(마이크로 배치 2→8, 글로벌 배치 256→1024)를 GPU 메모리 부족(OOM) 없이 가능하게 만든다.

#### 시사점

- 대규모 MoE·MLA 기반 모델을 학습할 때 GPU 메모리 제약으로 배치 크기나 시퀀스 길이를 줄여야 했던 상황에서, 호스트 오프로딩이 재계산(rematerialization) 없이도 더 큰 배치 구성을 가능하게 해준다.
- XLA 컴파일러 플래그(LHS, 파이프라인 오프로딩) 몇 줄 설정만으로 성능을 크게 개선할 수 있어, JAX 기반 학습 파이프라인에 상대적으로 적은 구현 비용으로 적용 가능하다.
- Blackwell 이상의 NVLink-C2C 통합 아키텍처에서 효과가 가장 크므로, 하드웨어와 컴파일러의 co-design이 실질적 성능 이점으로 이어지는 사례를 보여준다.

#### 용어 설명

- **HBM (High-Bandwidth Memory)**: GPU에 탑재된 고속 메모리로, 모델 가중치·활성값 등을 저장하는 용량 제한 자원.
- **호스트 오프로딩 (Host Offloading)**: GPU 메모리 부족을 완화하기 위해 일부 데이터를 CPU(호스트) 메모리로 옮겨두는 기법.
- **NVLink-C2C**: NVIDIA Grace CPU와 Blackwell GPU를 직접 연결하는 고대역폭 인터커넥트.
- **활성값 재계산 (Activation Rematerialization)**: 역전파 시 필요한 중간 계산값을 저장 대신 다시 계산해 메모리를 절약하는 기법.
- **LHS (Latency Hiding Scheduler)**: 데이터 전송 지연을 GPU 연산과 겹쳐 실행해 숨기는 XLA 컴파일러 스케줄러.
- **MoE (Mixture-of-Experts)**: 입력마다 일부 전문가(서브 네트워크)만 선택적으로 활성화하는 희소 모델 구조.
- **MLA (Multihead Latent Attention)**: DeepSeek-V3에서 사용하는 어텐션 메커니즘 변형.

#### 상세 내용

**호스트 오프로딩이란**

모델 크기, 시퀀스 길이, 배치 크기가 커질수록 GPU HBM 용량이 학습의 주된 병목이 된다. 호스트 오프로딩은 순전파 중 선택된 활성값을 고정(pinned) 호스트 메모리로 옮기고, 역전파 시 다시 스트리밍해오는 방식으로 활성값 재계산의 대안이 된다.

**Grace Blackwell에서 유리한 이유**

- Grace CPU와 Blackwell GPU는 NVLink-C2C로 연결되어 900 GB/s의 양방향 대역폭을 제공하며, Vera CPU-Rubin GPU는 1.8 TB/s로 확장된다.
- 단, 대역폭만으로는 부족하고 활성값 전송이 실제 GPU 연산과 겹쳐(overlap) 실행되어야 성능 이점이 발생한다.

**MaxText 실험 설정**

- MaxText는 XLA 컴파일러를 사용하는 JAX 기반 LLM 학습 프레임워크이며, 모든 실험은 GB200 NVL72(128 GPU)에서 진행됐다.
- Llama 3.1 405B(dense 트랜스포머, QKV 오프로딩 대상)와 DeepSeek-V3 671B(MoE + MLA, 처리량·메모리 용량 효과 모두 평가) 두 워크로드를 사용했다.

**DeepSeek-V3 671B 오프로딩 정책**

DeepSeek-V3 671B는 61개 디코더 레이어 중 처음 3개는 dense MLP, 나머지는 MoE 블록을 사용한다. MoE 레이어에서는 MLA의 쿼리·키/값 프로젝션 중간값과 MoE up 프로젝션 중간값을 오프로딩 대상으로 선택했다.

**배치 크기 확장 효과**

- 활성값을 GPU에 저장하는 경우 마이크로 배치 2, 글로벌 배치 256까지만 가능했지만, 최적화된 호스트 오프로딩은 마이크로 배치 8, 글로벌 배치 1024를 지원했다.
- 오프로딩·재계산 둘 다 사용하지 않으면 동일 배치(마이크로 8, 글로벌 1024)에서 OOM이 발생했다.
- LHS·파이프라이닝을 활성화한 오프로딩 실행은 GPU 메모리를 165.2 GiB 사용(비활성화 시 145.6 GiB)했는데, 이는 전송 오버랩을 위해 더 많은 복사 버퍼와 프리페치된 활성값을 GPU에 유지하기 때문이다.

**Llama 3.1 405B 결과**

- 배치 크기 2, 시퀀스 길이 8,192, FSDP(완전 샤딩 데이터 병렬) 128, bfloat16 활성값 + NVFP4 4비트 가중치 양자화 조건에서 실험했다.
- QKV 오프로딩+LHS는 처리량을 2,669→2,746 TFLOPs/s/device로 2.9% 향상시켰고, LHS를 끄면 2,569 TFLOPs/s/device로 저하되어 오버랩의 중요성을 보여줬다.
- 126개 레이어 전체 QKV 활성값 저장 용량은 70.9 GiB이지만, scan_layers=True 설정으로 역전파 시 한 번에 한 레이어의 활성값(약 576 MiB)만 GPU에 필요하다.

**언제 유용한가**

- GPU 메모리가 모델 크기·시퀀스 길이·배치 크기를 제한하고, 오프로딩 대상 텐서가 충분히 클 때 효과적이다.
- 오프로딩 성능은 전송 지연을 숨길 만큼 충분한 연산·통신 작업이 있는지에 좌우된다.
- 텐서가 작거나, 겹칠 독립 작업이 부족하거나, 메모리 외의 다른 요인이 병목인 경우에는 효과가 제한적이다.

**시작 방법**

- 대표성 있는 소규모 JAX 학습으로 시작해 큰 활성값을 선정하고, 오프로딩을 적용한 뒤 GPU/호스트 메모리 사용량과 스텝 시간을 측정한다.
- 오픈소스 JAX API는 `jax.remat`, 체크포인트 정책, `memory_kind="pinned_host"`, `jax.device_put()`을 활용한다.
- 실험에는 다음 XLA 플래그가 사용됐다: `--xla_gpu_enable_latency_hiding_scheduler=true`, `--xla_gpu_enable_pipelined_host_offloading=true`, `--xla_gpu_experimental_parallel_async_compute_limit=8`.
- NVIDIA Nsight Systems 등 프로파일링 도구로 디바이스-호스트 간 복사가 연산·NCCL 통신과 실제로 겹치는지 확인해야 한다.

**대상 독자**: JAX로 대규모 LLM(특히 MoE·dense 트랜스포머)을 학습하며 GPU HBM 용량 한계에 부딪힌 ML 인프라 엔지니어, 그리고 NVIDIA GB200/GB300, Vera Rubin 플랫폼에서 학습 처리량과 배치 크기를 최적화하려는 개발자에게 유용하다.

### [Kernel Fusion in NVIDIA CUDA: Optimizing Memory Traffic and Launch Overhead](https://developer.nvidia.com/blog/kernel-fusion-in-nvidia-cuda-optimizing-memory-traffic-and-launch-overhead/)

`CUDA` `Kernel Fusion` `torch.compile` `CCCL` `cuda.compute` `GPU Optimization`

> GPU 커널 병합으로 메모리 이동량을 줄이고 최대 3배 속도를 높이는 세 가지 방법

#### 요약

- GPU는 연산 속도에 비해 메모리 대역폭이 병목이 되는 경우가 많은데, 여러 커널을 하나로 합치는 "커널 퓨전(kernel fusion)"으로 중간 결과의 전역 메모리 왕복을 없애 이를 해결할 수 있다.
- `sum(abs(x))` 예제로 수동 CUDA C++ 융합, `torch.compile`을 통한 암묵적 융합, `cuda.compute`를 통한 명시적 파이썬 융합, 이렇게 세 가지 방식을 비교한다.
- 세 방식 모두 메모리 이동량을 3GB에서 1GB로 줄여 naive 대비 약 3배 속도 향상을 달성하지만, 융합 여부를 누가 결정하는지와 결과의 예측 가능성(determinism)이 다르다.

#### 시사점

- 메모리 대역폭에 발목 잡힌 GPU 코드가 있다면, 커널을 직접 새로 짜지 않고도 `cuda.compute`의 이터레이터 조합만으로 CUB 수준의 최적화된 단일 커널을 얻을 수 있다.
- `torch.compile`은 편리하지만 융합 전략이 컴파일러 결정에 따라 달라질 수 있어, dtype이나 shape 변경만으로도 예상치 못하게 커널 수가 바뀔 수 있음을 알아야 한다.
- 성능이 critical한 라이브러리나 프레임워크를 만드는 개발자는 `cuda.compute`로 파이썬 생산성과 수동 커널 수준의 예측 가능성을 동시에 얻을 수 있다.

#### 용어 설명

- **Kernel Fusion**: 여러 개의 GPU 연산(커널)을 하나로 합쳐 중간 결과가 메모리를 거치지 않게 하는 최적화 기법.
- **CUDA Graphs**: 커널 실행·메모리 복사·동기화 순서를 하나의 재사용 가능한 객체로 캡처해 호스트 측 오버헤드를 줄이는 기능. 커널 자체를 합치지는 않는다.
- **CCCL**: NVIDIA의 C++ 코어 컴퓨트 라이브러리(CUB, Thrust, libcu++ 등)를 포함하는 최신 CUDA C++ 런타임 모음.
- **torch.compile**: PyTorch 코드를 추적해 Torch Inductor 컴파일러가 자동으로 GPU 커널(Triton 코드)을 생성해주는 기능.
- **cuda.compute**: reduce, scan, sort, transform 같은 디바이스 전역 알고리즘과 이터레이터를 파이썬에서 조합해 명시적으로 커널 융합을 지정할 수 있게 하는 라이브러리.
- **CUB**: NVIDIA의 디바이스 단위 병렬 알고리즘(리덕션, 스캔, 정렬 등)을 제공하는 CUDA C++ 라이브러리로, `cuda.compute`의 기반이 된다.
- **Grid-stride loop**: 스레드 수보다 데이터가 많을 때 각 스레드가 일정 간격(stride)으로 여러 원소를 순회하며 처리하는 CUDA 프로그래밍 패턴.

#### 상세 내용

**문제: 메모리 대역폭 병목**

GPU 연산 속도는 매우 빠르지만, 고대역폭 디바이스 메모리조차 이를 완전히 활용하지 못하는 경우가 흔하다. 여러 GPU 연산을 별도 커널로 나누면 중간 결과가 전역 메모리를 거쳐야 해서 불필요한 메모리 이동이 발생한다. 커널 퓨전은 이런 연산들을 하나의 커널로 합쳐 중간 결과를 레지스터에만 유지함으로써 이 문제를 해결한다.

- CUDA Graphs는 커널 실행 시퀀스를 캡처해 호스트 측 오버헤드(launch overhead)를 줄이는 별개의 최적화로, 커널 바디 자체를 합치지는 않는다. 두 기법은 상호 보완적으로 함께 쓸 수 있다.

**Naive 구현: 2개 커널**

`sum(abs(x))`(배열 절댓값의 합)을 예제로, 먼저 `abs`를 계산해 임시 버퍼에 쓰는 커널과 이를 리듀스하는 커널, 두 단계로 구현한다.

![Nsight Systems profile showing 65% time spent in abs kernel and 35% spent in sum kernel.](https://developer-blogs.nvidia.com/wp-content/uploads/2026/07/image-14.webp)
*이미지 출처: [원문](https://developer.nvidia.com/blog/kernel-fusion-in-nvidia-cuda-optimizing-memory-traffic-and-launch-overhead/)*

- Nsight Systems 프로파일에서 `abs_kernel`이 65%, `sum_kernel`이 35%의 시간을 차지하며, 두 커널이 독립적으로 실행되고 중간 결과가 필요하다.

**수동 커널 융합**

두 커널을 하나의 `sum_abs_kernel`로 재작성하면 중간 버퍼가 사라진다.

- `fabsf(x[i])`를 레지스터에서 바로 계산(inline)하고, grid-stride loop로 스레드당 여러 원소를 누적한다.
- `cub::BlockReduce`로 블록 단위 리덕션을 수행하고, `cuda::atomic_ref`로 블록당 한 스레드가 전역 결과에 원자적으로 더한다.

![Nsight Systems profile of the manually fused sum + abs kernel, showing 100% runtime for this kernel.](https://developer-blogs.nvidia.com/wp-content/uploads/2026/07/image-15.webp)
*이미지 출처: [원문](https://developer.nvidia.com/blog/kernel-fusion-in-nvidia-cuda-optimizing-memory-traffic-and-launch-overhead/)*

- 두 버전 모두 대역폭 한계(이론상 1,008GB/s의 약 90%)에 도달해 있으며, 융합 버전이 빠른 이유는 처리할 메모리 작업량 자체가 줄었기 때문이다.
- 수동 작성 커널은 최고 성능에 가장 가깝지만, 작성 노력·유지보수 비용·아키텍처 간 이식성 문제가 있다. CUB, `libcu++`, `nvmath.device`, NVSHMEM 같은 디바이스 측 라이브러리가 이를 완화해준다.

**암묵적 커널 융합: torch.compile**

파이썬으로 연산을 기술하고 컴파일러가 커널을 생성하게 하는 방식으로, `torch.compile`이 이를 수행한다. 내부적으로 Torch Inductor가 코드를 분석해 Triton 커널을 만든다.

*이미지 출처: [원문](https://developer.nvidia.com/blog/kernel-fusion-in-nvidia-cuda-optimizing-memory-traffic-and-launch-overhead/)*

- Eager 모드(컴파일 없음)는 예상대로 `abs`, `sum` 각각 별도 커널 2개를 실행한다.
- 컴파일 버전도 커널 2개(`triton_red_fused_abs_sum_0`, `_1`)가 생성되지만, 생성된 Triton 코드를 보면 `abs`가 리덕션 커널 내부 레지스터에서 인라인으로 계산되어 원소별 중간 버퍼는 없다. 두 번째 커널은 2,048개의 블록 부분합을 하나의 스칼라로 리듀스한다.
- 컴파일러가 자동으로 융합을 해주지만, dtype·shape 변화나 연산 추가에 따라 생성되는 커널 구성이 예고 없이 바뀔 수 있어 예측 가능성이 떨어진다.

**명시적 커널 융합: cuda.compute**

`cuda.compute`는 `reduce`, `scan`, `sort`, `transform` 같은 디바이스 전역 알고리즘과, 입력을 읽는 방식을 조합할 수 있는 이터레이터를 제공한다. 커널을 직접 작성하지 않고 계산을 조합해 알고리즘에 전달하면, 개발자가 명시적으로 요청한 대로 융합이 일어난다.

- `TransformIterator`는 아무것도 할당하거나 커널을 실행하지 않는 지연(lazy) 뷰로, 원소 `i`가 요청될 때 `x[i]`를 읽고 `abs`를 적용한다.
- `reduce_into`가 이 이터레이터를 통해 단일 디바이스 전역 리덕션을 수행하며, `abs`는 전역 메모리에서 로드되는 즉시 레지스터에서 인라인으로 계산된다.
- PyTorch 텐서 외에도 DLPack이나 CUDA Array API를 구현한 CuPy 배열 등도 지원한다.

![Nsight Systems profile showing one kernel due to the kernel fusion.](https://developer-blogs.nvidia.com/wp-content/uploads/2026/07/image-18.webp)
*이미지 출처: [원문](https://developer.nvidia.com/blog/kernel-fusion-in-nvidia-cuda-optimizing-memory-traffic-and-launch-overhead/)*

- 프로파일 결과 `NondeterministicDeviceReduceAtomicKernel`이라는 단일 융합 커널로 나타난다. 이는 `cuda.compute`의 기반인 CUB가 생성한 것으로, 컴파일러 버전 변경 등으로 융합 전략이 조용히 바뀌는 일이 없어 결정론적(deterministic) 결과를 제공한다.

**세 가지 방식 비교**

| 지표 | Naive | 수동 융합 | `torch.compile` | `cuda.compute` |
|---|---|---|---|---|
| 실행 커널 수 | 2 | 1 | 2 | 1 |
| 원소별 중간 버퍼 | 있음 | 없음 | 없음 | 없음 |
| Naive 대비 속도 | – | 3배 | 3배 | 3배 |
| 융합 결정 주체 | – | 개발자 | 컴파일러 | 개발자 |
| 결정론성 | – | 완전 | 가변적 | 예측 가능 |

- 세 융합 방식 모두 1GB 메모리 이동, 약 3배 속도 향상이라는 동일한 결과에 도달하지만, 융합을 누가 통제하는지가 다르다.
- `cuda.compute`는 수동 융합처럼 명시적 보장을 제공하면서도, CUB의 검증된 최적화 구현을 그대로 활용할 수 있어 직접 커널을 유지보수할 필요가 없다.

**대상 독자**: GPU 메모리 대역폭 병목을 겪는 CUDA/PyTorch 개발자, 그리고 파이썬에서 예측 가능한 고성능 GPU 연산을 라이브러리나 프레임워크 형태로 제공하려는 개발자에게 유용하다.

### [AI Model Co-Design: Hardware-Friendly LLM Design](https://developer.nvidia.com/blog/ai-model-co-design-hardware-friendly-llm-design/)

`LLM` `GPU Architecture` `Quantization` `NVFP4` `Mixture-of-Experts` `TensorRT-LLM`

> LLM 설계 단계부터 하드웨어 특성을 고려하면 처리량과 응답성을 동시에 높일 수 있다.

#### 요약

- AI 성능은 정확도·처리량(throughput)·응답성(interactivity) 세 축으로 결정되며, 정확도를 고정하면 처리량과 응답성은 트레이드오프 관계에 놓인다.
- 모델의 은닉 차원($H$), 중간 투영 차원($H'$), 레이어 수($L$) 같은 설계 선택이 GPU에서의 연산 효율(arithmetic intensity)과 병렬화 방식에 큰 영향을 준다.
- 정사각형에 가까운 행렬 크기, 128/256/512 배수 정렬, NVFP4 양자화, 폭이 넓고 얕은 구조, 반복 가능한 레이어 패턴 등 7가지 가이드라인을 제시한다.
- Expert Parallelism, Chunked Pipeline Parallelism, Helix Parallelism 등 배포 시점의 병렬화 전략도 모델 설계와 맞물려야 최대 성능이 나온다.

#### 시사점

- 모델 아키텍처를 설계할 때부터 하드웨어 정렬(hardware alignment)을 고려하면 별도 시스템 엔지니어링 없이도 추론 속도와 비용 효율을 크게 개선할 수 있다.
- NVIDIA Model Optimizer, LLM Compressor, TensorRT-LLM 같은 툴체인이 이 가이드라인들을 실제로 적용할 수 있게 지원한다.
- 대규모 서빙을 설계하는 개발자에게는 워크로드 특성(짧은/긴 컨텍스트, 처리량/지연 중심)에 따라 어디에 최적화 노력을 집중해야 하는지에 대한 실용적 기준을 제공한다.

#### 용어 설명

- **GEMM (General Matrix Multiply)**: 두 행렬을 곱하는 연산으로, 트랜스포머의 선형 레이어 계산의 기본 단위.
- **Arithmetic Intensity**: 메모리에서 옮긴 바이트당 수행한 연산 수. 이 값이 낮으면 메모리 대역폭에, 높으면 연산 성능에 의해 성능이 제한된다.
- **NVFP4**: NVIDIA가 설계한 4비트 부동소수점 양자화 포맷으로, 정확도 손실을 최소화하면서 연산 속도를 높인다.
- **Mixture-of-Experts (MoE)**: 여러 개의 전문가(expert) 서브네트워크 중 일부만 활성화해 연산하는 모델 구조.
- **Expert Parallelism (EP)**: MoE 모델의 전문가들을 여러 GPU에 분산 배치하는 병렬화 기법.
- **Tensor Parallelism (TP)**: 하나의 레이어 연산을 여러 GPU에 나눠 수행하는 병렬화 기법.
- **Chunked Pipeline Parallelism (CPP)**: 모델 레이어와 입력 토큰을 동시에 나누어 파이프라인 형태로 처리하는 병렬화 기법.

#### 상세 내용

**세 가지 성능 축과 워크로드 유형**

AI 배포 성능은 정확도, 처리량(tokens/sec), 응답성(tokens/sec/user, 지연시간의 역수)의 균형으로 결정된다. 이 글은 정확도를 유지한 채 처리량과 응답성을 함께 끌어올리는 방법에 집중한다.

- 워크로드는 컨텍스트 길이(짧음~긴)와 서비스 목표(처리량 중심~지연 중심) 두 축으로 나뉘며, 사분면마다 시간이 소요되는 구간(어텐션, FFN, 통신 등)이 다르다.
- 암달의 법칙(Amdahl's law)에 따라, 어텐션이 실행 시간의 77%를 차지한다면 FFN을 최적화해봐야 이득이 미미하므로 병목이 어디인지 파악하는 것이 우선이다.

**선형 레이어의 하드웨어 친화적 설계**

트랜스포머의 폭(은닉 차원 $H$, 중간 차원 $H'$)과 깊이($L$)는 GEMM의 모양을 결정하며, 이는 곧 연산 효율에 직결된다. 로직상 정사각형에 가까운 GEMM일수록 연산 강도가 높아 컴퓨팅 자원을 잘 활용한다.

- 예시로 $H'=512$처럼 투영 차원이 작으면, 토큰 수가 많아도 메모리 바운드(memory-bound) 상태에 머문다.
- GB300 실측 결과, reduction 차원($K$)이나 projection 차원($N$)이 작을 때 처리량이 급격히 떨어지며, 지속 처리량의 80%를 얻으려면 각각 $K>3072$, $N>2560$이 필요하다.

**가이드라인 1**: 파라미터 수가 고정된 모델이라면 투영/축소 차원 중 어느 하나도 너무 작지 않게, 정사각형에 가까운 가중치 행렬을 선호한다.

**GPU의 GEMM 실행 방식과 타일 정렬**

GPU는 출력 행렬을 타일로 나눠 스트리밍 멀티프로세서(SM)가 처리한다. clusterMMA와 Cooperative Grid Array(CGA)를 통해 여러 SM이 협력해 더 큰 타일을 처리할 수 있는데, 모델 차원이 이 타일 크기의 배수가 아니면 일부 연산 자원이 낭비된다(타일 양자화).

- 128 배수는 안전한 최소 기준이며, 256(clusterMMA) 또는 512(CGA) 배수가 가장 높은 효율을 낸다.

**가이드라인 2**: 모델 차원은 최소 128의 배수로, 가능하면 256 또는 512 배수로 맞춘다.

**깊은 모델보다 넓은 모델이 유리**

파라미터 수가 같다면, 넓은 모델이 가중치 재사용이 많고 순차적 임계 경로(critical path)가 짧아 처리량과 응답성 모두에서 유리하다. 다만 깊이는 표현력에도 기여하므로 정확도가 유지되는 선에서만 폭을 늘려야 한다.

**가이드라인 3**: 가능하면 적고 큰 연산을 선호한다 — 즉, 얕고 넓은 트랜스포머가 하드웨어에 더 친화적이다.

**양자화를 통한 성능 개선**

Blackwell 시스템은 NVFP4, FP8, FP16/BF16을 지원하며, FP4는 FP16/BF16 대비 약 6배(약 15 PFLOPS vs 2.5 PFLOPS) 높은 텐서 코어 처리량을 제공한다. NVFP4는 16개 값 단위의 미세 블록마다 FP8(E4M3) 스케일과 텐서 단위의 FP32 스케일을 함께 적용하는 계층적 스케일링으로 4비트 연산 속도를 유지하면서 정확도 손실을 최소화한다.

- DeepSeek-R1 기준, NVFP4 정확도는 FP8 대비 대부분 벤치마크에서 약 1점 이내 차이이며 SciCode, Math-500, AIME 2024에서는 FP8과 동등하거나 더 우수하다.
- NVIDIA Model Optimizer와 LLM Compressor가 PTQ(학습 후 양자화), QAT(양자화 인식 학습), 캘리브레이션을 지원한다.

**가이드라인 4**: 연산 비용이 큰 레이어를 설계할 때 배포 시 양자화 가능 여부를 고려한다.

**대규모 Expert Parallelism으로 처리량 확보**

최신 LLM 상당수가 Mixture-of-Experts(MoE) 구조이며, 어텐션은 데이터 병렬(DP)로, FFN 전문가는 여러 GPU에 분산(EP)하는 방식이 효과적이다. DP 어텐션은 TP의 AllReduce 통신 오버헤드를 피할 수 있어 동시성이 커질수록 유리하다.

- GEMM-M(토큰 수)은 (전역 동시성 × top-k) / 전문가 수로 결정되며, EP를 넓게 확장할수록 GPU당 동시성과 유효 대역폭이 늘어난다.
- TensorRT-LLM의 Wide-EP 기능은 고성능 all-to-all 커널과 적응형 부하 분산기로 EP 확장의 통신 오버헤드와 전문가 부하 불균형 문제를 해결한다.

**가이드라인 5**: 전문가 수가 많은 희소(sparse) MoE 모델도 EP를 넓게 확장하면 높은 처리량을 낼 수 있다.

**파이프라인 병렬성을 고려한 설계**

prefill과 decode를 분리 배포(disaggregation)하는 전략에서, prefill은 긴 컨텍스트에서도 첫 토큰 지연(FTL)을 낮게 유지해야 한다. Chunked Pipeline Parallelism(CPP)은 레이어와 입력 청크를 함께 나눠 파이프라인으로 처리해 넓은 텐서 병렬성 없이도 이를 달성한다.

- DeepSeek-R1 256K 입력 길이 기준, 파이프라인 병렬 크기를 늘리면 GPU당 토큰 처리량은 거의 유지되면서 FTL이 꾸준히 감소한다.
- CPP는 파이프라인 단계가 균형 잡혀 있어야 효과적이며, 불균형하면 GPU 유휴 시간(파이프라인 버블)이 생긴다.

**가이드라인 6**: 균형 있게 나눌 수 있는 규칙적이고 반복 가능한 레이어 패턴으로 모델을 설계한다.

**지연 중심 서비스를 위한 하이브리드 병렬화**

지연 중심 서빙에서는 배치가 작아질수록 FFN이 메모리 바운드가 되므로, 어텐션과 FFN을 독립적으로 병렬화해야 한다. FFN은 TP·EP·TP×EP로, 어텐션은 TP와 KV 병렬화로 가속하며, MQA/GQA/MLA처럼 KV 헤드 수가 적은 모델에서는 Helix Parallelism이 시퀀스 차원으로 KV 캐시를 샤딩해 이 병목을 해소한다. Helix는 TensorRT-LLM에서 지원된다.

**가이드라인 7**: 어텐션과 FFN의 병렬화를 분리 설계해, GPU를 늘렸을 때 지배적인 병목을 정확히 겨냥해 응답성을 높인다.

**대상 독자**: 대규모 LLM을 자체 설계하거나 파인튜닝하는 모델 개발자, 그리고 GPU 인프라에서 처리량·지연시간을 최적화해야 하는 추론 시스템 엔지니어에게 유용하다.

### [Accelerating End-to-End Co-Folding Performance with NVIDIA BioNeMo Agent Toolkit](https://developer.nvidia.com/blog/accelerating-end-to-end-co-folding-performance-with-nvidia-bionemo-agent-toolkit/)

`NVIDIA BioNeMo` `OpenFold3` `cuEquivariance` `NIM` `Blackwell` `Drug Discovery`

> MSA부터 멀티 GPU 확장까지, 단백질 코폴딩 파이프라인 전 구간을 가속

#### 요약

- MSA(Multiple Sequence Alignment) 생성, 코폴딩 추론, 서빙, 멀티 GPU 확장 등 구조 예측 파이프라인 전 단계를 NVIDIA가 가속
- GPU MSA(MMseqs2-GPU)로 상동성 검색을 CPU JackHMMER 대비 최대 177배 가속
- cuEquivariance와 OpenFold3 NIM으로 추론 지연시간을 최대 4배 단축, B300 단일 GPU에서 최대 약 6,400 토큰까지 처리
- Fold-CP의 컨텍스트 병렬화로 64개 B300 GPU에서 32,000 토큰까지 확장(단일 GPU 대비 약 12배)

#### 시사점

- 가상 스크리닝처럼 대규모 화합물 라이브러리를 다루는 작업에서 구조 기반 예측을 신약 개발 초기 단계부터 적용 가능
- 리보솜, 스플라이소좀 등 기존에는 계산이 불가능했던 대형 생체분자 복합체 예측이 현실적인 선택지가 됨
- BioNeMo Agent Toolkit을 통해 AI 에이전트가 MSA 생성부터 폴딩, 멀티 GPU 추론까지 도구로 호출·조합해 엔드투엔드 워크플로우를 자동 실행

#### 용어 설명

- **MSA (Multiple Sequence Alignment)**: 여러 단백질 서열을 정렬해 진화적으로 유사한 서열을 찾는 생물정보학 기법, 구조 예측의 입력으로 사용
- **Co-folding**: 단백질-리간드 등 여러 분자의 3차원 결합 구조를 동시에 예측하는 작업
- **OpenFold3**: 단백질 구조를 예측하는 오픈소스 코폴딩 모델
- **NIM (NVIDIA Inference Microservice)**: NVIDIA가 제공하는 사전 최적화된 추론용 마이크로서비스
- **cuEquivariance**: 삼각형 어텐션 등 기하학적 딥러닝 연산을 가속하는 CUDA-X 라이브러리
- **Fold-CP**: 코폴딩 모델의 메모리 요구량을 여러 GPU에 컨텍스트 병렬(context-parallel)로 분산하는 기법
- **HBM**: GPU에 탑재되는 고대역폭 메모리로, 처리 가능한 시퀀스 길이의 한계를 결정

**GPU MSA로 병목 제거**

기존에는 MSA 구축이 CPU 기반 작업이라 전체 처리 시간을 지배하는 경우가 많았다. MMseqs2-GPU는 이 상동성 검색을 GPU로 옮겨 Hopper와 Blackwell 아키텍처 모두에서 시퀀스 길이에 비례해 확장되도록 개선했다.

- 최신 GPU 가속 버전은 Grace 시스템에서 GPU 메모리보다 큰 데이터베이스 검색을 지원하고, CUDA 13.2의 Blackwell DPX 명령어로 추가 속도 향상을 제공
- 해당 GPU 가속 기능은 MMseqs2 공식 저장소에 업스트림되어 커뮤니티 전체가 활용 가능
- MSA Search NIM은 단일 L40S에서 CPU JackHMMER 대비 최대 177배 빠른 정렬을 제공(Nature Methods 논문 기준)
- H100·B300에서 1만 토큰 이상까지 매끄럽게 확장(약 1만 토큰 기준 H100 463초, B300 429초)

**cuEquivariance와 OpenFold3 NIM으로 추론 가속**

cuEquivariance는 코폴딩 연산을 지배하는 Triangle Attention, Triangle Multiplication, Attention Pair Bias 커널을 가속하는 CUDA-X 라이브러리다. B300에서 지연시간을 최대 약 3배 줄인다.

| 2,048 (B300) | 300.1초 | 97.6초 | 3.1× |

**Fold-CP로 단일 GPU를 넘어선 확장**

단일 GPU 메모리는 그동안 코폴딩 모델이 다룰 수 있는 잔기(residue) 수의 상한을 결정해 왔다. B300(Blackwell Ultra)의 더 큰 HBM과 아키텍처 효율성만으로도 한계가 크게 올라가지만, 그것으로도 부족한 경우가 있다.

- Fold-CP는 GPU당 메모리 요구량이 O(N²/P)로 줄어드는 새로운 병렬화 기법(N: 토큰 수, P: GPU 수)을 도입
- Boltz-2 모델 기준 64개 B300 GPU에서 32,000 토큰까지 처리 가능, 단일 GPU 한계 대비 약 12배 향상
- boltz-cp 코드베이스를 에이전트에 연결해 멀티 GPU 추론을 바로 요청 가능(torchrun 기반)

**활용 예시: 에이전트를 통한 실행**

각 도구는 build.nvidia.com에 호스팅된 NIM API를 자연어 프롬프트로 호출하거나, 셀프 호스팅 컨테이너로 배포해 에이전트 워크플로우에 조합할 수 있다. 예: `npx skills add NVIDIA-BioNeMo/bionemo-agent-toolkit --skill msa-search-nim`으로 MSA Search NIM을, `--skill openfold3-nim`으로 OpenFold3 NIM을 에이전트에 추가한 뒤 자연어로 "target.fasta로 MSA를 만들고 이를 이용해 폴딩하라"고 요청하는 방식이다. build.nvidia.com 엔드포인트는 대용량 요청에는 적합하지 않아 대규모 작업에는 셀프 호스팅 NIM이 권장된다.

### [Synthetic Data Generation for Financial AI Research with NVIDIA NeMo](https://developer.nvidia.com/blog/synthetic-data-generation-for-financial-ai-research-with-nvidia-nemo/)

`NVIDIA NeMo` `NeMo Data Designer` `NeMo Curator` `Nemotron` `Synthetic Data` `Financial NLP`

> 반복 생성-중복제거 루프로 금융 헤드라인 50만 개 합성 데이터셋 구축

#### 요약

- 실제 금융 뉴스는 실적·주가 관련 데이터가 편중되어 신용등급 변경 등 희귀 이벤트 데이터가 부족한 문제를 해결하기 위해 합성 데이터 생성 파이프라인을 구축
- NeMo Data Designer(구조화된 생성), NeMo Curator(시맨틱 중복 제거), Nemotron 모델(고속 헤드라인 생성)을 결합한 반복형 워크플로우 설계
- 단순 5만 건 생성 시 65%가 중복 제거되는 문제를 "생성→필터링→전역 중복제거→few-shot 예시 선별→카테고리 가중치 보정"을 반복하는 방식으로 해결
- 8-way NVIDIA B200 노드에서 약 6일간 82회 반복하여 13개 카테고리에 걸친 고유 헤드라인 502,536건을 생성

#### 시사점

- 대량 합성 데이터를 한 번에 생성하는 대신 반복적 생성-중복제거 루프를 적용하면 데이터 다양성을 크게 높일 수 있어, 금융처럼 이벤트 분포가 불균형한 도메인의 LLM 파인튜닝 데이터 확보에 활용 가능
- 생성된 데이터셋(FinHeadlineMix)과 파이프라인이 공개되어, 자체 도메인에 맞춰 재현하거나 확장할 수 있음
- 대형 teacher 모델로 라벨링한 합성 데이터를 활용한 소형 student 모델 distillation으로 비용 효율적인 파인튜닝이 가능함을 실증

#### 용어 설명

- **NeMo Data Designer**: 카테고리 샘플링, few-shot 프롬프트 등을 선언적으로 구성해 합성 데이터를 생성하는 NVIDIA 도구
- **NeMo Curator**: 대규모 텍스트 데이터의 시맨틱 중복 제거 등 데이터 정제를 담당하는 NVIDIA 라이브러리
- **Nemotron**: 본 파이프라인에서 헤드라인 생성에 사용된 NVIDIA의 LLM(Mixture-of-Experts 구조)
- **시맨틱 중복 제거(Semantic Deduplication)**: 텍스트를 임베딩으로 변환해 의미가 유사한(코사인 유사도 기준) 항목을 제거하는 기법
- **Few-shot 예시**: 모델에게 원하는 출력 스타일을 보여주기 위해 프롬프트에 포함하는 몇 개의 예시
- **K-means 클러스터링**: 임베딩 벡터들을 유사도에 따라 그룹(클러스터)으로 묶는 비지도 학습 기법
- **LoRA(Low-Rank Adaptation)**: 대형 모델의 일부 파라미터만 저비용으로 파인튜닝하는 기법

#### 상세 내용

**파이프라인 개요**

실제 금융 뉴스 피드는 실적·주가 관련 기사가 압도적으로 많고 신용등급 변경, 제품 승인 등 희귀 이벤트는 데이터가 적다. 5만 건 규모의 베이스라인 실험에서 시맨틱 중복 제거 후 고유 헤드라인은 17,348건에 불과해, 배치를 단순히 키우는 방식은 커버리지 향상에 비효율적임을 확인했다.

- 이를 해결하기 위해 매 반복마다 카테고리 가중치 기반 배치 생성 → malformed 출력 필터링 → 전체 누적 코퍼스 대비 중복 제거 → 다양한 few-shot 예시 선별 → 카테고리 가중치 조정을 수행하는 폐루프(closed loop) 구조를 설계
- 핵심 설계는 **전역 중복 제거(global deduplication)**: 각 배치를 이전 배치가 아니라 지금까지 누적된 전체 코퍼스와 비교해 배치 간 중복을 방지

![반복 헤드라인 생성 파이프라인의 5단계(Initialize, Generate, Filter, Deduplicate, Extract examples, Adjust weights) 순환 구조](https://developer-blogs.nvidia.com/wp-content/uploads/2026/06/image1-13.webp)
*이미지 출처: [원문](https://developer.nvidia.com/blog/synthetic-data-generation-for-financial-ai-research-with-nvidia-nemo/)*

**Step 1-2: 헤드라인 생성 및 품질 필터링**

vLLM으로 Nemotron 3 Nano(30B 파라미터, 활성 파라미터 3B, MoE 구조)를 4-way 텐서 병렬화와 448개 동시 요청으로 서빙했다. NeMo Data Designer는 12개 토픽 + "Other" 카테고리에 대한 가중치 샘플러와, 샘플링된 카테고리 및 현재 few-shot 예시를 조건으로 헤드라인을 생성하는 LLM 컬럼으로 구성된다.

- 다양성 확보를 위해 temperature 0.95, top_p 0.95 등 고다양성 샘플링 파라미터를 사용
- 생성 후 단어 수(5~100단어), 문자 수, 괄호 개수, 특수문자 비율 등 규칙 기반 필터를 적용했으나, 이 단계에서 제거되는 비율은 배치당 1% 미만으로 대부분의 품질 관리는 다음 단계의 시맨틱 중복 제거가 담당

**Step 3: NeMo Curator를 통한 시맨틱 중복 제거**

파이프라인의 핵심 품질 메커니즘이다. 신규 배치와 누적 코퍼스를 합쳐 `TextSemanticDeduplicationWorkflow`를 실행하며, `all-MiniLM-L6-v2`로 임베딩 → K-means로 클러스터링 → 클러스터 내 pairwise 코사인 유사도 비교 → 90% 이상 유사한 헤드라인 제거 순으로 동작한다.

- 클러스터 수는 500개로 설정: 카테고리당 1개(13개) 클러스터를 쓸 경우 비교 연산량이 약 190억 건까지 증가하지만, 500개 클러스터는 평균 클러스터 크기 약 1,000건, 총 비교량 약 5억 건 수준으로 억제
- 매 반복마다 코사인 유사도 분포의 ECDF(누적분포함수)를 모니터링해 중복 경향을 추적

**Step 4: 다음 반복을 위한 다양한 few-shot 예시 추출**

K-means 클러스터의 중심(centroid)에서 가장 먼 헤드라인을 우선 선택하는 "farthest-from-centroid" 전략으로, 해당 의미 영역에서 가장 이례적이고 정보량이 많은 예시를 뽑는다.

- 추가로 이전에 사용된 모든 few-shot 예시와 코사인 유사도 80% 이상인 후보는 제외해 반복 간 프롬프트 신호의 의미적 중복을 방지
- 선택 우선순위는 (1) centroid에서 가장 먼 예시 → (2) 유사도 필터 통과 → (3) 카테고리 풀에서 무작위 샘플 → (4) 수동 큐레이션된 시드 예시 순
- 매 반복 카테고리당 3개씩 총 39개 예시를 선정하며, 후반 반복(82회차)으로 갈수록 예시가 더 구체적이고 세부적인 내용으로 변화(예: "Google Parent Alphabet Posts $1.84 EPS..." → "ThermoGlow Posts Q2 Beat, Lifts FY Guidance on Record Orders for Ultra-Low-VOC Automotive Adhesive")

**Step 5: 동적 분포 보정**

가중 샘플링만으로는 모델이 "Other", "Stock Movement" 같은 쉬운 카테고리를 선호하는 편향을 막지 못한다. 매 반복 후 목표 분포와 실제 분포를 비교해 과소 대표 카테고리의 가중치를 높이고(비율 0.2~5.0으로 clamp), 정규화해 다음 배치에 반영한다.

- 82회차 기준 "Credit Ratings", "Product Approval" 같은 희귀 카테고리는 목표치(1%)에 근접했으나, "Other"는 여전히 과대 대표되는 경향이 남음

**결과**

- 최종 고유 헤드라인: 502,536건(목표 500,000건 초과 달성), 총 82회 반복, 배치당 35,000건

**다운스트림 활용: 모델 Distillation**

- 25,000개 라벨 데이터로 학습한 3B student 모델이 헤드라인 분류 과제에서 teacher 모델 F1-score의 95%를 달성
- 데이터셋의 시맨틱 다양성과 카테고리 균형이 실제 데이터에서 수집하기 어려운 희귀 금융 이벤트·엣지 케이스를 student 모델에 노출시키는 데 중요하게 작용

**실전 원칙**

- 대량 단일 생성이 아니라 반복적으로 생성할 것: 82회의 소규모 반복과 진화하는 프롬프트가 단일 50만 건 생성보다 훨씬 다양한 코퍼스를 만듦
- 배치 단위가 아닌 전역 단위로 중복 제거: 매 반복이 누적된 전체 데이터셋과 비교해야 배치 간 중복을 막을 수 있음

### [A Practical Guide to GPU-Initiated Communication for Molecular Dynamics at Scale](https://developer.nvidia.com/blog/a-practical-guide-to-gpu-initiated-communication-for-molecular-dynamics-at-scale/)

`GROMACS` `NVSHMEM` `Molecular Dynamics` `GPU-initiated Communication` `NVLink` `MPI`

> MPI 대신 NVSHMEM 기반 GPU 통신으로 GROMACS 분자동역학 시뮬레이션 병목 제거

#### 요약

- GROMACS의 halo exchange가 CPU-GPU 핸드오프로 인해 피크 시 CPU wall time의 50% 이상을 소비해 확장성을 제한함
- NVSHMEM을 도입해 GPU 커널이 직접 원격 메모리에 접근하도록 하여 CPU를 통신 경로에서 제거
- pack, put, wait를 하나의 fused 커널로 묶고 pulse(통신 단계) 간 의존성을 세분화해 병렬 처리
- NVLink로 연결된 GPU는 직접 메모리 store를, InfiniBand 등은 NVSHMEM put을 사용하는 인터커넥트별 최적 경로 채택

#### 시사점

- 마이크로초 단위 커널 시간대에서 강한 확장(strong scaling)을 노리는 HPC 애플리케이션은 CPU 중심 MPI 대신 GPU-native 통신 모델이 필요함을 보여줌
- halo exchange 패턴은 CFD, 천체물리, 격자 QCD 등 경계 데이터 교환이 필요한 다른 계산과학 분야에도 그대로 적용 가능
- intra-node 최대 1.5배, GB200 NVL72 멀티노드 클러스터에서 최대 2배 성능 향상을 확인해 대규모 GPU 클러스터 활용 개발자에게 실질적 이득 제공

#### 용어 설명

- **MPI (Message Passing Interface)**: 병렬 컴퓨팅에서 여러 프로세스 간 데이터를 주고받는 표준 통신 인터페이스
- **NVSHMEM**: GPU 커널이 CPU 개입 없이 직접 원격 GPU 메모리에 접근할 수 있게 하는 NVIDIA의 PGAS(Partitioned Global Address Space) 기반 통신 라이브러리
- **Halo exchange**: 시뮬레이션 공간을 여러 GPU에 나눈 뒤 경계 영역의 원자 데이터를 인접 도메인과 주고받는 알고리즘
- **RMA (Remote Memory Access)**: 원격 노드의 메모리를 직접 읽고 쓰는 통신 방식
- **TMA (Tensor Memory Accelerator)**: NVIDIA Hopper 이후 GPU에 탑재된, 데이터 복사를 SM 대신 처리하는 비동기 전용 하드웨어 엔진
- **Strong scaling**: 문제(시뮬레이션) 크기는 고정한 채 GPU 수를 늘려 처리 속도를 높이는 병렬화 방식
- **Domain decomposition (DD)**: 시뮬레이션 공간을 여러 GPU/프로세스에 나눠 할당하는 방식

#### 상세 내용

**배경: GROMACS와 통신 병목**

분자동역학(MD) 시뮬레이션은 수십만~수천만 개 원자를 femtosecond 단위로 수십억 스텝 진행하는 고비용 연산이다. GROMACS는 GPU 가속으로 스텝당 100~200마이크로초까지 도달했지만, GPU 간 통신이 확장성의 근본적 병목으로 남아있다.

- MPI는 원래 CPU 중심 실행을 위해 설계됨
- GROMACS의 halo exchange는 세 공간 축(X, Y, Z)마다 CPU가 GPU를 멈추고 데이터 전송을 조율한 뒤 재개시키는 과정을 반복
- 이 핸드오프가 피크 반복률에서 전체 CPU wall time의 50% 이상을 차지

**NVSHMEM을 이용한 가속**

NVSHMEM은 OpenSHMEM PGAS 모델 기반의 원격 메모리 접근 라이브러리로, GPU 커널이 직접 데이터 전송을 시작해 CPU를 크리티컬 패스에서 제거한다.

- GROMACS halo exchange는 중간 랭크를 거쳐 데이터를 릴레이하는 staged forwarding 방식(pulse 단위)을 사용
- 각 pulse는 경계 원자를 buffer로 모으는 pack 커널로 시작되며, Z→Y→X 단계 간 의존성 체인이 존재
- 기본 stream-triggered API(`nvshmemx_put_signal_nbi_on_stream`)는 CPU-GPU 동기화 장벽은 없애지만, 커널 경계에서만 통신이 시작되고 pulse 간 fusion이 불가능하다는 한계가 있음

**MPI 기반에서 GPU-native halo exchange로**

기존 MPI 방식은 pulse마다 pack 커널 완료를 기다리는 `cudaStreamSynchronize`와 `MPI_Waitall` 두 번의 블로킹 동기화가 필요하다. 3D 분할과 dimension당 1 pulse 기준으로 좌표 전송에 6회, force 전송에 6회, 총 12회의 블로킹 대기가 발생해 지연을 누적시킨다.

- **호스트 측 통신을 NVSHMEM으로 대체**: pack, remote put, completion-wait를 하나의 커널(`packSendBufAndPutNvshmemKernel`)로 통합해 pulse 간 CPU-GPU 장벽 제거. 다만 여전히 pulse는 순차 처리되고 pulse마다 별도 커널 launch가 필요

**NVLink 연결 GPU 간 전송 최적화**

NVLink로 연결된 GPU는 `nvshmem_ptr()`로 non-null 포인터를 얻어 상대 GPU 메모리에 직접 store할 수 있어 별도 staging buffer와 put 호출을 생략할 수 있다.

- NVLink 경로: 많은 SM이 동시에 store를 수행해야 대역폭 포화 가능
- InfiniBand 경로: 단일 스레드로 NVSHMEM put을 통한 벌크 전송만으로 충분
- 남은 병목은 pulse별 커널 launch 오버헤드와 경직된 순차 순서

**커널 퓨전을 통한 pulse 간 병렬화**

핵심 아이디어는 pulse 내 모든 원자가 이전 pulse에 의존하지는 않는다는 점이다. `dependencyAtomOffset` 기준으로 독립 원자와 의존 원자를 분리해 하나의 커널이 모든 pulse를 동시 처리한다.

- 독립 원자는 즉시 pack·전송, 의존 원자는 해당 pulse의 signal만 대기
- `packHaloCoords`가 2단계(독립 → 의존) 패킹을 수행, `loadRelaxedSys`(PTX `ld.relaxed.sys.global.u64`)로 signal 확인
- `signalPeerOnLastBlock`이 블록 완료 카운터로 마지막 블록만 선정해 시스템 스코프 signal 전송(GPU-scope release atomic + 최종 1회 system-scope release)
- **force halo exchange**는 반대 방향(X→Y→Z)으로 의존성 체인이 역전됨: 마지막 pulse의 force가 먼저 준비되고 이전 pulse가 이를 기다림
- **SM 점유율/스케줄링**: 로컬 non-bonded force 커널이 SM을 가득 채워 통신 커널이 대기해야 하는데, 기존 방식은 pulse마다 이 지연을 반복 지불하지만 fused 커널은 한 번만 지불

**NVLink 경로: TMA 기반 직접 store**

Hopper 이후 GPU에서는 SM 대신 TMA(Tensor Memory Accelerator) 비동기 복사 엔진으로 데이터 이동을 오프로드해 SM 자원을 확보한다.

- 각 warp가 독립적으로 shared memory에 pack 후 `cp_async_bulk`로 단일 TMA store 발행
- 의존 원자가 있는 warp만 리더가 signal 대기, 나머지 warp는 block-wide 동기화 없이 독립 진행

**전략 요약**

- 커널 퓨전 + 의존성 기반 분할: pulse당 6회 launch를 1회로 축소
- 계층적 release scope로 블록 동기화 경량화
- 이벤트 기반, 호스트-프리 실행: `cudaStreamSynchronize` 없이 GPU-visible signal로 의존성 표현
- 인터커넥트 인지 전송: NVLink는 직접 store, 그 외는 NVSHMEM put(InfiniBand, Slingshot 등)

**성능 결과**

NVIDIA Eos 슈퍼컴퓨터(576개 DGX H100 노드, NVLink 4.0 + 400Gb/s InfiniBand NDR)에서 water-ethanol 혼합물(45,000~23M 원자)로 벤치마크를 진행했다.

- Intra-node에서 GPU-aware MPI 대비 최대 1.5배 성능, 45,000원자·4GPU 구성에서 46% 개선(1,649 vs. 1,126 ns/day)
- GB200 NVL72 멀티노드 NVLink 클러스터에서는 최대 2배, 표준 InfiniBand 클러스터에서는 1.3배 개선
- 단, GPU 자원을 일부 소모하는 트레이드오프로 인해 대규모·연산 집약적·저노드수 구성에서는 기존 MPI가 1~3% 우위

**향후 전망**

이 접근은 CPU 중심 MPI에서 GPU-native 통신으로의 더 넓은 전환을 시사한다. Halo exchange 패턴은 CFD, 천체물리, 격자 QCD 등 도메인 분할 기반 계산과학 전반에 그대로 적용 가능하다.

- Kokkos Remote Spaces, `std::execution` 같은 분산 데이터 추상화/실행 모델이 이 패턴을 이식 가능한 인터페이스로 캡슐화하는 중
- GPU-native 확장(디바이스 주도 통신, 세분화 signal, peer 메모리 직접 접근)은 아직 OpenSHMEM 표준 범위 밖이라 표준화 필요
- GROMACS 2026부터 GPU-initiated halo exchange 사용 가능

- 파인튜닝 없이 LangChain Deep Agents의 "하니스 프로필"을 조정해 NVIDIA Nemotron 3 Ultra 모델의 에이전트 성능을 개선하는 방법을 소개.
- 평가 벤치마크로 실패 사례를 찾고, 프롬프트·미들웨어 변경으로 원인을 고친 뒤 재검증하는 반복 절차(수동 루프)를 설명.
- 이 수동 루프를 자동화한 "ralph loop" 방식(제안-검증-롤백-재검사)과 참조 구현(NemoClaw)을 시연.
- read_file 페이지네이션 실패 사례에서 미들웨어 추가로 관련 테스트 3/3 통과, 전체 벤치마크 점수가 94→96/127로 향상.

#### 시사점

- 값비싼 프론티어 모델 대신 오픈 모델 + 하니스 튜닝만으로 유사한 정확도를 확보할 수 있어 비용 효율적인 에이전트 구축이 가능해짐.
- 모델 파인튜닝 없이도 에이전트 프레임워크 레벨(프롬프트, 미들웨어, 툴 설명)에서 성능 문제를 진단·수정하는 표준 워크플로를 얻을 수 있음.
- 자동화된 개선 루프는 LangChain 외 다른 에이전트 프레임워크에도 적용 가능해, 자체 에이전트 시스템의 지속적 품질 개선 파이프라인 설계에 참고할 수 있음.

#### 용어 설명

- **LangChain Deep Agents**: 복잡한 다단계 작업(코딩, 데이터 분석 등)을 수행하도록 설계된 오픈소스 에이전트 프레임워크.
- **Harness Profile**: 모델별로 에이전트 동작(프롬프트, 툴, 미들웨어)을 커스터마이즈할 수 있게 해주는 LangChain의 확장 지점.
- **Middleware**: 에이전트의 툴 호출 전후에 개입해 요청/응답을 가공하는 코드 레이어.
- **Ralph Loop**: 모델이 상태를 읽고 한 가지 변경을 시도한 뒤 파일시스템에 기록하며 반복하는 자율 개선 루프 패턴.
- **LangSmith Engine**: 프로덕션 트레이스에서 실패를 감지·진단하고 수정안을 제안하는 LangChain의 관리형 자동화 도구.
- **Overfitting(과적합)**: 특정 테스트 케이스에만 맞춘 지나치게 구체적인 수정으로, 일반화된 개선이 아닌 경우.

#### 상세 내용

**문제 배경: 정확도 vs 비용**

에이전트 시스템은 고성능 독점 프론티어 모델(비쌈)과 저비용 오픈 모델(정확도 낮음) 사이에서 트레이드오프가 있다. 파인튜닝이 대안이지만 전문성과 학습·호스팅용 하드웨어가 필요하다.

- 최근에는 하니스별 평가 벤치마크와 모델별 커스터마이징 진입점(LangChain의 harness profile)이 등장하면서, 파인튜닝 없이 프롬프트·툴 설정만 조정해 성능을 검증 가능하게 개선하는 방식이 가능해졌다.

**수동 튜닝 절차**

Nemotron 3 Ultra용 harness profile을 만드는 절차는 다음과 같다.

- 하니스 프로필 없이 평가 벤치마크를 실행해 베이스라인 측정
- 실패 사례 분석
- 실패 원인을 해결하는 프로필 변경 제안 (프롬프트 수정, 툴/미들웨어 제외 또는 추가)
- 벤치마크 재실행으로 개선 여부와 회귀(regression) 여부 확인

실제 사례로, `read_file` 툴이 파일 마지막 줄을 찾는 테스트에서 실패했다(첫 페이지만 읽고 답변). 원인은 모델이 페이지네이션(offset/limit)으로 계속 읽어야 함을 인지하지 못한 것.

- 해결책으로 `ReadFileContinuationNoticeMiddleware`를 작성해, 반환된 라인 수가 limit에 도달하면 "파일이 더 있을 수 있다"는 안내 문구를 결과에 추가.
- 이 미들웨어를 `HarnessProfile`에 등록해 `nvidia:nemotron-ultra` 프로필로 사용.

검증 결과, read_file 테스트는 0/3 → 3/3으로 통과했고, 전체 평가 벤치마크 평균 점수는 94/127 → 96/127로 상승했다(표 1). 저자는 이 수정이 "기계적 수정"(툴 호출 방법을 가르침)이라 과적합 위험이 낮다고 설명하며, 반대로 도메인 용어의 의미를 하드코딩하는 식의 수정은 과적합 우려가 크다고 지적한다.

**하니스 프로필 생성 자동화**

수동 절차(벤치마크 실행 → 실패 분석 → 프로필 수정 → 재실행)는 반복 루프이므로 에이전트가 무인으로 수행하기에 적합하다. Geoffrey Huntley가 명명한 "ralph loop"(모델이 현재 상태를 읽고 한 가지 변경을 시도하며 파일시스템을 메모리로 사용하는 패턴)를 하니스 엔지니어링에 적용한다.

![개선 루프 다이어그램: 벤치마크 실행 → 수정 제안 → 검증 → 반복](https://developer-blogs.nvidia.com/wp-content/uploads/2026/07/image-12.webp)
*이미지 출처: [원문](https://developer.nvidia.com/blog/create-a-langchain-deep-agents-harness-profile-for-nvidia-nemotron-3-ultra-to-improve-performance/)*

LangSmith Engine은 이 루프의 LangChain 관리형 버전으로, 프로덕션 트레이스에서 실패를 감지하고 원인을 진단해 수정안을 제안하며, 회귀 방지를 위한 평가자(evaluator)를 추가한다. 각 변경은 사람이 검토 후 배포한다. 블로그는 NemoClaw 커뮤니티 저장소에 공개된 간소화된 참조 구현을 소개한다.

**개선 루프의 핵심 원칙**

- **믿기 전에 검증**: 모델 호출과 LLM 채점 벤치마크는 확률적이므로, 수정안은 동일 테스트를 여러 번 연속 통과해야 채택됨(우연한 통과 배제).
- **스냅샷과 롤백**: 시도 전 프로필을 저장하고, 도움이 안 되면 복원 — 프로필이 이전보다 나빠지는 일을 방지.
- **직전 시도로부터 학습**: 실패 시 다음 시도에 이전 시도 내용과 실패 원인을 전달해 같은 수정을 반복 제안하지 않도록 함.
- **전체 스위트 재검사**: 수정 후 해당 테스트뿐 아니라 전체 벤치마크를 재실행해 회귀 및 새로 노출된 문제를 확인.

루프는 프로필이 완전히 통과하거나, 한 라운드에서 개선이 없거나, 반복 예산이 소진될 때까지 계속된다.

**에이전트형 제안자(Proposer)**

수정 제안 단계에서 에이전트는 프로필의 쓰기 가능한 사본과, 실패 테스트·관찰된 에이전트 궤적·SDK/벤치마크 코드에 대한 읽기 전용 접근 권한을 받는다.

- read, edit, grep, glob 같은 일반 파일 툴로 미들웨어 훅이나 툴 기본 동작을 직접 확인한 뒤 최소한의 수정을 가하고, 변경 이유를 설명하는 짧은 글을 작성.
- 쓰기 권한은 프로필 파일로만 제한되며, 특정 테스트에 맞춘 땜질(hack)보다 일반화된 수정을 선호하도록 지시받음.
- 과적합 방지를 위해 평가 스위트 일부를 검증용(held-out)으로 분리할 수 있으며, 에이전트 루프는 이 테스트를 보지 못하고 점수만 검증 용도로 사용됨.

참조 구현을 Deep Agents 하니스와 Nemotron 3 Ultra에 대해 실행한 결과, `read_file` 페이지네이션 실패의 근본 원인(페이지가 다 찼다는 신호 부재)을 진단하고 미들웨어·프롬프트 수정을 제안, 3회 연속 검증 통과 후 전체 스위트에서 20→21 통과, 실패 1→0으로 개선되었다.

**다른 하니스로의 적용**

이 자동화 루프는 LangChain Deep Agents에 국한되지 않는다. 다른 에이전트 프레임워크에 적용하려면 다음 세 가지만 노출하면 된다.

- 테스트별 pass/fail 결과와 궤적을 보고하는 평가 실행 방법
- 프로그램적으로 편집·검증 가능한 프로필/설정 파일
- 수정안을 제안할 프론티어급 품질의 모델

이 세 가지가 갖춰지면 제안-검증-유지/롤백-재실행이라는 동일한 루프를 그대로 적용할 수 있다.

**대상 독자**: LangChain Deep Agents나 유사 프레임워크로 오픈소스 모델 기반 에이전트를 운영하며, 파인튜닝 없이 비용 대비 성능을 개선하고 싶은 개발자, 그리고 에이전트 품질 개선을 자동화된 평가 루프로 체계화하려는 팀에 유용하다.

### [Running Low-Latency Analytical Workloads with GPU-Accelerated Presto on NVIDIA GB200 NVL72](https://developer.nvidia.com/blog/running-low-latency-analytical-workloads-with-gpu-accelerated-presto-on-nvidia-gb200-nvl72/)

`Presto` `cuDF` `NVLink` `GB200 NVL72` `GPUDirect Storage` `DGX B200`

> GPU 가속 Presto, CPU 클러스터 대비 최대 8배 빠른 분석 쿼리 성능 달성

#### 요약

- GPU 가속 Presto는 NVIDIA cuDF 알고리즘과 NVLink 통신을 활용해 TPC-H 기반 벤치마크에서 CPU 클러스터 대비 2.5x~8.2x 낮은 지연시간을 기록
- NVIDIA GB200 NVL72(18노드)와 IBM Storage Scale을 결합한 스케일 아웃 테스트에서 I/O·통신 최적화로 총 64% 쿼리 실행시간 단축
- GPUDirect Storage(GDS)는 POSIX 방식 대비 약 2배 빠른 읽기 성능을 제공하며, GB200 NVL72에서 성능·비용 효율의 핵심 요소로 확인됨
- IBM watsonx.data 플랫폼에 통합되어 프로덕션 워크로드 테스트가 가능한 단계에 도달

#### 시사점

- 대화형 대시보드나 야간 배치 작업처럼 지연시간에 민감한 분석 워크로드를 GPU로 가속해 응답 속도를 크게 개선할 수 있음
- 데이터 파이프라인에서 스토리지-GPU 간 직접 전송(GDS)을 활용하면 CPU 병목과 메모리 복사 오버헤드를 줄여 비용 대비 성능을 높일 수 있음
- 대규모 분산 SQL 엔진을 GPU 클러스터로 확장할 때 I/O 튜닝(태스크 크기, 스레드 수)과 쿼리 재작성이 실질적인 성능 차이를 만든다는 실전 사례 제공

#### 용어 설명

- **Presto**: 대용량 데이터셋에 대해 빠른 대화형 SQL 쿼리를 실행하는 오픈소스 분산 SQL 엔진
- **cuDF**: NVIDIA GPU에서 데이터프레임 연산을 가속하는 라이브러리
- **NVLink**: GPU 간 초고속 직접 연결 기술로, GB200 NVL72에서는 세대(5.0)당 1,800GB/s 양방향 대역폭 제공
- **GPUDirect Storage (GDS)**: 스토리지 장치에서 GPU 메모리로 데이터를 직접 전송해 CPU·시스템 메모리 병목을 우회하는 기술
- **TPC-H**: 분석 쿼리 성능을 측정하기 위한 표준 벤치마크 스위트(22개 쿼리)
- **IBM Storage Scale (구 GPFS)**: POSIX 호환 병렬 파일 시스템으로 InfiniBand/RoCE 기반 RDMA 전송을 지원하는 클러스터형 스토리지
- **UcxExchange**: GPU 워커 간 고성능 데이터 교환을 담당하는 통신 계층

#### 상세 내용

**GPU 가속 Presto의 성능 우위**

DGX B200 단일 노드는 8개 GPU가 NVLink 5.0(1,800GB/s 양방향 대역폭)으로 연결되어 8개의 Presto GPU 워커를 지원한다. 벤치마크는 parquet 데이터 소스를 사용한 TPC-H 파생 쿼리 22개로 진행됐으며, 각 쿼리를 5회 실행해 마지막 4회 값을 평균했다.

- 스케일 팩터 1K(약 1TB): 8노드 CPU 클러스터 대비 GPU 1개로 2.5배, GPU 8개로 8.2배 빠른 실행 시간
- 스케일 팩터 3K(약 3TB): 10노드 CPU 클러스터 대비 GPU 3개로 3.6배, GPU 8개로 7.8배 빠른 실행 시간

![Bar chart showing Presto CPU performance with 8-10 nodes on scale factors 1K and 3K, and Presto GPU performance with 1 to 8 GPUs.](https://developer-blogs.nvidia.com/wp-content/uploads/2026/07/presto-cpu-gpu-performance.webp)
*이미지 출처: [원문](https://developer.nvidia.com/blog/running-low-latency-analytical-workloads-with-gpu-accelerated-presto-on-nvidia-gb200-nvl72/)*

**GB200 NVL72에서의 스케일 아웃**

GB200 NVL72는 총 18개 노드로 구성되며, 각 노드는 Grace CPU 2개, B200 GPU 4개, ConnectX-7(400Gbps) NIC 4개를 포함한다. 벤치마크에서는 18개 노드 중 8개 활성 노드(32개 Presto GPU 워커)를 사용했고, IBM Storage Scale(20개 스토리지 노드, 10PB 용량, 최대 대역폭 약 4.5TiB/s)을 데이터 소스로 결합했다.

최적화 단계별 성능 개선:
- GDS 활성화 + I/O 태스크 크기를 4MiB→16MiB로 확대: 약 30% 향상
- I/O 스레드를 4개→16개로 증가(NVLink 포화도 개선): 추가 약 17% 향상
- 리배칭 및 Q11 쿼리 재작성: 추가 35% 향상
- 전체 누적: 64% 빠른 쿼리 실행시간

Q11은 원래 SELECT 문에서 GPU 사용률이 5% 미만으로 떨어지는 병목(HttpExchange를 통한 워커→코디네이터 결과 전송)이 있었으나, INSERT INTO 문으로 바꿔 GPU 기반 parquet 라이터로 결과를 IBM Storage Scale에 저장하도록 하자 실행시간이 50초에서 2초로 단축됐다.

![Bar chart showing total runtime for "TPC-H derived" with 10K and 30K scale factor and node counts of eight.](https://developer-blogs.nvidia.com/wp-content/uploads/2026/07/scale-out-testing-presto-gpu-tpc-h-nvidia-gb200-nvl72.webp)
*이미지 출처: [원문](https://developer.nvidia.com/blog/running-low-latency-analytical-workloads-with-gpu-accelerated-presto-on-nvidia-gb200-nvl72/)*

**GDS를 통한 빠른 I/O**

IBM Storage Scale은 두 가지 데이터 경로를 제공한다.

- **POSIX 읽기**: 클라이언트 페이지 풀에 데이터를 스테이징한 후 GPU 메모리로 복사(현재 버전은 토폴로지 인식 미지원으로 NUMA 경계 통과 페널티 발생)
- **GDS 읽기**: RDMA를 통해 GPU 메모리에 직접 데이터를 채우며, CX7 네트워크 카드-GPU 메모리 간 경로를 동일 NUMA 노드 내로 유지

스케일 팩터 10K, 2노드(8 GPU) 환경에서 GDS 콜드 읽기는 POSIX 콜드 읽기 대비 약 2배 빠른 실행시간을 보였다.

**활용 현황**

### [NVIDIA Vera CPU Boosts AI Factory Throughput to Accelerate Agentic Workloads](https://developer.nvidia.com/blog/nvidia-vera-cpu-boosts-ai-factory-throughput-to-accelerate-agentic-workloads/)

`NVIDIA Vera CPU` `Agentic AI` `Reinforcement Learning` `KV Cache` `AI Factory` `GPU Efficiency`

> Vera CPU가 코어 성능과 지연시간을 개선해 에이전트형 AI 파이프라인 전체를 가속

#### 요약

- 에이전트 AI 워크플로는 GPU 추론 사이사이에 CPU가 담당하는 툴 호출, 코드 실행, 샌드박스 평가, KV 캐시 관리 등이 끼어들며 성능을 좌우한다.
- NVIDIA Vera CPU는 강화학습(RL) 환경 평가 완료율을 45%에서 85%로 끌어올리고, 부하 시 최대 지연시간을 x86 CPU 대비 40% 낮춘다.
- 코어당 최대 14 GB/s, 총 1.2 TB/s의 LPDDR5x 메모리 대역폭으로 수천 개의 동시 샌드박스·툴 호출을 처리한다.
- CPU 병목을 줄이면 GPU의 KV 캐시 축출과 재계산이 줄어, GPU 시간이 더 많이 실제 토큰 생성에 쓰인다.

#### 시사점

- RL 학습, 실시간 에이전트 서빙, GPU 캐시 효율이라는 세 가지 지점 모두 CPU 성능에 의해 좌우되므로, 에이전트 시스템을 설계할 때 GPU뿐 아니라 CPU 사양도 병목 요인으로 고려해야 한다.
- 툴 호출·샌드박스 실행이 많은 에이전트 파이프라인을 운영하는 개발자는 CPU 지연시간이 SLA(서비스 수준 협약) 준수와 직결됨을 이해하고 인프라를 설계할 수 있다.

#### 용어 설명

- **RL (강화학습, Reinforcement Learning)**: 모델이 시행착오와 보상 신호를 통해 정책을 개선하는 학습 방식.
- **롤아웃(rollout)**: RL에서 환경과 상호작용하며 경험 데이터를 생성하는 과정.
- **그래디언트(gradient)**: 신경망의 정책을 어떻게 업데이트할지 알려주는 수학적 지표.
- **KV 캐시**: 트랜스포머 모델이 이전 토큰들의 계산 결과를 저장해 재계산을 줄이는 메모리 구조.
- **Olympus 코어**: NVIDIA Vera CPU에 탑재된, 순차적·분기 많은 연산에 최적화된 코어 설계.
- **NUMA / 칩렛(chiplet)**: 여러 개의 다이(die)를 하나의 CPU 패키지로 묶는 구조로, 칩렛 간 이동 시 지연이 발생할 수 있다.
- **SCF (Scalable Coherency Fabric)**: NVIDIA가 설계한, 코어 간 데이터 이동을 균일하게 만드는 상호연결 패브릭.

#### 상세 내용

**에이전트 워크플로에서 CPU의 역할**

에이전트 시스템은 추론, 툴 사용, 코드 실행, 검색(retrieval), 오케스트레이션, 결과 처리 같은 다단계 워크플로로 모델의 추론을 행동으로 전환한다. 이 과정에서 GPU 사이사이에 실행되는 샌드박스 평가, 툴 호출, 코드 실행, 데이터 처리, KV 캐시 조율 등은 모두 CPU가 담당한다.

- 에이전트 AI에서 가장 중요한 CPU 지표는 소켓 전체가 부하를 받는 상태에서의 **지속적인 코어당 성능**이다.
- 코어 수는 워크플로 간 병렬성을 늘리지만, 각 워크플로가 얼마나 빨리 다음 단계로 진행하는지는 코어 속도가 결정한다.
- CPU 실행이 느려지면 (1) RL 사이클당 유효 평가 수가 줄어 학습 시간이 늘어나고, (2) 개별 사용자 응답이 느려지며, (3) KV 캐시가 축출되어 캐시된 컨텍스트의 연산 절감 효과가 사라진다.

**더 똑똑하고 효율적인 에이전트를 만드는 Vera CPU**

RL은 GPU와 CPU 사이의 지속적인 상호작용 피드백 루프를 요구한다. 환경 롤아웃(경험 데이터 생성)은 순차적이고 로직 기반의 처리에 크게 의존하기 때문에, CPU가 이 단계에서 지연되면 전체 학습 파이프라인이 타격을 입는다.

![Circular diagram of NVIDIA Vera's RL feedback loop between environment, agent, CPU, and GPU.](https://developer-blogs.nvidia.com/wp-content/uploads/2026/07/image-6.webp)

- 문제가 순차적으로 깊을수록 CPU 코어당 성능이 학습 윈도우 내 완료 가능한 환경 평가 수를 좌우한다.
- 예시로 기존 CPU는 평가의 45%만 완료하지만, Vera CPU는 코어가 1.8배 빠른 덕분에 같은 시간 내 최대 85%까지 완료한다.

이러한 향상은 RL과 에이전트 실행에 지배적인 순차적·분기 많은 작업을 위해 설계된 **NVIDIA Olympus 코어**를 통해 달성된다. 주요 특징은 다음과 같다.

- **신경망 기반 분기 예측기**: Python, 시뮬레이터, 보상 로직, 툴에서 발생하는 복잡한 제어 흐름에서도 파이프라인이 멈추지 않게 한다.

- **깊은 비순차 실행(out-of-order execution)**: 장시간 지연되는 연산 주변에서도 진행을 이어가 불규칙한 RL 워크로드의 정체를 줄인다.
- **NVIDIA Spatial Multithreading**: 수천 개의 병렬 환경으로 확장해도 코어당 높은 성능을 유지한다.

**GPU 시간당 더 많은 사용자를 서빙**

오프라인 학습에서 실시간 대화형 에이전트 서비스로 넘어가면 최적화 지표가 순수 처리량에서 엄격하고 예측 가능한 지연시간으로 바뀐다. 각 단계마다 툴 호출, 코드 실행, 테스트 컴파일, 데이터 조회 등이 모델 진행 전에 완료돼야 한다.

**세션당 GPU 연산 활용 극대화**

에이전트 추론에서 GPU는 한 번에 쭉 이어서 작동하지 않고, 모델 단계 사이에 CPU 측 툴 호출·코드 실행·검색·DB 조회·샌드박스 평가가 끼어든다. 이 공백 동안 GPU는 다른 요청을 처리하며, 원래 요청의 KV 캐시를 유지하기 어려워진다.

- 툴 호출이 끝난 뒤 GPU는 캐시된 상태에서 재개하지 못하고, 이전 시퀀스를 큰 입력 프롬프트로 다시 처리(재계산)해야 할 수 있다.
- Vera CPU는 빠른 툴 실행, 높은 코어당 성능, 높은 메모리 대역폭, 예측 가능한 지연시간으로 GPU 단계 사이 대기 시간을 줄여 KV 캐시가 축출 압력에 노출되는 시간을 단축한다.
- 결과적으로 더 많은 GPU 시간이 컨텍스트 재구성이 아닌 실제 토큰 생성에 쓰이게 된다.

### [Develop Humanoid Robot Policies End-to-End with NVIDIA Isaac GR00T](https://developer.nvidia.com/blog/develop-humanoid-robot-policies-end-to-end-with-nvidia-isaac-gr00t/)

- **LEAPP bundle**: 학습된 모델을 실제 로봇에 배포 가능한 형태로 내보낸(export) 패키지

### [Maximize Spectral Efficiency with AI-Native RAN and NVIDIA AI Aerial](https://developer.nvidia.com/blog/maximize-spectral-efficiency-with-ai-native-ran-and-nvidia-ai-aerial/)

`NVIDIA AI Aerial` `RAN` `Massive MIMO` `GPU Acceleration` `Deep Reinforcement Learning` `5G/6G`

> GPU 기반 AI-native RAN으로 매시브 MIMO의 스펙트럼 효율 한계를 돌파

#### 요약

- Massive MIMO는 이론상 스펙트럼 효율을 크게 높일 수 있지만, CPU 컴퓨팅 제약 때문에 실제 배포에서는 성능을 충분히 끌어내지 못하고 있다.
- NVIDIA AI Aerial은 병렬 컴퓨팅을 활용해 "컴퓨팅에 알고리즘을 맞추는" 방식 대신 "스펙트럼 극대화에 맞춰 알고리즘을 재설계"하는 접근을 가능하게 한다.
- AI 기반 빔포밍은 32개 레이어에서 기존 rZF 빔포밍 대비 최대 1.62배 처리량 향상을, DRL 기반 링크 적응은 셀 엣지에서 OLLA 대비 1.3배 처리량 향상을 보였다.
- SoftBank와의 실외 실증에서 GPU 기반 AI-RAN 플랫폼이 16-레이어 매시브 MU-MIMO를 안정적으로 구동하며 기존 4-레이어 대비 약 3배의 스펙트럼 효율을 달성했다.

#### 시사점

- RAN 알고리즘을 CPU 제약이 아닌 무선 성능 극대화 관점에서 재설계할 수 있어, 통신사가 기존에 확보한 값비싼 스펙트럼 자산의 가치를 더 끌어올릴 수 있다.
- GPU의 프로그래머블한 텐서 컴퓨팅 덕분에 ASIC처럼 하드웨어 교체 없이 소프트웨어만으로 AI 모델을 지속적으로 키우고 개선할 수 있다.
- 5G/6G 워크로드와 AI 추론 워크로드를 같은 GPU에서 동적으로 배분해, 트래픽이 적은 시간대의 유휴 컴퓨팅 자원을 수익화할 수 있다.

#### 용어 설명

- **RAN (Radio Access Network)**: 기지국과 단말기 간 무선 연결을 담당하는 통신망 구성 요소.
- **Massive MIMO**: 다수의 안테나를 동시에 사용해 여러 사용자에게 데이터를 병렬 전송함으로써 용량을 늘리는 무선 기술.
- **스펙트럼 효율 (Spectral Efficiency)**: 주어진 주파수 대역에서 초당 전송 가능한 데이터량(bits/second/Hertz)을 나타내는 지표.
- **빔포밍 (Beamforming)**: 안테나 신호를 조합해 특정 방향으로 신호를 집중시켜 수신 품질을 높이는 기술.
- **DRL (Deep Reinforcement Learning) 링크 적응**: 채널 상태를 관찰하며 변조/코딩 방식(MCS)을 학습 기반으로 선택하는 제어 기법.
- **OLLA (Outer-Loop Link Adaptation)**: CPU 벡터 엔진에서 동작하는 전통적인 규칙 기반 링크 적응 방식.
- **MCS (Modulation and Coding Scheme)**: 처리량과 오류율 사이의 균형을 맞추기 위해 선택하는 변조·코딩 조합.

#### 상세 내용

**GPU 가속이 스펙트럼 효율에 기여하는 이유**

RAN 파이프라인은 수학적으로 연산량이 많은 작업들로 구성되며, GPU는 이런 작업들에 특히 적합하다.

- MU-MIMO(다중 사용자 MIMO) 사용자 페어링: 대규모 사용자 풀에서 조합 탐색이 필요해 GPU의 병렬 처리와 AI 추론 능력이 요구된다.
- 빔포밍/프리코딩: 대규모 행렬 연산이 필요해 GPU의 텐서 연산 구조와 잘 맞는다.
- DRL 링크 적응: 상태 이력·ACK/NACK·CQI 등을 활용한 AI 추론에 큰 배치 처리가 필요하다.
- 채널 추정, 스케줄링, 뉴럴 리시버 등도 각각 CPU 코어 한계를 넘어서는 대규모 연산이 요구된다.

**빔포밍**

기존 rZF(정규화된 Zero Forcing) 빔포밍은 단순화된 모델에 의존해 계산량을 줄이지만, 안테나 수가 늘어날수록 SINR(신호 대 간섭 잡음비) 손실과 처리량 저하가 발생한다.

- ML 기반 빔포밍은 더 풍부한 채널 정보를 활용해 가중치를 계산하며, 연산량이 크게 증가한다.
- 64T64R MU-MIMO(16명 사용자, 레이어당 2개, SNR 0~20dB 무작위 배정) 시나리오에서 rZF는 셀당 272M FLOPs, AI 빔포밍은 2.58B FLOPs가 필요하다.
- 그 대가로 16레이어에서 1.28배, 32레이어에서 1.62배의 처리량 향상을 얻는다.

![Figure 1 shows a chart showing spectral efficiency (bits/s/Hz) versus number of layers.](https://developer-blogs.nvidia.com/wp-content/uploads/2026/07/image-1.webp)
*이미지 출처: [원문](https://developer.nvidia.com/blog/maximize-spectral-efficiency-with-ai-native-ran-and-nvidia-ai-aerial/)*

SoftBank와 NVIDIA는 GPU 기반 AI-RAN 플랫폼으로 실외 16-레이어 매시브 MU-MIMO를 안정적으로 운영했으며, 기존 4-레이어 대비 약 3배의 스펙트럼 효율을 달성했다.

**DRL 링크 적응**

링크 적응은 처리량을 극대화하면서 목표 블록 오류율(BLER)을 유지하도록 변조·코딩 방식(MCS)을 지속적으로 선택하는 MAC 계층 제어 기능이다.

- 전통적인 OLLA는 CPU 벡터 엔진에서 동작하는 경량 규칙 기반 방식이다.
- DRL 기반 링크 적응은 CQI 이력, ACK/NACK 피드백, 단기 채널 변화를 학습해 사이트별 조건에 실시간 적응한다.
- 채널 직교성 기반 사용자 페어링과 결합 시, 셀 엣지에서 OLLA 대비 1.3배 처리량 향상을 보였다.

![Figure 2 shows relative spectral efficiency at the cell edge for DRL link adaptation compared against OLLA methods.](https://developer-blogs.nvidia.com/wp-content/uploads/2026/07/image-2.webp)
*이미지 출처: [원문](https://developer.nvidia.com/blog/maximize-spectral-efficiency-with-ai-native-ran-and-nvidia-ai-aerial/)*

성능 향상의 핵심은 지연 시간 확장성에 있다. 소규모 경량 모델은 CPU에서도 구동 가능하지만, 더 큰 모델일수록 스펙트럼 효율 향상 폭이 커진다.

- GPU(TensorRT, GreenCtx 16SM) 기반 아키텍처는 396K 파라미터 모델에서도 테스트된 사용자 범위 전반에서 약 30μs의 지연 예산을 유지한다.
- 반면 단일 코어 CPU 구현은 첫 스케줄링 사용자부터 이미 지연 예산을 초과한다.
- 결과적으로 CPU는 저복잡도 모델만 지원 가능하지만, GPU는 더 큰 모델을 통해 더 큰 성능 향상을 이끌어낸다.

![Figure 3 shows a chart describing DRL MU-MIMO link adaptation model inference latency vs. batch size.](https://developer-blogs.nvidia.com/wp-content/uploads/2026/07/image-3.webp)
*이미지 출처: [원문](https://developer.nvidia.com/blog/maximize-spectral-efficiency-with-ai-native-ran-and-nvidia-ai-aerial/)*

**연구 검증**

학계 연구도 동일한 결과를 뒷받침한다.

- 학습형 리시버/파일럿 감소 기법: 스펙트럼 효율 20% 개선.
- AI 에이전트 기반 자율 네트워크 제어: URLLC 시나리오에서 OLLA 대비 BLER 67% 감소.
- 실전 DRL 링크 적응: 고이동성 시나리오에서 기존 OLLA 대비 처리량 최대 70% 증가.

**NVIDIA AI Aerial의 5가지 핵심 역량**

1. **알고리즘 우선 효율성**: CPU 예산에 맞춘 단순화된 휴리스틱 대신, 수학적으로 정밀한 AI-native L1/L2(물리 계층/MAC 계층) 모델을 실시간으로 실행한다.
2. **재설계 없는 모델 성장**: ASIC은 알고리즘을 하드웨어에 고정하지만, GPU의 프로그래머블 텐서 컴퓨팅은 소프트웨어만으로 모델 성장을 흡수한다.
3. **규모와 조정**: cuPHY와 cuMAC 간 공유 데이터 공간과 대규모 메모리 대역폭으로 셀 간 간섭 추적 등 복잡한 다중 셀 연산을 즉시 처리한다.
4. **통합 센싱·통신(ISAC)**: 무선망을 레이더 시스템처럼 활용해, 통신 처리와 딥러닝 분류 모델을 동시에 병렬 실행한다.
5. **AI 인프라 수익화**: 5G/6G와 AI 워크로드를 동일 GPU에 동적으로 배분해, 유휴 시간대 컴퓨팅 자원을 수익화 가능한 엣지 추론 애플리케이션에 활용한다.

**AI 시대의 아키텍처**

레거시 RAN에서 AI-enhanced RAN, 그리고 완전한 AI-native RAN으로의 전환은 이론적 스펙트럼 효율을 실제 성능 향상으로 전환하는 경로다.

### [Building an Analysis AI Agent for Industrial Alarm Management with NVIDIA Nemotron](https://developer.nvidia.com/blog/building-an-analysis-ai-agent-for-industrial-alarm-management-with-nvidia-nemotron/)

`NVIDIA Nemotron` `AI Agent` `NVIDIA OpenShell` `NeMo Retriever` `RAG` `CUDA-X`

#### 시사점

- 반복적인 알람 트리아지 업무를 자동화해 기술자가 복잡한 문제에 집중할 수 있게 됨
- 오픈 웨이트 모델인 Nemotron을 자체 플레이북·도메인 언어에 맞춰 파인튜닝할 수 있어 정확도를 높일 수 있음
- NeMo Agent Toolkit, AI-Q Blueprint 등 기존 NVIDIA 스택 컴포넌트를 조합해 빠르게 구축 가능

#### 용어 설명

- **NVIDIA Nemotron**: 오픈 가중치·학습 데이터를 제공하는 NVIDIA의 LLM 계열, 에이전트의 추론(reasoning)을 담당
- **NVIDIA OpenShell**: 자율 AI 에이전트를 위한 보안 샌드박스 런타임으로, YAML 정책으로 파일 접근·네트워크 활동을 통제

### [Enhancing Goodput in Large-Scale LLM Training with Nonuniform Tensor Parallelism](https://developer.nvidia.com/blog/enhancing-goodput-in-large-scale-llm-training-with-nonuniform-tensor-parallelism/)

`Tensor Parallelism` `LLM Training` `NVIDIA NVLink` `Fault Tolerance` `Megatron Core` `Distributed Systems`

> GPU 장애 시 TP 차수를 동적으로 줄여 대규모 LLM 학습 처리량을 유지하는 NTP 기법

#### 요약

- 대규모 GPU 클러스터에서 일부 장치에 일시적 문제가 생겨도 학습을 멈추지 않도록 하는 실험적 기법 Nonuniform Tensor Parallelism(NTP)을 소개.
- 텐서 병렬 그룹 내 GPU 일부가 이탈하면 남은 GPU만으로 TP 차수를 자동 축소해 해당 데이터 병렬 복제본의 학습을 지속.
- 성능 저하를 보완하기 위해 남은 GPU에 전력을 더 공급하는 파워 부스팅과, 연산 단계와 겹쳐 수행하는 효율적 리샤딩(1% 미만 오버헤드)을 결합.
- NVIDIA Megatron Core 개발 브랜치에 최근 추가되었으며, MoE 모델을 위한 Nonuniform Expert Parallelism(NEP) 연구도 진행 중.

#### 시사점

- 수천 개 GPU로 장기간 학습을 운영하는 개발자는 하드웨어 장애로 인한 처리량 손실(Goodput 저하)을 체크포인트 재시작이나 예비 장치 교체보다 더 낮은 오버헤드로 완화할 수 있는 방법을 얻게 됨.
- 하드웨어(전력·열 설계)와 소프트웨어(병렬화 전략)를 공동 설계함으로써 대규모 AI 인프라의 회복탄력성을 높이는 방향성을 보여줌.
- 아직 실험적 기능이지만, 향후 대규모 학습 인프라 설계 및 장애 대응 전략을 고민하는 엔지니어에게 참고할 만한 사례.

#### 용어 설명

- **Goodput**: 하드웨어 처리량 중 실제로 모델 수렴에 기여하는 유효한 작업량을 나타내는 지표.
- **Tensor Parallelism (TP)**: 신경망의 각 레이어를 여러 GPU에 나눠 계산하는 병렬화 기법.
- **Data Parallelism (DP)**: 동일한 모델을 여러 GPU 그룹(복제본)에 복사해 서로 다른 데이터 배치를 처리하는 병렬화 기법.
- **Scale-up domain**: NVLink 같은 초고속 인터커넥트로 촘촘히 연결된 GPU 그룹의 범위.
- **NVIDIA NVLink**: GPU 간 초고속 all-to-all 통신을 지원하는 인터커넥트 기술.
- **Resharding**: TP 차수 변경 시 모델의 텐서 조각(shard)을 남은 GPU들에 재분배하는 과정.
- **Mixture-of-Experts (MoE)**: 입력마다 일부 전문가(서브 네트워크)만 선택적으로 활성화하는 모델 구조.

#### 상세 내용

**대규모 학습의 과제**

수천 개 GPU에 걸친 LLM 학습은 텐서 병렬성(TP)으로 레이어를 나눠 처리하며, 이 GPU 그룹의 크기가 곧 scale-up domain이다.

- NVIDIA Blackwell/Blackwell Ultra 시스템은 NVLink로 최대 72개 GPU를 1,800GB/s 속도로 연결해 단일 홉 all-to-all 통신을 지원.
- 데이터 병렬성(DP)은 이런 scale-up domain을 여러 개 복제해 서로 다른 데이터 배치를 처리.
- 하나의 TP 그룹 내 GPU는 밀접하게 결합된 연산을 공유하므로, 그중 하나에 문제가 생기면 전체 그룹의 동기화가 지연되거나 재조정이 필요해짐.
- scale-up domain이 8개에서 72개 이상으로 커지면서, 정상 GPU의 가동 시간을 최대한 살리는 것이 Goodput 확보의 핵심이 됨.

The figure shows the B300 scale-up domain size of 8 GPUs while GB300 has a much larger scale-up domain size of 72 GPUs.](https://developer-blogs.nvidia.com/wp-content/uploads/2026/06/image-40.webp)

**NTP가 학습을 유지하는 방식**

NTP의 핵심 아이디어는 일시적 하드웨어 장애 중에도 DP 복제본이 계속 유효한 작업을 하도록 만드는 것이다.

- **동적 TP 차수 조정**: 8개 GPU로 구성된 TP 그룹에서 1개가 이탈하면 TP 차수를 7로 자동 전환해, 나머지 GPU가 작업량을 늘려 처리를 지속.
- **파워 부스팅**: TP 차수가 줄면 해당 DP 복제본이 느려져 전체 DP 시스템이 이를 기다리며 정체될 수 있음. 이를 막기 위해 전기·열 설계를 개선한 랙 구조로 남은 GPU에 전력을 더 공급해 클럭 속도와 연산 처리량을 일시적으로 끌어올림.
- **효율적 리샤딩**: TP 차수 변경 시 텐서 조각을 재분배하는 과정을 backward 연산 및 파라미터 동기화 단계와 겹쳐서 수행, 정상 복제본에 미치는 오버헤드를 1% 미만으로 최소화.

![Diagram showing how NTP reshards gradients before and after synchronization to hide reconfiguration costs.](https://developer-blogs.nvidia.com/wp-content/uploads/2026/06/NTP-Resharding.webp)
*이미지 출처: [원문](https://developer.nvidia.com/blog/enhancing-goodput-in-large-scale-llm-training-with-nonuniform-tensor-parallelism/)*

**향후 방향**

이 연구는 하드웨어와 소프트웨어를 함께 설계하는 것이 대규모 AI 학습의 회복탄력성 확보에 필수적임을 보여준다.

- NTP는 아직 실험적 기능이며, NVIDIA Megatron Core 개발 브랜치에 최근 추가됨.
- 표준 TP가 적합하지 않은 MoE 모델을 위해 Nonuniform Expert Parallelism(NEP)로 개념을 확장하는 연구가 진행 중.
- 프로덕션 수준의 장애 대응 기능은 NVIDIA Resiliency Extension(NVRx)에서 제공.

**대상 독자**: 수천 개 GPU 규모의 LLM 학습 인프라를 설계·운영하는 MLOps 엔지니어 및 대규모 분산 학습 시스템에 관심 있는 개발자에게 유용하다.

### [Hardware-Rooted AI Security That Won't Slow You Down](https://developer.nvidia.com/blog/hardware-rooted-ai-security-that-wont-slow-you-down/)

`Confidential Computing` `Blackwell` `NVLink` `SGLang` `Attestation` `HGX B300`

> NVIDIA Confidential Computing, 성능 저하 거의 없이 AI 추론 데이터 보호

#### 요약

- CC(Confidential Computing)는 실리콘, 인터커넥트, 시스템 소프트웨어 전반에 걸쳐 데이터·코드·모델의 무결성과 기밀성을 보장하는 보안 계층이다.
- Blackwell GPU(RTX PRO 6000, HGX B200, HGX B300)에 하드웨어 수준으로 내장되며, HGX B200/B300은 최대 8개 GPU까지 NVLink 암호화로 CC를 지원한다.
- 원격 증명(attestation)으로 워크로드 실행 전 무결성을 검증한 뒤에만 비밀 키를 배포하며, 이후 개별 추론 요청에는 추가 지연이 없다.
- Qwen3.5-397B-A17B-FP8 모델을 SGLang에서 벤치마크한 결과 CC 활성화 시 처리량·TPOT 저하는 대부분 -1%~-8% 수준으로 미미했다.

#### 시사점

- 데이터 프라이버시·주권 규제를 준수하면서도 성능 저하 없이 민감한 AI 워크로드와 독점 모델 가중치를 클라우드에서 안전하게 운영할 수 있다.
- FlashInfer, SGLang 등 추론 프레임워크의 최적화(비동기 D2H 복사, CUDA 그래프 등)를 통해 CC의 오버헤드를 실질적으로 최소화한 구체적 사례를 참고할 수 있다.

#### 용어 설명

- **Confidential Computing (CC)**: 데이터가 사용 중(in use)일 때도 암호화된 상태로 보호하는 보안 기술
- **TEE (Trusted Execution Environment)**: 하드웨어로 격리되어 외부에서 접근할 수 없는 안전한 실행 환경
- **Attestation(증명)**: 워크로드가 변조되지 않은 신뢰할 수 있는 환경에서 실행 중인지 원격으로 검증하는 절차
- **NRAS (NVIDIA Remote Attestation Service)**: GPU와 CPU의 증명 정보를 기준 무결성 매니페스트와 대조해 검증하는 NVIDIA 서비스
- **NVLink**: 여러 GPU를 고속으로 연결하는 NVIDIA의 인터커넥트 기술
- **TTFT/TPOT**: 각각 첫 토큰까지 걸리는 시간과 토큰당 생성 지연 시간을 나타내는 추론 성능 지표
- **SEV-SNP/TDX**: AMD와 Intel이 제공하는 CPU 수준의 기밀 컴퓨팅(TEE) 기술

#### 상세 내용

**데이터·코드·모델 무결성**

CC는 실리콘부터 인터커넥트, 시스템 소프트웨어까지 아우르는 보안 계층으로 데이터와 코드의 무결성·기밀성을 보장한다.

**하드웨어 신뢰 루트 (Hardware Root of Trust)**

- Blackwell GPU(RTX PRO 6000, HGX B200, HGX B300)는 제조 시점에 퓨징된 비공개 서명키를 GPU 내부에 저장하며, 이 키는 소프트웨어·펌웨어·호스트 시스템에 절대 노출되지 않는다. 이 키가 증명 체인의 근간이 된다.
- HGX B200/B300은 NVLink 암호화를 통해 최대 8개 GPU에 걸쳐 CC를 지원한다.

**증명: 실행 전 검증**

- 기밀 워크로드는 모델 복호화 키 등 비밀 정보를 받기 전 원격 증명 절차를 거친다.
- NRAS가 GPU 하드웨어 리포트와 CPU TEE(AMD SEV-SNP 또는 Intel TDX) 측정값을 기준 무결성 매니페스트(RIM)와 대조해 검증한다.
- CVM(Confidential VM)이 검증된, 변조되지 않은 상태로 확인되면 비밀이 배포된다. 증명 핸드셰이크는 보통 시작 시 1회만 발생하며, 이후 개별 추론 요청에는 지연을 추가하지 않는다.

**추론 성능 최적화**

CC로 인한 성능 영향은 두 가지 요인에서 발생한다.

- 보안 작업 제출 지연: 암호화·커널 실행 오버헤드로 작은 작업 단위일수록 영향이 크며, GPU 작업 실행당 처리량을 늘리면 완화된다.
- 호스트-디바이스 간 대역폭 감소: 입력 전송 의존도가 큰 워크로드는 암호화 전송 대역폭이 병목이 될 수 있다.

성능 최적화 기법:
- CC-safe autotuner timing: FlashInfer가 CC 모드에서 이벤트 타이머 대신 GPU 글로벌 타이머 레지스터를 사용해 커널 후보를 정확히 비교하고 가장 빠른 구현을 선택
- Async D2H copy worker: SGLang이 토큰 리드백을 스케줄러의 크리티컬 패스에서 분리해 compute/copy 오버랩을 복원
- Piecewise CUDA graph support: SGLang이 prefill 및 혼합 배치에 CUDA 그래프 리플레이를 추가해 CC 모드에서 증폭되는 커널 실행 오버헤드를 감소

**벤치마크 결과**

- HGX B300(Blackwell Ultra), Qwen/Qwen3.5-397B-A17B-FP8 모델, SGLang 서버 기준으로 측정했다.
- ISL/OSL(입력/출력 토큰 길이) 1024/1024, 8192/1024 두 조건에서 동시 요청 수(concurrency) 4~256을 테스트했다.
- CC 활성화 시 처리량(throughput)·TPOT 저하는 대체로 -1%~-8% 수준이었다. 예를 들어 concurrency 128, ISL/OSL 1024/1024에서 처리량 -7.5%, TPOT -8.1%였으며, ISL/OSL 8192/1024에서는 -1.0%~-3.6% 범위로 더 낮았다.
- 테스트 환경: Intel TDX 플랫폼, Ubuntu 25.10 호스트 / Ubuntu 24.04.4 게스트, NVIDIA Driver 595.71.05, CUDA 13.2, SGLang v0.5.12-cu130, NCCL v2.28.9-1 등.

**대상 독자**: 규제 산업(금융, 의료 등)에서 민감 데이터나 독점 모델을 클라우드 GPU에서 안전하게 추론해야 하는 인프라·보안 엔지니어, 그리고 CC 도입 시 성능 트레이드오프를 확인하려는 ML 인프라 담당자에게 유용하다.

### [Mastering Agentic Techniques: AI Agent Reinforcement Learning](https://developer.nvidia.com/blog/mastering-agentic-techniques-ai-agent-reinforcement-learning/)

`Reinforcement Learning` `GRPO` `NeMo RL` `NeMo Gym` `Nemotron` `AI Agent`

> RL로 도메인 특화 AI 에이전트를 학습시키는 실전 가이드

#### 요약

- 프롬프팅·RAG·SFT만으로 해결 안 되는 에이전트의 반복 실수, 장기 워크플로 실패 문제를 강화학습(RL)으로 해결하는 방법을 다룸
- 검증 가능한 보상(RLVR)과 GRPO 알고리즘을 활용한 최소 RL 루프(정책 모델, 태스크, 액션, 환경, 검증기, 롤아웃, 정책 업데이트) 구조를 소개
- NeMo RL, NeMo Gym, NeMo Data Designer를 활용해 도구 호출 에이전트를 학습시키는 7단계 실습 절차를 제시
- Nemotron 3 Super는 21개 NeMo Gym 검증기와 37개 데이터셋으로 약 120만 건의 환경 롤아웃을 생성해 다중 환경 RL로 사후학습됨

#### 시사점

- 오픈 모델(Nemotron 등)을 RL로 커스터마이징하면 데이터·IP·배포에 대한 통제권을 유지하면서 보안 트리아지, CLI 자동화, 데이터 분석 등 도메인 특화 에이전트를 구축할 수 있음
- 언제 RAG/프롬프팅/SFT/DPO/RLVR/RLHF 중 무엇을 써야 하는지에 대한 의사결정 기준을 얻을 수 있어, 무작정 RL부터 시도하는 시행착오를 줄일 수 있음
- 작은 모델·작은 태스크로 시작해 보상 함수와 환경을 검증한 뒤 확장하는 실용적 워크플로를 그대로 따라 할 수 있음

#### 용어 설명

- **RLVR (Reinforcement Learning with Verifiable Rewards)**: 정답 여부를 코드나 테스트로 자동 검증할 수 있는 작업에 적용하는 강화학습 방식
- **GRPO (Group Relative Policy Optimization)**: 프롬프트당 여러 응답을 생성해 그룹 내 상대 성능으로 모델을 업데이트하는 RL 알고리즘, PPO보다 구조가 단순
- **SFT (Supervised Fine-Tuning)**: 정답 예시(입력-출력 쌍)를 보여주며 모델이 특정 형식이나 행동을 모방하도록 학습시키는 방법
- **DPO (Direct Preference Optimization)**: "이 답이 저 답보다 낫다"는 선호 쌍 데이터로 모델을 학습시키는 방법
- **NeMo Gym**: 에이전트·모델·도구·검증기를 연결해 RL 학습용 환경(태스크, 하네스, 검증기, 상태)을 구축하는 NVIDIA 인프라
- **롤아웃(Rollout)**: 현재 모델이 생성한 시도(응답이나 행동 시퀀스) 샘플
- **롱호라이즌(Long-horizon) 워크플로**: 여러 단계의 도구 호출과 대화 턴을 거쳐야 완료되는 장기 작업

#### 상세 내용

**RL이 에이전트에 필요한 이유**

모델을 두뇌, 에이전트 하네스를 몸, 도구를 작업 공간에 비유하면, 하네스나 도구를 개선해도 모델 행동 자체가 바뀌지 않는 경우가 많다.

- 에이전트가 도구 호출 실수를 반복하거나, 긴 워크플로에서 실패하거나, 출력 형식을 잘못 만들거나, 잘못된 전략을 선택할 때 학습 신호가 필요
- RL은 성공을 정의하고, 시도를 생성하고, 점수를 매기고, 성공 행동의 확률을 높이도록 모델 가중치를 업데이트하는 과정
- 보상은 테스트, 도구 실행, 스키마 검증, 시뮬레이터, 리워드 모델, LLM-as-judge, 사람 선호 라벨 등 검증기(verifier)에서 나옴

![Flowchart showing RL training preparation from benchmarking a model to selecting or developing an environment, profiling rewards, training the model, and validating benchmark and capability improvements.](https://developer-blogs.nvidia.com/wp-content/uploads/2026/07/image3.webp)
*이미지 출처: [원문](https://developer.nvidia.com/blog/mastering-agentic-techniques-ai-agent-reinforcement-learning/)*

**RAG·SFT·DPO·RLVR·RLHF, 언제 무엇을 쓸까**

"어떤 알고리즘을 쓸까"가 아니라 "어떤 행동을 늘리고 싶고, 어떻게 측정할까"부터 시작해야 한다.

- 모델이 도메인 지식이 부족하면 RAG, 형식을 안 지키면 프롬프팅 후 SFT, 예시를 모방해야 하면 SFT(LoRA/QLoRA)
- 선호/비선호 출력 쌍이 있으면 DPO, 알고리즘적으로 성공 여부를 검증할 수 있으면 GRPO 기반 RLVR
- 사람의 미묘한 선호를 반영해야 하면 RLHF나 리워드 모델링
- 도구 호출·에이전트 워크플로의 일반적 경로: 필요시 SFT → 검증 가능한 보상 기반 GRPO → 평가 → 실패 분석 → 반복
- GRPO는 프롬프트당 여러 응답을 생성해 검증기로 채점하고 그룹 내 상대 성능으로 업데이트하는 방식으로, PPO 스타일보다 단순해 RLVR의 기본값으로 많이 쓰임
- 파생 기법으로 동적 샘플링과 비대칭 클리핑을 쓰는 DAPO, 토큰이 아닌 시퀀스 단위로 최적화해 MoE 모델 안정성을 높이는 GSPO가 있음

**최소 RL 루프의 7가지 요소**

정책 모델, 태스크, 액션(모델 출력·도구 호출·코드 패치 등), 환경, 검증기, 롤아웃, 정책 업데이트로 구성된다.

- 학습 전에 먼저 홀드아웃 태스크로 현재 모델을 평가하고 실패를 분석하며 검증기/보상 함수를 프로파일링해야 함
- 모델이 가끔은 맞는 행동을 하지만 일관되지 않을 때 RL이 가장 효과적이며, 보상이 잘못되면 RL은 잘못된 행동을 최적화하게 됨

**태스크·학습 데이터, 그리고 환경 설계**

SFT에는 입출력 예시가, RLVR에는 도구와 검증기를 갖춘 환경 로직이 필요하다.

- NeMo Data Designer로 구조화된 태스크 데이터셋을 생성하고, NeMo Gym으로 이를 실행해 채점된 궤적(trajectory)을 생성해 SFT·DPO·RL에 활용 가능
- 합성 데이터는 정답 그 자체가 아니므로 소량의 고품질 시드셋 유지, 중복 제거, 평가셋 분리, 실패 사례 검토가 필요
- 단일 스텝 작업은 정적 데이터셋으로 충분하지만, 다중 스텝·다중 턴 에이전트는 데이터셋·에이전트 하네스·검증기·상태를 모두 정의하는 환경이 필요

*이미지 출처: [원문](https://developer.nvidia.com/blog/mastering-agentic-techniques-ai-agent-reinforcement-learning/)*

**보상·검증기 설계: 단순하게 시작**

가장 단순한 보상(검증기 통과 시 +1, 아니면 0)부터 시작하고, 실제 진전을 측정하는 신호만 점진적으로 추가한다.

- 좋은 보상 함수의 3요소: 실제 태스크를 측정할 것, 조작(hacking)하기 어려울 것, 잘못됐을 때 눈에 띄게 실패할 것
- 학습 전 50~100개 모델 출력에 보상 함수를 실행해 사람 판단과 일치하는지 수동 검토 필요

**컴퓨팅: 학습과 롤아웃 예산**

RL 비용은 롤아웃과 학습 두 워크로드에서 발생하며, 배치 크기·모델 크기·시퀀스 길이의 영향을 받는다.

- 롤아웃 비용은 도구 호출 수, 대화 턴, 환경 스텝 수에 비례해 커지며 vLLM, NeMo Gym이 이를 개선
- 학습 비용은 데이터셋 크기와 정책 업데이트 횟수에 비례하며 Megatron, NeMo Automodel, NeMo RL이 처리량을 높임
- 약 1B~8B 규모의 어댑터 기반 실험은 GPU 1대나 소규모 멀티 GPU 노드로 시작 가능, 컴퓨팅이 부족하면 모델 크기·최대 토큰·프롬프트당 생성 수·병렬 환경 수를 먼저 줄일 것

**실전 첫 RL 학습: 도구 호출 에이전트 예제**

자연어 요청을 올바른 JSON 도구 호출로 변환하는 워크플레이스 어시스턴트 에이전트를 예로 7단계 절차를 제시한다.

- 1단계: 자동 평가 가능한 행동 하나 선정 (예: "다음 화요일 2시에 Alex와 캘린더 일정 생성" → 올바른 `calendar.create_event` JSON 호출)
- 2단계: 기준 모델로 검증 세트를 평가해 JSON 유효율, 도구 정확도, 인자 정확도, 실행 성공률 등을 측정하고 실패를 유형별로 분류
- 3단계: 형식을 거의 못 지키면 SFT부터, 가끔 성공하지만 일관성이 없으면 GRPO 기반 RLVR로 이동
- 4단계: 평가 로직을 결정론적 보상 함수로 전환 (JSON 유효성 -1.0, 도구 일치 +0.4, 인자 일치 +0.4, 안전 실행 +0.2 등 예시)
- 5단계: `nvidia/Nemotron-Nano-9B-v2` 등 소형 모델·LoRA 어댑터로 프롬프트당 8개 생성하는 소규모 GRPO 잡 실행
- 6단계: 학습 보상뿐 아니라 검증 보상, 성공률, 무효 출력, 안전하지 않은 행동, 지연시간, 비용까지 추적
- 7단계: 매 체크포인트에서 보상 해킹, 형식 퇴보, 안전 문제, 보상은 오르지만 실질 품질이 떨어지는 경우를 확인 후 승격

실제로는 NeMo RL의 getting-started 예제로 파이프라인을 정리한 뒤, Nemotron Nano 9B v2를 GRPO로 학습시키는 NeMo RL·NeMo Gym Workplace Assistant 튜토리얼로 확장하는 경로를 권장한다.

**장기 실행 에이전트의 지속적 개선 루프**

프로덕션 실패 → 회귀 테스트/환경 태스크 → 보상 → 모델 개선 → 재배포 전 재검증으로 이어지는 "에이전트 플라이휠"을 제안한다.

- 실제 궤적(프롬프트, 도구 호출, 관찰, 출력, 실패, 사람 개입)을 로깅하고 실패를 평가로 전환
- 형식 오류, 잘못된 도구 선택, 안전하지 않은 행동 등 실패 유형을 구분하고 가장 가벼운 수정(프롬프트 변경 → SFT → DPO → RLVR/GRPO 순)부터 시도
- 학습에 쓰지 않는 고정 홀드아웃 태스크로 평가하고, 성공률·안전 실패·비용·지연시간이 개선될 때만 승격, 튜닝된 체크포인트/어댑터는 버전 관리

**대상 독자**: 도메인 특화 AI 에이전트를 구축하는 모델 빌더, 리서치 팀, 에이전트 개발자에게 유용하며, RL 도입 여부 판단과 첫 학습 루프 구성에 실질적인 참고가 된다.

### [Designing GPU-Accelerated Query Engines with NVIDIA GQE](https://developer.nvidia.com/blog/designing-gpu-accelerated-query-engines-with-nvidia-gqe/)

`GQE` `cuDF` `nvCOMP` `NVLink-C2C` `Blackwell` `TPC-H`

> GPU 쿼리 엔진 GQE, 압축·파티션 프루닝으로 DuckDB 대비 7.5배 속도 향상

#### 요약

- NVIDIA가 SQL 쿼리를 GPU에서 고성능으로 실행하는 참조 아키텍처 GQE(GPU Query Engine)를 소개, cuDF·nvCOMP·CCCL·nvSHMEM 등 CUDA-X 라이브러리를 기반으로 함
- 데이터 압축(nvCOMP, Blackwell Decompression Engine)과 파티션 프루닝(zone map 기반 필터링)으로 CPU-GPU 간 데이터 전송량을 최소화
- 파이프라인 병렬성으로 스케줄링·전송·압축해제·GPU 연산 단계를 겹쳐 실행해 전송 지연을 숨김
- TPC-H 1TB 벤치마크에서 GQE가 DuckDB 대비 총 실행시간 7.5배, 일부 쿼리는 최대 25.5배 빠름

#### 시사점

- GPU 하드웨어의 대역폭·압축해제 가속 기능을 실제 쿼리 엔진 설계에 반영하는 구체적인 패턴(데이터 레이아웃, 전송 오케스트레이션, 압축 알고리즘 선택)을 제시해, 데이터베이스/분석 엔진 개발자가 참고할 수 있음
- 오픈소스 참조 아키텍처로 공개되어 있어, 기존 쿼리 엔진에 GPU 가속을 접목하려는 개발자가 실험 및 벤치마크에 활용 가능

#### 용어 설명

- **GQE (GPU Query Engine)**: NVIDIA가 공개한 GPU 기반 SQL 쿼리 실행 참조 아키텍처
- **cuDF**: GPU 상에서 데이터프레임 연산(조인, 정렬 등)을 수행하는 NVIDIA의 오픈소스 라이브러리
- **nvCOMP**: GPU 가속 압축/압축해제를 지원하는 NVIDIA 라이브러리
- **NVLink-C2C**: CPU-GPU 간 초고속 데이터 전송을 지원하는 NVIDIA의 칩투칩 인터커넥트
- **Decompression Engine (DE)**: NVIDIA Blackwell GPU에 내장된 전용 압축해제 하드웨어로, SM(스트리밍 멀티프로세서) 자원을 소모하지 않고 압축해제 수행
- **Substrait**: 쿼리 실행 계획을 표준화해 서로 다른 엔진 간 교환 가능하게 하는 오픈소스 포맷
- **Zone map**: 각 데이터 파티션의 컬럼별 최소/최대값을 저장한 메타데이터로, 불필요한 파티션을 건너뛰는 데 사용
- **Partition pruning (파티션 프루닝)**: 쿼리 조건과 무관한 데이터 파티션을 미리 걸러내 전송량을 줄이는 최적화 기법

#### 상세 내용

**GQE 아키텍처 개요**

GQE는 query, data, execution 세 계층으로 구성된다.

![Architecture diagram tracing a SQL query from parsing and Substrait plan optimization, through physical plan generation and task graph construction, down to GPU-accelerated reads, joins and sorts, built on cuDF and nvCOMP.](https://developer-blogs.nvidia.com/wp-content/uploads/2026/06/agentic-ai-diagrams-architecture-overview-gqe-fig-2-1920x1080-1.webp)
*이미지 출처: [원문](https://developer.nvidia.com/blog/designing-gpu-accelerated-query-engines-with-nvidia-gqe/)*

- **Query layer**: SQL 파서와 쿼리 옵티마이저를 포함하며, Substrait 계획을 네이티브로 수용. 예를 들어 Apache DataFusion이 SQL을 Substrait 계획으로 변환하면 GQE가 이를 받아 최적화·물리 계획으로 전환
- **Data layer**: GPU 메모리, CPU 메모리, 디스크를 지원하는 플러그형 리더로 데이터를 관리하며, 전체 데이터셋을 GPU에 올리지 않고 청크 단위로 온디맨드 전송
- **Execution layer**: 물리 계획을 task graph로 변환해 실행하며, cuDF 기반 관계 연산자를 파이프라인 CUDA 스트림으로 동시 실행

**데이터 레이아웃과 전송 오케스트레이션**

테이블은 row group 단위로 수평 분할되고, 각 row group 내 컬럼은 비연속(non-contiguous) 파티션으로 저장된다.

![Diagram of an in-memory table divided into row groups, each containing metadata and columnar partitions, with an arrow showing conversion into a cuDF table on the GPU.](https://developer-blogs.nvidia.com/wp-content/uploads/2026/06/image-26.webp)
*이미지 출처: [원문](https://developer.nvidia.com/blog/designing-gpu-accelerated-query-engines-with-nvidia-gqe/)*

전송 시 4단계 파이프라인이 서로 겹쳐 실행되어 지연을 숨긴다.

![Timeline showing four row groups moving through overlapping pipeline stages, including host scheduling, H2D transfer, decompression, and CUDA kernel execution across concurrent CUDA streams.](https://developer-blogs.nvidia.com/wp-content/uploads/2026/06/image-29.webp)
*이미지 출처: [원문](https://developer.nvidia.com/blog/designing-gpu-accelerated-query-engines-with-nvidia-gqe/)*

- Stage 0: 호스트 스레드가 전송 범위 계산, 버퍼 할당 등 스케줄링 수행
- Stage 1: GPU가 Host-to-Device(H2D) 전송 수행
- Stage 2: 압축 해제
- Stage 3: CUDA 커널이 쿼리 연산 수행

**압축 최적화**

GQE는 압축을 통해 처리 가능한 데이터셋 용량을 늘리고 전송 속도도 높인다.

- nvCOMP는 표준 및 GPU 최적화 압축 포맷을 지원하며 LZ4hc 같은 CPU 라이브러리도 감쌀 수 있음
- Blackwell 아키텍처의 전용 Decompression Engine(DE)은 LZ4, Snappy, Deflate 같은 LZ77 기반 포맷을 SM 자원 소모 없이 압축 해제
- B200 GPU 단일 기준 DE는 최대 400 GB/s 처리 가능, 4배 압축률 기준 약 400 GB/s의 유효 H2D 처리량을 내면서 C2C 대역폭 100 GB/s를 다른 용도로 남길 수 있음
- GQE는 Cascaded(구조화된 패턴에 특화)와 LZ4(범용, DE 지원) 두 알고리즘을 모두 시도해 더 나은 쪽을 선택하는 하이브리드 방식 사용, Cascaded는 B200에서 약 500 GB/s의 매우 빠른 압축 속도를 냄

![Four-panel walkthrough of cascaded compression: an original column of 16-bit values is reduced by delta encoding, then run-length encoding, and finally bit-packing into a compact binary representation.](https://developer-blogs.nvidia.com/wp-content/uploads/2026/06/image-30.webp)
*이미지 출처: [원문](https://developer.nvidia.com/blog/designing-gpu-accelerated-query-engines-with-nvidia-gqe/)*

**파티션 프루닝**

GQE는 zone map(파티션별 최소/최대값 메타데이터)을 이용해 쿼리 조건과 무관한 파티션을 GPU 전송 전에 걸러낸다.

![Diagram showing a query predicate compared against min/max zone-map metadata for each partition. Partitions that cannot match are pruned; only retained partitions are transferred and assembled into a cuDF table on the GPU.](https://developer-blogs.nvidia.com/wp-content/uploads/2026/06/image-27.webp)
*이미지 출처: [원문](https://developer.nvidia.com/blog/designing-gpu-accelerated-query-engines-with-nvidia-gqe/)*

- 기본 파티션 크기는 1000만(10M) 행, zone map 계산은 최초 Parquet 로드 시 약 1%의 시간만 추가되며 쿼리 실행 중에는 재계산하지 않음
- TPC-H 1TB 벤치마크의 22개 쿼리 전체에서 프루닝이 데이터의 31%를 건너뛰어 종단 간(end-to-end) 1.43배 속도 향상
- zone map 평가 오버헤드는 쿼리당 평균 2.2ms
- 여러 파티션을 cudaMemcpyBatchAsync로 한 번에 배치 전송하는 최적화를 도입해 세분화된 파티션의 오버헤드와 CUDA 스트림 간 지연을 줄임

**성능 결과**

NVIDIA GB200 NVL4 서버의 B200 GPU 1개(Grace CPU와 NVLink-C2C로 연결)에서 TPC-H Scale Factor 1000(1TB)을 벤치마크했으며, 베이스라인은 Turin Epyc 9755 CPU에서 구동한 DuckDB 1.4.1이다.

![Bar chart comparison for queries-per-second with GQE on NVIDIA GB200 versus DuckDB on one- and two-socket AMD Turin EPYC 9755 across TPC-H SF1000 queries Q1–Q22, with GQE achieving higher throughput on over 90% of queries based on TPC-H.](https://developer-blogs.nvidia.com/wp-content/uploads/2026/06/image-31.webp)

- 전체 22개 쿼리 실행 시간: GQE 9.0초 vs DuckDB 단일 소켓 74.0초, 듀얼 소켓 70.6초

- DuckDB 최적 CPU 구성 대비 최대 25.5배, 17개 쿼리에서 3배 이상, 전체 집계 기준 7.5배 속도 향상
- 해당 결과는 TPC-H 벤치마크에서 파생되었으나 공식 TPC-H 사양을 준수하지 않아 공식 발표 결과와 비교 불가

**대상 독자**: GPU 가속 데이터베이스/쿼리 엔진을 설계·최적화하려는 데이터베이스 엔지니어, 대용량 분석 파이프라인에서 CPU-GPU 데이터 전송 병목을 해결하려는 시스템 개발자에게 유용하다.

### [Optimizing a Neural Reconstruction Pipeline Using NVIDIA Nsight Developer Tools](https://developer.nvidia.com/blog/optimizing-a-neural-reconstruction-pipeline-using-nvidia-nsight-developer-tools/)

`NVIDIA Nsight Systems` `NVIDIA Nsight Compute` `NuRec` `CUDA` `Gaussian Splatting` `Autonomous Vehicles`

> Nsight Systems·Compute로 NuRec 신경망 재구성 파이프라인 병목을 찾아 대폭 최적화

#### 요약

- NVIDIA Omniverse NuRec은 카메라·라이다 등 멀티센서 데이터로 3D 환경을 재구성하는 신경망 렌더링 파이프라인으로, 자율주행·로보틱스 시뮬레이션에 사용됨
- Nsight Systems로 프로파일링해 `interpolate` 함수의 작은 커널들을 하나로 병합, 4.184ms에서 83.81us로 약 50배 속도 개선
- 불필요한 `cudaStreamSynchronize` 동기화 지점을 제거해 GPU 활용률을 촘촘하게 개선
- Nsight Compute로 `renderBackward` 커널을 카메라용/라이다용으로 분리하고 레지스터·공유 메모리 설정을 튜닝해 점유율(occupancy)을 ~15%에서 30~50%로, 최장 라이다 커널 실행 시간을 31ms에서 18ms로 단축

#### 시사점

- Nsight Systems(전체 워크플로 타임라인)와 Nsight Compute(개별 커널 심층 분석)를 단계적으로 조합하는 프로파일링·최적화 방법론을 실제 사례로 확인할 수 있음
- 재구성 시간이 짧아지면 AV·로보틱스 엔지니어의 디버깅 반복 속도가 빨라지고, 대규모 렌더링 워크로드(RL, 합성 데이터 생성)의 GPU 비용도 크게 절감됨
- PyTorch 기반 워크로드에서 NVTX 계측으로 병목을 좁혀가는 접근과, CUDA 커널의 `launch_bounds`·공유 메모리·캐시 설정 튜닝 기법을 참고할 수 있음

#### 용어 설명

- **NuRec**: NVIDIA Omniverse의 신경망 재구성 파이프라인으로, 센서 데이터에서 고품질 3D 장면을 생성
- **Gaussian Splatting**: 점 구름을 가우시안 형태로 표현해 빠르고 사실적인 3D 렌더링을 가능케 하는 신경망 렌더링 기법
- **Nsight Systems**: CPU·GPU·네트워크 등 전체 시스템 성능을 시각화하는 NVIDIA 프로파일링 도구
- **Nsight Compute**: 개별 CUDA 커널을 세밀하게 분석·최적화하는 NVIDIA 프로파일링 도구
- **NVTX (NVIDIA Tools Extension SDK)**: 코드에 구간 주석을 달아 프로파일러에서 특정 함수·단계를 식별하게 해주는 계측 도구
- **occupancy(점유율)**: GPU의 SM(스트리밍 멀티프로세서)에서 동시에 활성화된 워프(warp) 비율을 나타내는 지표로, 높을수록 GPU 자원을 효율적으로 사용
- **cudaStreamSynchronize**: CPU가 GPU 작업 완료를 기다리도록 강제하는 CUDA API로, 과도하게 쓰이면 GPU 유휴 시간을 늘림

#### 상세 내용

**NuRec과 성능 최적화의 필요성**

NuRec은 카메라·라이다 데이터를 결합해 실제 주행·로보틱스 장면을 시뮬레이션 가능한 3D 환경으로 재구성한다. 문제는 재구성 속도로, 최적화 이전에는 짧은 캡처조차 한 시간에서 수 시간이 걸렸다.

- 목표는 30초 분량 캡처를 약 30초 안에 재구성하는 실시간 성능
- 재구성 이후 RL, 합성 데이터 생성(SDG) 등 대규모 렌더링 워크로드에서도 작은 성능 개선이 GPU 비용에 큰 영향을 미침

**Nsight Systems를 통한 프로파일링과 최적화**

먼저 PyTorch에 내장된 NVTX와 Nsight Systems 함수 지원을 이용해 forward pass 한 iteration을 들여다봤다. 예상과 달리 렌더링 커널이 아니라 GPU가 상당 시간 유휴 상태였고, 수많은 작은 커널이 사용되고 있었다.

*이미지 출처: [원문](https://developer.nvidia.com/blog/optimizing-a-neural-reconstruction-pipeline-using-nvidia-nsight-developer-tools/)*

### [How to Govern Autonomous Agents in Enterprise AI Factories](https://developer.nvidia.com/blog/how-to-govern-autonomous-agents-in-enterprise-ai-factories/)

`AI Agent` `AI Factory` `MLOps` `OpenShell` `Enterprise Security` `Zero Trust`

> AI 에이전트를 안전하게 운영하기 위한 격리 워크스페이스 아키텍처 소개

#### 요약

- NVIDIA의 Secure Agent Workspace Reference Design은 사용자의 로컬 기기(노트북, 브라우저, IDE)를 '표시 계층'으로만 쓰고, 실제 에이전트 실행은 관리형 워크스페이스(VM)에서 수행하도록 분리한다.
- 구현은 2단계로 진행된다: 1단계는 VM 외곽 경계 보안(SSO 로그인, 네트워크 차단, 인간 승인, 중앙 로깅), 2단계는 VM 내부 런타임 보안(샌드박싱, 서명된 정책, 자격증명 프록시, 지속적 검증)이다.
- 에이전트 워크플로우는 목표·도구·서비스·데이터 범위·쓰기 권한·검토 게이트·로깅을 정의한 "블루프린트" 템플릿으로 표준화해 배포한다.
- 온프레미스는 Red Hat OpenShift Virtualization, 클라우드는 Microsoft Azure를 통해 사용자당 VM을 프로비저닝하고, GitOps로 정책과 인프라 상태를 관리한다.

#### 시사점

- 에이전트가 장시간 자율적으로 작동하며 사내 시스템에 접근하는 시대에, 개발자는 이런 격리·감사 구조를 이해해야 안전하게 에이전트 기반 워크플로우를 설계할 수 있다.
- 자격증명을 코드에 하드코딩하지 않고 프록시를 통한 단기 토큰으로 관리하는 패턴은 일반적인 에이전트 개발에도 바로 적용 가능한 보안 모범 사례다.
- 코드 병합, 티켓 상태 변경 등 시스템을 변경하는 행동에 인간 승인 게이트를 두는 "blast radius(피해 반경)" 제어 개념은 자체 에이전트 설계 시 참고할 수 있는 거버넌스 틀을 제공한다.

#### 용어 설명

- **AI Factory**: 기업이 AI를 대규모로 생산·운영하기 위한 인프라 및 프로세스 체계.
- **OpenShell**: NVIDIA가 제공하는 에이전트 실행 감시용 샌드박스 런타임.
- **SSO (Single Sign-On)**: 하나의 인증으로 여러 시스템에 접근할 수 있게 하는 로그인 방식.
- **Egress**: 내부 네트워크에서 외부로 나가는 트래픽. 기본적으로 차단(default-deny)하고 승인된 목적지만 허용하는 방식이 언급된다.
- **GitOps**: 인프라와 정책 설정을 Git 저장소에 코드로 관리하고 자동 반영하는 운영 방식.
- **OCSF (Open Cybersecurity Schema Framework)**: 보안 로그를 표준화된 형식으로 남겨 감사·SIEM 연동을 쉽게 하는 스키마.
- **RBAC (Role-Based Access Control)**: 역할 기반으로 접근 권한을 부여하는 방식.

#### 상세 내용

**배경: 왜 격리된 워크스페이스가 필요한가**

AI 에이전트는 이제 단순 채팅을 넘어 코드 검사, 테스트 실행, 문서 읽기, 내부 시스템 조회 등을 수행하며 몇 시간씩 자율적으로 작동한다. 이는 생산성을 높이지만 민감한 기업 데이터 접근과 시스템 변경 권한을 동반하므로, 안전하고 통제된 환경이 필수다.

- 핵심 아이디어는 사용자 로컬 기기를 "표시 계층(presentation layer)"으로, 관리형 워크스페이스를 "실행 계층(execution layer)"으로 분리하는 것이다.
- 워크스페이스에서 아이덴티티, 네트워크 접근, 자격증명, 런타임 정책, 감사, 인간 검토가 일관되게 적용된다.

![Enterprise AI Factory 아키텍처: 사용자가 SSH/HTTPS로 신뢰된 접근 브로커를 통해 Secure Agent Workspace에 연결하고, 워크스페이스는 온프레미스/클라우드 추론 엔드포인트와 기업 시스템에 접근하며 SIEM/관측 시스템으로 로그를 전송한다.](https://developer-blogs.nvidia.com/wp-content/uploads/2026/06/image-34.webp)
*이미지 출처: [원문](https://developer.nvidia.com/blog/how-to-govern-autonomous-agents-in-enterprise-ai-factories/)*

**구현 1단계: VM 외곽 경계 보안**

VM을 1차 격리 경계로 삼아 에이전트 활동을 관찰 가능하고, 제한적이며, 언제든 취소 가능하게 만드는 단계다.

- 사용자별 전용 관리형 VM 제공
- SSO 기반 로그인 게이트 강제
- 기본적으로 모든 인터넷 트래픽 차단, 사전 승인된 서비스만 허용
- 시스템을 변경하는 에이전트 행동(코드 병합, 티켓 업데이트 등)은 반드시 인간 승인 필요
- 모든 워크스페이스 활동 로그를 중앙 집중화

**구현 2단계: VM 내부 런타임 보안**

파일 읽기, 명령 실행, 서비스 접근 등 도구 호출(tool-call) 경계에 더 가까운 보호를 추가하는 단계다.

- 모든 행동을 실시간 감시하는 전용 런타임(예: NVIDIA OpenShell)에서 에이전트 실행
- 서명된 보안 정책 번들을 중앙에서 워크스페이스로 배포
- 자격증명은 워크스페이스에 직접 저장하지 않고, 보안 프록시가 대신 처리해 에이전트가 원본 비밀정보를 보지 못하게 함
- 모든 행동 실행 전 보안 규칙 작동 여부를 자동으로 지속 검증

![Secure Agent Workspace 내부 구조: 사용자 엔드포인트가 액세스 플레인을 거쳐 워크스페이스 플레인으로 연결되며, 내부 런타임 샌드박스에는 에이전트 하니스, 도구/코드 인터프리터, 자격증명 프록시, 라우팅된 추론 브로커, 텔레메트리 이미터, 네트워크 경계 allowlist가 포함된다.](https://developer-blogs.nvidia.com/wp-content/uploads/2026/06/image-33.webp)

**에이전트 블루프린트 설정**

블루프린트는 워크스페이스 위에서 실행되는 재사용 가능한 워크플로우 템플릿으로, 목표·도구·허용 서비스·데이터 범위·쓰기 권한·검토 게이트·로깅 요건을 정의한다. 개발자는 최대 권한 범위로 구성된 블루프린트를 자신의 용도에 맞게 최소한으로 축소해 사용한다.

- **에이전트 아이덴티티 정의**: SSO를 통해 사용자/스폰서와 연결된 논리적 아이덴티티로 에이전트를 등록하고, 위임 기록(delegation record)으로 허용 행동을 명시
- **비밀정보 처리**: 하드코딩 없이 자격증명 프록시를 통해 단기 캐퍼빌리티 토큰 사용
- **추론 설정**: 게이트웨이 계층이 할당량, RBAC, 동적 속도 제한을 관리
- **거버넌스 잠금**: "blast radius" 제어로 인간 검토가 필요한 행동을 정의하고, 모든 로그를 OCSF 형식으로 출력

**온프레미스/클라우드 배포**

온프레미스는 Red Hat OpenShift Virtualization, 클라우드는 Microsoft Azure를 사용하며 핵심 패턴은 동일하다. 사용자마다 전용 VM을 받고, 로컬 엔드포인트는 그 워크스페이스에만 연결된다.

- 사용자당 VM 1개 프로비저닝 (Linux 또는 Windows)
- 신뢰된 접근 브로커 앞단 배치, 기업 SSO와 단기·감사 가능한 세션으로 연결
- 네트워크는 기본 차단(default-deny egress) 후 승인된 목적지만 허용 — OpenShift에서는 `NetworkPolicy`, `EgressFirewall` 등 사용, Azure에서는 Azure Firewall Premium과 BGP 라우트 전파 비활성화 등 적용
- 승인된 VM 이미지만 사용 — OpenShift는 GitOps로 VM 프로파일 관리, Azure는 Packer로 골든 이미지 빌드 후 Azure Compute Gallery로 배포
- VM 프로파일, 네트워크 규칙, 정책 메타데이터를 Git에 저장하고 GitOps로 상태를 조정, 서명된 런타임 정책 번들은 통제된 릴리스 채널로 배포
- Azure는 Workload Identity Federation, 관리 ID, Private Endpoint를 통한 Azure Key Vault 등으로 비밀정보를 보호
- 워크스페이스 생명주기 이벤트, 브로커 세션, 정책 릴리스, 네트워크 허용/차단, 런타임/도구 이벤트를 Azure Monitor, Log Analytics, Microsoft Sentinel 등 SIEM으로 중앙 집중화

**대상 독자**: 엔터프라이즈 환경에서 자율 AI 에이전트를 도입·운영하려는 플랫폼/보안 엔지니어, 그리고 에이전트 기반 워크플로우를 설계하는 MLOps 담당자에게 유용하다.

#### 요약

- NVIDIA AI-Q Blueprint는 LangChain Deep Agents와 NeMo Agent Toolkit 기반의 오픈소스 장기 추론(long-horizon) 에이전트 레퍼런스로, 즉답형 질의와 출처 인용이 딸린 심층 리서치 리포트를 모두 지원한다.
- Terraform으로 OCI 인프라(VCN, OKE 클러스터, Load Balancer, Vault)를 생성하고, Helm으로 NGC에 게시된 AI-Q 백엔드·프론트엔드·PostgreSQL을 OKE에 설치하는 절차를 다룬다.
- 전체 배포는 약 20~25분이 걸리며, `terraform destroy` 한 번으로 전체 리소스를 정리할 수 있다.
- API 키(NGC, Tavily)는 OCI Vault에 암호화 저장되지만, 실제 파드는 Kubernetes 시크릿(`aiq-credentials`)에서 값을 읽으므로 키 교체 시 시크릿을 재생성해야 한다.

#### 시사점

- 로컬 노트북이 아닌 클라우드 프로덕션 환경에서 멀티 에이전트 시스템을 직접 운영해보고 싶은 개발자에게 실전 배포 경로를 제공한다.
- 모델, 툴, RAG 백엔드, 서브 에이전트 등 모든 계층이 YAML 설정이나 NeMo Agent Toolkit 플러그인 시스템으로 교체 가능해, 코드 재작성 없이 구성 변경만으로 확장할 수 있다.
- Terraform/Helm 분리 구조 덕분에 인프라와 애플리케이션 계층을 독립적으로 관리·재현할 수 있다.

#### 용어 설명

- **AI-Q Blueprint**: NVIDIA가 공개한 멀티 에이전트 리서치 시스템 참조 구현체.
- **Deep Agent**: 여러 단계를 계획하고 서브 에이전트로 작업을 분담하는 장기 실행 에이전트.
- **NeMo Agent Toolkit**: 에이전트 워크플로를 구성·확장하는 NVIDIA의 플러그인 기반 툴킷.
- **OKE (Oracle Kubernetes Engine)**: 오라클 클라우드의 관리형 쿠버네티스 서비스.
- **OCI Vault**: API 키 등 민감정보를 AES-256으로 암호화 저장하는 OCI의 비밀 관리 서비스.
- **NGC**: NVIDIA의 컨테이너·모델 레지스트리(nvcr.io)로, 이미지 풀과 추론 API 키 인증에 함께 쓰인다.
- **Terraform / Helm**: 인프라를 코드로 정의하는 프로비저닝 도구(Terraform)와 쿠버네티스 애플리케이션 패키지 배포 도구(Helm).

**멀티 에이전트 아키텍처**

AI-Q는 사용자 질의를 받는 **intent router**가 요청 성격에 따라 두 경로로 분기한다.

![Diagram of the AI-Q multi-agent architecture. A user query goes into an intent router, which sends it to either a Shallow Research Agent or a Deep Agent. The Deep Agent has a Planning sub-agent and a Researcher sub-agent. They share a Filesystem layer (to-do lists, memory, file storage) and run skills like Data Analysis and Image Processing in isolated sandboxes. Data sources at the entry point include MCP, AI Data Platforms, Web Search, and user-uploaded documents.](https://developer-blogs.nvidia.com/wp-content/uploads/2026/05/AI-Q-multi-agent-architecture.webp)
*이미지 출처: [원문](https://developer.nvidia.com/blog/deploy-a-production-ready-nvidia-ai-q-blueprint-on-oracle-cloud-infrastructure/)*

- **Shallow Research Agent**: 빠르고 범위가 제한된 도구 기반 검색을 수행.
- **Deep Agent**: Planning 서브 에이전트와 Researcher 서브 에이전트가 협업하며, 할 일 목록·메모리·파일 저장을 공유하는 Filesystem 레이어를 함께 사용하고, 데이터 분석·이미지 처리 같은 스킬은 격리된 샌드박스에서 실행된다.
- 진입 시 사용 가능한 데이터 소스는 MCP, AI 데이터 플랫폼, 웹 검색, 사용자 업로드 문서 등이다.

**OCI 배포 아키텍처**

Terraform이 인프라를, Helm이 쿠버네티스 워크로드를 담당하는 구조로, 인프라와 애플리케이션 계층이 분리돼 있다.

![Architecture diagram of the AI-Q deployment on OCI. A public OCI Load Balancer in front of an OKE cluster inside a VCN, with public and OKE subnets. The OKE cluster runs three workloads pulled from the NVIDIA NGC registry: an AI-Q backend (FastAPI), an AI-Q frontend (Next.js), and a PostgreSQL pod. OCI Vault stores the NGC and Tavily API keys at provision time.](https://developer-blogs.nvidia.com/wp-content/uploads/2026/06/oci-aiq-arch-diagram.webp)
*이미지 출처: [원문](https://developer.nvidia.com/blog/deploy-a-production-ready-nvidia-ai-q-blueprint-on-oracle-cloud-infrastructure/)*

Terraform 모듈 구성:
- `network`: VCN, 서브넷, 게이트웨이, NSG로 퍼블릭/OKE 서브넷을 분리해 네트워크 격리.
- `oke`: Enhanced 클러스터와 VCN-native CNI로 구성된 쿠버네티스 런타임.
- `loadbalancer`: 80번 포트로 들어온 트래픽을 NodePort 30080으로 전달하는 Flexible Load Balancer.
- `vault`: API 키와 자격증명을 AES-256으로 암호화 저장.

Helm 차트가 설치하는 3개 워크로드:
- **aiq-backend**: FastAPI 기반 에이전트 서버.
- **aiq-frontend**: NodePort 30080으로 노출되는 Next.js 웹 UI.
- **aiq-postgres**: 작업 스토어, 체크포인트, 요약 데이터를 담는 클러스터 내 PostgreSQL.

**배포 절차**

레포를 클론한 뒤 4단계로 진행하며 전체 소요 시간은 약 20~25분이다.

- **1단계**: `deploy/terraform`에서 `terraform.tfvars`를 작성 — tenancy/compartment/region, OCI 인증 정보, DB 비밀번호, NVIDIA NGC 키, Tavily 키를 설정.
- **2단계**: `terraform init/plan/apply`로 VCN·OKE·Load Balancer·Vault를 생성(10~15분 소요). `oke_cluster_id`, `lb_public_ip` 출력값을 확보.
- **3단계**: `kubectl`을 OKE에 연결하고, `ns-aiq` 네임스페이스에 `aiq-credentials`(NVIDIA/Tavily 키, DB 계정)와 `ngc-secret`(nvcr.io 이미지 풀용) 시크릿을 생성한 뒤, NGC에서 Helm 차트(`aiq2-web-2.0.0.tgz`)를 pull하여 `values-oci-ngc.yaml` 오버레이와 함께 설치.
- **4단계**: 브라우저에서 `http://<lb_public_ip>`로 접속해 AI-Q 프론트엔드 확인. 간단한 질문으로 라우팅을 검증한 뒤, 비교·분석형 질문으로 Deep Agent 동작을 확인.

**트러블슈팅 및 운영 팁**

- OKE 생성 시 쿼터 오류가 나면 컴파트먼트의 클러스터/노드 수 제한을 확인.
- `ImagePullBackOff`는 이미지 풀 시크릿 또는 NGC 키 오류일 가능성이 높음.
- PostgreSQL 파드가 `Pending`으로 멈추면 Block Volume PVC 프로비저닝 문제(StorageClass, CSI 드라이버, 쿼터)를 점검.
- Load Balancer IP가 `null`이면 `terraform refresh` 후 재확인.
- 쿼리 응답이 500 오류면 `aiq-credentials` 시크릿의 API 키를 점검.
- 비용 관리: OKE 노드 풀과 Load Balancer는 운영 중 지속 과금되므로, 실험 사이에는 스택을 삭제하거나 노드 풀을 0으로 스케일.

**대상 독자**: Kubernetes, Terraform, 쉘 사용에 익숙하고 랩톱이 아닌 클라우드 환경에서 AI-Q 에이전트 블루프린트를 프로덕션 수준으로 운영하려는 개발자·플랫폼 엔지니어에게 유용하다.
