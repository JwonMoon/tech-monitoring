# NVIDIA 블로그 요약 — 2026-08-16

### [NVIDIA Achieves Leading Agentic Coding Performance on First Agentic AI Benchmark](https://developer.nvidia.com/blog/nvidia-achieves-leading-agentic-coding-performance-on-first-agentic-ai-benchmark/)

`AA-AgentPerf` `GB300 NVL72` `DeepSeek-V4-Pro` `Agentic AI` `MoE` `Vera Rubin`

> 업계 최초 에이전트 코딩 벤치마크에서 NVIDIA GB300이 H200 대비 최대 20배 성능 달성

#### 요약

- Artificial Analysis가 만든 AA-AgentPerf는 업계 최초의 멀티벤더 에이전트 AI 벤치마크로, SLO(서비스 수준 목표) 기준을 충족하며 지원 가능한 동시 AI 에이전트 수를 측정한다.
- 실제 코드 저장소 이슈 해결, 12개 이상 프로그래밍 언어, 프론티어 모델 응답을 기반으로 한 사전 녹화된 에이전트 트래젝토리(궤적)를 사용해 비결정적인 LLM 호출·툴 호출 패턴을 재현한다.
- 런칭 시점 DeepSeek-V4-Pro 모델과 3단계 SLO 티어를 기준으로 테스트했으며, NVIDIA GB300 NVL72는 이전 세대 H200 대비 메가와트당 최대 20배 많은 동시 에이전트를 지원한다.
- 이 성능은 NVLink 스케일업 도메인, WideEP/DeepEP 같은 MoE 분산 최적화, DeepGEMM·MXFP4/MXFP8 커널 등 하드웨어·소프트웨어 공동 설계(extreme co-design) 덕분이다.

#### 시사점

- 에이전트형 AI 서비스를 운영하는 개발자는 GPU/전력 예산 대비 몇 개의 에이전트 세션을 동시에 지원할 수 있는지 표준화된 지표로 용량 계획(capacity planning)을 세울 수 있다.
- SGLang, TensorRT LLM, vLLM 같은 런타임에서의 MoE 분산 최적화 기법이 실제로 대규모 동시 에이전트 처리 성능에 직결됨을 보여준다.
- 벤치마크 테스트셋이 비공개로 유지되어 벤치마크 타겟 최적화(치팅)를 방지하므로, 결과가 실제 운영 환경 성능을 더 신뢰성 있게 반영한다.

#### 용어 설명

- **SLO (Service Level Objective)**: 출력 토큰 속도, TTFT 등으로 정의되는 서비스 성능 목표 기준치.
- **TTFT (Time-to-First-Token)**: 요청 후 첫 번째 출력 토큰이 나오기까지 걸리는 시간.
- **에이전트 트래젝토리(Agent Trajectory)**: AI 에이전트가 작업을 시작부터 끝까지 수행하며 거치는 행동·판단·관찰의 전체 시퀀스.
- **MoE (Mixture of Experts)**: 여러 전문가(서브 네트워크) 중 일부만 선택적으로 활성화해 연산하는 모델 구조.
- **NVLink**: GPU 간 초고속 데이터 공유를 가능하게 하는 NVIDIA의 GPU 상호연결 기술.
- **WideEP / DeepEP**: MoE의 전문가(expert) 연산을 GPU 클러스터 전체에 분산시키는 최적화 기법.
- **NVFP4**: NVIDIA의 4비트 부동소수점 연산 포맷으로, 연산 처리량을 높이기 위한 저정밀도 포맷.

### [Run DiffusionGemma on NVIDIA for Developer-Ready, High-Throughput Text Generation](https://developer.nvidia.com/blog/run-diffusiongemma-on-nvidia-for-developer-ready-high-throughput-text-generation/)

`DiffusionGemma` `NVIDIA NIM` `vLLM` `DGX Spark` `DGX Station` `NVFP4`

> 병렬 토큰 생성으로 초당 최대 2,000토큰을 내는 확산 기반 언어모델

#### 요약

- Google DeepMind가 만든 DiffusionGemma는 토큰을 한 번에 하나씩 생성하는 기존 방식 대신, 확산 기반 디노이징으로 스텝당 256개 토큰을 병렬 생성한다.
- NVIDIA H100에서 최대 1,000 tokens/sec, DGX Spark에서 최대 150 tokens/sec, DGX Station에서 최대 2,000 tokens/sec 처리량을 낸다.
- Gemma 4 26B A4B MoE 아키텍처 기반이며, 총 파라미터 25.2B 중 활성 파라미터는 3.8B로 저지연·메모리 효율적인 추론에 최적화됐다.
- Hugging Face Transformers, vLLM, NVIDIA NIM 등으로 Day 0(출시 당일)부터 프로토타이핑에서 프로덕션 배포까지 지원되며, NeMo AutoModel로 즉시 파인튜닝도 가능하다.

#### 시사점

- 토큰 병렬 생성 덕분에 채팅 어시스턴트, 코파일럿, 에이전틱 워크플로 등 실시간 응답성이 중요한 애플리케이션의 서빙 비용 절감과 동시 처리량 향상이 가능해진다.
- BF16 체크포인트 외에 NVFP4 양자화 버전도 제공돼 메모리 제약이 있는 로컬/엣지 환경(RTX, DGX Spark 등)에서도 구동할 수 있다.
- NIM 컨테이너로 OpenAI 호환 API를 통해 온프레미스·클라우드·하이브리드 어디서든 표준화된 방식으로 배포할 수 있어 도입 장벽이 낮다.

#### 용어 설명

- **DiffusionGemma**: Google DeepMind가 만든, 확산(diffusion) 방식으로 텍스트를 병렬 생성하는 언어모델.
- **Diffusion 기반 디노이징**: 이미지 생성 모델처럼 노이즈를 점진적으로 제거해가며 결과(텍스트)를 만드는 방식으로, 토큰을 순차가 아닌 병렬로 생성 가능하게 함.
- **MoE (Mixture of Experts)**: 전체 파라미터 중 일부(전문가)만 활성화해 연산하는 구조로, 총 파라미터 대비 실제 연산량을 줄여 효율을 높인다.
- **NVFP4**: NVIDIA의 4비트 부동소수점 양자화 포맷으로, 모델 크기와 메모리 사용량을 줄이면서 추론 속도를 높인다.
- **NVIDIA NIM**: 모델을 표준 API를 갖춘 컨테이너화된 추론 마이크로서비스로 패키징해 배포를 간소화하는 NVIDIA 솔루션.
- **vLLM**: 대규모 언어모델의 고처리량·다중 사용자 서빙에 최적화된 오픈소스 추론 엔진.
- **NeMo AutoModel**: Hugging Face 체크포인트를 변환 없이 바로 파인튜닝할 수 있게 해주는 NVIDIA NeMo 프레임워크의 라이브러리.

#### 상세 내용

**모델 개요**

DiffusionGemma는 텍스트와 이미지 모달리티를 지원하며, 총 파라미터 25.2B, 활성 파라미터 3.8B의 MoE 구조다.

- 컨텍스트 길이는 최대 256K 토큰까지 지원
- 정밀도 포맷은 BF16과 NVFP4를 제공

**플랫폼별 성능**

세 가지 NVIDIA 플랫폼에서 각기 다른 처리량을 보인다.

- H100 Tensor Core GPU 1대: 최대 1,000 tokens/sec
- DGX Spark: 최대 150 tokens/sec (GB10 Grace Blackwell Superchip, 128GB 통합 메모리, 1 PFLOP FP4 연산)
- DGX Station: 최대 2,000 tokens/sec (GB300 Grace Blackwell Ultra Superchip, 748GB 코히런트 메모리, 최대 20 PFLOPS FP4 연산, 최대 1T 파라미터 모델 지원)
- RTX / RTX PRO: 데스크톱 및 워크스테이션 환경에서 로컬 추론에 최적화

**빌드 및 프로토타이핑**

초기 테스트는 Hugging Face Transformers로 GeForce RTX 5090이나 DGX Spark에서 진행할 수 있다.

- 더 높은 처리량이나 다중 사용자 동시 서빙이 필요하면 DGX Spark, DGX Station, RTX PRO에서 vLLM 사용을 권장
- build.nvidia.com의 NVIDIA Developer Program을 통해 GPU 가속 엔드포인트에 무료로 접근해 프로토타이핑 가능
- BF16 체크포인트와 NVIDIA Model Optimizer로 만든 NVFP4 양자화 체크포인트가 Hugging Face에 공개돼 있음

**NVIDIA NIM을 통한 엔터프라이즈 배포**

NIM은 모델을 최적화된 컨테이너형 추론 마이크로서비스로 패키징해 온프레미스·클라우드·하이브리드 환경에 배포할 수 있게 해준다.

- 컨테이너 다운로드 후 `docker run`으로 NIM 서버 실행 (예: `nvcr.io/nim/google/diffusiongemma-26b-a4b-it:latest`)
- OpenAI 호환 API로 표준 형식의 추론 요청 전송 가능 (예시 코드에서 `client.chat.completions.create` 사용)

**Day 0 파인튜닝**

NVIDIA NeMo AutoModel 라이브러리를 통해 특정 태스크나 도메인에 맞춘 파인튜닝 가이드와 레시피가 제공된다.

- LLM, VLM, DiffusionLM을 Hugging Face 체크포인트 위에서 변환 없이 바로 파인튜닝 가능
- NVIDIA는 오픈소스 생태계에 수백 개 프로젝트를 공개해왔으며, DiffusionGemma 같은 오픈 모델을 통해 AI 투명성과 안전성 연구를 지원

**대상 독자**: 실시간 응답성이 중요한 챗봇·코파일럿·에이전트 애플리케이션을 개발하며, 로컬(RTX, DGX Spark)부터 엔터프라이즈 프로덕션(NIM, DGX Station)까지 다양한 환경에서 고처리량 텍스트 생성 모델을 배포하려는 개발자에게 유용하다.

### [Deploy Long-Context Reasoning and Agentic Workflows with MiniMax M3 on NVIDIA Accelerated Infrastructure](https://developer.nvidia.com/blog/deploy-long-context-reasoning-and-agentic-workflows-with-minimax-m3-on-nvidia-accelerated-infrastructure/)

`MiniMax M3` `NVIDIA Blackwell` `TensorRT LLM` `NVIDIA Dynamo` `NeMo Framework` `Mixture-of-Experts`

> NVIDIA 인프라에서 100만 토큰 멀티모달 MoE 모델 M3를 빠르게 서빙

#### 요약

- MiniMax M3는 4,280억 파라미터 MoE(Mixture of Experts) 모델로 최대 100만 토큰 컨텍스트와 비디오·이미지·텍스트 멀티모달 입력을 지원한다.
- 핵심 기술인 MiniMax Sparse Attention(MSA)이 기존 M2 대비 100만 토큰 기준 토큰당 연산량을 1/20로 줄이고, prefill 9배·decoding 15배 속도 향상을 이끌어낸다.
- NVIDIA Blackwell Ultra(B300)는 이전 세대 Hopper(H100) 대비 최대 10배 높은 처리량을 제공한다.
- TensorRT LLM, SGLang, vLLM 등 오픈소스 추론 엔진과 NVIDIA Dynamo, NeMo Framework를 통해 배포·확장·파인튜닝이 가능하다.

#### 시사점

- 텍스트·비전·코드용으로 모델을 따로 두던 파이프라인을 하나의 멀티모달 모델로 통합해 복잡도와 비용을 줄일 수 있다.
- 8시간 이상의 장시간 코딩 세션, 긴 비디오 이해 등 초장문 컨텍스트가 필요한 에이전틱 워크플로우를 실제 서비스 수준으로 구현할 수 있다.
- NeMo AutoModel/NeMo RL로 Hugging Face 체크포인트를 변환 없이 바로 SFT·LoRA·강화학습으로 커스터마이징할 수 있다.

#### 용어 설명

- **MoE (Mixture of Experts)**: 입력마다 전체 파라미터 중 일부 "전문가" 서브네트워크만 활성화해 연산량을 줄이는 모델 구조.
- **MSA (MiniMax Sparse Attention)**: 관련 있는 컨텍스트 블록만 먼저 골라내 어텐션을 수행하는 희소 어텐션 기법으로, 표준 어텐션의 연산량을 크게 낮춘다.
- **KV 캐시**: 트랜스포머 추론 중 재사용을 위해 저장해두는 Key/Value 값 저장소로, 긴 컨텍스트 처리 속도에 큰 영향을 준다.
- **NVFP4**: NVIDIA의 저정밀도(4비트) 수치 포맷으로 정확도 손실을 최소화하며 추론을 가속하는 기술.
- **Speculative Decoding / MTP**: 다음 토큰을 미리 예측해 검증하는 방식으로 생성 속도를 높이는 디코딩 기법.
- **NVIDIA Dynamo**: 대규모 모델을 여러 추론 엔진과 연동해 분산 서빙하는 오픈소스 플랫폼.
- **ISL/OSL**: 입력 시퀀스 길이(Input Sequence Length)/출력 시퀀스 길이(Output Sequence Length)를 뜻하는 벤치마크 조건 표기.

#### 상세 내용

**모델 개요**

MiniMax M3는 비디오·이미지·텍스트를 입력으로 받는 VLM(Vision-Language Model) MoE로, 전체 4,280억 파라미터 중 활성 파라미터는 220억이다.

- 시각 인코더 파라미터: 6억
- 전문가(Experts) 총 128개, 토큰당 4개 활성화
- 지원 정밀도: BF16, MXFP8
- 컨텍스트 길이: 최대 100만 토큰

모델은 후처리로 멀티모달을 추가한 것이 아니라, 약 100조 개의 인터리브(interleaved) 텍스트·이미지·비디오 토큰으로 처음부터 함께 학습됐다.

**MiniMax Sparse Attention(MSA) 구조**

표준 어텐션은 시퀀스 길이에 따라 연산량이 제곱으로 늘어나는(quadratic) 한계가 있는데, MSA는 사전 필터링(pre-filtering) 단계로 관련성 높은 컨텍스트 블록만 골라 그 블록에만 어텐션을 수행한다.

- 연산자 수준에서 각 KV 캐시 블록을 연속된 메모리 접근(contiguous memory access)으로 한 번만 읽어, 기존 희소 어텐션 구현보다 4배 이상 빠르다.
- 결과적으로 100만 토큰 컨텍스트 기준 M2 대비 토큰당 연산량 1/20, prefill 9배, decoding 15배 속도 향상을 달성했다.
- Key-Value를 압축하거나 정확도를 희생하지 않고 이 성능을 얻는다.

**NVIDIA Blackwell 성능**

![A line chart with a green B300 MTP curve remains well above a gray H100 M3 Eagle curve across increasing interactivity, with a 10x callout near the middle of the chart highlighting much higher throughput per GPU and a more responsive user experience.](https://developer-blogs.nvidia.com/wp-content/uploads/2026/06/Throughput.webp)
*이미지 출처: [원문](https://developer.nvidia.com/blog/deploy-long-context-reasoning-and-agentic-workflows-with-minimax-m3-on-nvidia-accelerated-infrastructure/)*

ISL/OSL 8K/1K 조건에서 NVIDIA Blackwell B300(MTP 적용)은 이전 세대 H100 대비 최대 10배 높은 처리량을 보이며, GPU당 응답성과 AI 팩토리 전체 처리량을 함께 높인다.

- Speculative decoding, MTP, 정확도를 보존하는 NVFP4 가속을 조합한 하드웨어-소프트웨어 공동 설계(co-design)가 성능 향상의 기반이다.
- NVIDIA Dynamo와 CUDA 커널 최적화가 계속 진행되면서 성능이 추가로 개선될 예정이다.

**오픈소스 추론 배포**

개발자는 원하는 오픈소스 추론 엔진으로 NVIDIA 가속 컴퓨팅을 활용할 수 있다.

- **TensorRT LLM(텍스트 전용)**: GitHub 저장소에서 최적화 코드를 제공하며, Quick Start 가이드로 Hugging Face 체크포인트 다운로드부터 Docker 컨테이너 실행, 저지연/고처리량 서빙 설정까지 지원. Transformers 라이브러리와도 협업.
- **SGLang**: 8-GPU 노드 기준 예시 명령으로 `--tp-size 8`, `--ep-size 8`, `--quantization mxfp8`, `--reasoning-parser minimax-m3` 등의 옵션으로 서버 실행.
- **vLLM**: `--tensor-parallel-size 8`, `--enable-expert-parallel`, `--reasoning-parser minimax_m3` 등의 옵션으로 서빙 가능.

**NVIDIA Dynamo를 통한 스케일링**

Dynamo는 대규모 서비스를 위한 오픈소스 분산 추론 서빙 플랫폼으로, PyTorch·SGLang·TensorRT LLM·vLLM 등 주요 엔진과 통합된다.

- LLM 인지 라우팅(LLM-aware routing), 탄력적 오토스케일링, 저지연 데이터 전송 기능 제공.
- Dynamo와 TensorRT LLM을 결합하면 GPU 예산을 늘리거나 처리량을 희생하지 않고도 긴 입력 시퀀스 처리 성능을 개선할 수 있다.

**NeMo Framework를 통한 커스터마이징**

NVIDIA NeMo Framework로 MiniMax M3를 파인튜닝하거나 강화학습을 적용할 수 있다.

- **NeMo AutoModel**: Hugging Face 체크포인트를 변환 없이 그대로 SFT·LoRA 파인튜닝 가능. 전체 N-D 병렬화로 고처리량 가속을 지원하며, 컨텍스트 병렬(context parallel)은 시퀀스 길이 최대 128k까지 지원.
- **NeMo RL**: MiniMax M3 위에서 강화학습을 수행할 수 있다.

**시작하기**

개발자는 build.nvidia.com의 GPU 가속 API를 통해 MiniMax M3를 프로토타이핑·평가하거나, Hugging Face에서 가중치를 직접 다운로드해 사용할 수 있다.

**대상 독자**: 장문 컨텍스트·멀티모달 에이전틱 애플리케이션(장시간 코딩 세션, 긴 비디오 이해 등)을 NVIDIA GPU 인프라에서 직접 배포·최적화하려는 ML 인프라 엔지니어와 LLM 서빙 담당 개발자에게 유용하다.

### [One-Click Multi-Tenant Security with NVIDIA Quantum InfiniBand](https://developer.nvidia.com/blog/one-click-multi-tenant-security-with-nvidia-quantum-infiniband/)

`InfiniBand` `Unified Fabric Manager` `Multi-Tenant Security` `Network Isolation` `Cybersecurity`

> UFM 인텐트 기반 보안 프로필로 InfiniBand 멀티테넌트 보안을 원클릭 구성

#### 요약

- NVIDIA Quantum InfiniBand의 Unified Fabric Manager(UFM)가 인텐트 기반 보안 프로필을 도입해 멀티테넌트 환경 보안 설정을 자동화한다.
- General, Bare Metal Cloud, Secured Bare Metal Cloud 세 가지 프로필로 PKey 격리, MAD 키 보호, GUID 기반 접근 제어, 지속적 검증을 자동 구성한다.
- 배포 시간을 수시간~수일에서 수분으로 단축하며, 수만 개 GPU 규모에서도 수동 Subnet Manager(SM) 설정 없이 하드웨어 강제 테넌트 격리를 구현한다.
- Continuous Security Verification(CSV) 기능으로 정적 분석 및 로그 기반 감사를 수행하고 "Security Health Score"와 자동 개선 조치를 제공한다.

#### 시사점

- 대규모 AI/HPC 클러스터를 운영하는 클라우드 사업자는 수동 설정 오류로 인한 테넌트 간 데이터 유출 위험을 크게 줄일 수 있다.
- 네트워크 보안 전문 지식이 없는 관리자도 프로필 선택만으로 검증된 보안 구성을 즉시 적용할 수 있어 진입 장벽이 낮아진다.
- 새 보안 기능이 릴리스되면 프로필에 자동 반영되므로, 기능 출시와 실제 적용 사이의 공백(보안 다운타임)이 사라진다.

#### 용어 설명

- **InfiniBand**: 초저지연·고대역폭을 제공하는 데이터센터용 고성능 네트워크 기술로, GPU 클러스터 연결에 널리 쓰인다.
- **UFM (Unified Fabric Manager)**: NVIDIA InfiniBand 네트워크를 중앙에서 관리·모니터링·보안 설정하는 관리 소프트웨어.
- **Subnet Manager (SM)**: InfiniBand 네트워크의 경로 설정, 파티션 할당 등 핵심 제어를 담당하는 소프트웨어 구성 요소.
- **PKey (Partition Key)**: InfiniBand에서 노드/포트 간 접근을 분리하는 하드웨어 기반 파티션 식별자로, Ethernet의 VLAN과 유사한 개념.
- **MAD (Management Datagram)**: InfiniBand 관리 트래픽을 전달하는 패킷 형식으로, 다양한 키로 보호된다.
- **MKey (Management Key)**: SM과 InfiniBand 하드웨어만 아는 관리 전용 키로, 포트 속성 접근을 통제한다.
- **GUID (Global Unique Identifier)**: 네트워크 장치를 고유하게 식별하는 값으로, 접근 제어에 사용된다.

#### 상세 내용

**기존 네트워크의 한계**

InfiniBand는 소프트웨어로 정의되고 중앙에서 관리되는 패브릭이다. 전통적 네트워크는 각 엔드포인트가 독자적으로 라우팅·정책 결정을 내려 설정 오류와 정책 불일치가 발생하기 쉽지만, NVIDIA Quantum InfiniBand는 UFM이 전역 정책을 강제하고 경로를 최적화하며 상태를 모니터링해 이런 문제를 방지한다.

- InfiniBand는 하드웨어 강제 테넌트 격리 등 강력한 보안 기능을 갖추고 있지만, Ethernet만큼 널리 이해되지 않아 활용도가 낮았다.
- 수만 개 GPU와 수천 개 스위치를 연결하는 에이전틱 AI 환경에서는 사소한 격리 설정 오류도 민감 데이터 유출이나 대규모 분산 워크로드 중단으로 이어질 수 있다.

**인텐트 기반 보안 프로필**

사용자가 여러 파라미터를 직접 설정하는 대신 사전 정의된 프로필을 선택하면 UFM이 모든 하위 보안 설정을 자동으로 조율한다.

- **오류 감소**: NVIDIA 엔지니어링 의도대로 보안 기능이 구현·배포되어 설정 오해나 문서 누락으로 인한 실수를 방지.
- **설정 시간 단축**: 수동 다단계 UFM/SM 설정에서 사전 구성된 프로필로 전환해 학습·적용·테스트 시간을 수시간~수일에서 수분으로 단축.
- **제로터치 확장**: 수백 개 노드를 추가해도 보안 관리 부담이 선형적으로 증가하지 않음.
- **보안 공백 제거**: 새 보안 기능이 추가되면 즉시 해당 프로필에 반영되어 릴리스와 실제 적용 사이의 전환 기간이 사라짐.

세 가지 프로필 중 General은 단일 테넌트 환경을 위한 기본 구성이며, Bare Metal Cloud와 Secured Bare Metal Cloud는 멀티테넌트 클라우드 환경을 대상으로 한다.

**Bare Metal Cloud 프로필**

PKey 기반 격리를 통해 InfiniBand 관리 네트워크 상에서 테넌트를 분리한다.

- InfiniBand 파티셔닝은 Ethernet VLAN과 유사하게, 어떤 노드/포트가 네트워크 리소스에 접근할 수 있는지를 하드웨어 메커니즘으로 정의해 파티션 간 접근을 차단한다.
- 파티션 할당은 전적으로 SM이 제어하며, 노드나 애플리케이션은 자신의 파티션을 스스로 결정하거나 지정할 수 없고 이미 할당된 파티션만 참조 가능하다.
- 포트 속성은 하드웨어에 저장되고 SM과 InfiniBand 실리콘만 아는 MKey를 통해서만 접근할 수 있어, 호스트 측 소프트웨어 우회에 의존하지 않는 강력한 격리를 보장한다.

**Secured Bare Metal Cloud 프로필**

PKey 격리에 더해 고도로 보안이 필요한 멀티테넌트 환경을 위한 포괄적 보안 기능을 제공한다.

- 무작위 시드를 적용한 전체 MAD 키 보호 (MKEY, VSKEY, PMKEY, CCKEY, Class C key(N2N), AM/job keys, SMKEY, SAKEY)
- `allowed_guid_list` 기능을 이용한 GUID 기반 접근 제어
- `service_key`를 통한 서비스 수준 인증 (예: AM 서비스)
- 모든 명령에 적용되는 강화된 SA 신뢰 모델
- MAD 속도 제한(MAD Limiter)을 통한 남용·혼잡 방지
  - DoS/DDoS 방어: 개별 노드의 과도한 패킷 전송률을 자동 감지·제한해 관리 노드를 보호
  - 소스 기반 속도 제한: 각 노드의 소스 LID 주소 기준으로 트래픽을 모니터링·제어

**Continuous Security Verification(CSV)으로 보안 상태 검증**

CSV는 정적 분석과 로그 기반 감사를 수행하는 새로운 UFM 진단 기능으로, "Security Health Score"와 함께 발견된 취약점에 대한 구체적인 자동 개선 조치를 제공한다.

- System Health 탭에서 Security 메뉴를 선택해 새 보안 리포트를 실행할 수 있다.

### [Designing Production-Ready Battery Energy Storage Systems for AI Factories](https://developer.nvidia.com/blog/designing-production-ready-battery-energy-storage-systems-for-ai-factories/)

`BESS` `AI Factory` `DSX` `Data Center` `Grid Interconnection` `Energy`

> AI 팩토리 전력망의 핵심, 배터리 에너지 저장 시스템(BESS) 설계와 검증 방법

#### 요약

- AI 팩토리는 전력 밀도가 높고 부하가 급변하는 워크로드를 운영하므로, 배터리 에너지 저장 시스템(BESS)이 단순 백업 전원이 아닌 전력 아키텍처의 핵심 구성 요소로 자리잡고 있다.
- BESS는 배터리 셀, 전력 변환 시스템(PCS) 인버터, 텔레메트리, 제어 로직이 통합된 시스템으로, 부하 스무딩·전력 품질 개선·저전압 라이드스루·계통 연계 가속화 등을 지원한다.
- NVIDIA는 AI 팩토리에 특화된 BESS 자체 검증 가이드라인(BESS Self-Qualification Guidelines)을 발표해, 벤더가 시뮬레이션과 하드웨어인더루프(HIL) 테스트로 성능을 입증하도록 표준을 제시했다.
- 이 프레임워크는 NVIDIA DSX(AI 팩토리 플랫폼)의 전력 스택에 통합되어 있으며, 성능 검증뿐 아니라 제조·공급망·품질 체계까지 아우르는 산업용 인프라 기준을 지향한다.

#### 시사점

- AI 인프라를 설계·운영하는 개발자는 전력 안정성이 컴퓨팅 성능만큼 서비스 가용성에 직결된다는 점을 인지해야 하며, BESS 도입 여부가 데이터센터의 계통 연계 속도와 확장성을 좌우할 수 있다.
- 대규모 GPU 클러스터 운영 시 급격한 전력 수요 변동(로드 스파이크)이 실제 전력망과 발전 설비에 미치는 영향을 이해하면, 인프라 설계 단계에서 전력 안정성 요구사항을 조기에 반영할 수 있다.

#### 용어 설명

- **BESS(Battery Energy Storage System)**: 배터리로 전력을 저장했다가 필요 시 방출하는 시스템. 단순 저장 장치가 아니라 인버터와 제어 장치로 실시간 전력 흐름을 조정하는 지능형 자산.
- **PCS(Power Conversion System)**: 배터리의 직류 전력을 교류로 변환하고 반대로도 변환하는 인버터 장치로, BESS를 그리드와 상호작용 가능하게 만드는 핵심 부품.
- **DSX**: NVIDIA의 AI 팩토리용 플랫폼으로, 전력·냉각·컴퓨팅 인프라를 통합 설계하는 청사진(blueprint) 역할을 한다.
- **Interconnection(계통 연계)**: 데이터센터를 전력망(그리드)에 연결하는 절차와 인프라. 신규 AI 팩토리의 전력 수요 급증으로 연계 대기 시간이 병목이 되고 있다.
- **Ride-through(라이드스루)**: 정전이나 전압 변동 같은 계통 장애 발생 시 시스템이 끊김 없이 견디는 능력.
- **State-of-Charge(SoC)**: 배터리의 현재 충전 상태(잔량)를 나타내는 지표로, BESS가 여러 임무(안정화, 백업, 수요 대응)를 동시에 수행할 때 관리가 필요하다.
- **SCADA(Supervisory Control and Data Acquisition)**: 전력 설비의 원격 감시·제어·데이터 수집 시스템으로, BESS 검증 시 텔레메트리 점검 대상이 된다.

#### 상세 내용

**AI 팩토리에서 BESS가 중요한 이유**

기존 데이터센터는 완만하고 다양한 워크로드 패턴을 보이지만, AI 팩토리는 전력 밀도가 높고 부하가 빠르게 변하는 대규모 연산 부하로 작동한다.

- GPU/랙 단위의 전력 변동 억제 기술을 보완해, 잔여 과도현상(transient)이 상류 계통까지 도달하지 않도록 시설 규모의 완충 역할을 한다.
- 계통 측 라이드스루 요구사항이 점점 엄격해지는 가운데, 백업 전원의 부하 안정성과 계통 측 준수 사항 사이의 간극을 메운다.
- 그리드 연계, 발전기 연동, 독립 운전(islanded) 등 다양한 모드 전환을 지원하고 블랙스타트(정전 후 자체 기동)에도 기여한다.
- 계통 운영자 관점에서 사이트를 더 유연하고 예측 가능한 부하로 만들어, 제약된 계통 연계 일정을 해결 가능한 엔지니어링 문제로 전환시킨다.

**BESS 설계는 배터리 용량 이상의 문제**

BESS를 단순히 메가와트시(MWh) 단위로 용량을 산정하는 문제로 보면 안 된다. 배터리 셀, PCS, 제어, 텔레메트리, 모델링, 장애 대응, SoC 전략을 모두 통합적으로 설계해야 한다.

- 사이트 모델은 BESS뿐 아니라 IT/비IT 부하 거동, 램프 속도, 최소·최대 수요, 역률, UPS 운전 모드, 보호 설정, 재연결 로직까지 포함해야 한다.
- 설계 목표에는 소스 안정화(residual fluctuation 흡수), 그리드 적응형 운전(연계/발전기 연동/독립 운전 전환), 전류 제한 거동의 명확한 정의가 포함된다.
- 전압·전류·유효전력·무효전력·주파수·SoC·알람 등 핵심 신호를 실시간으로 정렬해 수집하는 고속 텔레메트리와 실시간 분석이 설계의 중심이 되어야 한다.
- BESS는 과도현상 안정화, 라이드스루용 예비 용량 확보, 수요 반응 참여 등 여러 임무를 동시에 수행해야 하므로, 우선순위와 SoC 표류 방지 전략이 명시적으로 필요하다.

**검증이 설계를 신뢰할 수 있게 만든다**

AI 팩토리는 기존 표준이 다루지 못한 새로운 인프라 범주이며, NVIDIA는 BESS Self-Qualification Guidelines를 통해 엄격한 검증 방식을 제시한다.

- 이 가이드라인은 벤더가 AI 팩토리 특화 요구사항 대비 제품 성능을 입증할 구조화된 방법을 제공하고, 데이터센터 개발자에게는 신뢰 가능한 채택 근거를 제공한다.
- 검증에는 준공 모델 검증, 운전 모드 기능 테스트, 전부하/무부하 테스트 증거, SCADA·텔레메트리 점검, 보호·제어 설정 검증, 유틸리티·계통운영자·인근 발전사업자와의 조정이 포함된다.
- 직접 테스트가 어려운 엣지 케이스를 위해 전자기 과도(electromagnetic transient) 모델과 소신호(small-signal) 아티팩트 제출도 요구된다.
- 검증 항목에는 텔레메트리 정확성, 장애 이벤트 기록, 독립 운전 시 전압·주파수 규제 안정성, 전류 제한 도달 시 거동, 약한 계통(weak-grid) 조건에서의 AI형 램프 프로파일 버퍼링 능력 등이 포함된다.

**검증만으로는 충분하지 않다**

검증은 기술적 투명성과 재현성, 비교 가능성을 위한 공통 기준을 제공하지만, 그 자체가 최종 목표는 아니다.

- 실제 목표는 유틸리티 상호작용, 온사이트 발전 연동, 캠퍼스 제어 통합, 보호 철학, 제조 가능성, 유지보수성, 대규모 신뢰성까지 아우르는 전력 아키텍처를 구축하는 것이다.
- NVIDIA의 검증 프레임워크는 성능 테스트를 넘어 비즈니스 준비도, 공급망 신뢰성, 품질 시스템, 신뢰성 증거까지 포괄한다.
- 장비 단위 검증을 통과해도 요구 규모로 제조·유지보수·품질 지원이 안 되면 프로덕션 인프라로는 부적합하다는 것이 핵심 관점이다.

### [Delivering Lifecycle Control for AI Infrastructure at Scale with NVIDIA DGX Spark Enterprise Manageability](https://developer.nvidia.com/blog/delivering-lifecycle-control-for-ai-infrastructure-at-scale-with-nvidia-dgx-spark-enterprise-manageability/)

`DGX Spark` `GB10` `Enterprise Manageability` `AI Infrastructure` `Fleet Management` `Cloud-Init`

> DGX Spark에 도입부터 폐기까지 전 생애주기를 관리하는 엔터프라이즈 관리 프레임워크 제공

- NVIDIA DGX Spark와 GB10 시스템에 프로비저닝부터 폐기까지 6단계 운영 생애주기를 다루는 Enterprise Manageability 프레임워크가 추가됨

- 완전 폐쇄망(에어갭) 환경에서도 cloud-init 기반 커스텀 설치로 사전 구성 가능

#### 시사점

- 엔터프라이즈 IT팀이 별도의 관리 인프라를 새로 구축하지 않고 기존 Ansible, Tanium, Landscape 등 오케스트레이션 도구로 DGX Spark 플릿을 관리할 수 있음
- 표준 JSON 출력 포맷 덕분에 CMDB, SIEM, 모니터링 파이프라인에 바로 연동 가능해 대규모 AI 인프라 운영의 자동화 문턱이 낮아짐
- 인터넷 연결이 제한된 보안·규제 환경(금융, 국방 등)에서도 표준 도구만으로 AI 인프라를 안전하게 프로비저닝·감사할 수 있음

#### 용어 설명

- **DGX Spark**: NVIDIA의 소형 AI 개발용 컴퓨터 시스템
- **GB10**: DGX Spark에 탑재된 NVIDIA의 슈퍼칩(Grace Blackwell 계열)
- **Air-gapped**: 외부 인터넷과 물리적으로 분리된 폐쇄망 환경
- **CMDB**: 조직 내 IT 자산(하드웨어·소프트웨어) 정보를 관리하는 구성관리 데이터베이스
- **SIEM**: 보안 이벤트와 로그를 수집·분석하는 보안 정보 및 이벤트 관리 시스템
- **cloud-init**: 클라우드/온프레미스 서버의 초기 설정을 자동화하는 표준 도구
- **RBAC**: 역할 기반으로 접근 권한을 부여하는 보안 모델

#### 상세 내용

**기존 IT 워크플로우와의 통합 방식**

DGX Spark 관리 프레임워크는 별도 상주 에이전트 없이 SSH로 도구를 호출하고, 결과를 표준화된 JSON 형태로 반환하는 방식으로 동작한다.

- Progress Chef, Perforce Puppet, Canonical Landscape 등 파트너 도구와 연동 지원
- 각 도구 실행 결과는 `status`, `rc`, `duration_ms`, `summary`, `warnings` 등을 포함한 동일한 JSON 포맷으로 반환되어 CMDB·SIEM·모니터링 파이프라인에 바로 연결 가능
- 생애주기는 조달/입고, 초기 프로비저닝, 상시 모니터링, 유지보수 윈도우, 인시던트 대응, 폐기/재배치의 6단계로 구성
- 상태를 바꾸지 않는 읽기 전용 "collector"와 변경 권한이 필요한 "controller"를 분리해 최소 권한 원칙을 IT 거버넌스 체계에 맞춤

**커스텀 설치를 통한 초기 상태 표준화**

인터넷 접근이 제한된 환경에서 시스템을 "알려진 정상 상태(known-good state)"로 만드는 과정 자체가 큰 운영 부담이라는 점에 착안해, DGX Spark Custom Installation 기능이 도입됐다.

- USB 드라이브나 로컬 서버로 부팅 전 사전 구성 가능, 온보딩(out-of-box) 과정 생략
- 인터넷 연결 환경과 에어갭 환경 모두 지원
- cloud-init, USB 내 OEM Data 파티션, 프로비저닝 훅 스크립트를 기반으로 동작하며, 완전 에어갭 플릿을 위한 온프레미스 미러도 선택적으로 사용 가능

**진단 도구**

원격 진단이 어려운 AI 인프라 장애(펌웨어 회귀, PCIe 이슈, 예기치 않은 리셋 등)에 대응하기 위해 두 가지 도구가 제공된다.

- `spark_diagctl.py`: SSH로 원격 실행되는 진단 도구로, L1(디스크·네트워크·드라이버 상태를 담은 경량 JSON 헬스 요약)과 L2(GPU 텔레메트리, 커널 로그, PCIe 상태, 펌웨어 정보 등을 포함한 전체 진단 번들) 두 모드로 동작
- `reset_reason_reporter.py`: 시스템 이벤트 로그, BMC 기록, 커널 오류, 펌웨어 이벤트 등 여러 근거를 종합해 재부팅 원인을 구조화된 형태로 분석하며, 불확실한 경우 추측 대신 모호함으로 표시
- 두 도구 모두 동일한 JSON 포맷을 반환해 기존 Ansible playbook, Tanium 패키지, Landscape 스크립트를 변경 없이 재사용 가능

**멀티레이어 업데이트 관리**

`spark_updatectl.py`는 커널, GPU 드라이버, 펌웨어, 컨테이너 런타임, AI 프레임워크, 보안 패치 등 서로 얽힌 여러 계층의 업데이트를 조율하는 제어 도구다.

- 업데이트가 필요한 패키지, 적용 가능한 펌웨어, 재부팅 대기 여부 등을 JSON 리포트로 제공
- 유지보수 윈도우 스케줄링과 연동해 디바이스 링(ring) 단위 단계적 배포, 사전/사후 점검 증거 수집, 펌웨어 롤백 가시성을 지원

**보안 범위**

프레임워크는 보안을 핵심 요구사항으로 취급하며 다음 기능을 제공한다.

- 디스크 암호화 상태 리포팅(보안 감사 보존 요구사항에 맞춰 180~365일 이상 권장)
- APT 패키지 서명 검증(PASS/FAIL/UNKNOWN 결과와 상세 증거 제공)
- 체인 오브 커스터디를 갖춘 팩토리 리셋(방법, 타임스탬프, 성공/실패 상태를 포함한 폐기 증명서 생성)

- collector는 권한 없이, controller는 특정 작업에 한정된 sudo 권한으로 실행되는 최소 권한 RBAC 설계

### [Model Quantization: Turn FP8 Checkpoints into High-Performance Inference Engines with NVIDIA TensorRT](https://developer.nvidia.com/blog/model-quantization-turn-fp8-checkpoints-into-high-performance-inference-engines-with-nvidia-tensorrt/)

`TensorRT` `FP8 Quantization` `ONNX` `CLIP` `Model Optimizer` `Nsight Deep Learning Designer`

> FP8 양자화된 CLIP을 TensorRT 엔진으로 변환해 실제 추론 속도 향상을 검증

#### 요약

- FP8로 양자화된 ModelOpt 체크포인트를 ONNX로 내보내고 TensorRT 엔진으로 빌드하는 전체 워크플로우를 설명
- ONNX 파일 크기가 텍스트 인코더 약 34%, 이미지 인코더 약 50% 감소
- `trtexec`와 Nsight Deep Learning Designer로 FP16 대비 FP8의 엔진 크기·지연시간을 벤치마크
- TensorRT가 Q/DQ 노드를 인접 레이어에 융합해 FP8 전용 커널로 실행하는 내부 동작 원리를 소개

#### 시사점

- FP16 대비 엔진 크기와 VRAM 사용량을 거의 절반으로 줄이면서 추론 지연시간도 개선할 수 있어 프로덕션 배포 비용을 낮출 수 있음
- Nsight Deep Learning Designer로 레이어별 프로파일링을 통해 성능 개선이 실제로 어디서 발생하는지(GEMM, MHA 커널 등) 구체적으로 확인 가능
- ModelOpt → ONNX → TensorRT로 이어지는 재현 가능한 파이프라인을 제공해 다른 모델에도 적용 가능

#### 용어 설명

- **FP8**: 8비트 부동소수점 정밀도. FP16/FP32보다 메모리와 연산량이 적어 추론 속도와 메모리 효율을 높임
- **TensorRT**: NVIDIA의 딥러닝 추론 최적화 및 런타임 엔진
- **ONNX**: 여러 딥러닝 프레임워크 간 모델을 교환하기 위한 공개 포맷
- **Q/DQ (QuantizeLinear/DequantizeLinear)**: 텐서가 고정밀도와 저정밀도 사이를 오가는 지점을 표시하는 ONNX 노드 쌍
- **CLIP (Contrastive Language-Image Pretraining)**: 이미지와 텍스트를 함께 이해하도록 학습된 멀티모달 모델
- **GEMM**: 행렬곱(General Matrix Multiply) 연산으로, 신경망 연산의 핵심 병목 지점
- **trtexec**: ONNX 모델을 TensorRT 엔진으로 빌드하고 벤치마크하는 커맨드라인 도구

#### 상세 내용

**전체 워크플로우**

FP8 양자화 배포는 PyTorch 모델 → ModelOpt 체크포인트 양자화 → ONNX(Q/DQ 노드 포함) 내보내기 → TensorRT 엔진 빌드 → 런타임 추론의 5단계로 진행된다. 이는 CLIP 같은 모델의 표준 파이프라인이며, 양자화된 LLM은 TensorRT-LLM을 통한 별도 경로를 따른다.

![Workflow diagram showing five stages from a PyTorch model to TensorRT runtime inference](https://developer-blogs.nvidia.com/wp-content/uploads/2026/06/E2E-Quantization.webp)
*이미지 출처: [원문](https://developer.nvidia.com/blog/model-quantization-turn-fp8-checkpoints-into-high-performance-inference-engines-with-nvidia-tensorrt/)*

**ONNX 내보내기**

ModelOpt의 내장 헬퍼(`get_onnx_bytes_and_metadata`)를 사용해 FP8 양자화된 CLIP 체크포인트를 ONNX opset 20+ 형식으로 내보낸다.

- 가중치 쪽 Q-DQ 쌍을 FP8로 저장된 DQ-only 체인으로 접어(fold) ONNX 파일 크기를 줄임
- 텍스트 인코더: 156MB(FP8) vs 237MB(FP16), 약 34% 감소
- 이미지 인코더: 292MB(FP8) vs 582MB(FP16), 약 50% 감소
- Nsight Deep Learning Designer로 ONNX 그래프를 시각화하면 attention MatMul 주변에 Q/DQ 노드가 FP8 경계를 표시하는 것을 확인 가능

![A Portion of the FP8 ONNX graph around an attention MatMul](https://developer-blogs.nvidia.com/wp-content/uploads/2026/06/FP8-ONNX-Graph.webp)
*이미지 출처: [원문](https://developer.nvidia.com/blog/model-quantization-turn-fp8-checkpoints-into-high-performance-inference-engines-with-nvidia-tensorrt/)*

**TensorRT로 ONNX 프로파일링**

`trtexec`로 ONNX 모델을 TensorRT 엔진으로 빌드하고 벤치마크한다. `--stronglyTyped` 옵션은 ModelOpt가 부여한 정밀도 주석(FP8)을 그대로 강제 실행하도록 하지만, attention scaling이 FP32로 왕복하는 부분과 충돌해 타입 불일치 오류가 발생할 수 있어 사전에 FP32 초기화값과 Cast 연산을 FP16으로 재변환하는 전처리가 필요하다.

- 벤치마크 환경: NVIDIA RTX 6000 Ada GPU, TensorRT 10.16, 배치 크기 128
- FP8은 Ada 이상 아키텍처(compute capability 8.9+)에서만 GEMM에 지원됨
- 엔진 크기: 이미지 인코더 588MB→294MB(50%↓), 텍스트 인코더 238MB→156MB(34%↓)
- 지연시간: 이미지 인코더 204ms→127ms(1.61배), 텍스트 인코더 19ms→11.4ms(1.67배) — 본문 하단에는 166.2ms→119.8ms(1.39배), 13.2ms→9.1ms(1.45배)로 별도 수치도 제시됨

![A bar chart comparing CLIP FP8 vs FP16 on TensorRT](https://developer-blogs.nvidia.com/wp-content/uploads/2026/06/FP8-FP16.webp)
*이미지 출처: [원문](https://developer.nvidia.com/blog/model-quantization-turn-fp8-checkpoints-into-high-performance-inference-engines-with-nvidia-tensorrt/)*

**속도 향상의 원인**

Nsight Deep Learning Designer로 FP16/FP8 이미지 인코더를 레이어별로 비교한 결과 세 가지 차이가 확인됐다.

- GEMM 레이어 지연시간이 약 1.8ms→0.84ms로 2배 이상 감소 (RTX 6000 Ada의 FP8 Tensor Core 덕분)
- FP16에 존재하던 별도의 "fusion" 레이어 카테고리가 FP8에서는 사라짐 — attention 블록 전체가 전용 FP8 MHA(Multi-Head Attention) 커널로 처리되기 때문
- 정밀도 비중을 나타내는 도넛 차트가 FP16(주황) 중심에서 FP8(보라) 중심으로 이동

![Nsight Deep Learning Designer profiles comparing FP16 and FP8 CLIP image encoders](https://developer-blogs.nvidia.com/wp-content/uploads/2026/06/CLIP-Layering.webp)
*이미지 출처: [원문](https://developer.nvidia.com/blog/model-quantization-turn-fp8-checkpoints-into-high-performance-inference-engines-with-nvidia-tensorrt/)*

**TensorRT의 양자화 처리 방식**

TensorRT는 ONNX를 임포트할 때 Q/DQ 노드를 찾아 정밀도 전환 지점을 파악한다. 엔진 빌드 시 이 Q/DQ 노드를 인접 레이어에 융합하고, 원래 레이어를 저정밀도 텐서에서 직접 동작하는 전용 커널로 대체해 불필요한 양자화-역양자화 왕복을 제거한다.

- FP8 GEMM의 경우 활성화(activation)와 가중치 텐서 각각의 Q/DQ 쌍이 융합되어 FP8 활성화와 사전 저장된 FP8 가중치를 바로 사용하는 단일 FP8 GEMM 커널로 축소됨

![A diagram showing how TensorRT fuses the FP8 QuantizeLinear and DequantizeLinear nodes around a GEMM](https://developer-blogs.nvidia.com/wp-content/uploads/2026/06/FP8-GEMM-Fusion-625x382.png)
*이미지 출처: [원문](https://developer.nvidia.com/blog/model-quantization-turn-fp8-checkpoints-into-high-performance-inference-engines-with-nvidia-tensorrt/)*

**대상 독자**: FP8 양자화 모델을 실제 프로덕션 추론 파이프라인에 배포하려는 ML 엔지니어, 특히 TensorRT/ModelOpt로 CLIP과 같은 멀티모달 모델의 지연시간·메모리 최적화를 검토하는 개발자에게 유용하다.

### [Accelerating Federated Learning Research with AI Agents and NVIDIA FLARE Auto-FL](https://developer.nvidia.com/blog/accelerating-federated-learning-research-with-ai-agents-and-nvidia-flare-auto-fl/)

`NVIDIA FLARE` `Federated Learning` `AI Agent` `LoRA` `FedAvg` `Auto-FL`

> AI 에이전트가 연합학습 전략을 자동 탐색·검증하는 NVIDIA FLARE Auto-FL 소개

#### 요약

- Auto-FL은 고정된 벤치마크 예산, 제한된 변경 범위(mutation surface), 실험 원장(ledger)을 기반으로 AI 에이전트가 연합학습(Federated Learning, FL) 전략을 자동으로 반복 탐색하는 NVIDIA FLARE의 연구 루프이다.
- 에이전트는 `program.md`라는 제어판을 기준으로 후보 전략을 제안하고, 동일한 학습 예산으로 실행한 뒤 결과를 `results.tsv`에 기록하여 유지·축소·폐기를 결정한다.
- 성능 향상이 정체되면 문헌 검색 기반 회복 루프(literature-grounded recovery)로 전환해 근거 있는 새 제안을 도출하고, 다시 동일한 통제된 실험 루프로 복귀한다.
- CIFAR-10 시뮬레이션 외에도 의료 VLM(Vision-Language Model) 과제(Qwen3-VL + LoRA)에 적용해 FedAvg 대비 성능 향상을 확인했다.

#### 시사점

- 연합학습 실험은 서버-클라이언트-데이터 분할-평가 로직 간 계약이 복잡해 코딩 에이전트가 자칫 비교 기준 자체를 훼손할 수 있는데, Auto-FL은 이를 구조적으로 방지한다.
- 연구자는 태스크 프로파일(데이터셋, 지표, 변경 제약)만 정의하면 동일한 자동 실험 프레임워크를 다양한 모델·데이터셋에 재사용할 수 있다.
- 폐기된 후보까지 원장에 남겨 동일한 저가치 아이디어의 반복 시도를 막아, 반복 실험의 재현성과 신뢰성을 높인다.

#### 용어 설명

- **Federated Learning (FL)**: 데이터를 중앙에 모으지 않고 여러 클라이언트(사이트)에서 각각 학습한 뒤 모델 업데이트만 취합하는 분산 학습 방식.
- **NVIDIA FLARE**: NVIDIA의 연합학습 개발 프레임워크로, Client API와 Recipe API를 제공한다.
- **FedAvg / FedProx / FedOpt(FedAdam) / SCAFFOLD**: 연합학습에서 여러 클라이언트의 모델 업데이트를 서버에서 집계(aggregation)하는 다양한 알고리즘들.
- **Mutation surface**: 에이전트가 실험에서 변경할 수 있도록 허용된 제한된 파라미터·설정 범위.
- **Experiment ledger**: 각 실험 후보의 점수, 실행 시간, 상태 등을 기록하는 표(`results.tsv`) 형태의 실험 기록부.
- **LoRA (Low-Rank Adaptation)**: 대형 모델 전체를 재학습하지 않고 저랭크 어댑터만 학습해 효율적으로 미세조정하는 기법.
- **VLM (Vision-Language Model)**: 이미지와 텍스트를 함께 이해·생성하는 멀티모달 모델.

#### 상세 내용

**Auto-FL이란?**

Auto-FL은 FL 전략을 테스트·최적화하는 자동화된 AI 기반 연구 루프다.

- 고정된 학습 예산과 일관된 채점 기준을 갖는 비교 가능한 벤치마크 작업에서 시작한다.
- 에이전트는 FLARE의 Client API와 Recipe API 계약을 유지하면서 후보 FL 전략을 자율적으로 반복 탐색한다.
- 실험은 계약을 깨지 않을 만큼 제한적이고, 비교 가능할 만큼 측정 가능하며, 장기 자율 캠페인에도 안정적이고, 결과를 재현 가능한 보고서로 전환할 수 있을 만큼 상세해야 한다.

8개의 시뮬레이션 클라이언트로 이질적인(heterogeneous) CIFAR-10 데이터를 분할한 캠페인 예시로, 회색 점은 폐기된 실행, 파란 점은 진행 중 후보, 초록 점은 채택된 실행, 초록 계단선은 관측된 최고 교차 사이트 평가 점수의 추이, 보라색 선은 문헌 검토 이벤트를 나타낸다.

**연구 루프를 명시적으로 만드는 방법**

FL 실험은 서버, 클라이언트, 모델 업데이트, 메타데이터, 데이터 분할, 평가 로직 간 계약에 정확성이 달려 있다. 후보 변경이 평가 데이터, 모델 용량, 통신 예산 등을 몰래 바꿔 점수만 높이는 경우가 생길 수 있다.

- 에이전트는 `program.md`를 읽고 제한된 변경을 제안, 동일 벤치마크 예산으로 실행, 비교 가능한 점수를 추출, `results.tsv`에 결과를 추가한다.
- 원장을 근거로 후보를 유지할지 폐기할지 결정하며, 사람은 언제든 캠페인을 중단하고 실험 이력을 분석할 수 있다.

**Auto-FL 구성 요소**

| 구성 요소 | 역할 |
|---|---|
| `program.md` | 에이전트용 연구 제어판 (메인 진입점) |

**문헌 기반 회복(literature-grounded recovery)의 역할**

원장이 특정 탐색 방향이 정체되었음을 보여주면, 캠페인은 지역적 미세 변경을 계속하는 대신 문헌 검토 루프로 전환한다.

- 에이전트는 현재 최고 스택, 최근 후보들, 반복된 오류, 무효/악화된 아이디어, 활성 변경 계약을 요약한다.
- 구조화된 워크시트를 작성하고 관련 방법을 검색해 챌린지 카드(challenge card)를 추출, 제안 카드를 생성한다.
- 중복·과거 실패 아이디어를 걸러내고 예상 이득, 구현 위험, 계약 안전성, 근거, 참신성, 실행 비용 기준으로 제안을 채점한다.
- 선택된 제안은 다시 동일한 제한된 실험 루프로 복귀해 검증된다.

사람이 캠페인을 수동으로 중단하면, 보고 스킬이 `results.tsv`가 있는 실험 브랜치에서 최종 진행 그래프를 만들고 보고서를 작성해 커밋한다.

### [Evaluate Clinical ASR Models Faster with Agent Skills and NVIDIA Nemotron Speech](https://developer.nvidia.com/blog/evaluate-clinical-asr-models-faster-with-agent-skills-and-nvidia-nemotron-speech/)

`NVIDIA Nemotron Speech` `NeMo Data Designer` `Magpie TTS` `Clinical ASR` `Synthetic Data Generation` `Agent Skills`

> AI 에이전트 스킬로 임상 음성인식 평가 벤치마크를 자동 생성·개선

#### 요약

- 의약품·수술명 등 임상 전문용어는 일반 ASR(음성인식) 모델이 자주 놓치는데, 실제 임상 음성 데이터는 HIPAA 등 규제로 수집·공유가 어려움
- NVIDIA는 발음이 정확한 합성 음성(SDG)과 AI 에이전트 스킬을 결합해 임상 ASR 벤치마크를 대화형으로 구축하고 평가·개선하는 워크플로를 제시
- NeMo Data Designer가 텍스트를 IPA(국제음성기호) 발음·SSML 마크업까지 포함한 데이터로 확장하고, Magpie TTS Multilingual이 이를 음성으로 합성
- 벤치마크 구축 → ASR 평가 → 모델 적응(파인튜닝) → 재평가로 이어지는 반복 개선 루프("flywheel")를 스킬이 안내

#### 시사점

- 실제 환자 음성 없이도 특정 전문 분야(정형외과, 종양학 등) 맞춤형 ASR 벤치마크를 몇 시간 내에 구축할 수 있어 컴플라이언스 부담을 크게 줄임
- 발음 오류로 인한 실패와 모델 자체의 한계를 구분해주는 라우팅 로직 덕분에 불필요한 파인튜닝을 피하고 정확한 개선 지점을 파악 가능
- 개체(entity) 단위 오류율 분석으로 어떤 용어 카테고리(약품명 등)가 취약한지 구체적으로 확인해 후속 데이터 수집 방향을 결정할 수 있음

#### 용어 설명

- **ASR (Automatic Speech Recognition)**: 음성을 텍스트로 변환하는 자동 음성인식 기술
- **TTS (Text-to-Speech)**: 텍스트를 음성으로 합성하는 기술
- **SDG (Synthetic Data Generation)**: 실제 데이터 대신 인공적으로 생성한 학습/평가용 데이터
- **IPA (International Phonetic Alphabet)**: 발음을 표기하는 국제 표준 기호 체계
- **SSML (Speech Synthesis Markup Language)**: TTS 엔진에 발음·속도·강세 등을 지시하는 XML 기반 마크업 언어
- **WER/CER/KER/SER**: 각각 단어 오류율, 문자 오류율, 핵심 키워드(임상 용어) 오류율, 문장 오류율을 뜻하는 ASR 성능 지표
- **NVIDIA Nemotron Speech**: 이 워크플로에서 실제 음성 전사(transcription)를 수행하는 NVIDIA의 음성 모델

#### 상세 내용

**왜 임상 ASR에는 반복 가능한 피드백 루프가 필요한가**

임상 음성 AI는 받아쓰기, 원격 문서화, 콜센터, 환자 접수 등 다양한 워크플로에 쓰이지만 약물명·수술명·해부학 용어처럼 희귀하지만 중요한 단어를 정확히 인식해야 한다.

- 실제 환자 음성은 HIPAA상 보호대상 건강정보(PHI)라 팀 간 공유, 버전 관리, 자동 테스트 파이프라인에 넣기가 사실상 어려움
- 합성 음성은 PHI가 없어 버전 관리·공유·테스트가 가능한 유일한 임상 음성 데이터 형태
- 공개 데이터셋은 특정 배포 환경에 필요한 정확한 용어를 포함하지 않을 수 있음
- 관건은 단순히 데이터를 늘리는 게 아니라, 프로필 정의 → 벤치마크 구축 → 발음 검토 → ASR 측정 → 개선까지 반복 가능한 절차를 만드는 것

**AI 에이전트 스킬은 어떻게 도움이 되는가**

에이전트 스킬은 Claude Code나 Codex 같은 에이전트 환경에서 대화형으로 실행되며, 개발자가 특정 임상 워크플로를 설명하면 벤치마크 초안을 생성한다.

- 스킬은 전문 분야, 관찰된 ASR 실패 유형, 일상적으로 쓰이는 용어와 어려운 용어를 한 번에 하나씩 질문
- 예: 정형외과 수술 후 지침 및 PACU(회복실) 인수인계에 초점을 맞춘 벤치마크 프로필을 약물·수술·해부학·질환 카테고리로 구성
- 이 방식으로 정형외과, 심장내과, 종양학, 행동건강 등 어느 도메인이든 동일한 flywheel을 재구성 가능

**TTS용 합성 음성을 생성하는 방법**

NeMo Data Designer가 시드 용어를 확장해 완전한 합성 음성 레코드를 생성한다. 각 레코드는 5개 컬럼(sample_id, sentence, ipa_pronunciation, ssml_sentence, audio_filepath)으로 구성된다.

![Diagram showing a clinical terminology list inputted into NeMo Data Designer to generate columns for sample ID, sentence, IPA, SSML, and audio path, then into Magpie TTS to generate an audio sample.](https://developer-blogs.nvidia.com/wp-content/uploads/2026/06/pipeline-pronunciation-aware-synthetic-audio-generation-1.webp)
*이미지 출처: [원문](https://developer.nvidia.com/blog/evaluate-clinical-asr-models-faster-with-agent-skills-and-nvidia-nemotron-speech/)*

- 생성된 문장은 대상 용어를 정확히 포함해야 하며, 상표명·약어·철자 변형으로 치환되면 스킬이 이를 감지해 재생성하거나 거부
- SSML 단계는 문장을 `<speak>` 요소로 감싸고 대상 용어마다 `<phoneme alphabet="ipa">` 태그를 삽입 (대소문자 무관 정규식 사용)

사전(dictionary)에 없는 신조어·상표명·희귀 용어는 수동 발음 검토 절차를 거친다.

- LLM이 IPA 후보 발음을 제안하되 이를 정답으로 취급하지 않고 검증·검토 대상으로만 사용
- 검토 루프: 낮은 신뢰도 IPA 표시 → 후보 제안 → TTS 음소 인벤토리 검증 → QA 클립 합성 → 인간 검토(승인/수정/거부) → 오버라이드 파일 기록 → SSML·오디오 재생성
- 정형외과 사례에서는 Femoroacetabular impingement, Hemiarthroplasty, Ketorolac 등의 용어가 검토 대상이었고, 최종적으로 67개 오디오 샘플이 검토되지 않은 발음 없이 생성됨

**오디오 합성과 매니페스트 생성**

NVIDIA Magpie TTS Multilingual은 IPA와 ARPAbet 기반 SSML 음소 태그를 지원해 검토된 발음 시퀀스로 음성을 렌더링한다.

- 최종 결과물은 NeMo 호환 JSONL 매니페스트로, 오디오 파일·전사문·시간(duration)·용어·카테고리·IPA 출처 등의 메타데이터를 포함
- 이 매니페스트는 SDG, ASR 평가, 모델 적응 단계를 잇는 연결점이며 개체 카테고리·발음 출처·문맥 유형별로 결과를 세분화하는 데 사용됨

**스킬 기반 임상 ASR 품질 flywheel**

벤치마크 구축, ASR 평가, 모델 적응(파인튜닝), 재평가로 이어지는 순환 구조다.

- 흥미로운 라우팅 규칙: Merriam-Webster 발음은 점수가 좋은데 Magpie 기본 발음은 낮으면, 이는 모델 문제가 아니라 발음 커버리지 문제이므로 파인튜닝 대신 다시 벤치마크 구축 단계로 되돌림 (TTS 발음 오류를 파인튜닝하면 모델이 스스로의 실수를 학습하게 됨)
- 적응(Adapt) 단계는 우선순위 카테고리 KER > 0.3, 매니페스트 100행 이상이라는 두 임계값을 충족해야 파인튜닝을 진행하며, 그렇지 않으면 벤치마크를 확장하는 build 단계로 회귀
- ASR 전사 자체는 NVIDIA Nemotron Speech가 담당

**성능 벤치마크 방법**

WER, CER, KER, SER 네 가지 지표를 사용하되, 단순 점수가 아니라 의사결정 신호로 해석한다.

- 발음 QA가 미완료면 다음 단계는 모델 훈련이 아니라 검토
- 오류가 특정 카테고리에 몰리면 다음 단계는 더 정밀한 데이터 확보
- 검토된 용어에서도 오류가 지속되면 모델 적응이 정당화됨
- 정형외과 시뮬레이션에서는 약물명이 가장 취약한 카테고리로 나타나 발음 검토, 약물명 커버리지 확대, 모델 적응이 후속 사이클의 초점이 됨

**flywheel의 한계**

- 합성 음성은 실제 임상 음성의 대체재가 아니며 프로덕션 검증에는 실제 환경 음성이 필요
- 발음 검증은 여전히 인간 검토가 필요하며, 자동 제안 발음을 청취 검증 없이 정답으로 취급해서는 안 됨
- 현재 벤치마크는 규모가 작아 held-out 용어, 다양한 화자·문맥, 음향 왜곡(알람, 마스크, 원격진료 마이크, 잔향, 구급차 소음 등)을 포함한 확장이 필요

**대상 독자**: 임상 받아쓰기·원격 진료·콜센터 등 헬스케어 음성 AI를 개발하거나 도메인 특화 ASR 평가 파이프라인을 구축하려는 개발자에게 유용하다.

### [Train Models Faster with JAX and MaxText Using NVFP4 on NVIDIA Blackwell](https://developer.nvidia.com/blog/train-models-faster-with-jax-and-maxtext-using-nvfp4-on-nvidia-blackwell/)

`NVFP4` `JAX` `MaxText` `NVIDIA Blackwell` `TransformerEngine` `LLM Pretraining`

> NVFP4 4비트 정밀도로 LLM 사전학습 속도를 최대 1.73배 높이는 방법

#### 요약

- TransformerEngine의 NVFP4 학습 레시피를 JAX 기반 LLM 프레임워크 MaxText에 적용해 FP8 대비 정확도 손실 없이 4비트 혼합정밀도 사전학습을 구현
- Micro block scaling, E4M3 블록 스케일, Random Hadamard Transform, 2D weight scaling, Stochastic rounding 등 5가지 기법을 조합해 저비트 정밀도에서도 수렴 성능 유지
- NVFP4는 트랜스포머 MLP(피드포워드) 레이어의 GEMM 연산에만 적용되고, 어텐션 블록은 기존 정밀도 유지
- Llama 3 8B/Llama 3.1 405B 벤치마크에서 GB200/GB300 대비 FP8 baseline 대비 1.31~1.73배 처리량 향상 확인

#### 시사점

- 동일한 하드웨어·시간 예산으로 더 크거나 더 많은 모델을 학습시킬 수 있어 AI 팩토리의 학습 비용과 시간을 크게 절감
- MaxText 설정 플래그 하나(`quantization=te_nvfp4`)만으로 NVFP4 학습을 활성화할 수 있어 도입 장벽이 낮음
- 손실 곡선이 FP8과 거의 동일해(평균 격차 +0.026 nats) 정확도 저하 우려 없이 저정밀도 학습 도입 가능

#### 용어 설명

- **NVFP4**: NVIDIA가 설계한 4비트 부동소수점 포맷으로, 블록 단위 스케일링을 통해 정밀도 손실을 최소화한 초저비트 수치 표현 방식
- **MaxText**: JAX 기반의 대규모 LLM 학습을 위한 고성능 오픈소스 프레임워크
- **TransformerEngine**: NVIDIA가 제공하는 트랜스포머 모델의 저정밀도(FP8/FP4) 학습·추론 가속 라이브러리
- **GEMM**: General Matrix Multiplication의 약자로, 딥러닝 연산의 핵심을 이루는 행렬 곱셈 연산
- **Micro block scaling**: 텐서를 작은 블록 단위로 나눠 각각 별도의 스케일 값을 적용하는 양자화 기법
- **Random Hadamard Transform**: 이상치(outlier) 값을 고르게 분산시켜 저비트 양자화 시 오차를 줄이는 수학적 변환
- **Stochastic rounding**: 반올림 시 확률적으로 값을 조정해 작은 업데이트 값이 소실되지 않도록 하는 반올림 기법

#### 상세 내용

**NVFP4 포맷의 특징**

NVFP4는 2단계(two-level) 마이크로스케일링 구조로 다른 마이크로스케일링 포맷보다 적은 오차로 높은 신호를 인코딩한다.

- NVIDIA GB300 Grace Blackwell Ultra Superchip에서 NVFP4를 네이티브 하드웨어로 지원해 NVIDIA Hopper의 FP8 대비 7배 GEMM 처리량 제공
- 이 처리량 향상과 학습 레시피가 결합되어 정확도 손실 없이 학습 스텝 시간을 단축

**NVFP4 사전학습 레시피의 5가지 핵심 기법**

- **Micro block scaling**: 16개 원소 단위 블록 사용(MXFP4의 32개 블록의 절반 크기)으로 이상치 하나가 공유 스케일에 미치는 영향을 줄임
- **E4M3 블록 스케일 팩터**: MXFP4의 2의 거듭제곱(E8M0) 스케일링 대신 가수(mantissa) 비트를 사용, FP32 텐서 단위 스케일 아래 층으로 배치. 8B 파라미터·1T 토큰 실험에서 MXFP4는 NVFP4와 동일한 최종 손실에 도달하는 데 약 36% 더 많은 토큰 필요
- **Random Hadamard Transform**: WGRAD(가중치 그래디언트) GEMM 입력에만 적용해 이상치를 가우시안화. FPROP·DGRAD에는 적용하지 않는데, 이는 2D 스케일 일관성이 깨지기 때문
- **2D weight scaling**: 16×16 가중치 블록당 하나의 FP8 스케일을 사용해 FPROP과 그 전치(transpose)인 DGRAD가 동일한 스케일 사용. 활성화와 그래디언트는 오버헤드가 낮은 1×16 스케일링 유지
- **Stochastic rounding**: 편향 없는 반올림으로 작은 업데이트 값이 0으로 사라지지 않도록 함. 가중치·활성화는 기존 round-to-nearest-even 방식 유지(SR 적용 시 오히려 오차 증폭). 두 모드 모두 Blackwell FP4 변환 명령어에 네이티브 지원

![NVFP4 양자화 선형 레이어의 연산 흐름을 보여주는 다이어그램. 모든 GEMM 연산이 NVFP4로 양자화된 입력을 사용한다.](https://developer-blogs.nvidia.com/wp-content/uploads/2026/06/NVFP4-Flow.webp)
*이미지 출처: [원문](https://developer.nvidia.com/blog/train-models-faster-with-jax-and-maxtext-using-nvfp4-on-nvidia-blackwell/)*

세 가지 GEMM 연산(FPROP, DGRAD, WGRAD)은 트랜스포머의 MLP 레이어에만 NVFP4로 양자화되고, 어텐션 블록의 GEMM(QKV 프로젝션, 출력 프로젝션, score/context 행렬곱)은 높은 정밀도를 유지한다.

- 어텐션의 소프트맥스는 QK^T 스코어의 양자화 노이즈를 지수적으로 증폭시키고, 어텐션 활성화 값에는 4비트로 표현하기 어려운 집중된 이상치가 존재하기 때문
- MLP가 학습 FLOPs의 대부분을 차지하므로, MLP에만 적용해도 수렴 위험 없이 대부분의 속도 향상 확보

세 MLP GEMM은 모두 NVFP4 입력을 받아 BF16 출력을 내고, 이는 옵티마이저 스텝에서 FP32 마스터 가중치로 통합된다.

**MaxText에서 NVFP4 활성화하기**

MaxText NVFP4 레시피는 JAX-Toolbox GitHub 저장소에서 제공되며, 런치 스크립트는 Blackwell에서 Llama 3 8B를 NVFP4로 학습시킨다.

- `quantization=te_nvfp4`: Random Hadamard Transform이 포함된 NVFP4. `te_nvfp4_no_rht`에서 수렴 품질이 부족할 때 권장
- `quantization=te_nvfp4_no_rht`: RHT 없는 NVFP4. 오버헤드가 가장 낮지만 수렴 품질이 떨어질 수 있음
- 공개 컨테이너 `ghcr.io/nvidia/jax:maxtext`를 사용해 JAX, NVIDIA Transformer Engine, CUDA/cuDNN이 설치된 환경에서 예제 스크립트 실행
- 실행 후 MaxText는 스텝 시간, TFLOP/s/device, tokens/s/device를 출력하고 NVIDIA Nsight Systems 트레이스를 생성

**성능 결과**

MaxText로 Llama 3 8B를 FSDP=4, 시퀀스 길이 8,192, 디바이스당 배치 크기 4, 50 스텝 조건에서 벤치마크했다.

### [NVIDIA Nemotron 3 Ultra Powers Faster, More Efficient Reasoning for Long-Running Agents](https://developer.nvidia.com/blog/nvidia-nemotron-3-ultra-powers-faster-more-efficient-reasoning-for-long-running-agents/)

`Nemotron 3 Ultra` `Mixture-of-Experts` `NVFP4` `Multi-Teacher On-Policy Distillation` `Agentic AI` `NemoClaw`

> 오픈 모델 Nemotron 3 Ultra로 장시간 실행되는 AI 에이전트를 더 빠르고 저렴하게

- 콘텐츠 안전 모델 Nemotron 3.5 Content Safety, 다국어 음성인식 모델 Nemotron 3.5 ASR도 함께 공개, 라이선스는 OpenMDW-1.1로 전환

#### 시사점

- 프런티어급 추론 모델을 오케스트레이터로, 경량 모델을 실행용으로 쓰는 '모델 시스템' 설계 시 Nemotron 3 Ultra를 오케스트레이션 계층으로 활용할 수 있음
- 동일 NVFP4 체크포인트가 Hopper·Blackwell·Ampere GPU에서 모두 구동되어, 하드웨어별 재양자화 없이 배포 유연성을 확보
- 가중치·학습 데이터·레시피가 모두 공개되어 있어 기업이 도메인 특화 파인튜닝(LoRA, SFT, RL)을 통해 자체 워크플로우에 맞게 조정 가능

#### 용어 설명

- **Mixture-of-Experts (MoE)**: 전체 파라미터 중 일부(전문가)만 선택적으로 활성화해 연산 효율을 높이는 모델 구조
- **NVFP4**: NVIDIA의 4비트 부동소수점 양자화 포맷으로 메모리와 연산량을 줄이면서 정확도를 유지하는 기술
- **Multi-Token Prediction (MTP)**: 한 번의 순전파(forward pass)로 여러 미래 토큰을 동시에 예측해 생성 속도를 높이는 기법
- **Multi-Teacher On-Policy Distillation (MOPD)**: 여러 전문 교사 모델로부터 동시에 학습하며 스스로 생성한 시도에 대해 보상을 받는 증류(distillation) 학습 방식
- **하이브리드 Mamba-Transformer**: 긴 시퀀스 처리에 효율적인 Mamba 레이어와 정확한 정보 검색에 강한 Transformer 레이어를 결합한 구조
- **RL 환경(RL Environment)**: 강화학습(reinforcement learning) 시 모델이 시행착오를 통해 학습하도록 구성된 작업 시뮬레이션 공간

#### 상세 내용

**에이전트 오케스트레이션을 위한 Nemotron 3 Ultra**

멀티 에이전트 워크플로우는 계획 수립, 도구 호출, 서브 에이전트 위임 등이 반복되며 토큰 사용량이 급증하는 문제가 있다. Nemotron 3 Ultra는 이런 워크플로우에서 소수지만 중요한 '고난도 호출'(예: 코딩 세션 전반의 아키텍처 결정 유지, 수백 개 리서치 소스 간 모순된 근거 종합, 수천 개 제약 조건에 걸친 칩 설계 검증)을 처리하도록 설계됐다.

- GLM 5.1(744B), Kimi K2.6(1T) 등 더 큰 모델과 비교해도 Agent Productivity PinchBench 91%, Instruction Following IFBench 82%, Long Context Ruler @1M 95% 등에서 경쟁력 있는 성능을 보임

**Nemotron 3 Ultra를 뒷받침하는 아키텍처 혁신**

효율성과 정확도 간 상충을 줄이기 위해 다음과 같은 기술이 적용됐다.

- **에이전트 하네스 전용 사후학습**: NVIDIA NeMo RL과 Gym 라이브러리로 대규모 장기 작업·도구 사용 데이터셋을 사용해 학습, 단순 단일턴 채팅이 아닌 계획·도구 호출·서브 에이전트 위임·오류 복구 등 실제 에이전트 워크플로우에 최적화
- **하이브리드 Mamba-Transformer**: Mamba 레이어로 긴 컨텍스트 처리 효율을 높이고, Transformer 레이어로 대형 컨텍스트 내 특정 사실 검색 정확도 유지
- **NVFP4 정밀도**: 동일 체크포인트가 Hopper·Blackwell·Ampere GPU에서 모두 구동되며, Blackwell에서 BF16 대비 동일 인터랙티비티에서 최대 5배 높은 GPU당 처리량 달성
- **LatentMoE**: 추론·코드 생성·도구 호출·도메인 특화 로직에 걸친 워크플로우 처리를 위한 효율적인 전문가 라우팅 지원
- **멀티토큰 예측(MTP)**: 한 번의 순전파로 여러 미래 토큰을 예측해 긴 출력 및 멀티턴 워크플로우의 처리량 개선

**Multi-Teacher On-Policy Distillation(MOPD) 도입**

MOPD는 Ultra가 학습 중 자신의 시도를 생성하면서 동시에 10개 이상의 도메인 특화 교사 모델로부터 학습하는 방식이다. 각 교사는 자신의 전문 영역에서 모델을 평가해 도메인별 추론 능력을 효율적으로 향상시킨다.

- 학생 모델의 롤아웃 생성, 교사 채점, 학생 최적화가 완전히 파이프라인화되어 비동기로 실행돼 효율 극대화

### [Build Personal AI Agents on Windows PCs with New Tools from Microsoft and NVIDIA](https://developer.nvidia.com/blog/build-personal-ai-agents-on-windows-pcs-with-new-tools-from-microsoft-and-nvidia/)

`Windows AI` `NVIDIA RTX` `llama.cpp` `vLLM` `AI Agent` `ComfyUI`

> MS·NVIDIA가 온디바이스 AI 에이전트용 보안·추론 가속 도구를 대거 공개

#### 요약

- Microsoft eXecution Containers(MXC)와 NVIDIA OpenShell로 Windows에서 에이전트를 안전하게 샌드박싱하는 보안 계층 발표
- NVIDIA RTX Spark 제품군, NemoClaw, Hermes Agent, H Company의 Holo 3.1 등 온디바이스 에이전트 실행·구축 도구 확대
- llama.cpp·vLLM에 MTP(Multi-Token Prediction), PDL(Programmatic Dependent Launch) 등을 적용해 최대 2.6배 추론 속도 향상
- llama.cpp와 ComfyUI에 멀티 GPU(텐서 병렬, CFG) 지원을 추가해 RTX PC에서 더 큰 모델을 더 빠르게 구동 가능

#### 시사점

- 프롬프트 인젝션 등 보안 위험이 있는 자율 에이전트를 로컬 파일·앱 접근을 제한하며 안전하게 상시 구동할 수 있는 표준 프레임워크가 생김
- 별도 재학습 없이 기존 모델에 적용 가능한 추론 최적화(MTP 등)로 로컬 LLM 서빙 성능을 손쉽게 끌어올릴 수 있음
- 단일 GPU 메모리 한계를 넘어 두 장의 GPU로 더 큰 모델을 돌리는 경로가 PC 프레임워크(llama.cpp, ComfyUI)에도 열려, 소비자용 하드웨어에서 데이터센터급 활용이 가능해짐

#### 용어 설명

- **MXC(Microsoft eXecution Containers)**: 에이전트의 파일·시스템 접근을 격리·제어하는 Windows 보안 정책 계층
- **OpenShell**: NVIDIA가 만든 에이전트 실행 런타임으로, MXC 기반의 정책 관리·PII(개인식별정보) 마스킹 등을 제공
- **MoE(Mixture-of-Experts)**: 입력마다 일부 전문가(서브 네트워크)만 활성화해 계산량을 줄이는 모델 구조
- **MTP(Multi-Token Prediction)**: 작은 드래프트 모델이 여러 토큰을 미리 제안하고 본 모델이 한 번에 검증해 속도를 높이는 추측 디코딩 기법
- **PDL(Programmatic Dependent Launch)**: 같은 CUDA 스트림 내 의존 커널을 동시 실행해 디코딩 속도를 높이는 기법
- **텐서 병렬(Tensor Parallelism, TP)**: 모델 연산을 여러 GPU에 분산해 메모리와 연산 성능을 함께 늘리는 방식
- **CFG(Classifier-Free Guidance)**: 이미지 생성 모델에서 조건부·비조건부 예측을 함께 계산해 결과 품질을 조정하는 기법
- **WSL-C(Windows Subsystem for Linux Containers)**: Windows 네이티브 앱에서 Linux AI 컨테이너를 직접 생성·실행할 수 있게 하는 내장 기능

#### 상세 내용

**Microsoft eXecution Containers와 NVIDIA OpenShell로 로컬 에이전트 보안 강화**

Microsoft Build에서 발표된 MXC는 에이전트가 코드 실행, 파일 조작, 시스템 간 작업 오케스트레이션을 할 때 ID·정책 기반으로 격리·통제하는 정책 계층이다. Windows OS의 네이티브 구성 요소를 활용해 이 정책을 적용한다.

- 에이전트의 프롬프트 인젝션 위험을 줄이기 위해 시스템 전체 접근을 차단
- NVIDIA OpenShell 런타임이 MXC를 기반으로 Windows에 통합되며, 정책 생성·관리, 추론 라우팅, PII(개인식별정보) 난독화 기능 제공
- 오픈소스 에이전트 OpenClaw, Hermes Agent 등이 MXC·OpenShell 도입을 추진 중

### [Deploy Self-Evolving Agents for Faster, More Secure Research with a Hermes Agent and NVIDIA NemoClaw](https://developer.nvidia.com/blog/deploy-self-evolving-agents-for-faster-more-secure-research-with-a-hermes-agent-and-nvidia-nemoclaw/)

`NemoClaw` `Hermes Agent` `OpenShell` `AI Agent` `NVIDIA Nemotron` `Agentic AI`

> Slack·Outlook·GitHub 데이터를 안전하게 다루며 스스로 학습하는 에이전트 구축법

#### 요약

- Hermes Agent와 NVIDIA NemoClaw를 이용해 Slack, Outlook, GitHub 등 내부·공개 데이터를 함께 다루는 자기진화형(self-evolving) 리서치 에이전트를 오픈소스로 공개.
- NVIDIA OpenShell이 보안 승인된 런타임(샌드박스)을 강제해, 에이전트가 민감한 내부 데이터를 다루면서도 자격증명 노출이나 외부 유출을 막음.
- 대화 중 사용자가 원하는 포맷을 알려주면 에이전트가 SKILL.md 파일로 스킬을 스스로 작성해 저장하고, 이후 재배포되어도 스냅샷/복원을 통해 학습된 상태가 유지됨.
- 모델(Nemotron)·하네스(Hermes Agent)·런타임(OpenShell) 3계층 구조로 동작하며, ATIF 트레이스와 Arize Phoenix로 관찰 가능성(observability)을 확보.

#### 시사점

- 사내 채팅·메일·코드 저장소 등 여러 소스를 섞어 쓰는 리서치·고객지원·경쟁분석 같은 업무에 안전하게 AI 에이전트를 적용할 수 있는 패턴을 제공.
- 코드 수정이나 게이트웨이 재시작 없이 대화만으로 에이전트에게 새로운 업무 포맷을 가르치고 영구히 기억시킬 수 있음.
- 네트워크 정책을 YAML 코드로 명시해 에이전트의 접근 범위를 통제하므로, 손상된 에이전트라도 데이터를 외부로 유출할 수 없는 구조.

#### 용어 설명

- **NemoClaw**: 오픈 모델과 보안 런타임을 결합해 오픈 에이전트를 만드는 NVIDIA의 블루프린트.
- **Hermes Agent**: 스킬·세션·메모리·브리지·훅 기능을 제공하는 에이전트 하네스(실행 프레임워크).
- **NVIDIA OpenShell**: 파일시스템/네트워크 정책 강제, 자격증명 브로커링을 담당하는 샌드박스 런타임.
- **SKILL.md**: 에이전트가 학습한 응답 포맷·절차를 저장하는 파일로, YAML 프런트매터와 본문으로 구성.
- **ATIF (Agent Trajectory Format)**: 에이전트의 의사결정 과정(툴 호출, 인자 등)을 기록하는 트레이스 포맷.
- **NeMo Relay**: 샌드박스 이미지에 기본 포함되어 ATIF 트레이스를 수집하는 도구.
- **Arize Phoenix**: 트레이스를 실시간 스트리밍해 인터랙티브하게 디버깅할 수 있는 관찰 도구.

#### 상세 내용

**Hermes 설치 및 구동**

리포지토리를 클론하고 `install.sh`로 OpenShell을 설치한 뒤, `.env`에 추론 API 키와 최소 1개의 메시징 채널(Outlook 또는 Slack) 정보를 입력한다.

- `scripts/00-host-services.sh`로 호스트 서비스를 띄우고, `scripts/bring-up.sh`로 샌드박스 안에서 Hermes를 실행.
- OpenShell 샌드박스는 두 가지 핵심 역할을 수행: (1) 자격증명 관리 — Hermes는 Slack/Outlook 토큰을 절대 직접 보지 않고, 인증은 요청이 샌드박스 프록시를 빠져나갈 때 이루어짐. (2) 네트워크 접근 정책 강제 — 민감한 내부 데이터를 다루는 에이전트는 공개 인터넷 접근이 차단됨.
- GitHub·NVIDIA 포럼 데이터는 별도 ETL(추출·변환·적재) 프로세스로 가져와 읽기 전용으로 제공, 손상된 에이전트라도 외부로 데이터를 게시할 수 없음.
- `openshell sandbox list`와 `curl .../health`로 상태를 확인할 수 있음.

**한 번 가르치면 어디서든 재현**

사용자가 채팅으로 "GitHub 이슈 5개, 논의 3개, 번호/제목/상태/URL/한줄 요약 포함" 같은 포맷을 요청하고 만족하면, "이 포맷을 앞으로도 써 달라"고 긍정 강화 트리거를 주면 된다.

- Hermes는 패턴을 인식해 파일시스템에 `SKILL.md`(YAML 프런트매터 + 포맷 본문)를 자동 작성.
- 운영 환경에서는 코드 배포나 설정 변경 시 에이전트가 재구축되는데, `snapshot.sh`(스냅샷 저장) → `tear-down.sh`(샌드박스 파괴) → `bring-up.sh`(이미지에서 재구축) → `restore.sh`(데이터 복원) 순서로 학습된 스킬·메모리·세션·예약 작업을 그대로 유지할 수 있음.
- 스냅샷은 `.env`, `*token*`, `*secret*` 같은 파일을 자동 제외해 안전하게 공유 가능.
- 새 대화에서 같은 요청을 하면 스킬에 저장된 포맷이 그대로 재현되고, 숫자·제목 등 데이터만 바뀜 — 포맷은 대화 메모리가 아니라 스킬 파일에 저장되기 때문.

**아키텍처: 모델, 하네스, 런타임**

| Harness | 스킬, 세션, 메모리, 브리지, 훅 | Hermes Agent |
| Runtime | 파일시스템/네트워크 정책, 프로바이더 주입, 자격증명 브로커링 | NVIDIA OpenShell |

- 네트워크 정책은 프롬프트가 아니라 코드(`policy.yaml`)로 명시되며, 허용된 목적지·포트·HTTP 메서드·바이너리를 선언.
- 예: `integrate.api.nvidia.com`에 대해 `/v1/chat/completions`, `/v1/embeddings`, `/v1/models` 경로만 허용.

**관찰 가능성: NeMo Relay와 Arize Phoenix**

에이전트는 매 턴마다 어떤 스킬을 호출할지, 어떤 툴에 어떤 인자를 넘길지 등 많은 결정을 내리므로, 문제 발생 시 실제 동작을 볼 수 있어야 한다.

- 샌드박스 이미지에 기본 포함된 NeMo Relay가 ATIF 형식 트레이스를 별도 설정 없이 기록.
- `scripts/download-traces.sh`로 샌드박스 파괴 전 트레이스를 추출 가능.
- `.env`에 `PHOENIX_COLLECTOR_ENDPOINT`를 설정하면 Phoenix 수집기로 실시간 스트리밍하여 인터랙티브 디버깅 가능.

**다양한 사용 사례로 확장**

예제는 배포 전에도 커스터마이즈 가능하며, `agents/hermes/skills/` 폴더의 스킬 5종이 게이트웨이에 자동 인식된다.

- OpenShell 정책을 수정해 다른 데이터 소스나 툴에 대한 접근을 부여 가능.
- Claude Code, Codex, Hermes Skills Hub에 내장된 NVIDIA 검증 스킬을 활용하거나, skills.sh 카탈로그를 통해 Cursor, Gemini CLI, GitHub Copilot, Windsurf 등에서도 사용 가능.

**대상 독자**: 사내 데이터(Slack, Outlook, GitHub 등)와 공개 데이터를 함께 다루는 리서치·고객지원·엔지니어링 트리아지 자동화를 안전하게 구현하려는 개발자에게 유용하다.

### [Deploy Agentic-Ready AI at the Edge with Memory Efficiency in NVIDIA JetPack 7.2](https://developer.nvidia.com/blog/deploy-agentic-ready-ai-at-the-edge-with-memory-efficiency-in-nvidia-jetpack-7-2/)

`NVIDIA Jetson` `JetPack` `Edge AI` `AI Agent` `Multi-Instance GPU (MIG)` `Robotics`

> JetPack 7.2로 젯슨에서 에이전트형 AI를 메모리 효율적으로 배포

#### 요약

- JetPack 7.2는 NemoClaw 원커맨드 배포, Jetson 전용 에이전트 스킬, Jetson Thor용 MIG 지원, 공식 Yocto Project 지원, Jetson AGX Orin 32GB Super Mode를 새로 제공한다.
- Orin과 Thor 플랫폼을 Ubuntu 24.04·커널 6.8·CUDA Toolkit 13.0 기반의 단일 통합 소프트웨어 스택으로 묶었다.
- MIG는 Jetson Thor의 Blackwell GPU를 두 개의 독립 파티션(12 SM/1536 코어, 8 SM/1024 코어)으로 나눠 혼재된 워크로드의 결정적 실행을 지원한다.
- Super Mode는 Jetson AGX Orin 32GB의 GPU 주파수를 930MHz→1.3GHz, 전력을 최대 60W로 높여 성능을 200 TOPS에서 241 TOPS로 20% 이상 끌어올린다.

#### 시사점

- 기존 Jetson 하드웨어를 교체하지 않고도 소프트웨어 업데이트만으로 더 높은 성능과 새로운 기능(에이전트 워크플로우, GPU 파티셔닝)을 얻을 수 있다.
- Jetson 에이전트 스킬을 활용하면 BSP 커스터마이징, 메모리 최적화, 모델 벤치마킹 같은 반복 작업을 AI 에이전트가 자동화해 개발 기간을 단축할 수 있다.
- 로보틱스·산업자동화 등에서 지연시간 민감 워크로드와 범용 추론 워크로드를 하나의 SoC에서 안전하게 격리 실행해야 하는 개발자에게 MIG가 실질적 해법이 된다.

#### 용어 설명

- **NVIDIA Jetson**: 로봇·엣지 디바이스용 NVIDIA의 임베디드 AI 컴퓨팅 모듈 및 개발 플랫폼.
- **JetPack**: Jetson용 OS·라이브러리·툴체인을 묶은 NVIDIA의 소프트웨어 개발 키트(SDK).
- **NemoClaw**: OpenClaw에 프라이버시·보안 제어를 더한 오픈소스 에이전트 스택.
- **Multi-Instance GPU (MIG)**: 하나의 GPU를 컴퓨트·캐시·메모리 대역폭이 독립된 여러 인스턴스로 분할하는 기술.
- **BSP (Board Support Package)**: 특정 하드웨어에서 OS가 동작하도록 하는 저수준 드라이버·설정 묶음.
- **Yocto Project**: 임베디드 하드웨어용 맞춤형 리눅스 배포판을 만들 수 있게 해주는 오픈소스 Linux Foundation 프로젝트.
- **TOPS (Tera Operations Per Second)**: AI 가속기의 초당 연산 처리량을 나타내는 성능 지표.

#### 상세 내용

**에이전트 준비가 된 JetPack 7.2 소프트웨어**

JetPack 7.2는 NemoClaw 실행에 필요한 의존성과 스택을 사전 구성해, 별도 환경 설정 없이 로보틱스·산업 자동화·비전 에이전트·엣지 AI 애플리케이션을 바로 구축할 수 있게 한다.

- 설치는 `curl -fsSL https://www.nvidia.com/nemoclaw.sh | bash` 한 줄로 끝난다.

**Jetson 전용 에이전트 스킬**

에이전트 스킬은 어떤 도구를 호출하고, 어떤 결과를 만들고, 어떻게 검증할지를 정의한 반복 실행 가능한 지침 세트로, 개발자가 각 단계를 수작업으로 설정하지 않아도 에이전트가 자동 처리하게 해준다. 디바이스 측과 BSP 측 스킬로 나뉘어 제공된다.

- **Jetson Linux 커스터마이징 스킬**: 커스텀 캐리어보드용 BSP를 처음부터 구성(I/O, 클록, 팬 제어, 전력 프로파일 등). 이전에 수 주 걸리던 작업을 에이전트가 처리할 수 있다.
- **메모리 최적화 스킬**: 부트로더 메모리 carveout, 커널 메모리 예약, 중복 사용자 공간 프로세스 등을 조정해 가장 메모리 효율적인 스택을 구성, TCO(총소유비용)를 낮춘다.
- **모델 벤치마킹 스킬**: 모델 벤치마킹·추론 최적화·Jetson 진단을 지원해 특정 디바이스·태스크에 가장 효율적인 모델 구성을 찾도록 돕는다.
- 이 외에 NVIDIA DeepStream과 NVIDIA Metropolis Blueprint for Video Search and Summarization(VSS)을 활용한 비전 파이프라인 구축 스킬도 함께 제공된다.

### [Run Local AI Agents with Faster Models and Multi-Node Clustering on NVIDIA DGX Spark](https://developer.nvidia.com/blog/run-local-ai-agents-with-faster-models-and-multi-node-clustering-on-nvidia-dgx-spark/)

`DGX Spark` `NemoClaw` `OpenClaw` `Qwen3.6` `vLLM` `NVIDIA Sync`

#### 요약

- NVIDIA는 Computex 2026에서 DGX Spark에 로컬 AI 에이전트를 손쉽게 설치·실행할 수 있는 NemoClaw 설치 경로를 공개했다.
- Qwen3.6-35B 모델을 vLLM에서 NVFP4 양자화와 MTP 최적화로 구동해 최대 2.6배 빠른 추론 성능을 제공한다.
- NVIDIA Sync의 클러스터 어시스턴트를 통해 DGX Spark 2~4대를 고대역폭으로 연결해 최대 512GB 통합 메모리를 확보할 수 있다.
- 설치부터 첫 에이전트 실행까지의 과정을 단순화해 로컬 에이전트 구축의 진입 장벽을 낮췄다.

#### 시사점

- 클라우드 의존 없이 온디바이스에서 민감한 컨텍스트를 유지하며 에이전트를 실행할 수 있어 보안·개인정보 요구가 중요한 개발 환경에 유리하다.
- 토큰당 비용 없이 로컬에서 대형 MoE 모델, 다중 에이전트 파이프라인, 파인튜닝까지 시도해볼 수 있다.
- 단일 명령어 설치와 샌드박스 관리 CLI로 실험적인 에이전트 프로토타이핑 속도가 크게 빨라진다.

#### 용어 설명

- **DGX Spark**: NVIDIA의 로컬 AI 개발용 소형 워크스테이션 하드웨어.
- **NemoClaw**: 오픈 모델, 에이전트 하네스, OpenShell 런타임을 하나로 묶은 오픈소스 블루프린트(설치 패키지).
- **OpenShell**: 자율 에이전트를 안전하게 실행하기 위한 샌드박스(격리) 실행 환경.
- **MTP (Multi-Token Prediction)**: 한 번에 여러 토큰을 예측해 추론 속도를 높이는 최적화 기법.
- **NVFP4**: NVIDIA의 4비트 부동소수점 양자화 포맷으로, 모델 크기와 연산량을 줄여 추론을 가속.
- **ConnectX-7**: 노드 간 200Gbps급 고속 네트워킹을 지원하는 NVIDIA 네트워크 카드(NIC).
- **RoCE (RDMA over Converged Ethernet)**: 이더넷 위에서 낮은 지연으로 원격 메모리 접근을 가능하게 하는 네트워크 프로토콜.

#### 상세 내용

**언박싱부터 로컬 에이전트 실행까지**

- 2026년 6월 DGX Spark 시스템 소프트웨어부터는 초기 설정 시 OTA(무선) 업데이트를 기본 설치하지 않아 Ubuntu 데스크톱까지 도달하는 시간이 단축됐다.
- NemoClaw는 오픈 모델, Hermes Agent나 OpenClaw 같은 에이전트 하네스, OpenShell 런타임을 한 번에 설치하는 블루프린트다.
- OpenShell은 접근 제어, 개인정보 보호, 운영 가드레일을 에이전트 루프에 추가해 온디바이스 추론과 결합된 기본 보안 태세를 제공한다.

### [How to Post-Train Autonomous Vehicle Models in Closed-Loop with NVIDIA Alpamayo](https://developer.nvidia.com/blog/how-to-post-train-autonomous-vehicle-models-in-closed-loop-with-nvidia-alpamayo/)

`NVIDIA Alpamayo` `AlpaGym` `AlpaSim` `Reinforcement Learning` `Autonomous Vehicles` `Cosmos-RL`

> AlpaGym으로 자율주행 모델을 시뮬레이션 폐루프에서 강화학습 후처리 훈련

#### 요약

- 자율주행(AV) VLA 모델은 보통 정답 궤적과 직접 비교하는 개루프(open-loop)로 학습되지만, 실제 주행은 매 판단이 환경에 영향을 미치는 폐루프(closed-loop)라 오차가 누적되는 문제가 있다.
- NVIDIA Alpamayo의 구성 요소인 AlpaSim(시뮬레이션 플랫폼)과 AlpaGym(폐루프 훈련 프레임워크)이 시뮬레이터 롤아웃을 실제 훈련 경험으로 연결한다.
- AlpaGym은 AlpaSim 마이크로서비스, NVIDIA Physical AI Open Datasets, 분산 Cosmos-RL 훈련 프레임워크를 결합해 단일 GPU부터 멀티노드 GPU 클러스터까지 확장 가능한 비동기 분산 RL 파이프라인을 제공하며 기본 알고리즘으로 GRPO를 사용한다.
- 설치→보상 함수 정의→훈련 실행→체크포인트 추출의 4단계 워크플로가 제시되며, Alpamayo 1.5(10B 파라미터) 모델을 예시로 사용한다.

#### 시사점

- AV 모델 개발자가 정적 데이터셋만으로는 드러나지 않는 실패 모드(충돌, 오프로드 등)를 시뮬레이션 폐루프에서 직접 발견하고 보정할 수 있다.
- Hydra 설정 기반으로 보상 함수, 시뮬레이션 시나리오, 훈련 파라미터를 유연하게 정의할 수 있어 자체 AV 모델과 보상 설계에 맞춰 확장 가능하다.
- 오픈소스로 공개되어 있어(NVlabs/alpagym) 훈련-배포 간 성능 격차를 줄이는 재현 가능한 워크플로를 직접 구축할 수 있다.

#### 용어 설명

- **VLA (Vision-Language-Action) 모델**: 시각·언어 정보를 바탕으로 주행 행동을 추론·생성하는 모델.
- **개루프(open-loop) / 폐루프(closed-loop)**: 개루프는 모델 출력을 정답과 단순 비교하는 방식, 폐루프는 모델의 행동이 실제로 환경(다음 상태)에 영향을 미치는 방식.
- **AlpaSim**: NVIDIA Alpamayo의 AV 시뮬레이션 플랫폼.
- **AlpaGym**: 시뮬레이션 롤아웃을 훈련 데이터로 연결하는 폐루프 강화학습 훈련 프레임워크.
- **GRPO**: AlpaGym에서 기본으로 사용하는 강화학습 알고리즘.
- **Cosmos-RL**: 분산 훈련을 담당하는 NVIDIA의 RL 훈련 프레임워크.
- **NuRec 데이터셋**: 보상 함수 테스트 및 시나리오 소스로 쓰이는 NVIDIA Physical AI AV 데이터셋.

#### 상세 내용

**왜 폐루프 훈련이 필요한가**

기존 VLA 모델은 로그된 전문가 궤적과의 비교(개루프)로 학습되지만, 실제 배포 시에는 매 제동·조향·경로 결정이 다음 환경 상태에 영향을 준다. AlpaGym은 이 훈련-배포 간 간극을 줄이기 위해 시뮬레이션을 단순 최종 평가 단계가 아니라 훈련 루프에 직접 연결한다.

![Workflow diagram showing a driving model (such as Alpamayo) undergoing reinforcement learning post-training in AlpaGym, including Data Collection, Closed-Loop Simulation, Driving Model, Policy Training and Orchestration.](https://developer-blogs.nvidia.com/wp-content/uploads/2026/05/end-to-end-workflow-post-train-av-model-nvidia-alpamayo-alpagym.webp)

**AlpaGym의 구조**

AlpaGym은 AlpaSim과 Cosmos RL을 런타임/오케스트레이션 계층으로 통합하고, 사용자 코드 변경 없이 단일 GPU에서 멀티노드까지 비동기적이고 안정적인 분산 RL 파이프라인을 지원한다. Alpamayo 모델 및 Physical AI AV NuRec 데이터셋에 검증된 참조 보상 함수도 함께 제공된다.

![Perspective grid of driving-scene clips showing many AlpaSim closed-loop rollout instances running in parallel across different road scenarios for AlpaGym reinforcement learning.](https://developer-blogs.nvidia.com/wp-content/uploads/2026/05/grid-car-street-videos.gif)
*이미지 출처: [원문](https://developer.nvidia.com/blog/how-to-post-train-autonomous-vehicle-models-in-closed-loop-with-nvidia-alpamayo/)*

**1단계: 설치 및 설정**

- 권장 사양: VRAM 40GB 이상 CUDA GPU, 약 100~150GB 여유 디스크(환경+컨테이너 이미지+약 21GB 가중치), NuRec 씬당 약 1.5GB(public_2601 전체 스위트는 약 1.5TB).
- `uv`로 파이썬 환경을 관리하고, cuDNN·NCCL·redis-server는 호스트 의존성으로 별도 설치.
- 게이트된 NuRec 데이터셋 접근을 위해 Hugging Face 인증이 필요.
- AlpaGym 실행은 Hydra 설정 하나로 정책 체크포인트, AlpaSim 씬 세트, 롤아웃 병렬도, 보상 함수, Cosmos-RL 훈련 파라미터를 지정한다.

**2단계: 폐루프 보상 정의**

- 궤적 품질 개선을 위한 대표적 보상 항목: 진행도(progress), 차선 유지, 충돌 회피, 오프로드율, 승차감, 참조 궤적과의 거리.
- 실전 첫 보상 예시는 progress(+1.0), collision_any(-10.0), offroad(-5.0), distance_to_gt(-0.01)의 단순 합으로 구성.
- 파이프라인이 안정화되면 AlpaSim 영상·지표에서 관찰된 실패 모드에 맞춰 세분화된 보상 항목을 추가할 수 있다.

**3단계: 폐루프 훈련 실행**

- AlpaGym은 현재 Alpamayo 1.5(10B 파라미터) 모델을 지원하며, 자체 AV 모델 적용 방법은 NVlabs/alpagym GitHub 저장소에 안내되어 있다.
- Alpamayo 1.5 체크포인트를 다운로드해 AlpaGym 호환 체크포인트로 변환한 뒤 훈련을 시작한다.
- 2x 50GB RTX 6000 Ada 환경에서 테스트되었으며, 10B 모델은 GPU 1개에 들어가지 않는다(단일 GPU용 경량화 스크립트는 계획 중).
- 훈련 중 AlpaSim에 씬 롤아웃을 요청하고, 에피소드별 아티팩트를 수집해 보상을 계산하고 정책을 업데이트한다. 평균 보상, 보상 분산, 실패율, 정책 손실, 롤아웃 처리량 등이 주요 신호이며 결과는 tmp/alpagym-runs/, outputs/ 경로에 저장된다.

**4단계: 후처리 체크포인트 추출**

- 훈련 후 생성된 Cosmos-RL safetensors 내보내기는 추론 포맷으로 변환해야 AlpaSim 드라이버가 로드할 수 있다.
- 변환된 체크포인트를 대표 시나리오에서 실행해 정책·드라이버·시뮬레이션 루프가 올바르게 연결됐는지 검증하며, 이 평가에는 게이트된 nvidia/Cosmos-Reason2-8B VLM 접근이 필요하다.
- 폐루프 롤아웃을 통해 모델이 안정적인 궤적을 생성하는지, 주행 가능 영역 내에 머무는지, 주변 교통 참여자에 어떻게 반응하는지 등을 정성적으로 확인할 수 있다.
- 이렇게 수집된 롤아웃 영상, 에피소드별 지표, 보상 추이, 실패 사례는 보상 설계 디버깅과 후속 평가용 체크포인트 선정에 활용된다.

**대상 독자**: 자율주행 정책을 시뮬레이션 기반으로 반복 개선하려는 AV/로보틱스 개발자, 강화학습 기반 폐루프 훈련 파이프라인을 직접 구축하려는 ML 엔지니어에게 유용하다.

### [Develop Physical AI Reasoning, World, and Action Models with NVIDIA Cosmos 3](https://developer.nvidia.com/blog/develop-physical-ai-reasoning-world-and-action-models-with-nvidia-cosmos-3/)

`NVIDIA Cosmos 3` `Physical AI` `World Model` `Vision-Language Model` `NVIDIA NIM` `Robotics`

> 물리 AI를 위한 오픈소스 파운데이션 모델 Cosmos 3 공개

#### 요약

- Cosmos 3는 물리적 추론(reasoning), 월드 생성(world generation), 액션 생성(action generation)을 하나의 오픈 모델로 통합한 physical AI 파운데이션 모델이다.
- Mixture-of-Transformers(MoT) 아키텍처를 기반으로 Reasoner tower(자기회귀 VLM)와 Generator tower(디퓨전 기반)라는 두 개의 타워로 구성된다.
- 16B 파라미터의 Nano와 64B 파라미터의 Super 두 가지 크기로 제공되며, 체크포인트·학습 스크립트·데이터셋·NIM 마이크로서비스가 모두 오픈소스로 공개됐다.
- 새로운 HUE(Human Evaluation) 벤치마크로 평가했으며, PAI-Bench·R-Bench Physics-IQ·RoboLab 등 여러 벤치마크에서 오픈소스 SOTA(state-of-the-art)를 기록했다.

#### 시사점

- 로보틱스, 자율주행, 창고 모니터링 등 물리 AI 애플리케이션 개발자가 여러 모델을 조합하지 않고 단일 모델로 추론과 생성을 모두 처리할 수 있다.
- 오픈 데이터셋과 SFT·액션 post-training 레시피가 제공되어 자체 도메인·임베디먼트(로봇 형태)에 맞춘 커스터마이징이 가능하다.
- NIM 마이크로서비스와 FP8/NVFP4 양자화, vLLM 기반 서빙을 지원해 별도 인프라 튜닝 없이 실서비스 배포와 추론 최적화가 쉬워진다.

#### 용어 설명

- **Physical AI**: 로봇, 자율주행차, 스마트 공간처럼 물리적 현실 세계를 인식하고 그 안에서 행동하는 AI 시스템.
- **VLM (Vision-Language Model)**: 이미지·영상과 텍스트를 함께 입력받아 이해하는 모델.
- **Mixture-of-Transformers (MoT)**: 서로 다른 역할을 하는 트랜스포머 모듈들을 하나의 모델 안에서 결합하는 아키텍처.
- **디퓨전(diffusion) 모델**: 노이즈에서 점진적으로 실제 데이터(영상 등)를 생성해내는 생성 모델 기법.
- **NIM (NVIDIA Inference Microservices)**: NVIDIA가 제공하는 최적화된 추론 런타임 포함 모델 배포용 마이크로서비스.
- **양자화(Quantization)**: 모델 연산의 수치 정밀도를 낮춰 속도와 메모리 효율을 높이는 기법(예: BF16 → FP8/NVFP4).
- **vLLM**: 연속 배칭, 페이지드 어텐션 등을 활용해 LLM을 효율적으로 서빙하는 오픈소스 추론 엔진.

#### 상세 내용

**Cosmos 3의 새로운 점**

기존 Cosmos 모델들은 월드 생성, 물리 이해, 제어된 장면 생성을 각각 다른 모델과 워크플로로 분리해서 처리했다. Cosmos 3는 이를 하나의 MoT 아키텍처로 통합했다.

- Reasoner tower: 이미지·영상·텍스트 등 멀티모달 입력을 자기회귀(autoregressive) 방식으로 해석하고 움직임·객체 상호작용 등 물리적 맥락을 이해하는 '두뇌' 역할.
- Generator tower: Reasoner tower의 이해를 바탕으로 디퓨전 기반 방식으로 물리적으로 타당한 영상·액션을 생성. 단독 호출도 가능한 Reasoner와 달리 Generator는 항상 두 타워를 함께 활성화한다.

![Cosmos 3 architecture diagram](https://developer-blogs.nvidia.com/wp-content/uploads/2026/05/image-11-e1780000686151.webp)
*이미지 출처: [원문](https://developer.nvidia.com/blog/develop-physical-ai-reasoning-world-and-action-models-with-nvidia-cosmos-3/)*

이 구조 덕분에 하나의 모델로 추론과 생성을 모두 처리해 여러 모델·추론 파이프라인 간 오케스트레이션이 필요 없어진다.

**모델 크기 선택**

- Cosmos 3 Nano: 16B 파라미터의 경량 모델로 실시간 추론에 최적화되어 있으며, NVIDIA RTX PRO 6000 같은 워크스테이션급 GPU에서 실시간 로보틱스 추론용으로 설계됨.
- Cosmos 3 Super: 64B 파라미터 모델로 최고 성능·품질을 목표로 하며, NVIDIA Hopper/Blackwell GPU 기반 데이터센터에 배포되어 대규모 합성 데이터 생성과 고급 물리적 추론에 적합.

**지원 모달리티**

Cosmos 3는 하나의 통합 아키텍처로 다양한 입출력 조합을 지원한다. 텍스트→이미지 생성, 텍스트/이미지→영상(월드 모델), 이미지·영상·텍스트→텍스트(VLM 추론), 액션·영상·텍스트→영상(액션 조건부 월드 모델), 영상·텍스트→영상·액션(로봇 정책 모델용 world action model) 등이 가능하다.

**오픈 데이터셋**

**NVIDIA Cosmos Human Evaluation(HUE) 벤치마크**

기존 자동화 리더보드는 SOTA 영상 생성 모델들의 점수 차이가 점점 좁아져 유의미한 비교가 어려워졌다. HUE는 주관적 채점 대신 객관적 사실 검증 방식을 도입해, 각 생성 영상을 의미 일치·물리 법칙·기하학적 추론·시각적 완결성이라는 4개 차원의 예/아니오 질문으로 분해해 평가한다. 이 질문들은 VLM 파이프라인으로 생성 후 인간 전문가가 다듬어 Hugging Face에 오픈소스로 공개됐다.

**벤치마크 결과**

- 추론 벤치마크: VANTAGE-Bench에서 Cosmos 3 Super(32B 티어)와 Nano(8B 티어)가 각각 선두를 기록. Traffic Anomaly Reasoning(TAR)은 AI City Challenge 2026 Track 3 공식 리더보드로 채택됨.
- 생성 벤치마크: Artificial Analysis(Text to Image, Image to Video 리더보드), R-Bench, PAI-Bench, Physics-IQ, RoboLab 등 공개 리더보드에서 오픈소스 SOTA를 기록.

**학습 레시피(Training recipes)**

- Supervised Fine-Tuning(SFT): 커스텀 영상 데이터셋을 위한 vision generation post-training과 로보틱스·물리 AI용 액션 지향 레시피를 GitHub에 코드·설정과 함께 공개.

**NVIDIA NIM 마이크로서비스로 배포**

- **제로트러스트(Zero-trust)**: 모든 접근 요청을 기본적으로 신뢰하지 않고 매번 검증·인가하는 보안 원칙

**왜 CPU가 에이전틱 시대에 더 중요해지는가**

에이전트 AI 루프는 GPU가 도구 호출 파라미터를 생성하면 CPU가 이를 실제로 실행(코드 컴파일·실행, 데이터 조회·처리, 결과 계산, 스케줄링)하고, 그 결과를 다시 GPU에 피드백하는 구조로 반복된다.

![Diagram of the agentic AI loop, showing the CPU executes model-generated content (tool calls, sandboxed code, retrieval, data processing) to provide new context for the next step.](https://developer-blogs.nvidia.com/wp-content/uploads/2026/05/CPU-Execution.webp)
*이미지 출처: [원문](https://developer.nvidia.com/blog/nvidia-vera-cpu-sets-a-new-standard-for-agentic-workloads-in-ai-factories/)*

- 에이전트가 더 정교해질수록 단계 수, 도구 호출 수, 검증 횟수가 늘어나며 CPU 실행 시간이 누적됨
- 기존 데이터센터 CPU는 "코어당 비용" 최적화 중심이었으나, AI 팩토리는 "달러당 토큰 출력량" 관점으로 전환 필요
- 새로운 CPU 설계 요구사항: 높은 코어 수(수천 개의 동시 에이전트·RL 환경 지원), 높은 코어당 성능, 에너지 효율적 메모리 대역폭

![A graphic illustrating the need for a new CPU design point for agentic AI. It shows the shift in priority from maximizing "cores per dollar" for general-purpose cloud services to maximizing "tokens per dollar" for AI factories, which requires many cores, high per-core performance, and energy-efficient memory bandwidth.](https://developer-blogs.nvidia.com/wp-content/uploads/2026/05/AI-CPU.webp)
*이미지 출처: [원문](https://developer.nvidia.com/blog/nvidia-vera-cpu-sets-a-new-standard-for-agentic-workloads-in-ai-factories/)*

**NVIDIA Vera CPU: AI 에이전트를 위한 설계**

Vera CPU는 88개의 NVIDIA Olympus 코어와 최대 1.2TB/s LPDDR5X 메모리 대역폭을 결합해 도구 호출, 네이티브 코드 및 Python·JavaScript 등의 샌드박스 실행, 데이터 조회·처리, 오케스트레이션 작업을 뒷받침한다.

- 클라우드 가상머신과 달리 CPU 소켓이 항상 완전히 로드된 상태로 다수 에이전트를 동시 처리해야 하므로, 고부하 상태에서도 빠른 코어 성능 유지가 핵심
- 빠른 코어는 에이전트의 멀티스텝 요청 지연을 줄이고, 강화학습에서는 학습 윈도우당 더 많은 평가·데이터를 확보 가능

![Diagram of the NVIDIA Vera CPU architecture, highlighting key components like the Olympus custom core, 1.2TB/s LPDDR5X memory subsystem, and NVIDIA Scalable Coherency Fabric (SCF), all engineered for the agentic design point for high per-core performance and efficient memory bandwidth.](https://developer-blogs.nvidia.com/wp-content/uploads/2026/05/Vera-CPU-Agentic.webp)
*이미지 출처: [원문](https://developer.nvidia.com/blog/nvidia-vera-cpu-sets-a-new-standard-for-agentic-workloads-in-ai-factories/)*

**Olympus 코어와 메모리 서브시스템**

Olympus 코어는 NVIDIA Grace 대비 최대 50% 높은 IPC를 제공하며, 넓은 프론트엔드, 고급 분기 예측, 깊은 비순차(out-of-order) 명령어 스케줄링, 특화된 메모리 프리페칭을 결합했다.

- 신경망 기반 분기 예측기로 사이클당 2개의 분기(branch)를 페널티 없이 처리해 PyTorch, 그래프 워크로드, 스크립팅 엔진 등 깊은 소프트웨어 스택에서 처리량 유지
- 10-wide 디코드 유닛과 대형 버퍼로 코드 경로·의존성·메모리 접근 패턴이 바뀌어도 높은 IPC 유지
- 최대 1.2TB/s LPDDR5X 대역폭에서 부하 시에도 피크 대역폭의 90% 이상 유지, x86 CPU 대비 피크 메모리 지연시간 40% 감소
- 그래프 분석·에이전트 메모리 순회에 특화된 신규 그래프 프리페처 탑재, x86 대비 그래프 순회 작업에서 3배 이상 성능
- NVIDIA Scalable Coherency Fabric(SCF)이 모든 코어와 통합 캐시를 단일 메시 구조로 연결, 다이(die)가 분리된 CPU 대비 코어 간 데이터 이동 속도 50% 향상

이 조합으로 Vera CPU는 완전 부하 상태의 에이전틱 워크로드에서 경쟁 제품 대비 1.8배 이상 높은 샌드박스 성능을 보인다.

![Bar chart illustrating that the NVIDIA Vera CPU delivers more than 1.8x higher agentic sandbox performance under peak load compared to x86-based architectures across a broad set of workloads, including code compilation, code analysis, and Python.](https://developer-blogs.nvidia.com/wp-content/uploads/2026/05/Sandbox-Performance.webp)

**시스템 효율성**

수천 대 규모의 CPU로 확장되는 AI 팩토리에서는 메모리 전력이 전체 플랫폼 전력·냉각 비용의 주요 요인이 될 수 있다.

- SOCAMM LPDDR5X 메모리 서브시스템은 일반적으로 30W 미만 소비, DDR5 구성은 100W 이상 소비
- MRDIMM 기반 시스템은 메모리 전력이 더 높아질 수 있음
- Vera CPU는 250W~450W로 설정 가능한 TDP 범위에서 CPU·메모리 전력을 줄이면서 에이전트 추론과 강화학습 환경에 필요한 대역폭 제공

**대상 독자**: 에이전틱 AI·강화학습 파이프라인을 운영하거나 AI 인프라의 CPU 병목·전력 효율을 검토하는 인프라/플랫폼 엔지니어, ML 시스템 설계자에게 유용한 내용입니다.
