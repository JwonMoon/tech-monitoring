# NVIDIA 블로그 요약 — 2026-08-19

### [How AI Coding Agents Can Unlock Materials Simulation with NVIDIA ALCHEMI Toolkit](https://developer.nvidia.com/blog/how-ai-coding-agents-can-unlock-materials-simulation-with-nvidia-alchemi-toolkit/)

`NVIDIA ALCHEMI Toolkit` `AI Coding Agents` `MLIP` `Materials Simulation` `Claude Code` `GPU`

> AI 코딩 에이전트와 ALCHEMI Toolkit으로 GPU 기반 재료 시뮬레이션 코드를 자동 생성

#### 요약

- NVIDIA ALCHEMI Toolkit의 Agent Skills를 활용하면 AI 코딩 에이전트가 머신러닝 원자간 포텐셜(MLIP) 기반 GPU 시뮬레이션 코드를 자연어 프롬프트만으로 생성할 수 있다.
- 실리콘 상태방정식, Cu(111) 산소 흡착, 리튬 자기확산 등 3개 워크플로우에 대해 프롬프트 상세도를 5단계(L1~L5)로 나눠 총 45개 파이프라인을 NVIDIA H200 GPU에서 벤치마크했다.
- 물성값 정확도는 프롬프트 상세도와 무관하게 항상 정확했지만, API 패턴 준수도와 코드 재사용성은 프롬프트가 구체적일수록(특히 L4~L5) 크게 향상됐다.
- 에이전트는 물리적으로 잘못 설정된 요청(예: 측정 불가능한 시간 스케일의 특성)을 스스로 걸러내지 못하므로, 검증과 전제 확인을 명시적으로 요구해야 한다.

#### 시사점

- 재료과학·화학 전문 지식이 없어도 일반 개발자가 자연어 프롬프트만으로 GPU 가속 원자 시뮬레이션 파이프라인을 구축할 수 있게 된다.
- Agent Skills 표준(Claude Code, Cursor, OpenCode 등에서 지원)을 활용하면 특정 툴킷의 API를 몰라도 에이전트가 올바른 사용 패턴을 자동으로 참조한다.
- 코드 생성 자동화가 과학적 판단(무엇을 시뮬레이션할지, 결과가 물리적으로 타당한지)을 대체하지는 못하므로, 독립적 기준값과의 비교 검증이 필수적이다.

#### 용어 설명

- **ALCHEMI Toolkit**: NVIDIA가 제공하는 PyTorch 기반의 GPU 가속 원자 시뮬레이션 구성 도구 모음.
- **MLIP (Machine Learning Interatomic Potential)**: 원자 간 상호작용력을 머신러닝으로 근사해 계산하는 포텐셜 모델. 기존 물리 기반 힘장보다 유연하게 다양한 물질을 다룰 수 있다.
- **Agent Skills**: AI 코딩 에이전트가 특정 라이브러리의 API 사용법을 온디맨드로 참조할 수 있게 해주는 참조 파일/문서 표준.
- **Birch-Murnaghan 피팅**: 에너지-부피 곡선에서 격자상수와 체적탄성률(bulk modulus)을 구하는 상태방정식 피팅 기법.
- **NVE / Langevin 앙상블**: 분자동역학에서 에너지를 보존하는(NVE) 또는 온도조절기(thermostat)로 온도를 제어하는(Langevin) 시뮬레이션 방식. 온도조절기의 마찰력이 확산계수 등 수송 물성을 왜곡시킬 수 있다.
- **MSD (Mean-Squared Displacement)**: 원자가 시간에 따라 이동한 거리의 제곱 평균으로, 그 기울기로부터 자기확산계수를 구한다(Einstein 관계).
- **FIRE / FIRE2**: 원자 구조를 에너지 극소점으로 완화(relax)시키는 최적화 알고리즘.

#### 상세 내용

**배경: 세 번째 장벽, 접근성**

원자 시뮬레이션에는 과학적 지식, 계산 효율적 구현, 그리고 접근 가능한 인터페이스가 필요하다. ALCHEMI Toolkit은 PyTorch 네이티브 구성 요소와 인플라이트 배칭(in-flight batching)으로 두 번째 장벽(구현)을 낮췄지만, 세 번째 장벽인 '접근성'은 여전히 남아 있었다.

- MLIP 생태계는 아직 신생 단계라 기존 화학자들이 익숙한 소프트웨어 스택과 다르다.
- AI 코딩 에이전트가 자연어로 코드를 생성할 수는 있지만, 툴킷의 API를 몰라 그럴듯해 보이지만 틀린 코드를 만들 수 있다.
- ALCHEMI Toolkit의 Agent Skills와 참조 파일이 API 패턴을 제공함으로써 프롬프트는 순수하게 과학적 내용(물질, 조건, 제약)에 집중할 수 있게 된다.

**설치 및 시작 방법**

Python 3.11~3.13, PyTorch 2.8 이상, CUDA 12/13, RTX 20xx 이상 GPU가 필요하다.

- `uv` 패키지 매니저로 가상환경 생성 후 `nvalchemi-toolkit[mace,ase]==0.2.0` 설치
- 동일 릴리스 태그의 Agent Skills를 `npx degit`으로 다운로드해 API 버전 일치
- Claude Code 등 코딩 에이전트를 설치해 로컬 프로젝트 폴더에서 실행

에이전트가 직접 코드를 실행할 수 있는 환경(runnable shell)을 구성하면 임포트 오류나 존재하지 않는 API 참조 같은 기계적 오류가 거의 사라진다. 셸 없이 소스만 체크아웃한 경우도 대안이 되지만, pip 설치만 하고 셸도 소스도 없는 구성이 가장 취약했다.

**좋은 프롬프트 작성법**

5단계 프롬프트 수준(L1 Sketch ~ L5 Contract)을 비교한 결과에 기반한 원칙이다.

![프롬프트 5단계 사다리](https://developer-blogs.nvidia.com/wp-content/uploads/2026/08/image8-2.webp)
*이미지 출처: [원문](https://developer.nvidia.com/blog/how-ai-coding-agents-can-unlock-materials-simulation-with-nvidia-alchemi-toolkit/)*

- 물질·방법·규모는 항상 명시하고, 완전한 CLI 계약(무인 실행용)은 필요할 때만 추가한다. L5(Contract)는 재사용성은 완벽했지만 토큰 비용이 L1 대비 약 4배, 코드량은 2.3배 늘었다.
- 물질, 상(phase), 기준 관례(reference convention)를 명확히 명시해야 한다. 예를 들어 "Li 물질의 수송 특성"이라는 모호한 요청은 아르곤 데모를 만들어냈고, 온도조절기 지정 없이는 Langevin 동역학이 확산을 3~5배 감쇠시켰다.
- 내부 API 구현이 아니라 달성해야 할 제약 조건을 명시한다. 파이프라인 구성 요소 이름을 직접 지정해도 구현이 바뀌지 않았고, 완전한 인터페이스 계약 없이 내부 이름만 지정하면 오히려 취약해졌다.
- 자체 검증, 전제 확인, 불확실성 추정을 명시적으로 요청해야 한다. 에이전트는 스스로 이를 추가하지 않는다.

**한계**

- 어떤 프롬프트 조건에서도 에이전트가 물리적으로 잘못 설정된 작업(예: 측정 불가능한 시간 스케일의 확산 특성)을 스스로 거부한 사례는 없었다.
- MACE-MPA-0 같은 MLIP 파운데이션 모델은 학습 분포 밖에서 정확도가 떨어질 수 있어, 새로운 화학종은 반드시 DFT나 실험과 대조 검증해야 한다.
- 통계적으로는 안정적이지만 물리적으로 틀린 결과가 나올 수 있다(예: Langevin 열조절기로 감쇠된 리튬 확산계수). 검증은 독립적인 기준과 비교해야 하며, 한 스크립트는 동일한 잘못된 상수로 합성 데이터를 만들어 자체 테스트를 통과시킨 사례도 있었다.

**생태계 도입 현황**

Matlantis(150개 이상 기업이 사용하는 AI 시뮬레이션 플랫폼)는 자체 Skills 라이브러리를 공개하고 Claude Code 연동을 발표했으며, Dassault Systèmes BIOVIA는 NVIDIA ALCHEMI NIM을 AI 가상 동반자 MARIE에 활용해 시뮬레이션 접근성을 넓히고 있다.

**대상 독자**: 재료과학·화학 도메인 지식은 있지만 GPU 시뮬레이션 코드 작성에 익숙하지 않은 연구자, 그리고 AI 코딩 에이전트를 활용해 도메인 특화 과학 컴퓨팅 워크플로우를 자동화하려는 개발자에게 유용하다.

### [Run Massive-Scale UMAP in Minutes Using Multiple GPUs—Without Losing Accuracy](https://developer.nvidia.com/blog/run-massive-scale-umap-in-minutes-using-multiple-gpus-without-losing-accuracy/)

`UMAP` `NVIDIA cuML` `NVIDIA cuVS` `Multi-GPU` `kNN Graph` `RAPIDS`

> 다중 GPU로 대규모 UMAP kNN 그래프 구축, CPU 대비 최대 74배 가속

#### 요약

- NVIDIA cuML/cuVS 25.06부터 UMAP 학습의 핵심 병목인 all-neighbors kNN 그래프 구축을 여러 GPU에 분산 처리할 수 있게 됨
- 데이터를 균형 잡힌 클러스터로 나누고 경계 간 오버랩을 두어 로컬 kNN 그래프를 독립적으로 계산 후 병합하는 방식으로 GPU 간 통신 비용을 최소화
- 1억 6백만(106M) 벡터 규모 MIRACL 데이터셋에서 8개 H100 GPU로 8분 만에 전체 UMAP 처리 완료, CPU 대비 최대 74배 속도 향상
- GPU 수를 늘릴수록 임베딩 품질(trustworthiness) 저하 없이 성능이 지속적으로 향상되는 강한 스케일링(strong scaling) 확인

#### 시사점

- 기존에는 단일 GPU 메모리 한계 때문에 수억 개 벡터 규모의 데이터셋에 UMAP을 적용하기 어려웠는데, 이제 여러 GPU에 분산해 시간과 메모리 제약을 동시에 해결할 수 있음
- 탐색적 데이터 분석, 토픽 모델링, 단일세포(single-cell) 분석처럼 파라미터를 바꿔가며 UMAP을 반복 실행해야 하는 워크플로우에서 반복 주기(iteration)를 대폭 단축 가능
- `cuVS`의 all-neighbors API는 UMAP뿐 아니라 독립적인 kNN 그래프 구축이 필요한 다른 애플리케이션에도 활용 가능

#### 용어 설명

- **UMAP (Uniform Manifold Approximation and Projection)**: 고차원 데이터를 저차원(주로 2D)으로 축소해 시각화나 특징 추출에 쓰는 차원 축소 기법
- **kNN 그래프 (k-nearest neighbors graph)**: 데이터셋의 모든 벡터에 대해 가장 가까운 이웃 k개를 연결한 그래프로, UMAP 학습의 핵심 입력
- **NVIDIA cuML**: GPU 가속 머신러닝 라이브러리로, scikit-learn과 유사한 API로 UMAP 등을 GPU에서 실행
- **NVIDIA cuVS**: GPU 가속 벡터 검색/유사도 탐색 라이브러리로, UMAP 내부에서 kNN 그래프 구축에 사용됨
- **Out-of-core**: 데이터 전체가 GPU 메모리에 한 번에 들어가지 않아도 처리할 수 있게 하는 방식
- **Trustworthiness score**: 원본 고차원 공간의 이웃 관계가 저차원 임베딩에서 얼마나 잘 보존되는지를 0~1로 나타내는 임베딩 품질 지표
- **NN-descent**: 근사 최근접 이웃(approximate nearest neighbor)을 빠르게 찾는 알고리즘으로, 본문 예제의 `algo="nn_descent"`에 사용됨

#### 상세 내용

**배경: UMAP의 확장성 문제**

UMAP은 탐색적 분석에서 반복적으로 실행되는데, 데이터가 커질수록 매 실행 비용이 급증해 상호작용적 분석이 어려워진다. 이전 글에서는 out-of-core 방식으로 단일 GPU에서 대규모 데이터셋을 처리할 수 있게 했지만, 학습(training) 단계 자체는 여전히 단일 GPU로 제한되어 있었고 `transform()` 단계만 멀티 GPU를 활용할 수 있었다. 이번 cuML/cuVS 25.06 릴리스는 가장 비용이 큰 all-neighbors kNN 그래프 구축 단계를 여러 GPU로 분산시켜 이 한계를 제거했다.

**다중 GPU 확장 방식**

기존 out-of-core 방식은 데이터셋을 균형 잡힌 클러스터로 나누고, 클러스터 경계에서 벡터를 겹치게(overlap) 배치해 이웃 관계를 보존한다. 각 클러스터에 대해 로컬 kNN 그래프를 독립적으로 계산한 뒤 전역 그래프로 병합한다.

- 이 방식은 이미 작업을 독립적인 단위로 분해하고 있어 멀티 GPU 환경으로 자연스럽게 확장됨
- 각 GPU는 자신에게 할당된 클러스터의 데이터를 CPU 메모리에서 가져와 독립적으로 로컬 kNN 그래프를 계산
- 클러스터 간 조율이 필요 없어 분산 all-neighbors kNN 작업의 성능을 제한하는 값비싼 all-to-all 통신을 피할 수 있음

**설정 방법과 주요 하이퍼파라미터**

멀티 GPU UMAP은 단일 GPU 구현과 동일한 절차를 따르되 두 가지 하이퍼파라미터가 추가된다.

- `knn_n_clusters`: 데이터를 나눌 클러스터 수. 값을 늘리면 클러스터당 데이터가 줄어 GPU 메모리 부담이 감소
- `knn_overlap_factor`: 각 데이터 포인트가 할당되는 최근접 클러스터 개수. 값을 늘리면 클러스터 경계의 실제 최근접 이웃이 더 잘 보존돼 kNN 그래프 및 최종 임베딩 품질이 향상되지만, 계산 시간과 메모리 사용량도 증가

이 두 파라미터는 `cuVS`의 all-neighbors API를 통해 직접 노출되며, `cuML` UMAP은 내부적으로 이를 그대로 전달한다.

```python
from cuvs.neighbors import all_neighbors
from cuvs.common import MultiGpuResources
params = all_neighbors.AllNeighborsParams(
    algo="nn_descent",
    n_clusters=32,
    overlap_factor=2
)
res = MultiGpuResources()
indices, distances = all_neighbors.build(
    data, k, params,
    distances=cupy.empty((n_rows, k)),
    resources=res
)
```

**실전 설정 팁**

- 좋은 출발점은 `knn_overlap_factor=2`
- 중간 규모에서는 2→3→4처럼 작은 증분, `knn_n_clusters`가 100을 넘는 대규모에서는 2→4→6처럼 큰 증분 권장
- `knn_overlap_factor`를 올리면 kNN recall(재현율)은 좋아지지만 클러스터당 계산 시간이 크게 늘어나므로 신중히 조정
- 메모리 사용량을 일정하게 유지하려면 `knn_overlap_factor`를 늘릴 때 `knn_n_clusters`도 함께 늘려 클러스터당 포인트 수를 맞추는 것이 좋음

**GPU 메모리 요구량**

데이터 메모리($M_{data}$)와 그래프 메모리($M_{graph}$)는 각각 `knn_overlap_factor`에 비례하고 `knn_n_clusters`에 반비례한다. 예시로 80GB GPU, N=1억, D=1024(float32, 총 409GB) 데이터셋에서 `knn_overlap_factor=2`, `knn_n_clusters=24`를 선택하면 클러스터당 데이터 크기는 약 34GB, 그래프 크기(k=15, int64 인덱스, float32 거리)는 약 1.5GB로 총 35.5GB가 되어 여유 메모리를 확보할 수 있다.

**cuML에서 멀티 GPU UMAP 사용법**

```python
from cuml.manifold import UMAP
umap = UMAP(
    build_kwds={"knn_n_clusters": 32, "knn_overlap_factor": 2},
    device_ids="all",  # 또는 device_ids=[0, 4, 5]
)
embedding = umap.fit_transform(data)
```

`device_ids`로 사용할 GPU를 지정하며, GPU 수를 늘릴수록 all-neighbors 구축이 분산되어 실행 시간이 줄어든다. 또한 `cuVS`로 미리 계산한 all-neighbors 그래프를 `precomputed_knn` 인자로 CPU/GPU UMAP 어느 쪽에도 전달할 수 있다.
