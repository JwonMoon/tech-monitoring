# NVIDIA 블로그 요약 — 2026-08-15

### [Creating the NVIDIA Nemotron 3 Ultra NVFP4 Checkpoint with NVIDIA Model Optimizer](https://developer.nvidia.com/blog/creating-the-nvidia-nemotron-3-ultra-nvfp4-checkpoint-with-nvidia-model-optimizer/)

`NVFP4` `Nemotron` `Quantization` `NVIDIA Model Optimizer` `Blackwell` `Megatron-LM`

> Nemotron 3 Ultra를 NVFP4로 양자화해 크기 3.2배 줄이고 정확도는 BF16 수준 유지

#### 요약

- NVIDIA Model Optimizer로 550B 규모 Nemotron 3 Ultra 모델을 NVFP4(4비트 부동소수점)로 양자화, BF16 대비 1,121GB→352.3GB(3.2배 축소)를 달성하면서 거의 모든 벤치마크에서 BF16 정확도를 유지.
- 레이어마다 다른 정밀도(NVFP4, FP8, BF16 등)를 혼합 적용하며, 특히 라우팅 전문가(routed experts) 가중치에 "four-over-six" 스케일링 기법을 새로 도입해 정확도 손실을 최소화.
- 단일 체크포인트로 Hopper(W4A16)와 Blackwell(W4A4) 양쪽 GPU에서 동작하도록 설계.
- Hugging Face Transformers 대비 Megatron-LM 기반 병렬 양자화 파이프라인이 총 소요시간을 120분에서 45분으로 단축.

#### 시사점

- 대형 MoE(전문가 혼합) 모델을 양자화할 때 단순 max 스케일링보다 데이터 분포를 고려한 스케일링 기법이 정확도-압축률 균형에 크게 영향을 준다는 실증 사례를 제공.
- NVIDIA Model Optimizer의 `auto_quantize`, YAML 레시피 등을 통해 개발자가 자신의 Hugging Face 모델에도 동일한 파이프라인을 그대로 적용해 NVFP4 체크포인트를 만들 수 있음.
- 추론 서빙 시 하드웨어(Hopper vs Blackwell)에 따라 자동으로 정밀도를 전환하는 설계는 배포 유연성을 높여준다.

#### 용어 설명

- **NVFP4**: NVIDIA Blackwell 아키텍처에서 도입된 4비트 부동소수점 양자화 포맷.
- **양자화(Quantization)**: 모델 가중치를 더 작은 데이터 형식으로 압축해 메모리와 연산량을 줄이는 최적화 기법.
- **스케일(Scale)**: 양자화 시 원래 값 범위를 표현 가능한 제한된 값 집합으로 매핑하는 배율.
- **MoE(Mixture of Experts)**: 여러 개의 전문가 서브네트워크 중 일부만 선택적으로 활성화하는 모델 구조.
- **GPTQ**: 2차 정보(헤시안)를 활용해 가중치를 정밀하게 양자화하는 기법.
- **BPE(Bits-Per-Element)**: 모델 가중치 하나를 저장하는 데 평균적으로 필요한 비트 수.
- **PTQ(Post-Training Quantization)**: 모델 학습 완료 후 별도 재학습 없이 양자화를 적용하는 방식.

#### 상세 내용

**Nemotron 3 Ultra NVFP4 체크포인트 구성**

NVFP4 체크포인트라고 해서 모든 레이어가 4비트로 저장되는 것은 아니다. 레이어별 민감도와 정확도 영향에 따라 정밀도가 다르게 할당된다.

- MoE 라우팅 전문가는 NVFP4, 공유 전문가·Mamba mixer 선형층은 FP8 per-tensor, 임베딩·출력 분류층·어텐션 선형층·Mamba conv1d 등은 BF16 유지.
- KV 캐시는 FP8, Mamba SSM 캐시는 확률적 반올림(stochastic rounding)을 적용한 FP16.
- 이 혼합 정밀도 구성으로 전체 모델 크기가 1,121GB(BF16)에서 352.3GB로 3.2배 축소.

![Figure 1 Table mapping each Nemotron 3 Ultra layer to its BF16 baseline and quantized precision, showing mixed NVFP4, FP8, BF16, and FP16 formats by layer type.](https://developer-blogs.nvidia.com/wp-content/uploads/2026/06/Ultra-3-Performance.webp)
*이미지 출처: [원문](https://developer.nvidia.com/blog/creating-the-nvidia-nemotron-3-ultra-nvfp4-checkpoint-with-nvidia-model-optimizer/)*

단일 체크포인트가 Hopper(FP4 텐서 코어 미지원, 자동으로 W4A16 전환)와 Blackwell(네이티브 W4A4 지원) 양쪽에서 동작하도록 설계됐다. Hopper에서 W8A8 대신 W4A16을 택한 이유는 Multi-Token Prediction(MTP) 기능을 함께 탑재할 메모리 여유를 확보하기 위해서다.

**FP4 양자화의 난제와 스케일 선택 방법**

FP4는 [0, 0.5, 1, 1.5, 2, 3, 4, 6] 단 8개의 양수 값만 표현 가능해, 스케일(배율) 선택이 정확도를 좌우한다.

- **Max(absmax) 스케일링**: 블록 내 최대값을 FP4 최대 표현값에 맞춘다. 구현은 간단(`mtq.NVFP4_DEFAULT_CFG`)하지만, 하나의 이상치(outlier)가 다른 작은 값들을 0으로 밀어내는 정보 손실이 발생하기 쉽다.

![Diagram showing six small FP32 weights collapsing to zero under absmax FP4 quantization while a single outlier (12.8) survives.](https://developer-blogs.nvidia.com/wp-content/uploads/2026/06/Max-Scaling-e1782328670195.webp)
*이미지 출처: [원문](https://developer.nvidia.com/blog/creating-the-nvidia-nemotron-3-ultra-nvfp4-checkpoint-with-nvidia-model-optimizer/)*

- **MSE(평균제곱오차) 스케일링**: 블록 전체의 복원 오차를 최소화하는 스케일을 탐색(`mtq.NVFP4_W4A4_WEIGHT_MSE_FP8_SWEEP_CFG`). Nemotron 3 Ultra 실험에서 텐서당 가중치 오차를 four-over-six 대비 27.1% 줄였지만, 다운스트림 벤치마크에서 일관된 개선으로 이어지지는 않았다.

![Diagram showing MSE-scaled FP4 quantization preserving small weights while clipping the outlier from 12.8 down to 2.0.](https://developer-blogs.nvidia.com/wp-content/uploads/2026/06/MSE-Scaling-1-e1782328711760.webp)
*이미지 출처: [원문](https://developer.nvidia.com/blog/creating-the-nvidia-nemotron-3-ultra-nvfp4-checkpoint-with-nvidia-model-optimizer/)*

**Four-over-six 스케일링**

FP4 표현값은 4 다음 바로 6으로 건너뛰어 그 사이 값에서 최대 13% 이상의 오차가 발생할 수 있다. 이를 해결하기 위해 각 가중치 블록이 최대값을 M=4 또는 M=6 중 오차가 작은 쪽으로 독립적으로 선택하는 방식이 four-over-six다(가중치에만 적용, 활성화는 기본 NVFP4로 처리).

![Range showing the gap of FP4 representable values between 4-6.](https://developer-blogs.nvidia.com/wp-content/uploads/2026/06/Error-Rounding.webp)
*이미지 출처: [원문](https://developer.nvidia.com/blog/creating-the-nvidia-nemotron-3-ultra-nvfp4-checkpoint-with-nvidia-model-optimizer/)*

![Two example blocks comparing M=6 and M=4 FP4 scaling, with mean squared error showing each block prefers a different grid.](https://developer-blogs.nvidia.com/wp-content/uploads/2026/06/Block-Scaling.webp)
*이미지 출처: [원문](https://developer.nvidia.com/blog/creating-the-nvidia-nemotron-3-ultra-nvfp4-checkpoint-with-nvidia-model-optimizer/)*

- Nemotron 3 Ultra의 MoE 라우팅 전문가 가중치 스케일을 four-over-six로 설정, 48개 MoE 전문가 레이어의 49,152개 프로젝션 가중치 전체에서 중앙값 복원 MSE를 표준 max 대비 16.4% 감소.
- 5.03 BPE(bits-per-element) 설정 기준 BF16 대비 98.5% 중앙값 정확도 회복(max 96.8%, MSE 98.4% 대비 우수).
- `mtq.NVFP4_FOUR_OVER_SIX_CFG`는 NVIDIA Model Optimizer 0.46(2026년 7월 예정)에 포함될 예정.

**Bits-per-element(BPE) 최적화**

BF16은 레이어당 16비트, NVFP4는 블록·텐서 스케일 오버헤드를 포함해 최소 4.5비트가 필요하다. 레이어별로 민감도가 달라 어떤 조합이 최적인지 탐색이 필요한데, 조합 수가 지수적으로 늘어나 전수 탐색이 불가능하다.

- NVIDIA Model Optimizer의 `mtq.auto_quantize`가 목표 비트 예산(예: `auto_quantize_bits=4.8`)과 후보 포맷 목록을 받아 레이어별 민감도를 평가하고 예산 내 최고 정확도 조합을 자동 탐색.
- Nemotron 3 Ultra에서 4.85~7.19 BPE 5개 지점을 비교한 결과, AA-LCR 벤치마크가 4.85→5.03 구간에서 2.4점 개선된 뒤 그 이상에서는 평탄화되어 5.03 BPE가 최적점으로 결정됨.

**양자화 파이프라인: Hugging Face vs Megatron-LM**

550B 규모 모델이라 병렬화가 중요해, 두 가지 양자화 경로를 지원한다.

- Hugging Face Transformers 경로: 4×B300 GPU, 총 120분 소요.
- Megatron-LM 경로: 16×B300 GPU, 전문가 병렬성(EP)=데이터 병렬성(DP)=16 설정으로 총 45분 소요(로딩·캘리브레이션이 85분→9분으로 단축).
- 캘리브레이션은 `nemotron-post-training-dataset-v2`로 블록 스케일을 조정하며, 정밀도 정책은 `quantize.sh`에 넘기는 YAML 레시피나 내장 설정(`NVFP4_DEFAULT_CFG` 등)으로 완전히 구성 가능.

**커스텀 양자화 설정**

Model Optimizer는 `NVFP4_DEFAULT_CFG`부터 `NVFP4_MLP_ONLY_CFG`, `NVFP4_EXPERTS_ONLY_CFG` 등 선택적 프리셋까지 다양한 설정을 제공한다.

- 설정은 모듈 이름 패턴(`*weight_quantizer`, `*input_quantizer`)에 매칭되는 규칙 목록으로 구성되며, 가중치·활성화 양자화를 독립적으로 제어할 수 있다.
- YAML 레시피(`nvfp4-4o6.yaml`)로 라우팅 전문가는 four-over-six NVFP4, 공유 전문가·Mamba는 FP8, KV 캐시는 FP8, 나머지는 BF16으로 세밀하게 지정 가능.
- 동일 파이프라인이 임의의 Hugging Face 모델에도 적용 가능하며, `export_hf_checkpoint`로 TRT-LLM/vLLM/SGLang용 통합 체크포인트를 내보낼 수 있다.
- 원클릭 런처(`launch.py`)로 Slurm 클러스터에서 전체 PTQ·익스포트 워크플로를 자동화할 수 있으며, 4노드×4 Blackwell GPU 환경에서 검증됨.

**대상 독자**: 대형 언어모델을 자체 인프라에 배포하며 메모리·추론 비용을 줄이려는 ML 엔지니어, 양자화 기법을 커스터마이징해 자체 모델에 적용하려는 개발자에게 유용하다.

### [Streamlining Resource Binding with End-to-End Support for Vulkan Descriptor Heaps](https://developer.nvidia.com/blog/streamlining-resource-binding-with-end-to-end-support-for-vulkan-descriptor-heaps/)

`Vulkan` `Descriptor Heaps` `D3D12` `Nsight Graphics` `Ray Tracing` `GPU Programming`

> Vulkan에 D3D12식 디스크립터 힙 도입으로 리소스 바인딩이 단순해짐

#### 요약

- 신규 `VK_EXT_descriptor_heap` 확장은 기존 디스크립터 셋 방식 대신 사용자가 직접 관리하는 메모리 힙에 디스크립터를 배치하는 방식으로 리소스 바인딩을 재설계함
- NVIDIA 드라이버 610 이상과 Nsight Graphics 2026.2에서 캡처·리플레이를 포함한 전 과정을 지원
- 셰이더는 셋/바인딩 인덱스로 매핑하거나, 힙을 직접 포인터로 인덱싱하는 방식(untyped pointers) 중 선택 가능
- 오픈소스 `descriptor_heap` 샘플 앱으로 실제 사용법을 학습할 수 있음

#### 시사점

- 동적 텍스처 인덱싱이나 복잡한 레이 트레이싱 셰이더를 쓰는 렌더러에서 디스크립터 관리 오버헤드와 성능 튜닝 부담이 줄어듦
- D3D12와 백엔드를 공유하는 렌더러의 경우 두 API 간 구조적 유사성이 커져 이식과 유지보수가 쉬워짐
- Nsight Graphics가 디스크립터 힙을 기존 셰이더 리소스 뷰에서 그대로 확인·디버깅할 수 있어 도입 장벽이 낮음

#### 용어 설명

- **디스크립터(Descriptor)**: GPU가 텍스처·버퍼 같은 리소스를 찾는 데 쓰는 벤더별 저수준 메타데이터 조각
- **디스크립터 셋(Descriptor Set)**: Vulkan에서 전통적으로 디스크립터를 묶어 관리하던 배열 구조로, 레이아웃과 풀(pool) 할당 등 부가 작업이 필요
- **디스크립터 힙(Descriptor Heap)**: 애플리케이션이 직접 할당·관리하는 단일 메모리 영역에 디스크립터를 배치하는 방식(D3D12 방식과 유사)
- **Vulkan**: 크로스 플랫폼 저수준 그래픽스/컴퓨트 API
- **D3D12**: 마이크로소프트의 저수준 그래픽스 API로, 원래부터 디스크립터 힙 개념을 사용
- **Nsight Graphics**: NVIDIA의 그래픽스 프레임 캡처·디버깅 도구
- **Nonuniform indexing / untyped pointers**: 셰이더가 배열 형태의 디스크립터를 동적으로, 혹은 포인터로 직접 인덱싱하는 접근 방식

#### 상세 내용

**디스크립터 셋에서 힙으로 전환하는 이유**

디스크립터는 텍스처나 버퍼 같은 리소스를 가리키는 벤더별 불투명(opaque) 데이터로, 셰이더 입장에서는 단순한 메모리 조각이다.

- 기존 Vulkan은 디스크립터 셋만 지원했으며, 셋 레이아웃 정의·풀 할당 등 번거로운 절차가 필요했음
- `VK_EXT_descriptor_buffer` 확장이 애플리케이션 관리 메모리를 도입했지만 여전히 셋 기반 바인딩 모델과 레이아웃 인프라를 유지
- `VK_EXT_descriptor_heap`은 이를 단순화해, 사용자가 직접 작성한 디스크립터를 사용자가 할당한 "힙" 메모리에 두는 구조로 바꿈
- 한 번에 하나의 리소스 디스크립터 힙만 바인딩 가능하며(샘플러는 별도 힙), 애플리케이션 생애주기 동안 동일 힙을 유지하는 것을 권장(힙 교체는 성능 비용이 큼)

**사용 방법**

필요한 환경: NVIDIA 드라이버 610 이상, Vulkan Headers 1.4.340 이상, Nsight Graphics 2026.2.

- 확장 사용 전 `VkDeviceCreateInfo`의 extensions와 `pNext` 체인에 `VK_EXT_DESCRIPTOR_HEAP_EXTENSION_NAME`, `VkPhysicalDeviceDescriptorHeapFeaturesEXT`를 추가해야 함
- 기존 셰이더 코드를 수정하지 않고 쓰려면 `VkShaderDescriptorSetAndBindingMappingInfoEXT`로 디스크립터를 셋/바인딩 인덱스에 매핑
- **Push Index 방식**: `VK_DESCRIPTOR_MAPPING_SOURCE_HEAP_WITH_PUSH_INDEX_EXT`로 설정하면 push constant 값만큼 디스크립터 위치가 오프셋되어, 같은 셰이더에서도 드로우콜마다 다른 디스크립터 범위를 선택 가능
- **Constant Offset 방식**: `VK_DESCRIPTOR_MAPPING_SOURCE_HEAP_WITH_CONSTANT_OFFSET_EXT`로 고정 오프셋을 더하는 단순한 방식

기존 API와의 대응 관계:

| 디스크립터 셋 | 디스크립터 힙 |
|---|---|
| `vkCreateDescriptorPool`, `vkAllocateDescriptorSets` | `VK_BUFFER_USAGE_DESCRIPTOR_HEAP_BIT_EXT`가 설정된 `VkBuffer` + `VkDeviceMemory` |
| `VkDescriptorSetLayoutBinding`, `vkCreateDescriptorSetLayout` | `VkShaderDescriptorSetAndBindingMappingInfoEXT` |
| `vkUpdateDescriptorSets`, `vkCmdPushDescriptorSet` | `vkWriteResourceDescriptorsEXT` |
| `vkCmdPushConstants` | `vkCmdPushDataEXT` |
| `vkCmdBindDescriptorSets` | `vkCmdBindSamplerHeapEXT`, `vkCmdBindResourceHeapEXT` |

이 구조는 셰이더가 디스크립터를 동적으로 인덱싱하고, 인덱스를 애플리케이션이 관리하며, 힙이 전역 바인딩 상태로 존재한다는 점에서 D3D12와 유사하다. 다만 Vulkan에서는 애플리케이션이 힙의 정확한 메모리 위치를 직접 선택하고, 디스크립터 타입별로 크기가 다를 수 있다는 차이가 있다.

**직접 힙 접근(Direct heap access)**

셰이더는 셋/바인딩 매핑 없이 바인딩된 리소스·샘플러 힙에서 디스크립터 배열을 직접 인덱싱할 수도 있다.

- 포인터 앨리어싱(pointer aliasing) 개념을 사용하며 `VK_KHR_shader_untyped_pointers` 확장 활성화가 필요
- `descriptor_heap` 샘플 앱에 예제가 포함되어 있고 Nsight Graphics에서도 동작
- 아직 셰이딩 언어·툴체인 전반에서 성숙 중인 기능

### [Scaling AI Inference Across Multiple GPUs Using NVIDIA TensorRT with Multi-Device Inference Support](https://developer.nvidia.com/blog/scaling-ai-inference-across-multiple-gpus-using-nvidia-tensorrt-with-multi-device-inference-support/)

`TensorRT` `NCCL` `Multi-GPU Inference` `Context Parallelism` `Torch-TensorRT` `Diffusion Models`

> TensorRT 11.0에 NCCL 기반 멀티 GPU 추론 기능 추가, 생성형 미디어 파이프라인 확장

#### 요약

- TensorRT 11.0에 NCCL 기반 멀티 디바이스 추론 기능이 새로 추가되어 여러 GPU에 걸친 네이티브 고성능 추론을 지원
- Torch-TensorRT와 결합해 PyTorch 모델을 프레임워크 밖에서 변환·배포, 단일 GPU 메모리·연산 한계를 극복
- 텐서 병렬화(tensor parallelism)와 컨텍스트 병렬화(context parallelism) 두 전략을 소개하고, 특히 컨텍스트 병렬화에 초점
- AllGather KV, Ring Attention, DeepSpeed Ulysses 세 가지 컨텍스트 병렬화 구현을 Cosmos 3·FLUX.1 모델로 벤치마크

#### 시사점

- C++ 프로덕션 환경에서 멀티 GPU 추론을 네이티브로 구현할 수 있어 대규모 생성형 미디어(비디오·이미지 생성) 파이프라인 배포가 쉬워짐
- PyTorch로 모델을 개발하고 TensorRT 엔진으로 변환·배포하는 워크플로우를 유지하면서 멀티 GPU로 확장 가능
- 긴 시퀀스(고해상도 이미지/비디오) 어텐션 연산 병목을 해결할 병렬화 전략 선택 기준을 제공

#### 용어 설명

- **TensorRT**: NVIDIA의 고성능 딥러닝 추론 최적화 엔진
- **NCCL**: 다중 GPU/노드 간 집합 통신(collective operations)을 최적화하는 NVIDIA 라이브러리
- **Tensor Parallelism (텐서 병렬화)**: 하나의 레이어 가중치를 여러 GPU에 분할해 계산하는 병렬화 기법
- **Context Parallelism (컨텍스트 병렬화)**: 입력 시퀀스를 여러 GPU에 분할해 처리하는 병렬화 기법
- **Torch-TensorRT**: PyTorch 모델을 TensorRT 엔진으로 변환해주는 도구
- **Ring Attention**: K/V를 링 토폴로지로 GPU 간 스트리밍하며 통신과 연산을 오버랩하는 어텐션 기법
- **DeepSpeed Ulysses**: all-to-all 통신으로 시퀀스 차원과 어텐션 헤드 차원을 서로 교환하는 컨텍스트 병렬화 기법

#### 상세 내용

**NCCL: 분산 추론의 통신 계층**
- NCCL은 대규모 모델 학습을 위한 다중 GPU/노드 집합 통신 라이브러리로, NVLink·NVSwitch·PCIe·InfiniBand 등 토폴로지에 맞는 최적 전송 방식을 자동 선택
- TensorRT가 NCCL과 직접 통합되어 추론 워크로드에서도 이 통신 최적화를 그대로 활용
- 지원 collective 연산: AllReduce, Broadcast, Reduce, AllGather, ReduceScatter, AlltoAll, Gather, Scatter

**텐서 병렬화 vs 컨텍스트 병렬화**
- 텐서 병렬화: 레이어 가중치를 GPU마다 분할 계산 후 collective로 결과를 합침. 개별 레이어 가중치가 GPU 메모리를 초과할 때 사실상 필수적인 선택
  - transformer 블록에서는 column-parallel projection(QKV, MLP up-projection)과 row-parallel projection(attention output, MLP down-projection)을 짝지어 블록당 AllReduce 1회로 통신 오버헤드를 제한

![column-wise와 row-wise 병렬 projection 비교](https://developer-blogs.nvidia.com/wp-content/uploads/2026/06/Projections.webp)
*이미지 출처: [원문](https://developer.nvidia.com/blog/scaling-ai-inference-across-multiple-gpus-using-nvidia-tensorrt-with-multi-device-inference-support/)*

- 컨텍스트 병렬화: 입력 시퀀스를 시퀀스 차원으로 GPU에 분할. 시퀀스 길이가 길수록 어텐션 연산이 제곱으로 증가하는 워크로드에 특히 효과적이며, 양방향 어텐션을 쓰는 diffusion/DiT 모델에 특히 적합
- TensorRT 11.0은 이런 병렬화 전략들을 위한 `IDistCollectiveLayer` 프리미티브를 지원하며, 이후 내용은 생성형 미디어의 핵심 병목인 컨텍스트 병렬화에 초점

**생성형 미디어를 위한 컨텍스트 병렬화**
- 고해상도 이미지 latent나 다중 프레임 비디오는 블록당 수만 개의 토큰 시퀀스를 만들어내며, 어텐션 연산량이 시퀀스 길이의 제곱에 비례해 증가

**AllGather KV**
- 각 GPU 랭크가 시퀀스 일부의 Q를 처리하고, attention 계산 전 AllGather collective로 K/V를 교환해 전체 시퀀스에 대해 attention을 수행
- attention 블록마다 collective 통신이 1회 추가되지만, 로컬 Q×Kᵀ 행렬곱 크기는 랭크 수에 비례해 감소

![AllGather KV 방식의 컨텍스트 병렬화](https://developer-blogs.nvidia.com/wp-content/uploads/2026/06/KV-Context-Parallelism.webp)
*이미지 출처: [원문](https://developer.nvidia.com/blog/scaling-ai-inference-across-multiple-gpus-using-nvidia-tensorrt-with-multi-device-inference-support/)*

**Ring Attention**
- AllGather KV의 개선판으로 통신과 연산을 오버랩. K/V가 링 토폴로지로 GPU 사이를 스트리밍되는 동안 각 GPU는 로컬 Q를 동시에 처리
- online softmax를 사용해 전체 크기의 K/V를 어느 GPU에도 완전히 올릴 필요가 없어 메모리 사용량도 절감

![Ring Attention 방식의 컨텍스트 병렬화](https://developer-blogs.nvidia.com/wp-content/uploads/2026/06/Ring-Attention-1.webp)
*이미지 출처: [원문](https://developer.nvidia.com/blog/scaling-ai-inference-across-multiple-gpus-using-nvidia-tensorrt-with-multi-device-inference-support/)*

**DeepSpeed Ulysses**
- 긴 컨텍스트(수만 토큰)에 적합한 방식으로, 먼저 시퀀스 차원으로 GPU 간 샘플을 분할한 뒤 attention 계산 전 Q/K/V에 all-to-all 통신을 적용
- 각 GPU가 전체 시퀀스 길이를 받되 겹치지 않는 attention head 부분집합만 담당해 병렬로 attention 계산, 이후 두 번째 all-to-all로 head 축 결과를 모아 다시 시퀀스 축으로 재분할

![DeepSpeed Ulysses 방식의 컨텍스트 병렬화](https://developer-blogs.nvidia.com/wp-content/uploads/2026/06/DeepSpeed-Ulysses.webp)

### [Q&A: How KRAFTON Built PUBG Ally, a Co-Playable Character Powered by NVIDIA ACE](https://developer.nvidia.com/blog/how-krafton-built-pubg-ally-a-co-playable-character-powered-by-nvidia-ace/)

`NVIDIA ACE` `PUBG` `Small Language Model` `KRAFTON` `Co-Playable Character` `On-Device AI`

> KRAFTON이 NVIDIA ACE로 만든 실시간 음성 AI 팀메이트 'PUBG Ally' 개발기

#### 요약

- *PUBG* Ally는 NVIDIA ACE 기반 ASR·SLM(Mistral-NeMo-Minitron-2B)·TTS 파이프라인으로 플레이어 음성과 게임 상태를 이해하고 실시간으로 응답하는 co-playable character(CPC)다.
- 모델을 온디바이스로 구동해 클라우드 LLM 대비 지연을 줄였고, 양자화를 거쳐 VRAM 8GB급 GPU에서도 동작한다.
- 즉각 반응은 behavior tree(System 1), 언어 추론은 SLM(System 2)이 담당하는 이원 구조로 전투 중 반응성과 자연스러운 대화를 동시에 확보했다.
- Sanhok 맵·AI Duo 모드로 범위를 제한한 폐쇄형 세계관에서 teacher-student distillation으로 도메인 지식을 학습시켰고, 세션 간 유지되는 장기 기억을 추가했다.

#### 시사점

- 실시간 게임 환경에서 온디바이스 SLM과 ACE 파이프라인을 결합해 대화형 AI 동료를 구현하는 구체적 실전 사례를 제공한다.
- System 1/System 2 분리, KV 캐시 최적화 등 지연 시간 최소화 기법은 게임 외 다른 실시간 AI 에이전트 설계에도 참고할 수 있다.
- tool-calling 기반 게임 상태 grounding과 teacher-student distillation을 통한 도메인 특화 방식은 환각(hallucination)을 줄이는 실용적 패턴을 보여준다.

#### 용어 설명

- **NVIDIA ACE**: 음성·언어·애니메이션 AI를 게임 캐릭터에 적용하기 위한 NVIDIA의 온디바이스·클라우드 AI 모델 스위트
- **Co-Playable Character (CPC)**: 정해진 대사만 반복하는 기존 NPC와 달리 협력·적응·기억이 가능한 새로운 AI 캐릭터 유형
- **ASR (Automatic Speech Recognition)**: 플레이어의 음성을 텍스트로 변환하는 음성 인식 기술
- **SLM (Small Language Model)**: 대형 LLM보다 파라미터가 적어 기기 내에서 빠르게 구동 가능한 언어모델. 여기서는 20억 파라미터의 Mistral-NeMo-Minitron-2B를 사용
- **TTS (Text-to-Speech)**: 텍스트를 음성으로 변환하는 기술
- **KV 캐시**: 트랜스포머 모델이 이전 턴의 연산 결과를 저장·재사용해 추론 속도를 높이는 캐싱 기법
- **Behavior Tree**: 이동·조준 등 즉각적인 게임 행동을 규칙 기반으로 빠르게 처리하는 구조

#### 상세 내용

**CPC란 무엇인가**

Ally는 자연어 음성으로 플레이어 의도를 파악하고, 현재 전투·루팅 상황에 맞춰 행동을 바꾸며, 실시간으로 소통한다. KRAFTON은 이를 스크립트 기반 NPC와 구분해 "co-playable character"라 명명했다.

- 팀워크, 커뮤니케이션, 예측 불가능한 상황이 핵심인 배틀로얄 장르 특성상 *PUBG*가 CPC 개념을 시험하기에 적합했다고 설명한다.

**기술 아키텍처: ASR-SLM-TTS 파이프라인**

파이프라인은 플레이어 음성과 실시간 게임 상태라는 두 입력을 받아, Ally의 발화와 인게임 행동이라는 두 출력을 만든다. ASR, SLM, 자체 개발 TTS가 모두 기기 내에서 동작한다.

- 플레이어가 말하면 ASR이 텍스트로 변환하고, 동시에 게임 엔진은 현재 매치 상태를 텍스트 형태의 observation tool로 제공한다.
- SLM은 이벤트 기반 루프로 동작하며, 발화된 텍스트는 TTS로, 행동 결정은 behavior tree로 전달되어 실행된다.

**왜 작은 언어모델인가**

클라우드 LLM 테스트에서는 네트워크 지연과 추론 지연이 겹쳐 실시간 스쿼드 커뮤니케이션에는 너무 느렸다. NVIDIA ACE의 Mistral-NeMo-Minitron-2B를 온디바이스로 구동하자 네트워크 왕복이 사라지고 응답 시간이 훨씬 예측 가능해졌다.

- *PUBG*는 이미 GPU 메모리를 많이 소모하는 그래픽 중심 타이틀이라 AI 컴패니언에 할당 가능한 VRAM이 제한적이었다.
- 2B 파라미터의 Mistral-NeMo-Minitron-2B를 추가로 양자화해, VRAM 8GB급 GPU에서도 *PUBG* Ally를 구동할 수 있도록 했다.

**지연 시간 최적화: System 1/System 2 구조**

프롬프트 구조를 KV 캐시 활용에 맞게 설계해, 안정적인 지시문·게임 컨텍스트는 유지하고 매 턴 갱신되는 정보만 최소화함으로써 중복 연산을 줄였다.

- 인간의 빠른 직관적 반응(System 1)과 느린 숙고적 추론(System 2)에 빗대어, behavior tree가 이동·조준·즉각적 전투 반응을 게임 틱 레이트로 처리한다.
- 언어모델(System 2)은 플레이어 의도 해석, 자연어 발화 생성 등 숙고가 필요한 작업만 담당해, 반사적 행동이 모델 응답을 기다리지 않도록 했다.
- 두 레이어의 경계를 어디에 둘지 정하는 데 상당한 엔지니어링 노력이 투입됐다.

**도메인 특화와 게임 상태 grounding**

먼저 "무엇을 다루지 않을지"부터 결정했다. Sanhok 맵과 AI Duo 모드 하나로 세계관을 제한하고, Ally가 사용할 수 있는 것·인식만 가능한 것·존재하지 않는 것을 구분하는 고정된 아이템 분류 체계를 만들었다.

- 결정론적인 *PUBG* 명세(맵 랜드마크, 아이템·무기 지식, Ally의 실제 가능 범위)를 더 큰 teacher 모델의 시스템 프롬프트에 넣고, 이를 통해 온디바이스 student 모델을 distillation했다.
- Ally는 자신의 상태, 팀메이트, 주변 아이템, 전투 상황 등을 tool call로 직접 조회해 답한다. 예: "M416 장착 중, 탄창 24/30발, 체력 78%, 세이프존 내부."
- 시스템 프롬프트는 이런 tool 결과만이 유일한 사실 정보임을 명시하며, 이전 턴 기억이 아니라 매번 재조회하는 습관을 distillation 과정에서 학습시켰다.

**다국어 지원**

*PUBG*의 커뮤니케이션은 짧은 명령어, 은어, 줄임말, 아이템명, 맵 콜아웃 등 표준 언어와 다르다. 영어·한국어·중국어 커뮤니티에서 실제 플레이어들이 어떻게 소통하는지 조사해 언어별 데이터를 구축하고, 언어 전문가와 함께 자연스러움과 게임 적합성을 검토했다.

**장기 기억**

Ally의 기억은 두 시간 척도로 구조화된다. 장기 기억은 매치를 넘어 유지되며 플레이어 이름, 선호 무기, 즐겨 찾는 낙하 지점, 개인 정보, 이전 매치 기록(최종 순위·특이 사항)을 담는다. 단기 기억은 현재 매치 내의 발화와 최근 사건이다.

- 플레이 테스트에서 한 플레이어가 첫 매치에서 Beryl(무기)을 부탁하자, 다음 매치부터 Ally가 요청 없이도 찾아주기 시작했다.
- 이름을 한 번 알려준 플레이어는 다음 매치에서 Ally가 그 이름을 바로 사용하는 것을 경험했다.

**테스트와 튜닝 방법론**

비결정론적 출력을 갖는 AI 팀메이트 테스트는 챗봇 테스트와 다르다. 자동화 평가로 상호작용 프로토콜 준수, tool 사용 적절성, 발화·행동 일관성을 점검했다.

- 후보 모델들을 실제 플레이 테스트와 A/B 테스트, 설문·자유 피드백으로 비교했다.
- 최종적으로 1,000명 이상의 실제 플레이어 대규모 플레이 테스트로 검증하고 개선했다.

**향후 전망**

KRAFTON은 아케이드 모드를 통해 플레이어들이 AI 동료와 함께할 때 실제로 어떤 재미를 원하는지 발견하는 것을 다음 단계 목표로 삼고 있으며, CPC가 스크립트 기반 시스템으로는 불가능한 방식으로 플레이어를 이해하고 적응할 수 있다고 본다.

**대상 독자**: 실시간 음성 AI 캐릭터나 온디바이스 SLM 파이프라인 구축에 관심 있는 게임 개발자, 지연 시간에 민감한 실시간 AI 에이전트 설계자에게 유용하다.

### [Accelerating BEV Pooling on NVIDIA GPUs for Physical AI Applications](https://developer.nvidia.com/blog/accelerating-bev-pooling-on-nvidia-gpus-for-physical-ai-applications/)

`BEV Pooling` `TensorRT` `CUDA` `Autonomous Vehicles` `Nsight Compute` `FP8`

> BEV 풀링을 GPU 메모리 특성에 맞춰 최적화해 최대 42배 지연시간을 줄인 사례

#### 요약

- BEVPoolV3는 자율주행·로보틱스에서 멀티카메라 이미지를 top-down BEV(bird's-eye-view) 격자로 변환하는 BEV 풀링 연산을 최적화한 구현체
- 중복 인덱스 로드 제거, 5-배열 INT32 스캐터 맵, 런타임 정수 나눗셈 제거, interval 단위 출력 쓰기 등 4가지 개선을 적용
- 워킹셋이 L2 캐시에 들어가는지 여부(DRAM-bound vs L2-resident)에 따라 GPU별로 다른 최적화 전략이 필요함을 보여줌
- RTX A6000에서 최대 19.31배, RTX PRO 6000 Blackwell Max-Q에서 최대 42배(V2 FP16 대비) 속도 향상 달성

#### 시사점

- 단순히 커널을 최적화하는 것이 아니라 워킹셋 크기와 GPU L2 캐시 용량을 먼저 비교해 병목 유형(대역폭/명령어 발행/점유율)을 분류하는 워크플로우는 스파스 임베딩, voxelization, 히스토그램 등 다른 gather/scatter 연산에도 그대로 적용 가능
- FP8은 L2-resident 워크로드에서 큰 이득을 주지만 NVFP4는 디코드 오버헤드 때문에 오히려 느려짐 — dtype 선택이 워크로드 특성에 따라 달라짐을 보여주는 실전 사례
- DRIVE AGX Thor 같은 엣지 플랫폼에서는 FP16 개선은 잘 이전되지만 FP8 이득은 자동으로 보장되지 않아 아키텍처별 검증이 필요

#### 용어 설명

- **BEV(Bird's-Eye-View) 풀링**: 여러 카메라 이미지의 특징(feature)을 깊이 정보로 가중해 하나의 top-down(위에서 내려다본) 격자로 모으는 연산
- **Scatter-reduce**: 여러 소스 데이터를 특정 목적지 인덱스에 누적(합산)하며 흩뿌리는 연산 패턴
- **L2 캐시 / DRAM-bound**: GPU 내 상대적으로 빠른 공유 캐시(L2)와, 워킹셋이 이 캐시에 안 들어가 느린 메모리(DRAM) 접근이 병목이 되는 상태
- **TensorRT IPluginV3**: NVIDIA TensorRT에서 사용자 정의 연산(커널)을 추론 엔진에 플러그인 형태로 통합하는 인터페이스
- **Nsight Compute**: CUDA 커널의 메모리 대역폭, 점유율(occupancy), 명령어 발행 등을 분석하는 NVIDIA 프로파일링 도구
- **FP8 / NVFP4**: 8비트, 4비트 부동소수점 저정밀도 데이터 타입으로, 메모리 대역폭과 연산량을 줄이는 데 사용
- **interval-owned write**: 하나의 BEV 격자 구간(interval)을 한 스레드(owner)가 전담해 로컬 누적 후 한 번만 출력을 쓰는 방식(atomic 연산 회피)

#### 상세 내용

**BEV 풀링이 왜 병목이 되는가**

BEV 풀링은 개념적으로는 간단하지만, 불규칙한 메모리 접근, 반복적인 인덱스 읽기, scatter-reduce 동작, GPU별 캐시 특성이 겹치면서 실제 배포 시 지연시간 병목이 되기 쉽다.

- BEV 인식 파이프라인: 6대 카메라 이미지 → 깊이 정보로 3D 포인트 리프팅 → BEV 격자로 scatter-reduce → detection/occupancy/planning 등 다운스트림 작업에 공급

![Four-panel diagram of BEV pooling pipeline from multicamera images to detection, occupancy, and planning](https://developer-blogs.nvidia.com/wp-content/uploads/2026/06/bev-pooling-convert-multicamera-image-features-1.webp)
*이미지 출처: [원문](https://developer.nvidia.com/blog/accelerating-bev-pooling-on-nvidia-gpus-for-physical-ai-applications/)*

**평가 환경과 성능 결과**

두 GPU를 비교: RTX A6000(Ampere SM86, L2 6MB, FP8 미지원)과 RTX PRO 6000 Blackwell Max-Q(Blackwell SM120, L2 128MB, FP8 지원). nuScenes 샘플 기반 표준 설정(약 20.9만 개 scatter point, 채널 80, 워킹셋 49MB)에서:

- RTX PRO 6000: V2 274.0µs → BEVPoolV3 FP16 17.3µs, FP8 16.4µs
- RTX A6000: DRAM에 맞춘 BEVPoolV3 FP16 90.0µs (V2 대비 19.31배)

![Bar chart of speedup over V2 FP16 baseline across GPUs and precisions](https://developer-blogs.nvidia.com/wp-content/uploads/2026/06/canonical-speedup-bevpoolv3-1.webp)
*이미지 출처: [원문](https://developer.nvidia.com/blog/accelerating-bev-pooling-on-nvidia-gpus-for-physical-ai-applications/)*

**메모리 레짐 분류**

워킹셋(49MB)이 GPU의 L2 캐시에 들어가는지가 최적화 방향을 결정한다.

- RTX A6000(L2 6MB): 워킹셋이 L2를 초과 → DRAM-bound 경로 → 바이트 절감과 캐시 보존형 출력 쓰기 우선
- RTX PRO 6000(L2 128MB): 워킹셋이 L2에 들어감 → L2-resident 경로 → 명령어 효율, 점유율, 벡터화 로드, FP8 특화 우선

![Two stacked bar charts comparing working set size against L2 cache capacity for two GPUs](https://developer-blogs.nvidia.com/wp-content/uploads/2026/06/canonical-bev-pooling-working-set-1.webp)
*이미지 출처: [원문](https://developer.nvidia.com/blog/accelerating-bev-pooling-on-nvidia-gpus-for-physical-ai-applications/)*

**중복 스캐터 트래픽 제거**

기존 BEVPoolV2는 채널 타일을 바깥 루프로 도는 구조라 채널=80, 8채널 타일 기준으로 동일한 스캐터 인덱스를 10번 반복해서 읽어(약 25.1MB 인덱스 트래픽, 1회만 읽으면 2.51MB로 충분) 낭비가 컸다. depth-outer(깊이를 바깥 루프로) 순서로 이를 해결한 것이 CUDA-BEVFusion의 V2+DO이며, BEVPoolV3는 여기서 한 발 더 나아가:

- interval 내 중복 depth 로드 축소
- ranks_depth, ranks_feat, ranks_bev, interval_starts, interval_lengths 5개 INT32 배열로 구성된 스캐터 맵
- 런타임 정수 나눗셈을 없앤 사전 계산 인덱스
- atomic 연산 없이 interval 단위로 출력을 한 번만 쓰는 구조

12바이트 int3 구조체 대신 별도 INT32 배열을 사용해 인접 스레드들이 정렬된(aligned) 메모리 로드를 병합할 수 있게 했다.

![Stacked bar chart of analytical memory traffic comparing V2, V2+DO, V3 FP16, V3 FP8](https://developer-blogs.nvidia.com/wp-content/uploads/2026/06/analytical-memory-traffic-chart.webp)
*이미지 출처: [원문](https://developer.nvidia.com/blog/accelerating-bev-pooling-on-nvidia-gpus-for-physical-ai-applications/)*

**Interval-owned scatter-reduce 구현**

각 BEV interval을 하나의 owner 스레드가 담당해, 해당 구간의 포인트들을 순회하며 채널을 누적하고 결과를 한 번만 쓰는 구조다. 런타임에 인덱스를 재구성하지 않고 사전 계산된 5개 배열을 그대로 읽는다.

- 소형 L2 GPU(RTX A6000): 바이트 절감, FP16 half2 누적, 캐시 스트리밍 출력 저장(출력 텐서가 L2의 인덱스 데이터를 밀어내지 않도록)
- 대형 L2 GPU(RTX PRO 6000): 고점유율 launch 구성, 사전 계산 인덱스, 벡터화 인덱스 로드, FP8 특화 내부 루프

**TensorRT 플러그인 배포 및 검증**

BEVPoolV3는 TensorRT IPluginV3 연산으로 노출되며, GPU 종류와 dtype에 따라 적절한 커널을 디스패치한다. `trtexec`를 이용한 ONNX→TensorRT 빌드와 CUDA Graph replay로 벤치마크했다.

- RTX A6000: FP64 참조값 대비 atol=1e-2 기준 전 테스트 통과, 최대 오차 0.0065
- RTX PRO 6000: V2와 V3가 동일한 출력 생성 (수치적 동등성 확인)

**하드웨어별 매핑 전략**

- RTX A6000: TILE_C를 8→16으로 늘려 채널 80 기준 타일 패스를 10→5로 축소, `__half2`/`__hfma2` 누적, 캐시 스트리밍 출력. 결과: 캐노니컬 설정 기준 90.0µs (V2 FP16 1,738.0µs 대비)
- RTX PRO 6000: 고점유율 launch 유지한 채 5-배열 스캐터 맵과 사전 계산 인덱스로 명령어 오버헤드 제거. V3 FP16 17.3µs vs V2+DO FP16 37.8µs (2.18배)
- FP8: 채널별 전용 엔트리 포인트, 채널 80용 LDG.64 인덱스 패킹, 채널 128/256용 넓은 로드 사용. 루프 언롤링을 추가로 얹으면 레지스터 압박과 spill로 오히려 성능이 나빠져 조합이 안 됨

**NVFP4 실험 결과**

- Nsight Compute 프로파일링 결과: 커널이 L2에 완전히 상주, DRAM 대역폭 사용률 낮음, `smsp__issue_active`가 최대치보다 훨씬 낮음, ALU 파이프라인이 FMA 파이프라인보다 훨씬 많은 명령어 처리
- 결론: NVFP4는 Tensor Core의 `MMA.kind::nvfp4`를 활용하는 연산 집약적 행렬곱에는 강력하지만, L2-resident scatter-reduce 워크로드에는 FP8이 더 적합

### [Maximize AI Factory Energy Efficiency Through Full-Stack Inference and Training Optimizations](https://developer.nvidia.com/blog/maximize-ai-factory-energy-efficiency-through-full-stack-inference-and-training-optimizations/)

#### 요약

- MoE(Mixture-of-Experts) 모델은 토큰마다 일부 전문가만 활성화되어 동일 파라미터 수의 밀집 모델보다 에너지 효율이 높다.

#### 시사점

- 모델 아키텍처(MoE), 정밀도(NVFP4), 배치 크기 등을 조정하는 것만으로 동일 전력 예산 내에서 더 많은 토큰을 생성하고 비용을 낮출 수 있다.
- 학습 단계에서 GPU별 처리 속도를 critical path에 맞춰 조정하면 종단간 학습 시간 변화 없이 에너지 낭비를 줄일 수 있어, 절감된 전력을 추가 학습이나 추론에 재배치할 수 있다.
- DSX 같은 팩토리 스케일 플랫폼을 활용하면 인프라 설계 단계의 시뮬레이션과 런타임 텔레메트리를 연결해 유휴 전력(stranded power)을 찾아내고 운영 효율을 지속적으로 개선할 수 있다.

#### 용어 설명

- **MoE (Mixture-of-Experts)**: 입력 토큰마다 전체 파라미터 중 일부 "전문가" 서브네트워크만 활성화하는 모델 구조로, 동일 지능 수준 대비 연산량이 적다.

- **PUE (Power Usage Effectiveness)**: 데이터센터가 소비하는 총 전력 대비 실제 컴퓨팅에 쓰이는 전력의 비율로, 낮을수록 효율적이다.
- **Critical path**: 파이프라인 내에서 가장 느린 작업 체인으로, 전체 완료 시간을 결정짓는 병목 구간.

### [Boost Inference Performance up to 15x on NVIDIA Blackwell Using DFlash Speculative Decoding](https://developer.nvidia.com/blog/boost-inference-performance-up-to-15x-on-nvidia-blackwell-using-dflash-speculative-decoding/)

`DFlash` `Speculative Decoding` `NVIDIA Blackwell` `TensorRT-LLM` `SGLang` `vLLM`

> 블록 확산 드래프터로 LLM 추론 속도를 Blackwell에서 최대 15배 높이는 DFlash

#### 요약

- DFlash는 블록 확산(block-diffusion) 방식의 경량 드래프트 모델로 speculative decoding을 가속하는 오픈소스 기법이다.
- NVIDIA Blackwell에서 gpt-oss-120b 기준 동일 인터랙티비티(interactivity) 대비 최대 15배 처리량 향상, EAGLE-3 대비도 1.5배 높은 성능을 보인다.
- Llama 3.1 8B에서는 동일 동시성(concurrency)에서 EAGLE-3 대비 인터랙티비티를 거의 2배로 끌어올린다.
- Hugging Face에 20개 DFlash 체크포인트(Qwen, Kimi K2.6, Llama, Gemma, gpt-oss 등)와 Blackwell/Hopper용 레시피가 공개되어 있고, SGLang·vLLM·TensorRT-LLM에서 바로 사용 가능하다.

#### 시사점

- 코드 애플리케이션 리팩토링 없이 기존 vLLM/SGLang 설정에서 드래프트 모델만 DFlash 체크포인트로 교체하면 되므로 도입 장벽이 낮다.
- 에이전트형 코딩·추론 워크로드처럼 사용자당 지연시간(latency)을 유지하면서 동시 사용자 수를 늘려야 하는 서비스에 특히 유리하다.
- Blackwell의 병렬 연산 자원을 더 잘 활용하게 해줘, 동일 하드웨어로 더 많은 동시 요청을 처리할 수 있다.

#### 용어 설명

- **Speculative Decoding**: 작은 드래프트 모델이 미래 토큰을 미리 제안하고, 큰 타깃 모델이 이를 병렬로 검증해 생성 속도를 높이는 기법.
- **Block-diffusion Drafting**: 토큰을 하나씩 순차 생성하는 대신, 마스킹된 토큰 블록 전체를 한 번의 forward pass로 예측하는 방식.
- **Interactivity**: 사용자 1인당 초당 생성 토큰 수(tokens/sec per user)로 측정되는 응답 체감 속도 지표.
- **EAGLE-3**: 기존 최신 speculative decoding 기법으로, DFlash와 비교 기준으로 사용됨.
- **KV Injection**: 타깃 모델의 컨텍스트 특징을 드래프트 모델의 key-value 프로젝션에 주입해 토큰 수용률(acceptance rate)을 높이는 기법.
- **NVFP4**: NVIDIA Blackwell이 지원하는 저정밀 부동소수점 연산 포맷으로 고밀도 컴퓨팅에 사용됨.

#### 상세 내용

**DFlash의 Blackwell 성능**

TensorRT-LLM 기반 8-GPU NVIDIA DGX B300 시스템에서 SPEED-Bench 코딩 데이터셋으로 측정한 결과, DFlash는 오토리그레시브(autoregressive) 디코딩 대비 생산 환경에 적합한 지연시간 구간에서 전반적으로 더 높은 처리량을 제공한다.

![Line graph titled "DFlash Delivers Up to 15x Higher Throughput on NVIDIA Blackwell at the Same Interactivity" showing throughput-interactivity Pareto curve for gpt-oss-120b with DFlash on eight NVIDIA DGX B300 GPUs using TensorRT-LLM.](https://developer-blogs.nvidia.com/wp-content/uploads/2026/06/dflash-throughput-nvidia-blackwell.webp)
*이미지 출처: [원문](https://developer.nvidia.com/blog/boost-inference-performance-up-to-15x-on-nvidia-blackwell-using-dflash-speculative-decoding/)*

- 사용자당 500~600 tokens/sec의 고인터랙티비티 구간에서, 오토리그레시브 대비 15배 이상, EAGLE-3 대비 1.5배 높은 처리량을 기록했다.
- 배치 크기 1(최저 동시성)에서는 인터랙티비티가 2배 이상 향상됐다.
- Blackwell Ultra GPU는 두 개의 레티클(reticle) 크기 다이를 10TB/s 칩투칩 인터커넥트로 연결해 160개 SM, 640개 5세대 Tensor Core를 하나의 컴퓨팅 도메인으로 구성하는데, DFlash의 블록 병렬 드래프팅이 15 PFLOPS급 NVFP4 연산 자원을 더 잘 활용하게 해준다.

데이터셋별 동시성 매칭 비교에서도 DFlash가 EAGLE-3보다 일관되게 높은 속도 향상을 보였다(코딩 2.6x vs 1.8x, RAG 2.3x vs 1.7x 등, gpt-oss-120b 기준 평균 2.3x vs 1.7x).

**프레임워크 통합: vLLM, SGLang, TensorRT-LLM**

UC San Diego 연구팀이 2026년 2월 논문으로 발표한 DFlash는 PyTorch와 네이티브 CUDA로 구현됐으며, NVIDIA와 오픈소스 커뮤니티의 협력으로 SGLang·vLLM에 통합됐다.

- vLLM에서는 오픈소스 Speculators 라이브러리를 통해 DFlash 드래프터가 타깃 모델의 hidden state와 연결되며, 설정값 변경만으로 EAGLE-3를 DFlash로 교체할 수 있다. Gemma 4 31B(단일 Blackwell Ultra GPU) 기준 오토리그레시브 대비 최대 5.8배 처리량 향상.
- SGLang에서는 speculative decoding 알고리즘을 DFlash로 지정하고 해당 체크포인트만 지정하면 된다. Qwen3 8B(단일 Blackwell GPU) 기준 오토리그레시브 대비 최대 5.1배 처리량 향상.
- Hugging Face에 공개된 20개 체크포인트는 Qwen, Kimi K2.6, Llama, Gemma, gpt-oss 등 다양한 모델 계열을 커버한다.

**DFlash의 동작 원리**

speculative decoding은 드래프팅과 검증 두 단계로 구성된다. 기존 방식은 드래프트 모델도 오토리그레시브하게 순차 생성하므로, 추측 토큰 수가 늘어날수록 드래프팅 비용도 증가해 처리량 향상에 한계가 있다.

![Gif comparing EAGLE 3-style speculative decode (left) versus Dflash block-diffusion decode (right).](https://developer-blogs.nvidia.com/wp-content/uploads/2026/06/speculative-decode-eagle-versus-dflash.gif)
*이미지 출처: [원문](https://developer.nvidia.com/blog/boost-inference-performance-up-to-15x-on-nvidia-blackwell-using-dflash-speculative-decoding/)*

DFlash는 다음 세 가지 핵심 기법을 결합한다.

- **Block-diffusion drafting**: 여러 미래 토큰을 한 번의 forward pass로 병렬 예측.
- **Target hidden-state conditioning**: 타깃 모델에서 추출한 컨텍스트 특징을 드래프터가 활용.
- **KV injection**: 타깃 모델의 컨텍스트 특징을 드래프트 모델의 레이어별 key-value 프로젝션에 주입해 높은 토큰 수용률을 유지.

타깃 모델이 여전히 검증을 수행하므로 DFlash는 타깃 모델의 출력 분포를 그대로 유지하면서 생성 속도만 가속한다.

**대상 독자**: 에이전트형 코딩·RAG·추론 등 낮은 지연시간과 높은 동시성이 동시에 필요한 LLM 서빙 시스템을 운영하며, vLLM·SGLang·TensorRT-LLM 등에서 speculative decoding 최적화를 적용하려는 인프라/ML 엔지니어에게 유용하다.

### [Build an AI Scientist for Life Science Discovery with NVIDIA BioNeMo Agent Toolkit](https://developer.nvidia.com/blog/build-an-ai-scientist-for-life-science-discovery-with-nvidia-bionemo-agent-toolkit/)

`NVIDIA BioNeMo` `NIM` `AI Agent` `Drug Discovery` `MCP` `BioNeMo Skills`

> AI 에이전트가 신뢰성 있게 생물학 모델을 다루도록 돕는 BioNeMo 툴킷

#### 요약

- NVIDIA BioNeMo는 일반 AI 에이전트가 단백질 접힘, 분자 도킹, 서열 설계 등 생물학 전문 모델을 정확히 호출·해석할 수 있도록 "BioNeMo Skills"라는 도구 인터페이스를 제공한다.
- NIM(가속 모델 서비스)과 Skills(에이전트용 사용 설명서)가 결합되어 에이전트가 올바른 모델 선택, 입력 준비, 결과 해석까지 수행할 수 있다.
- 벤치마크 결과, Skill을 사용한 에이전트는 작업 완료율이 57.1%에서 100%로 향상되었고, 토큰 대비 성공률(passing assertions)은 평균 2배 개선되었다.
- 호스팅형(NIM 엔드포인트)과 로컬 배포를 상황에 맞게 선택할 수 있으며, 반복 호출이 많은 워크플로우는 로컬 배포가 유리하다.

#### 시사점

- 범용 코딩 에이전트를 특정 과학 도메인에 투입할 때, 도메인 지식이 담긴 도구 명세(Skill)가 정확도와 효율성에 결정적 영향을 미친다는 것을 실증적으로 보여준다.
- MCP(Model Context Protocol) 래퍼를 통해 아직 NIM으로 패키징되지 않은 오픈 모델도 동일한 에이전트 호출 패턴으로 통합할 수 있어 확장성이 크다.
- 개발자는 이 패턴(모델을 문서화된 콜러블 리소스로 감싸기)을 다른 전문 도메인의 에이전트 툴 설계에도 참고할 수 있다.

#### 용어 설명

- **NVIDIA NIM**: 최적화된 AI 모델을 컨테이너화된 API 서비스로 배포하는 NVIDIA의 마이크로서비스 플랫폼.
- **BioNeMo Skills**: 각 생물학 모델의 용도, 입력, 파라미터, 예상 출력, 실패 모드를 문서화해 에이전트가 올바르게 호출하도록 돕는 인터페이스.
- **MCP(Model Context Protocol)**: 에이전트가 외부 도구·모델을 표준화된 방식으로 호출할 수 있게 하는 프로토콜.
- **분자 도킹(Molecular Docking)**: 리간드(작은 분자)가 단백질 표적에 어떻게 결합하는지 예측하는 계산 기법.
- **MSA(Multiple Sequence Alignment)**: 여러 단백질/DNA 서열을 정렬해 진화적 관계나 구조적 특징을 파악하는 기법.
- **cuEquivariance / Parabricks**: 각각 구조 예측 모델, 유전체학(genomics) 연산을 가속하는 NVIDIA 라이브러리.
- **Boltz-2, OpenFold3, DiffDock, GenMol, ProteinMPNN, RFdiffusion, Evo 2**: 단백질 구조 예측, 도킹, 분자 생성, 서열 설계 등에 쓰이는 대표적 생물학 AI 모델들.

#### 상세 내용

**문제 배경: 일반 에이전트와 과학 발견의 간극**

과학적 발견은 소프트웨어 개발처럼 테스트가 통과하면 끝나는 문제가 아니다. 반복적이고 불확실하며 물리적 현실에 근거해야 한다.

- 일반 코딩 에이전트를 생물학에 투입해도 새로운 신약이 저절로 나오지 않는다.
- 에이전트는 단백질 접힘, 도킹, 서열 설계 등이 관련 있다는 것은 알아도, 어떤 모델을 어떻게 호출하고 결과를 어떻게 해석할지는 모른다.
- BioNeMo는 가속 생물학 스택(NIM, 오픈 모델)을 에이전트가 쓸 수 있는 도구로 바꿔 이 간극을 메운다.

**AI 과학자 구축 4단계**

1. **과학적 워크플로우 계획**: 예를 들어 MMseqs2로 MSA 생성 → Boltz-2/OpenFold3로 펩타이드 접힘 → GenMol로 분자 생성 → DiffDock으로 리간드-단백질 도킹 같은 단계를 정의한다.
2. **에이전트를 플랫폼에 연결**: 단일 엔드포인트가 아니라 [bionemo-agent-toolkit 저장소](https://github.com/NVIDIA-BioNeMo/bionemo-agent-toolkit) 전체를 탐색하게 하여 사용 가능한 기능을 파악시킨다.
3. **호스팅형 vs 로컬 배포 선택**: 인프라 관리 없이 빠르게 접근하려면 호스팅형 NIM 엔드포인트가 유리하고, 반복 호출이 많거나 낮은 지연시간·데이터 로컬리티가 필요하면 로컬 배포가 낫다. 내부 테스트에서는 단일 GPU에서 반복 호출 워크로드를 로컬로 옮기자 웜(warm) 호출당 지연시간이 줄었다.
4. **Skill을 통한 모델 사용**: 모든 BioNeMo Skill(OpenFold3, Boltz-2, DiffDock, GenMol, ProteinMPNN, MSA Search, RFdiffusion, Evo 2 등)에 동일한 프롬프트 구조를 적용할 수 있다. 예: `Use the OpenFold3 BioNeMo Skill to fold MKTVRQERLKSIVR with the NVIDIA API endpoint at https://build.nvidia.com/openfold3`

**성능 측정: Skill 유무에 따른 차이**

BioNeMo NIM은 단순 래퍼가 아니라 실제로 빠르고 프로덕션에 바로 쓸 수 있는 가속 마이크로서비스다. 저자들은 동일 에이전트에 Skill을 주었을 때와 주지 않았을 때를 비교했다.

- Skill 없이는 작업 성공률 57.1%에 그치지만, Skill이 있으면 100% 성공한다.
- 토큰 효율성(1k 토큰당 통과한 assertion 수) 측면에서 Skill 사용 시 평균 2배 개선되었다.
- 모든 지표는 Codex CLI + GPT-5.5 fast로 측정했으며, BioNeMo NIM Skill은 에이전트 종류에 관계없이(agent-agnostic) 설계되어 다른 백엔드에서도 유사한 성능이 기대된다고 밝혔다.

**문제 해결 팁**

- SR-MPLS 백본망의 이상 탐지·복구, 무선 PHY/MAC 알고리즘 설계 등 실제 워크플로 사례를 통해 개념을 구체화한다.

#### 시사점

- 반복 작업 자동화를 넘어, 알려지지 않은 문제를 스스로 조사·검증·실행하는 에이전트 아키텍처 설계 패턴을 통신 외 다른 인프라 운영 도메인에도 참고할 수 있다.
- 심층 리서치 에이전트가 단일 정답 대신 트레이드오프가 명시된 복수의 실행 계획을 제시하는 구조는, 고위험 운영 자동화 시 인간 승인 절차를 설계하는 데 참고할 만하다.

#### 용어 설명

- **TM Forum 자율 네트워크 레벨**: 통신 업계 표준 단체가 정의한 네트워크 자동화 성숙도 지표(레벨 0~5, 레벨 5가 완전 자율).

- **SR-MPLS**: 통신사 백본망에서 트래픽 경로를 제어하는 세그먼트 라우팅 기반 프로토콜.

- **MCP(Model Context Protocol)**: 에이전트가 외부 도구·시스템에 표준화된 방식으로 접근하도록 하는 프로토콜.

### [CCCL Runtime: A Modern C++ Runtime for CUDA](https://developer.nvidia.com/blog/cccl-runtime-a-modern-c-runtime-for-cuda/)

`CUDA` `CCCL` `C++` `GPU Programming` `NVIDIA CUDA Toolkit`

> CUDA 13.2부터 도입된 새로운 C++ 런타임 API로 더 안전한 GPU 프로그래밍 제공

#### 요약

- CCCL(CUDA Core Compute Libraries)에 CUDA 13.2부터 포함된 새로운 C++ API 그룹 "CCCL runtime"을 소개
- 기존 CUDA runtime API와 마찬가지로 CUDA driver API 위에 구축되지만, 스트림·메모리·커널 실행을 명시적 의존성과 강타입으로 다루도록 재설계됨
- 스트림 순서(stream-ordered) 메모리 할당을 기본값으로 채택하고, 예외 기반 오류 처리와 컴파일타임 설정 정보를 커널 코드로 전달하는 메커니즘을 도입
- 기존 CUDA runtime API와 상호운용 가능해 점진적 도입이 가능함

#### 시사점

- 여러 라이브러리가 동일한 디바이스·스트림·메모리를 공유하는 복잡한 CUDA 프로그램에서, 암묵적 전역 상태(현재 디바이스, 기본 스트림 등)로 인한 버그를 컴파일 타임에 잡아낼 수 있음
- `CUDA_CHECK_ERROR` 매크로나 `cudaGetLastError()` 누락으로 인한 에러 미탐지 문제를 예외 처리로 해결해 코드 가독성과 안전성이 향상됨
- 커널 함수 시그니처가 실제 디바이스 측 데이터 사용 방식(`span` 등)을 그대로 반영해 코드 이해가 쉬워짐

#### 용어 설명

- **CCCL(CUDA Core Compute Libraries)**: CUDA 개발자를 위한 C++/Python 추상화 라이브러리 모음
- **CUDA driver API / runtime API**: CUDA driver API는 저수준 GPU 제어 인터페이스, runtime API는 그 위에 만들어진 편의 계층
- **스트림(stream)**: GPU 상에서 순서대로 실행되는 작업 큐. 여러 스트림을 병렬로 사용해 비동기 실행을 구현
- **메모리 풀(memory pool)**: 반복적인 GPU 메모리 할당/해제 비용을 줄이기 위해 미리 확보한 메모리 영역을 재사용하는 방식
- **stream-ordered allocation**: 메모리 할당·해제를 특정 스트림의 실행 순서에 맞춰 비동기로 수행하는 방식
- **커널 functor**: `__global__` 함수 대신 `__device__` 호출 연산자를 가진 구조체로 정의한 커널. 템플릿 인자가 자동으로 추론됨
- **trivially copyable**: 단순 메모리 복사만으로 값 복사가 가능한 C++ 타입 특성으로, CUDA 커널 인자로 넘길 수 있는 조건

#### 상세 내용

**CCCL runtime이란**

CCCL runtime은 CUDA 13.2부터 사용 가능한 새로운 C++ API 세트로, 스트림 관리, 메모리 할당, 커널 실행 등 CUDA의 핵심 기능을 담당한다. 기존 CUDA runtime API와 마찬가지로 CUDA driver API 위에 구축되지만, 모던 C++ 기능을 활용해 더 견고한 추상화를 제공한다.

- `<cuda/stream>`, `<cuda/buffer>`, `<cuda/launch>` 등의 헤더 형태로 제공
- 20년간의 CUDA 발전 과정에서 얻은 교훈을 API 설계에 반영
- 기존 CUDA runtime API와 호환 헬퍼를 제공해 점진적 도입 가능

![Both CCCL runtime API and CUDA runtime API are built on top of the CUDA driver API. Both runtimes are also easily interoperable with each other](https://developer-blogs.nvidia.com/wp-content/uploads/2026/06/image1-9.webp)
*이미지 출처: [원문](https://developer.nvidia.com/blog/cccl-runtime-a-modern-c-runtime-for-cuda/)*

**디바이스와 스트림: 명시적 의존성**

기존 CUDA runtime API는 `cudaStreamCreate`로 스트림을 생성할 때 "현재(current)" 디바이스에 암묵적으로 연결된다. 반면 CCCL runtime은 `cuda::stream stream{device};`처럼 디바이스를 생성자 인자로 명시적으로 전달한다.

- 디바이스는 `device_ref`, 스트림은 객체로 표현되어 정수나 포인터 대신 강타입을 사용 → 실수를 컴파일 타임에 검출
- 암묵적 전역 상태 대신 명시적 의존성을 사용해 함수만 봐도 동작을 파악 가능(로컬 추론), 여러 라이브러리 간 상태 충돌 방지
- 기본 스트림(default stream) 개념이 없으며, 모든 CCCL runtime 스트림은 non-blocking으로 생성됨

**소유 타입과 참조 타입**

`std::string`/`std::string_view` 패턴처럼 CUDA 객체마다 소유 타입과 `_ref` 접미사가 붙은 비소유 참조 타입이 존재한다.

- `cuda::stream`은 `cudaStream_t` 핸들을 소유하고 소멸자에서 해제, `cuda::stream_ref`는 소유권 없이 핸들만 참조
- `cudaStream_t`는 `cuda::stream_ref`로 암묵적 변환되어 기존 코드와 상호운용 가능
- `from_native_handle()`로 raw 핸들을 소유 타입으로 감싸고, `.release()`로 소유권 반환

**메모리 할당: 스트림 순서 기반 기본값**

`cuda::make_buffer<int>(stream, pool, num_elements, ...)` 형태로 비동기 메모리 할당과 초기화를 수행한다.

- 스트림을 첫 인자로 받는 API는 스트림 순서로 동작한다는 규칙을 일관되게 적용(동기 버전은 별도 제공하지 않음)
- CUDA 11.2부터 제공된 스트림 순서 메모리 관리(메모리 풀 기반)를 기본값으로 채택, CUDA 13.0에서 managed/host 메모리까지 확장됨
- 오래된 CUDA 버전에서는 non-stream-ordered 할당을 폴백으로 제공하지만 향후 제거 예정
- 초기화는 기본적으로 필수이며, `cuda::no_init`으로 명시적으로만 생략 가능(초기화되지 않은 메모리로 인한 버그 방지)
- 버퍼는 생성 시 전달된 스트림을 저장해 소멸 시 해당 스트림에서 `cudaFreeAsync`를 호출하며, `.set_stream()`이나 `.destroy()`로 재정의 가능

**커널 실행**

`cuda::launch(stream, config, kernel{}, A, B, C);` 형태로 커널을 구성하고 실행한다.

- `cuda::distribute<threads_per_block>(num_elements)`가 필요한 스레드 수를 채우는 설정 객체를 생성해 `(N + block_size - 1) / block_size` 같은 관용구를 대체
- 컴파일타임 정보(블록 크기 등)가 설정 객체의 타입에 인코딩되어 디바이스 코드로 자동 전달되며, `cuda::gpu_thread.rank()` 같은 계산에서 런타임 조회를 생략 가능
- `static_assert`를 통해 커널 구현이 가정하는 그리드/블록 형태를 컴파일 타임에 검증 가능

**커널 functor와 인자 자동 변환**

`__device__` 호출 연산자를 가진 구조체(kernel functor)를 `__global__` 함수 대신 사용할 수 있다.

- functor는 인자로부터 템플릿 타입이 자동 추론되지만, 기존 `__global__` 함수는 명시적 템플릿 인스턴스화가 필요
- `cuda::buffer`를 `cuda::launch`에 전달하면 자동으로 `cuda::std::span`으로 변환되어 수동 포인터 추출이 불필요

**오류 처리**

CCCL runtime은 예외 기반 오류 처리를 사용해 `cudaGetLastError()` 누락이나 반환값 미확인으로 인한 오류 무시를 방지하며, `CUDA_CHECK_ERROR` 매크로 없이 코드가 더 간결해진다.

**앞으로의 계획**

CCCL runtime API는 CUDA Toolkit 13.2 이상과 함께 배포되는 CCCL 3.2부터 사용 가능하다. 이벤트 관리, 데이터 이동, 동적 공유 메모리 등 추가 기능은 CCCL 문서에서 다룬다.

**대상 독자**: CUDA C++로 커널을 직접 작성하거나 여러 라이브러리가 GPU 자원을 공유하는 복잡한 프로그램을 개발하는 개발자에게 유용하며, 명시적 리소스 관리와 컴파일 타임 안전성을 원하는 경우 특히 도움이 된다.

- YAML 설정과 C++/Python API로 저수준 네트워킹 복잡성을 추상화해 개발자가 커스텀 추론·필터링 로직에만 집중 가능

#### 용어 설명

- **HL-LHC (High-Luminosity Large Hadron Collider)**: CERN 대형 강입자 충돌기의 고광도 업그레이드
- **FPGA**: 하드웨어 회로를 프로그래밍으로 재구성할 수 있는 반도체 칩
- **NIC**: 네트워크 연결을 담당하는 하드웨어 카드

#### 상세 내용

**배경: 데이터 병목의 이동**

과거 AlphaFold2는 50년간 축적된 약 17만 개 단백질 구조 데이터를 기반으로 성공했지만, 현대 센서·검출기는 훨씬 빠른 속도로 데이터를 생성한다. LCLS-II는 1MHz 반복률로 광자 펄스를 생성하는 등 출력 속도가 계속 증가하며, 병목이 "데이터 부족"에서 고속·단시간 데이터를 다루도록 설계되지 않은 "수집-저장-분석" 구조 자체로 옮겨가고 있다.

- DAQIRI는 데이터 소스에서 전처리를 수행하는 적응형 파이프라인으로 전환해 정보 손실을 줄이고 발견까지의 경로를 가속화

**DAQIRI 개요**

하드웨어 중심의 경직된 설계 대신 소프트웨어 중심의 유연한 데이터 수집 아키텍처를 제공한다.

- Holoscan(실시간 멀티모달·멀티레이트 처리), TensorRT(실시간 추론), nvCOMP(스트리밍 압축)와 연동하거나 커스텀 계측 소프트웨어에도 직접 스트리밍 가능
- ConnectX NIC를 갖춘 엣지 슈퍼컴퓨팅 시스템(DGX Spark, IGX Platform, RTX Pro Server, VR200 등)으로 스트리밍해 실험을 지속적으로 모니터링하고 조건 변화에 즉시 대응

**사례: CERN A-GHOST 프로젝트**

HL-LHC 업그레이드는 기존 대비 광도를 10배 높이며, ATLAS 검출기의 2단계 선택 시스템도 대역폭이 확대된다(1단계 100kHz→1MHz, 2단계 1kHz→10kHz).

- 이 증가된 처리율에서도 전체 충돌의 99% 이상은 여전히 온라인 시스템에서 버려짐
- A-GHOST는 DAQIRI를 활용해 폐기되는 데이터 스트림에 AI 기반 검색을 적용, FPGA 기반 하드웨어 보드와 GPU 처리 팜을 스트리밍 링크로 연결
- CERN Openlab, 시카고대, UCL 연구진이 주도하며 Convolutional Auto-Encoder, temporal CNN, transformer 기반 모델을 프로토타입 하드웨어로 테스트할 계획

**내부 동작 원리**

수백 Gbps 이상의 라인레이트로 UDP, RoCE v2 등 고대역폭 이더넷 트래픽을 처리하며, 리눅스 커널을 완전히 우회한다.

- DPDK로 제로카피 접근을 구현해 NIC 데이터를 GPU DMA 버퍼로 직접 라우팅, 지연시간과 CPU 오버헤드를 감소시킴

주요 기능:
- 고처리량·저지연: 적절한 하드웨어/CPU-NUMA 튜닝으로 인터페이스 라인레이트 달성
- 커스텀 수신 처리: 자동 패킷 재정렬, 데이터 타입 변환, 하드웨어 기반 플로우 스티어링
- 제로 메모리 카피: NIC 링버퍼에서 GPU 텐서로 직접 접근, 지연시간을 PCIe 전송 시간 수준으로 유지
- YAML 기반 설정: 최적화된 네트워크 설정을 손쉽게 구성
- 유연한 데이터 이동 백엔드: Linux Sockets, DPDK, RoCEv2 지원
- C++/Python API: 몇 시간이 아닌 몇 분 만에 실시간 애플리케이션 구축 가능

**DAQIRI 워크스루**

YAML 설정 파일로 사용할 NIC, GPU, 패킷 필터링 방식, 페이로드 조립 방식을 애플리케이션 실행 전에 정의한다.

- `rx_packets`(원시 패킷용 GPU 메모리)와 `rx_tensor`(재정렬 완료된 텐서용 메모리) 영역을 지정하고, 1024개 패킷을 배치로 묶어 텐서를 생성
- 재정렬 단계에서 int4 → fp16 같은 데이터 타입 변환도 동시에 수행할 수 있어 별도 언패킹 과정이 불필요
- 플로우 규칙으로 특정 UDP 스트림만 필터링해 해당 수신 큐로 전달
- 애플리케이션 코드는 `daqiri_init()`으로 초기화한 뒤 `get_rx_burst()`로 재정렬된 GPU 텐서를 받아 바로 모델·커널에 전달하는 몇 줄로 단순화됨

**대상 독자**: 고속 센서·검출기 데이터를 다루는 과학 계측 시스템 개발자, 실시간 AI 추론 파이프라인을 구축하려는 엔지니어, 대규모 실험 데이터 처리 인프라를 설계하는 연구자에게 유용하다.

### [Building AI Agents for AR Glasses and XR Devices with NVIDIA XR AI](https://developer.nvidia.com/blog/building-ai-agents-for-ar-glasses-and-xr-devices-with-nvidia-xr-ai/)

- 미디어 전송, 모델 서비스, 도구 접근, 에이전트 오케스트레이션, 클라이언트 전달을 모듈화해 컴포넌트 교체가 자유롭고, 다중 사용자·다중 에이전트 시나리오도 지원

#### 시사점

- 카메라·음성·엔터티티 데이터를 직접 통합하는 저수준 작업 없이, 검증된 아키텍처 위에서 XR용 멀티모달 에이전트를 빠르게 프로토타이핑 가능
- MCP 기반 표준 인터페이스로 사내 시스템(RAG, 데이터베이스, 디지털 트윈 등)을 손쉽게 연동할 수 있어, 현장 작업자 지원·원격 지원 등 hands-busy 환경의 실전 애플리케이션 개발에 유용

#### 용어 설명

- **XR (Extended Reality)**: AR·VR·MR을 아우르는 확장현실 기술의 통칭
- **VLM (Vision-Language Model)**: 이미지와 텍스트를 함께 이해하고 추론하는 AI 모델
- **MCP (Model Context Protocol)**: AI 에이전트가 외부 도구·데이터 소스에 접근할 수 있게 하는 표준 연동 프로토콜

- **NVIDIA Nemotron**: 언어 이해·추론·도구 호출을 담당하는 NVIDIA의 LLM 계열
- **NeMo Agent Toolkit**: 여러 모델과 도구를 오케스트레이션해 에이전트 워크플로우를 구성하는 프레임워크
- **CloudXR**: GPU 인프라에서 렌더링된 공간 콘텐츠를 XR 기기로 스트리밍하는 NVIDIA 기술

#### 상세 내용

**개발자가 마주한 인프라 공백**

AR 글래스나 웨어러블 기기용 하드웨어는 이미 준비돼 있지만, 실제 AI 경험을 만들려면 실시간 카메라·마이크 스트림, 멀티모달 모델, 엔터프라이즈 데이터, 도구 호출, 배포 인프라, 기기별 런타임을 모두 통합해야 하는 부담이 있다. XR AI는 이 통합 작업을 표준화된 재사용 기반으로 해결하려는 시도다.

**아키텍처 구성**

XR Media Hub가 카메라 프레임, 마이크 오디오, 데이터 메시지를 받아 필요한 모델·도구·에이전트로 라우팅한다.

- **NVIDIA Cosmos**: 시각적 맥락 이해(visual grounding) 담당
- **NVIDIA Nemotron**: 언어 이해·추론·도구 호출 담당
- **MCP 서버**: 엔터프라이즈 도구와 데이터 소스 노출
- **NeMo Agent Toolkit** 등 에이전트 프레임워크: 모델·도구 간 워크플로우 오케스트레이션
- **NVIDIA CloudXR**: 풍부한 3D 상호작용이 필요할 때 렌더링된 공간 콘텐츠 추가

영상 픽셀은 공유 메모리에 유지하고 가벼운 메타데이터만 시스템을 순회하도록 설계해, 작업이 실제로 필요할 때만 에이전트가 이미지 데이터를 가져오게 함으로써 불필요한 모델 추론과 데이터 이동을 줄인다. 참가자 식별(participant identity)이 라우팅 경계 역할을 해 다중 클라이언트·다중 에이전트 시나리오도 하나의 기반으로 지원한다.

**시작하기: 6단계 구축 과정**

1. **저장소 클론**: GitHub 저장소(`NVIDIA/xr-ai`)에는 샘플 에이전트, 모델 서버 런처, MCP 서버, 웹 클라이언트, 핵심 미디어 인프라가 포함됨
2. **AI 서비스 시작**: 모델 서버 스택은 다음을 포함
   - `nvidia/parakeet-tdt-0.6b-v3` (음성 인식)
   - `nvidia/Cosmos-Reason1-7B` (시각-언어 추론)
   - `nvidia/Llama-3.1-Nemotron-Nano-8B-v1` (빠른 지연 시간 언어 응답)
   - `NVIDIA-Nemotron-3-Nano-30B-A3B` (심층 도구 호출 워크플로우)
   
   `agent-sdk/xr-ai-models` 패키지가 `llm`, `agent_llm`, `vlm`, `stt`, `tts` 같은 논리적 서비스를 설정으로 참조하게 해, 엔드포인트 교체나 클라우드 호스팅 모델, OpenAI 호환 API 사용이 코드 변경 없이 가능
3. **센서 기반 XR 에이전트 실행**: `simple-vlm-example`을 실행하면 카메라·마이크·데이터 메시지 스트리밍 → XR Media Hub 라우팅 → 음성-텍스트 변환 → Cosmos 기반 VLM으로 최신 프레임 분석 → 응답 생성 → 텍스트+음성 합성 반환까지 전체 흐름이 동작
4. **MCP로 엔터프라이즈 데이터 연결**: `vlm-mcp`(시각 질의응답), `video-mcp`(영상 분석), `render-mcp`(장면 조작), `oxr-mcp`(OpenXR 공간 정보), `vec-mcp`(벡터·공간 유틸리티), `transcript-mcp`(트랜스크립트 수집·검색) 등 XR 전용 MCP 서버 제공. NVIDIA Video Search and Summarization(VSS) 같은 기술과 결합해 절차·점검·유지보수 활동을 색인·요약·검색 가능한 시각 지식 베이스로 축적 가능
5. **에이전트 오케스트레이션 추가**: NeMo Agent Toolkit의 `mcp_client` 패턴으로 XR AI MCP 서버가 노출하는 도구를 `react_agent` 워크플로우가 탐색하도록 구성하는 YAML 예시 제공
6. **CloudXR 기반 공간 경험 추가**: `xr-render-demo`는 XR Media Hub, CloudXR 런타임, 모델 서비스, MCP 서버, 에이전트 워커를 함께 실행. 에이전트가 MCP를 통해 렌더링 도구를 호출해 사용자의 공간 환경 내 객체를 생성·수정할 수 있으며, 작은 모델이 즉각 응답을, 큰 모델이 심층 추론을 담당하는 하이브리드 패턴도 시연

**대상 독자**: 필드 서비스, 원격 지원, 산업 운영, 헬스케어, 교육 훈련 등 hands-busy 환경을 위한 AR/XR 에이전트를 만들려는 개발자, 그리고 멀티모달 AI와 엔터프라이즈 도구 연동을 XR 기기에 통합하려는 팀에 유용하다.

- NVIDIA의 개발자 예제는 원시 거래 로그부터 파운데이션 모델(대량의 데이터로 미리 학습해 다양한 작업에 재사용하는 범용 모델) 학습, 임베딩 추출, 다운스트림 사기 분류기 증강까지 5단계 파이프라인을 GPU로 가속해 제공한다.

- cuDF·cuML 기반 GPU 도메인 토크나이저는 거래당 토큰 수를 범용 BPE 토크나이저의 39개에서 12개로 줄이고, 어휘 크기도 50,257개에서 6,251개로 축소해 동일 토큰 예산으로 3배 이상 긴 거래 이력을 다룰 수 있게 한다.
- 약 2,900만 파라미터의 디코더 전용 트랜포머(Llama 구조)를 NeMo AutoModel로 사전학습하며, 단일 GPU 스크립트를 그대로 다중 GPU·다중 노드로 확장 가능하다.

#### 시사점

- 수작업 특징 엔지니어링과 규칙 기반 시스템에 의존하던 금융 거래 데이터 분석을, 사전학습된 트랜스포머 임베딩으로 대체·보강할 수 있는 실전 레퍼런스를 제공한다.
- 하나의 백본 모델로 사기 탐지, 신용 평가, 고객 생애가치 예측, 세그멘테이션, 추천 등 여러 다운스트림 작업에 재사용 가능해 반복 개발 비용을 줄인다.
- 토크나이저·모델 아키텍처·다운스트림 헤드가 각각 독립적으로 교체 가능하게 설계되어, 다른 거래 스키마나 라벨(이탈 예측, 신용 평가 등)로 쉽게 확장할 수 있다.

#### 용어 설명

- **Foundation Model(파운데이션 모델)**: 대량의 비라벨 데이터로 사전학습해 여러 다운스트림 작업에 범용적으로 활용할 수 있는 모델.
- **cuDF / cuML**: NVIDIA CUDA-X 라이브러리군 중 GPU 가속 데이터프레임 처리(cuDF)와 머신러닝(cuML) 라이브러리.
- **NeMo AutoModel**: LLM·VLM 학습과 파인튜닝을 간소화·확장하는 PyTorch 기반 오픈소스 학습 라이브러리(NVIDIA NeMo 프레임워크의 일부).
- **Average Precision (AP)**: 정밀도-재현율 곡선 아래 면적으로, 모든 임계값에서 모델이 사기를 얼마나 잘 순위화하는지 나타내는 지표.
- **BPE(Byte Pair Encoding)**: 텍스트를 하위 단어 단위로 쪼개는 범용 토크나이저 방식으로, 표 형태 금융 데이터에는 비효율적.
- **FSDP2**: 대규모 모델을 여러 GPU에 샤딩(분할)해 학습시키는 완전 분산 데이터 병렬 기법.
- **UMAP**: 고차원 데이터를 2~3차원으로 축소해 시각화하는 차원 축소 기법.

#### 상세 내용

**왜 트랜스포머가 거래 이력에 적합한가**

거래 시퀀스(급여 입금, 식료품 구매, 대중교통 요금, 정기 구독, 대면 결제 등)는 순서와 맥락 속에 의미를 담고 있어, 언어모델이 문장을 학습하는 방식과 유사하다.

- 셀프 어텐션(self-attention)은 시간상 멀리 떨어진 이벤트끼리도 연결할 수 있어, 최근 여행 패턴이나 소액 승인의 급증 같은 맥락과 결합했을 때만 드러나는 사기 패턴을 포착한다.
- 기존 표 형태 특징은 엔지니어가 미리 윈도우·집계·규칙을 설계해야 하지만, 사전학습된 트랜스포머는 이러한 관계를 시퀀스에서 직접 학습한다.
- 이 접근은 계정·가맹점·기기 등 연결된 개체 간 관계를 포착하는 그래프 신경망(GNN) 기반의 NVIDIA AI Blueprint 사기 탐지 워크플로와 상호 보완적이다.

**데이터 로드 및 베이스라인 설정**

`01_dataset_baseline.ipynb`는 IBM TabFormer 데이터셋(약 2,440만 건 합성 카드 거래, 사기율 약 0.12%)을 cuDF로 GPU 메모리에 직접 로드한다.

- 데이터는 누적 거래 건수 기준으로 시간순 분할(학습 80%, 검증 10%, 테스트 10%)해 데이터 누수를 방지하고 실제 운영 환경을 반영한다.
- `tree_method="hist"`, `device="cuda"`로 GPU 가속된 XGBoost를 100만 건 균형 샘플로 학습하고, 실제 사기 비율(~0.1%)을 유지한 10만 건 계층화 홀드아웃으로 평가한다.
- 베이스라인 성능: 테스트 ROC-AUC 0.9885, 테스트 AP 0.1238. 클래스 불균형이 심한 상황에서는 ROC-AUC가 쉽게 포화되므로, 이 튜토리얼 전체에서 AP를 주요 지표로 삼는다.

**GPU 상에서 거래 토큰화**

범용 LLM 토크나이저는 표 형태 금융 데이터에 비효율적이다. BPE 토크나이저는 거래 하나를 약 39개 하위 단어 토큰으로 쪼개는데 대부분 쉼표·달러 기호를 인코딩하는 데 낭비된다.

*이미지 출처: [원문](https://developer.nvidia.com/blog/build-your-own-transaction-foundation-model-for-financial-intelligence/)*

- `02_seq_preproc_tokenization.ipynb`의 도메인 토크나이저는 거래당 약 12개 의미론적 토큰, 어휘 6,251개(BPE의 50,257개 대비 훨씬 작음)로 변환한다.
- 이 효율 덕분에 동일 토큰 예산에서 3배 이상 많은 거래를 담을 수 있다. 예를 들어 컨텍스트 윈도우 4,092 토큰 기준, 도메인 토크나이저는 약 315개 거래 이력을, BPE는 약 102개만 담을 수 있다.

**NeMo AutoModel로 사전학습**

`03_foundation_model_training.ipynb`는 토큰화된 코퍼스를 causal language modeling(다음 토큰 예측) 방식으로 디코더 전용 파운데이션 모델을 사전학습한다.

- 모델 구조(`configs/pretrain_financial_decoder.yaml`): 약 2,900만 파라미터, 히든 크기 512, 트랜스포머 레이어 8개, Grouped-Query Attention(쿼리 헤드 8개, KV 헤드 2개), 8,192 토큰 RoPE 컨텍스트 윈도우, SwiGLU 활성화, RMSNorm, 어휘 6,251개.
- 단일 GPU로 30스텝 데모 학습 시 손실이 무작위 추측 기준값 `ln(6251)≈8.74`에서 약 6.0으로 감소한다.
- `torchrun --nproc-per-node=8`을 명령어 앞에 붙이는 것만으로 8-GPU로 확장 가능하며, NeMo AutoModel이 FSDP2 샤딩, 혼합 정밀도, 그래디언트 누적, 체크포인트 통합을 YAML 설정만으로 처리한다.
- 체크포인트는 표준 `safetensors` 형식으로 저장되어 HuggingFace Transformers의 `AutoModelForCausalLM.from_pretrained()`로 바로 로드할 수 있다. 저장소에는 3,000스텝 학습된 전체 체크포인트가 포함되어 있다.

**대규모 임베딩 추출**

`04_inference_embedding_extraction.ipynb`는 사전학습된 백본을 특징 추출기로 전환한다.

- `output_hidden_states=True`로 마지막 히든 레이어를 사용자 이력당 512차원 벡터로 풀링한다.
- 디코더 전용 모델의 causal attention 특성상 시퀀스 전체를 관찰한 것은 마지막 위치뿐이므로, 마지막 non-pad 토큰의 히든 스테이트를 사용한다(last-token pooling).
- 배치 처리(`extract_embeddings_batched`)로 학습·검증·테스트 임베딩을 `.npy` 파일로 저장하고, 원본 표 특징과 재결합할 수 있도록 `metadata.json`도 함께 저장한다.

|---|---|---|---|

- 임베딩만 단독으로는 베이스라인보다 성능이 낮아, 이벤트 단위 원시 특징과 시퀀스 단위 이력 정보를 결합할 때 가장 큰 효과를 낸다.

**개발자 예제 커스터마이징**

- **토크나이저**: `src/tokenizer/`의 파이프라인은 `BaseTokenizer`를 상속해 기기 지문, 수취인 국가 등 새로운 필드로 쉽게 확장 가능.
- **모델 아키텍처**: 학습 YAML의 `model._target_`, `model.config._target_`만 수정하면 HuggingFace 호환 디코더로 교체 가능하며, 데이터 로더·FSDP2·체크포인팅 등 나머지 파이프라인은 그대로 유지된다.
- **다운스트림 작업**: XGBoost를 고정 길이 벡터를 입력받는 다른 모델로 교체해 이탈 예측, 고객 세그멘테이션, 생애가치 회귀, 다음 최선 행동 추천, 신용 평가 등에 동일한 임베딩+헤드 패턴을 적용할 수 있다.

**대상 독자**: 금융 거래 데이터를 다루는 데이터 사이언티스트·ML 엔지니어, 사기 탐지·신용 평가·고객 세그멘테이션 등 표 형태 금융 데이터 기반 모델을 GPU로 가속하고 파운데이션 모델 방식으로 고도화하려는 개발자에게 유용하다.

- **NVLink / NVLink Switch**: GPU들을 하나처럼 묶어 초고속으로 데이터를 주고받게 하는 NVIDIA 전용 인터커넥트
- **CUDA Graph**: 여러 GPU 연산을 하나의 그래프로 미리 기록해 반복 실행 시 CPU 개입(동기화) 없이 실행하는 기법
- **CuTe DSL**: GPU 커널의 메모리·연산을 세밀하게 제어해 여러 연산을 하나로 합치는(fusion) NVIDIA의 도메인 특화 언어
- **MXFP8**: 8비트 부동소수점 정밀도 포맷으로, 16비트 대비 연산 속도를 높이면서 정확도 손실을 최소화
- **Spectrum-X / Quantum InfiniBand**: 수천 개 GPU를 클러스터 단위로 연결하는 NVIDIA의 스케일아웃 네트워킹 플랫폼

#### 상세 내용

**대규모 확장과 스케일아웃 네트워킹**

MoE 모델의 전문가 병렬화는 특정 구간에 트래픽이 몰리는 "버스트성" 통신 패턴을 만들어 기존 ECMP(정적 경로 분산) 방식에서는 대역폭 손실이 발생하기 쉽다.

- Spectrum-X Ethernet의 Advanced Adaptive Routing이 실시간 링크 부하에 따라 패킷 단위로 경로를 분산해 이론적 대역폭에 근접한 성능을 유지한다.
- Spectrum-X Congestion Control은 실시간 텔레메트리로 트래픽 집중(incast)을 조기에 감지해 버퍼 오버플로 전에 송신 속도를 조절한다.
- 이를 통해 최대 8,192개 GPU 클러스터에서도 통신 지연이 연산 뒤로 숨겨져(overlap) 새로운 학습 시간 기록을 달성했다. 예: DeepSeek-V3 671B(8,192 GPU) 2.02분, Llama 3.1 405B(8,192 GPU) 7.07분.

**소프트웨어 최적화 6가지**

1. **토큰-드롭리스 MoE용 전체 반복 CUDA 그래프**: 동적 라우팅 때문에 CPU-GPU 동기화가 잦았던 문제를, 연산자를 동기화 불필요 모드로 전환하고 "paged stashing"으로 GPU 메모리를 호스트 개입 없이 관리해 해결. CPU를 임계 경로에서 완전히 제거했다.
2. **CuTe DSL 커널 퓨전**: 메모리 대역폭 제약 연산과 그룹 GEMM(행렬곱)을 하드웨어 레벨에서 결합, 동적 타일 스케줄링으로 통신과 연산을 겹치게 함. DeepSeek-V3에서 8% 이상, GPT-OSS에서 93% 종단 간 속도 향상.
3. **MXFP8 어텐션 블록**: 기존 16비트 대신 어텐션 연산에 8비트 정밀도를 적용해 모델 품질 저하 없이 속도 향상. cuDNN(Transformer Engine 라이브러리)에서 제공.
4. **라우터·하이브리드 EP(Expert Parallelism) 최적화**: 라우터의 여러 요소별 커널을 통합하고 FP64→FP32로 전환해 5배 커널 속도 향상, 전체적으로 5% 성능 개선.
5. **1F1B all-to-all 오버랩 최적화**: Megatron-Core의 1F1B(One Forward, One Backward) 스케줄링을 CUDA 그래프로 캡처해 CPU 오버헤드 제거, 통신 스트림 우선순위 조정 등으로 거의 100% 통신-연산 오버랩 달성, 8% 성능 향상.
6. **파이프라인 단계 불균형 최소화**: DeepSeek-V3의 비대칭 레이어 구조(앞단 dense 레이어 + 뒷단 MTP·logits GEMM)로 인한 병목을, Megatron-Core의 유연한 파이프라인 레이아웃과 MXFP8 적용으로 해결. 불균형을 1% 미만으로 줄여 4% 성능 절감.

### [How to Optimize Transformer-Based Models for Low-Precision Training](https://developer.nvidia.com/blog/how-to-optimize-transformer-based-models-for-low-precision-training/)

`Transformer Engine` `NVFP4` `FP8` `GEMM` `Low-Precision Training` `NVIDIA Blackwell`

> GEMM 형상을 벤치마크해 트랜스포머 저정밀도 학습 속도 향상을 사전 예측한다

#### 요약

- 트랜스포머 학습 시간 대부분은 GEMM(행렬곱) 연산이 차지하며, 모델 config만으로는 실제로 실행되는 GEMM 형상(M×K×N)을 알 수 없다.
- NVIDIA Transformer Engine의 벤치마크 툴로 모델 설정과 배치 크기를 GEMM 형상으로 변환해 BF16, FP8, NVFP4 등 여러 정밀도의 속도를 실측 비교할 수 있다.
- ESM2-15B(단백질 언어 모델) 사례에서 NVFP4는 autocast(실시간 양자화 포함) 기준 BF16 대비 2.69배, 양자화 오버헤드를 제거한 prequantized 기준으로는 4.01배 빠르다.
- 실측 GEMM 속도 향상과 실제 학습 속도 향상을 비교하면 양자화 오버헤드, 커널 미지원으로 인한 FP8/BF16 폴백 등 병목 원인을 진단할 수 있다.

#### 시사점

- 저정밀도 포맷 도입 전 실제 학습 속도 향상을 예측할 수 있어, 값비싼 전체 학습 실행 전에 최적의 정밀도를 선택할 수 있다.
- GEMM 단위 벤치마크와 GPU 메모리 비교를 통해 FP4 커널이 실제로 동작하는지, 조용히 FP8/BF16으로 폴백하고 있는지 진단 가능하다.
- 이 벤치마크 도구는 후보 모델 아키텍처를 비교하는 "아키텍처 공동 설계(co-design)" 도구로도 활용할 수 있다.

#### 용어 설명

- **GEMM**: General Matrix Multiplication의 약자로, 신경망 연산의 핵심인 대규모 행렬곱셈 연산.
- **NVFP4**: NVIDIA Blackwell GPU가 지원하는 4비트 부동소수점(FP4) 포맷으로, 연산량과 메모리를 크게 줄여준다.
- **FP8 (CurrentScaling / DelayedScaling)**: 8비트 부동소수점 포맷. CurrentScaling은 매 스텝 실시간으로, DelayedScaling은 과거 amax(최대 절댓값) 이력을 이용해 스케일을 계산하는 방식.
- **MXFP8**: 블록 단위 스케일링을 적용하는 FP8의 한 방식(Microscaling FP8).
- **Transformer Engine(TE)**: NVIDIA가 제공하는 라이브러리로, 트랜스포머 모델의 양자화 및 저정밀도 커널 디스패치를 자동 처리한다.
- **Autocast / Pre-quantize**: Autocast는 학습 중 매 GEMM 직전 입력을 동적으로 양자화하는 실제 학습 방식이며, Pre-quantize는 사전에 한 번만 양자화해 순수 커널 성능만 측정하는 방식.
- **Fprop / Dgrad / Wgrad**: 순전파(Forward propagation), 입력에 대한 역전파 기울기(Data gradient), 가중치에 대한 역전파 기울기(Weight gradient) 연산 단계.

#### 상세 내용

**모델 설정을 GEMM 워크로드로 변환**

ESM2-15B(hidden_size 5120, intermediate_size 20480, attention heads 40, layers 48)와 학습 설정(micro_batch_size 32, sequence_length 1024)을 벤치마크 스크립트에 입력하면, 이를 실제 GEMM 형상으로 자동 변환해 여러 정밀도로 벤치마크하고 속도 향상을 계산해 준다.

- `python benchmarks/gemm/benchmark_gemm.py` 명령 한 번으로 GEMM 형상 도출부터 벤치마크, 속도 분석까지 처리.
- `--no-fp8 --no-fp4` 옵션으로 Hopper 등 Blackwell 이전 GPU에 맞게 BF16과 3가지 FP8 레시피만 테스트 가능.

**Autocast 모드 vs Pre-quantize 모드**

기본 동작인 autocast 모드는 실제 학습처럼 매 GEMM 전에 입력을 동적으로 양자화하므로 양자화 비용과 커널 실행 시간이 모두 포함된 "현실적인" 수치를 보여준다. 반면 `--pre-quantize` 옵션은 입력을 미리 한 번만 양자화해 순수 GEMM 커널 성능만 측정한다.

![NVIDIA B300에서 정밀도별(BF16, FP8 Current, FP8 Delayed, MXFP8, NVFP4) Fprop+Dgrad 및 Wgrad 단계의 레이어당 GEMM 시간을 보여주는 막대그래프. BF16이 약 41ms로 가장 느리고 NVFP4가 약 15ms로 가장 빠르다.](https://developer-blogs.nvidia.com/wp-content/uploads/2026/06/per-layer-gemm-time-breakdown-nvidia-b300.webp)
*이미지 출처: [원문](https://developer.nvidia.com/blog/how-to-optimize-transformer-based-models-for-low-precision-training/)*

- ESM2-15B 설정 기준(M=32,768 토큰) autocast 모드에서 NVFP4는 BF16 대비 2.69배 빠름.
- FP8 DelayedScaling은 amax 이력을 사용해 동적 양자화 부담이 없어 autocast 모드에서 가장 빠른 FP8 레시피(23.76ms/layer, BF16 대비 1.74배)이며, prequantized 버전은 존재하지 않는다.

![NVIDIA B300 pre-quantized 모드에서 정밀도별 레이어당 GEMM 시간 막대그래프. NVFP4가 약 10ms로 BF16(41ms) 대비 극적으로 빨라져 FP4 텐서 코어의 실제 잠재력을 보여준다.](https://developer-blogs.nvidia.com/wp-content/uploads/2026/06/per-layer-gemm-time-breakdown-nvidia-b300-sxm6-ac-prequantized.webp)
*이미지 출처: [원문](https://developer.nvidia.com/blog/how-to-optimize-transformer-based-models-for-low-precision-training/)*

- pre-quantized 모드에서는 NVFP4가 BF16 대비 4.01배로 상승, autocast와의 차이(2.69배 vs 4.01배)가 곧 동적 양자화·Hadamard 변환·블록 스케일링 등의 오버헤드 비용.
- 실제 학습 속도 예측에는 autocast 결과를, 병목이 커널인지 양자화 오버헤드인지 구분할 때는 prequantized 결과를 사용해야 한다.

**실제 모델(ESM2-15B)에서의 해석**

Fprop 기준 NVFP4 대비 MXFP8 속도 향상은 QKV proj 1.81배, Attn out 1.44배, MLP up 1.91배, MLP down 1.81배로 나타났다.

- 15B 규모에서는 가장 작은 GEMM인 attention output도 1.44배 향상을 얻어, 작은 모델에서 흔히 보이는 "저정밀도 이득이 오버헤드에 묻히는" 현상이 완화됨.
- 대형 GEMM들의 실측 향상(1.81~1.91배)은 하드웨어 이론치(2~3배)보다 낮으며, 이는 양자화·비-GEMM 오버헤드가 실제 이득을 깎아먹기 때문.
- BF16은 Fprop과 Dgrad 시간이 거의 동일하지만, 양자화 포맷에서는 Dgrad가 4~5% 더 느리고 QKV Proj Dgrad는 K와 N이 뒤바뀌며 형상이 크게 달라져 15~22%까지 느려짐 — 이 때문에 도구는 Fprop과 Dgrad를 별도로 벤치마크함.

**속도 향상 진단 가이드**

GEMM 단위 실측 속도 향상과 실제 end-to-end 학습 속도 향상을 비교해 병목을 진단할 수 있다.

- GEMM 속도 향상 ≈ 학습 속도 향상: GEMM이 스텝 시간을 지배하는 정상 상태.
- GEMM 속도 향상 >> 학습 속도 향상: Random Hadamard 변환, stochastic rounding, 2D 블록 스케일링 등 GEMM 외 오버헤드가 이득을 잠식.
- GEMM 속도 향상 ≈ 1.0: FP4 커널이 해당 형상에서 실제로 빠르지 않거나, FP8로 조용히 폴백 중일 가능성 — `NVTE_LOG_LEVEL=1` 설정이나 NVIDIA Nsight Systems로 확인하고, GPU 메모리 사용량 비교로 FP4 가중치가 실제로 저장되는지 검증 권장.

**대상 독자**: 대규모 트랜스포머 모델을 Hopper/Blackwell GPU에서 학습하며 FP8·NVFP4 같은 저정밀도 포맷 도입 여부를 사전에 검증하고 싶은 ML 인프라 엔지니어 및 모델 학습 담당자에게 유용하다.

### [Fine-Tuning Biological Foundation Models with LoRA Using NVIDIA BioNeMo Recipes](https://developer.nvidia.com/blog/fine-tuning-biological-foundation-models-with-lora-using-nvidia-bionemo-recipes/)

`LoRA` `BioNeMo` `ESM2` `Evo2` `NVIDIA Transformer Engine` `PEFT`

> LoRA로 단백질·DNA 파운데이션 모델을 단일 GPU에서 효율적으로 미세조정

#### 요약

- NVIDIA BioNeMo Recipes를 활용해 ESM2-3B(단백질)와 Evo2-1B(DNA) 두 모델에 LoRA(저순위 적응) 기법을 적용, 전체 파라미터의 약 1%만 학습해 풀 파인튜닝에 준하는 성능을 달성.
- ESM2-3B + LoRA는 단백질 이차구조 예측(PSSP)에서 Porter 6, SPOT-1D-LM 등 공개 벤치마크와 대등한 정확도(Q3 84.80%, Q8 74.30%)를 기록.
- Evo2-1B + LoRA는 DNA 스플라이스 사이트 분류에서 헤드만 학습한 베이스라인(52.3%) 대비 정확도를 96.6%까지 끌어올림 (학습 파라미터는 전체의 1.42%).
- Transformer Engine과 시퀀스 패킹(THD 포맷) 적용으로 학습 처리량이 BSHD 대비 약 5.5배 향상되며, 전체 학습은 NVIDIA RTX 6000 Blackwell Workstation Edition GPU 1장으로 1시간 이내 완료.

#### 시사점

- 수십억 파라미터급 생물학 파운데이션 모델도 단일 워크스테이션 GPU에서 실용적으로 미세조정할 수 있어, 대규모 클러스터 없이도 도메인 특화 모델을 구축 가능.
- PyTorch/Hugging Face/Megatron-Bridge 기반의 익숙한 패턴으로 레시피가 제공되어, 생물정보학 비전문가 개발자도 접근성 높게 활용 가능.
- 단백질(트랜스포머 구조)과 DNA(Hyena 구조)처럼 아키텍처가 다른 모델에도 동일한 LoRA 레시피 패턴이 그대로 적용된다는 점에서 범용성 확인.

#### 용어 설명

- **LoRA(Low-Rank Adaptation)**: 사전학습된 모델 가중치는 고정하고, 작은 저순위 행렬만 추가로 학습해 적은 자원으로 미세조정하는 기법.
- **ESM2**: 단백질 서열을 학습한 단백질 언어 모델로, 구조·기능 예측 등에 활용.
- **Evo 2**: DNA 서열로 학습된 생성형 유전체 파운데이션 모델.
- **PSSP(단백질 이차구조 예측)**: 아미노산 서열의 각 잔기에 나선(helix)·가닥(strand) 등 국소 구조 라벨을 부여하는 작업.
- **Transformer Engine(TE)**: NVIDIA의 트랜스포머 연산 가속 라이브러리.
- **시퀀스 패킹(THD 포맷)**: 길이가 다른 시퀀스를 패딩 없이 이어붙여 GPU 연산 낭비를 줄이는 배치 방식.
- **PEFT(Parameter-Efficient Fine-Tuning)**: 전체 파라미터가 아닌 일부만 학습해 효율적으로 미세조정하는 기법군.

#### 상세 내용

**LoRA가 대규모 미세조정을 가능케 하는 방식**

풀 파인튜닝은 모델의 모든 파라미터와 옵티마이저 상태를 저장·업데이트해야 해 수십억 파라미터급 모델에서는 계산·저장 부담이 크다. LoRA는 원본 가중치 행렬 $W$는 고정한 채, 병렬로 작은 저순위 행렬 $W=BA$만 학습해 학습 파라미터 수와 메모리 사용량을 크게 줄인다.

![LoRA 재매개변수화 다이어그램](https://developer-blogs.nvidia.com/wp-content/uploads/2026/06/lora-reparametrization.webp)
*이미지 출처: [원문](https://developer.nvidia.com/blog/fine-tuning-biological-foundation-models-with-lora-using-nvidia-bionemo-recipes/)*

- 순위(rank) $r$: 추가되는 저순위 행렬 크기 및 학습 파라미터 수를 결정.
- 타깃 모듈: 어텐션·MLP 프로젝션 등 어댑터가 적용될 레이어를 지정.
- LoRA dropout: 데이터셋이 작을 때 정규화 용도로 사용 가능.

**ESM2-3B를 활용한 단백질 이차구조 예측**

PSSP는 아미노산 서열의 각 잔기에 구조 라벨(Q3: Helix/Strand/Coil, Q8: 8가지 세분화 라벨)을 부여하는 토큰 분류 문제다. 국소 구조는 단백질 기능과 강하게 연관되어 3차 구조 예측, 단백질-단백질 상호작용 예측 등 다양한 후속 작업의 기반이 된다.

- 잔기별 분류 헤드를 추가하고, PEFT 라이브러리로 LoRA 어댑터를 QKV(쿼리/키/값) 프로젝션에 적용, 백본은 동결.
- Porter 6 모델 저자가 공개한 데이터 분할과 테스트셋으로 학습·평가.
- TE와 시퀀스 패킹을 활성화해 RTX 6000 Blackwell Workstation Edition GPU 1장에서 1시간 이내 전체 학습 완료.
- 결과: Q3 정확도 84.80%, Q8 정확도 74.30%로 Porter 6(84.56%/74.18%), SPOT-1D-LM(84.30%/74.09%) 등 공개 벤치마크와 대등.

![ESM2-3B+LoRA 학습 곡선](https://developer-blogs.nvidia.com/wp-content/uploads/2026/06/lora-training-protein-secondary-structure-prediction-fine-tuning-3.webp)
*이미지 출처: [원문](https://developer.nvidia.com/blog/fine-tuning-biological-foundation-models-with-lora-using-nvidia-bionemo-recipes/)*

**시퀀스 패킹이 처리량을 높이는 이유**

단백질 데이터셋은 서열 길이가 제각각이라, 배치 내 최대 길이에 맞춰 패딩(BSHD 포맷)하면 상당수 토큰이 무의미한 패딩으로 낭비된다. 시퀀스 패킹(THD 포맷)은 실제 토큰만 이어붙이고 경계 정보를 별도로 관리해 이 낭비를 줄인다.

![THD vs BSHD 처리량 비교 차트](https://developer-blogs.nvidia.com/wp-content/uploads/2026/06/fine-tuning-throughput-thd-bshd-1.webp)
*이미지 출처: [원문](https://developer.nvidia.com/blog/fine-tuning-biological-foundation-models-with-lora-using-nvidia-bionemo-recipes/)*

- THD 포맷 적용 시 BSHD 대비 처리량(tokens/sec)이 약 5.5배 향상.
- 패딩 토큰에 소모되던 연산·메모리 대역폭이 줄어 동일 메모리로 더 많은 실제 토큰 처리 가능.

**Evo2-1B를 활용한 DNA 스플라이스 사이트 분류**

Evo 2는 모든 생물 도메인의 유전체 서열로 학습된 생성형 DNA 파운데이션 모델로, striped Hyena 블록(상태공간 방식의 긴 컨볼루션 연산자와 소수의 어텐션 레이어 조합) 구조를 사용해 긴 DNA 컨텍스트를 효율적으로 처리한다.

- 스플라이싱은 pre-mRNA에서 인트론을 제거하고 엑손을 잇는 과정으로, 경계는 도너 사이트(GT)와 억셉터 사이트(AG)로 정의됨.
- 동일한 GT/AG 패턴이 유전체 전반에 반복 등장해 단순 모티프 매칭으로는 부족하며, 더 넓은 문맥 학습이 필요.
- Nucleotide Transformer의 splice_sites_all 데이터셋(600bp 고정 길이, 약 3만 학습/3천 테스트 예시, 클래스 균형) 사용.
- 시퀀스 분류 헤드(평균 풀링 기반)를 추가하고, LoRA 어댑터를 어텐션·MLP·Hyena 믹서 프로젝션에 적용.

| 모드 | 학습 파라미터 | 학습 비율 | 테스트 정확도 |
|---|---|---|---|
| Head only | 3,697,923 | 0.33% | 52.3% |
| LoRA plus head | 15,985,923 | 1.42% | 96.6% |

- 잔여 오차는 대부분 도너↔억셉터 혼동에서 발생 (두 모티프 모두 GT/AG 이중 뉴클레오티드 구조를 공유해 장거리 문맥 구분이 필요하기 때문).
- 전체 워크플로우는 RTX 6000 Workstation Edition GPU 1장에서 약 1시간 내 완료.

**시작하기**

BioNeMo Recipes를 통해 TE, Megatron-Bridge, 시퀀스 패킹, PEFT가 통합된 워크플로우를 코드와 함께 제공하며, 단백질·DNA 등 모달리티가 달라도 동일한 LoRA 레시피 패턴을 재사용할 수 있다.

**대상 독자**: 생물학 파운데이션 모델(단백질/DNA)을 제한된 GPU 자원으로 특정 태스크에 맞게 미세조정하려는 생물정보학·머신러닝 엔지니어에게 유용하며, 구조 예측이나 서열 분류 등 실제 연구·응용 파이프라인 구축에 참고할 수 있다.

### [Boosting MoE Training Throughput with Advanced Fusion Kernels](https://developer.nvidia.com/blog/boosting-moe-training-throughput-with-advanced-fusion-kernels/)

`MoE` `CUDA` `CuTe DSL` `Transformer Engine` `Megatron-Core` `cuDNN`

> NVIDIA가 CuTe DSL 기반 융합 커널로 MoE 학습 속도를 최대 93% 개선

#### 요약

- NVIDIA가 CuTe DSL로 직접 구현한 융합(fused) MLP 커널을 공개, 커널 단위 1.3x~2x 속도 향상과 동기화 없는(sync-free) MoE 실행을 지원
- DeepSeek-V3 사전학습에서 8%, GPT-OSS 사전학습에서 93%의 종단간(end-to-end) 성능 향상 달성
- 활성화 함수·CPU 동기화·양자화라는 MoE 블록의 3대 병목을 GEMM(행렬곱) 커널에 직접 통합해 해결
- cuDNN Frontend, Transformer Engine, Megatron-Core 등 여러 추상화 계층에서 바로 사용 가능

#### 시사점

- 대규모 MoE 모델을 직접 학습시키는 개발자라면 별도 구현 없이 라이브러리 업그레이드만으로 학습 시간 단축 효과를 얻을 수 있음
- CPU-GPU 동기화를 없애 전체 학습 iteration을 CUDA 그래프로 감쌀 수 있게 되어, 대규모 분산 학습에서 통신 커널과의 오버랩 효율도 함께 개선됨
- MXFP8·NVFP4 같은 저정밀도 학습 레시피를 쓰는 경우 양자화로 인한 메모리 오버헤드가 크게 줄어듦

#### 용어 설명

- **MoE(Mixture-of-Experts)**: 입력마다 전체 파라미터 중 일부(전문가)만 활성화해 계산량 대비 모델 용량을 키우는 아키텍처
- **GEMM**: General Matrix Multiplication의 약자로, 딥러닝 연산의 핵심인 대규모 행렬곱 연산
- **CuTe DSL**: NVIDIA가 제공하는, GPU 텐서 연산을 세밀하게 제어해 커널을 작성할 수 있는 도메인 특화 언어
- **커널 퓨전(Kernel Fusion)**: 여러 연산 단계를 하나의 GPU 커널로 합쳐 중간 결과를 메모리에 쓰고 읽는 비용을 없애는 최적화 기법
- **GLU(Gated Linear Unit)**: 입력의 일부를 게이트로 사용해 나머지를 조절하는 활성화 함수 계열(SwiGLU, GeGLU 등)
- **MXFP8/NVFP4**: 학습 속도를 높이기 위해 정밀도를 낮춘 저정밀도 수치 포맷
- **CUDA Graph**: 여러 GPU 커널 실행을 하나의 그래프로 미리 정의해 반복 실행 시 CPU 오버헤드를 줄이는 기법

#### 상세 내용

**MoE 학습의 3대 병목**

MoE 블록의 실행 타임라인을 프로파일링한 결과 세 가지 병목이 확인되었습니다.

- 활성화 함수는 메모리 바운드(memory-bound) 연산이라 Tensor Core가 이 구간 동안 놀게 됨
- 전문가별 토큰 수는 런타임에 CPU에서 계산되는데, GPU 속도를 CPU가 못 따라가면 CPU 연산이 그대로 노출되어 지연 발생
- 고정밀→저정밀 양자화 역시 메모리 바운드 연산이라 Tensor Core 유휴 시간을 만듦

이를 해결하기 위해 GroupGemm+Quantize, GroupGemm+Activation+Quantize/Transpose, GroupGemm+dActivation+Quantize/Transpose 세 종류의 sync-free 커널을 새로 설계했습니다. 지원 활성화 함수는 SwiGLU, GeGLU, sReLU이며 클램핑(clamping)과 스케일링 옵션도 제공합니다.

![A flowchart illustrating kernel fusions in a MoE block. Shaded grey regions group the forward pass operations (FC1, Activation, and Quantize/Transpose) and the backward pass operations (FC2 dgrad, dActivation, and Quantize/Transpose) into single blocks. Arrows show the interconnected data flow between these fused kernels and the separate, unfused weight gradient blocks](https://developer-blogs.nvidia.com/wp-content/uploads/2026/06/image3-4-625x370.png)

**GLU 활성화 함수를 GEMM 에필로그에 융합**

SwiGLU, GeGLU 등 GLU 계열 활성화 함수는 FC1 레이어 출력을 두 청크(입력, 게이트)로 나눠 결합합니다. 문제는 이 두 청크가 보통 서로 다른 스레드 블록에서 계산되어, 결합하려면 결과를 한 번 글로벌 메모리에 썼다가 다시 읽어야 한다는 점입니다.

- 이를 해결하기 위해 가중치를 입력·게이트 열(column) 단위로 재배치(repack)해, 같은 스레드 블록이 두 청크에 모두 접근하도록 구성
- 재배치는 체크포인트 로딩 시점에 미리 수행 가능
- 그 결과 글로벌 메모리를 거치지 않고 GEMM 에필로그 안에서 바로 입력과 게이트를 결합
- 역전파에서도 에필로그가 GEMM 출력을 읽고 dSwiGLU를 계산·양자화한 뒤 곧바로 저장

![Diagram showing the SwiGLU fused-kernel data flow. Input and gate weights are swizzled into an interleaved layout so a single GEMM epilogue tile can access both paths, apply Swish to the gate values, and multiply them with the input values to generate the final SwiGLU output](https://developer-blogs.nvidia.com/wp-content/uploads/2026/06/image5-1-625x634.png)
*이미지 출처: [원문](https://developer.nvidia.com/blog/boosting-moe-training-throughput-with-advanced-fusion-kernels/)*

**호스트-디바이스 동기화 및 CPU 실행 오버헤드 제거**

기존 방식에서는 그룹별 토큰 수가 런타임에 정해지기 때문에, 이를 얻기 위해 CPU가 호스트에서 동기화를 거쳐야 하고 전문가(로컬 익스퍼트) 수만큼 커널을 개별 launch해야 했습니다.

- CuTe DSL GroupGEMM 커널은 그룹별 토큰 수를 GPU 메모리 내부에서 직접 추적
- CPU 의존성을 없애 iteration 전체를 CUDA 그래프로 감쌀 수 있게 되어 CPU 병목 제거

**MXFP8·NVFP4 양자화 융합으로 메모리 오버헤드 절감**

MXFP8은 활성화 함수 출력(BF16)을 읽어 MXFP8 값과 역전파용 전치(transpose) 버전을 함께 씁니다. 새 커널은 이 양자화 단계를 GEMM 커널 자체에 융합해 BF16 텐서의 추가 읽기·쓰기를 없앴습니다. NVFP4의 경우도 순전파에서 BF16 출력과 텐서 전체 최대값(amax)을 함께 계산하고, 역전파에서는 전치된 아다마르(Hadamard) 회전에 대한 amax를 계산해 추가 메모리 패스를 제거했습니다.

**커널 단위 성능에서 사전학습 속도 향상까지**

단위 마이크로벤치마크 기준으로 순전파는 최대 1.3x, 역전파는 최대 2.1x 가속되었습니다. 동적 스케줄링(다른 통신 커널과의 오버랩 지원)과 구성 가능한 클러스터 마진(다른 커널을 위한 SM 자원 여유 확보) 기능도 함께 제공됩니다.

- Sync-free 커널이 종단간 CUDA 그래프와 통신 커널과의 효율적 오버랩을 가능케 해, 애플리케이션 전체 수준에서는 더 큰 속도 향상 확인
- 내부 테스트 기준 DeepSeek-V3에서 최대 8%, GPT-OSS 사전학습에서 최대 93% 종단간 속도 향상

### [Pretrained to Imagine, Fine-Tuned to Act: The Rise of World-Action Models](https://developer.nvidia.com/blog/pretrained-to-imagine-fine-tuned-to-act-the-rise-of-world-action-models/)

`World-Action-Model` `VLA` `Robotics` `Video-Generation` `Cosmos` `Wan`

> 로봇 정책, VLM 대신 비디오 생성 모델을 기반으로 학습하는 새 흐름이 부상 중

#### 요약

- 기존 VLA(Vision-Language-Action)는 VLM(Vision-Language Model)을 기반으로 로봇 행동을 학습하지만, 언어를 실제 행동으로 연결하는 "그라운딩 갭"에 부딪혀 있다.
- WAM(World-Action Model)은 대신 대규모 비디오 생성 모델(Wan, Cosmos 등)을 백본으로 삼아, 미래 장면 변화를 예측하는 능력을 로봇 행동 예측에 전이시킨다.
- WAM은 예측 방식(역동역학/공동예측/표현전용), 행동 통합 방식(토큰/이미지형/잠재변수), 아키텍처(계층형/단일형/Mixture-of-Transformers) 세 축으로 다양하게 갈라지며 아직 표준 레시피가 없다.
- 실제 벤치마크(RoboArena)에서 DreamZero(WAM)가 Pi-0.5(VLA)보다 높은 점수를 기록했지만, WAM은 학습 비용이 크고(약 7.4배) 추론 속도도 3~4배 느려 VLA와 WAM의 하이브리드가 차세대 로봇 파운데이션 모델의 유력한 방향으로 제시된다.

#### 시사점

- 로봇 정책 설계 시 VLM 기반 VLA와 비디오 백본 기반 WAM 중 하나를 선택해야 하는 구조적 트레이드오프(학습 비용, 추론 속도, 데이터 그라운딩)가 존재함을 이해할 수 있다.
- 비디오 생성 모델의 "제로샷 상상력"이 실제 로봇 제어로 전이될 잠재력이 있다는 점은, 사전학습된 대형 비디오 모델을 활용한 응용 연구/제품 개발에 새로운 방향을 제시한다.
- Pi-0.7, Being-H0.7, Cortex 2.0 등 VLA+WAM 하이브리드 사례는 향후 로봇 AI 스택 설계 시 참고할 만한 실제 아키텍처 패턴을 보여준다.

#### 용어 설명

- **VLA (Vision-Language-Action model)**: 시각-언어 모델을 기반으로 관찰과 언어 지시로부터 로봇 행동을 생성하는 정책 모델.
- **WAM (World-Action Model)**: 사전학습된 비디오/월드 모델 백본을 기반으로 미래 장면 변화와 행동을 함께 예측하는 로봇 정책 모델.
- **월드 모델(World Model)**: 현재 상태와 행동(또는 언어)을 입력받아 미래 상태(이미지, 잠재 벡터 등)를 예측하는 모델.
- **그라운딩 갭(Grounding gap)**: 언어가 표현하는 의미와 실제로 물리적 세계에서 실행 가능한 행동 사이의 간극.
- **역동역학(Inverse dynamics)**: 현재 관찰과 미래 관찰이 주어졌을 때, 그 전이를 만들어낸 행동을 추론하는 문제.
- **DiT (Diffusion Transformer)**: 확산/플로우 매칭 기반 생성 모델에서 이미지·비디오·행동 토큰을 디노이즈하는 트랜스포머 백본.
- **Mixture-of-Transformers (MoT)**: 비디오용, 행동용 등 모달리티별로 별도 가중치를 갖는 트랜스포머들을 공유 어텐션으로 결합한 구조.

#### 상세 내용

**VLA와 WAM: 두 가지 대안**

로봇 파운데이션 모델은 현재 두 갈래로 나뉜다. Pi-0, GR00T 등은 VLM 백본으로 시작하는 전통적 VLA 방식을 쓰고, DreamZero, Cosmos Policy, LingBot-VA 등은 비디오 생성 모델(Wan, Cosmos)을 백본으로 삼는 WAM 방식을 쓴다.

![The two current bets for generalist manipulation policies: VLM-based VLAs vs video-backbone WAMs.](https://developer-blogs.nvidia.com/wp-content/uploads/2026/05/Figure-1.-The-two-current-bets-for-generalist-manipulation-policies-VLM-based-VLAs-vs-video-backbone-WAMs-300x294.png)
*이미지 출처: [원문](https://developer.nvidia.com/blog/pretrained-to-imagine-fine-tuned-to-act-the-rise-of-world-action-models/)*

- VLM 기반 VLA는 방대한 시각-언어 사전학습의 이점을 얻지만, 로봇 데이터로 언어-행동 그라운딩을 별도로 학습해야 한다.
- WAM은 언어 조건으로 장면이 어떻게 변하는지 이미 학습한 비디오 백본을 재사용해, 이 그라운딩 문제의 일부를 미리 해결하고 시작한다는 가설이다.

**왜 WAM인가: 세 가지 가설**

저자는 WAM이 유리할 수 있는 이유로 세 가지를 제시한다.

- 미래 상태를 예측하는 것이 행동을 직접 예측하는 것보다 쉬울 수 있다(역동역학이 순수 행동 생성보다 단순).
- 비디오 사전학습이 언어와 물리적 변화 사이의 연결을 이미 학습했을 수 있다.
- 방대한 웹 비디오 데이터가 상대적으로 적은 로봇 데이터에 대한 일종의 정규화(overfitting 방지) 역할을 할 수 있다.

Google Veo 3.1로 진행한 간단한 실험에서, 로봇 팔이 토스터 레버를 누르고 오렌지를 집는 동작을 제로샷으로 생성했을 때 움직임은 그럴듯했지만 그리퍼가 네 손가락 손으로 바뀌는 등 한계도 뚜렷했다.

- **파라다임**: 역동역학(미래 비디오 생성 후 행동 추론, 예: UniPi→LingBot-VA), 공동예측(비디오와 행동을 동시에 생성, 예: GR-1→DreamZero), 표현전용(추론 시 비디오 생성을 생략, 예: Fast-WAM).
- **행동 통합**: 기본 행동 토큰(대부분의 모델), 행동-이미지 변환(Cosmos Policy처럼 행동을 잠재 프레임으로 표현), 잠재 행동/계획(Being-H0.7처럼 압축된 행동 표현 사용).
- **아키텍처**: 계층형(비디오와 행동 모듈 분리), 단일형(하나의 트랜스포머가 모두 처리, 예: DreamZero), MoT(모달리티별 별도 가중치 + 공유 어텐션, 현재 주류, 예: LingBot-VA).

DreamZero는 14B 규모의 Wan 2.1 비디오 확산 백본을 단일 DiT로 확장해 비디오와 행동 토큰을 함께 디노이즈하며, 실제 RoboArena 벤치마크에서 1750점을 기록해 Pi-0.5(1622점)를 넘어섰다.

**실무적 제약: 비용과 속도**

WAM은 성능 잠재력에 비해 상당한 비용 부담이 있다.

- 학습 비용: 저자의 대략적인 추정에 따르면, DreamZero 스타일의 전체 WAM 스택(비디오 사전학습+행동 튜닝)은 약 51~75 ZFLOP 수준으로, 효율적인 VLA 레시피(약 6.9 ZFLOP)보다 약 7.4배 크다.
- 추론 속도: Fast-WAM 기준 일반 WAM은 행동 청크(chunk)당 590~800ms가 걸려, Pi-0.5의 약 190ms 대비 3~4배 느리다.
- 긴 비디오 토큰 시퀀스로 인해 GPU 메모리와 통신, 데이터 로딩 부담도 크다.

![Lower-bound dense-core training compute estimates in ZFLOPs.](https://developer-blogs.nvidia.com/wp-content/uploads/2026/06/normalized_dense_core_training_compute_zflops.webp)
*이미지 출처: [원문](https://developer.nvidia.com/blog/pretrained-to-imagine-fine-tuned-to-act-the-rise-of-world-action-models/)*

**현대 VLA도 여전히 강력하다**

VLM 기반 VLA도 이산 행동 토큰화(FAST, BEAST), VLM 보존형 co-training, 그래디언트 격리형 행동 헤드 등으로 빠르게 발전해왔다.

- Pi-FAST(이산 토큰, 1592점)는 원조 Pi-0(플로우 매칭, 1475점)보다 RoboArena 점수가 높아, 사전학습된 VLM 능력을 보존하는 학습 방식이 중요함을 보여준다.
- 그러나 VLA도 여전히 언어의 모호함으로 인한 그라운딩 문제를 완전히 해결하지 못한다.

**VLA와 WAM의 수렴: 하이브리드 모델**

두 접근법이 결국 하나로 합쳐질 가능성이 제기된다. Physical Intelligence의 Pi-0.7은 VLA 액션 전문가가 월드 모델이 생성한 시각적 서브골(subgoal) 이미지를 조건으로 동작을 실행하며, 언어 지시 이해와 학습 수렴 속도가 개선됐다고 보고한다. Being-H0.7은 VLA 사전학습 요소(InternVL3.5, Qwen3)와 V-JEPA2.1 기반 잠재 행동 인터페이스를 결합한 하이브리드 사례다.
