# NVIDIA 블로그 요약 — 2026-08-13

### [Serve Qwen3.8-2.4T-A95B, a 2.4T-Parameter Model, with Configurable Reasoning on NVIDIA GB300 NVL72](https://developer.nvidia.com/blog/serve-qwen3-8-2-4t-a95b-a-2-4t-parameter-model-with-configurable-reasoning-on-nvidia-gb300-nvl72/)

`Qwen3.8-2.4T-A95B` `GB300 NVL72` `Mixture of Experts` `TensorRT-LLM` `NVIDIA NIM` `NeMo AutoModel`

> 2.4조 파라미터 오픈 모델 Qwen3.8을 GB300 NVL72에서 고성능 서빙

#### 요약

- Alibaba가 2.4T 총 파라미터, 토큰당 95B 활성화되는 최대 규모 오픈 웨이트 모델 Qwen3.8-2.4T-A95B를 공개했으며, 최대 100만 토큰 컨텍스트와 128K 출력을 지원한다.
- 파인그레인드 MoE(Mixture of Experts) 구조와 풀 어텐션·선형 어텐션 하이브리드 아키텍처로 긴 컨텍스트에서도 연산량과 메모리 사용을 억제한다.
- 추가 튜닝 없이 NVIDIA GB300 NVL72(FP8)에서 GPU당 초당 4천 토큰 이상, 사용자당 초당 350 토큰 이상의 처리량을 Day 0에 달성했다.
- SGLang, vLLM, NVIDIA Dynamo 등 오픈소스 추론 스택과 모델-프리 NVIDIA NIM을 통해 배포 가능하며, NeMo AutoModel로 후속 학습(post-training)도 지원한다.

#### 시사점

- 데이터센터급 초대형 모델을 실제 서비스에 투입할 수 있는 레퍼런스 성능 수치와 배포 경로가 Day 0에 제공되어, 대규모 에이전틱 워크로드(코딩, 문서 분석, 멀티스텝 작업)를 직접 구축하려는 개발자에게 실질적인 시작점이 된다.
- 추론 강도(low/high/xhigh)를 요청 단위로 조절할 수 있어, 작업 특성에 맞춰 비용과 품질의 균형을 세밀하게 맞출 수 있다.
- Hugging Face 체크포인트를 변환 없이 바로 파인튜닝할 수 있어, 도메인 특화 모델 구축까지의 진입장벽이 낮아진다.

#### 용어 설명

- **MoE(Mixture of Experts)**: 하나의 큰 모델 대신 여러 개의 작은 "전문가" 네트워크를 두고, 토큰마다 일부만 선택적으로 활성화해 연산 비용을 줄이는 구조.
- **파인그레인드 MoE**: 소수의 대형 전문가 대신 다수의 소형 전문가로 세분화해 라우팅 효율과 전문화를 높인 MoE 변형.
- **KV 캐시**: 어텐션 계산에서 이전 토큰들의 키·값을 저장해 재사용하는 메모리 공간으로, 컨텍스트가 길어질수록 커진다.
- **선형 어텐션(linear attention)**: 커지는 KV 캐시 대신 고정 크기의 순환 상태(recurrent state)로 컨텍스트를 처리해 메모리·연산을 일정하게 유지하는 방식.
- **NVLink**: GPU 간 초고속 직접 연결 기술로, GB300 NVL72에서는 72개 GPU를 하나의 도메인으로 묶어 130TB/s급 통신을 지원한다.
- **NVIDIA NIM**: 모델별 커스터마이징 없이 다양한 모델을 서빙할 수 있는 단일 추론 컨테이너.
- **TensorRT-LLM**: NVIDIA GPU에서 대형 언어모델 추론을 최적화하는 런타임/컴파일러.

**모델 개요**

Qwen3.8-2.4T-A95B(Qwen3.8-Max)는 Alibaba가 공개한 오픈 웨이트 모델 중 최대 규모다.

- 총 파라미터 2.4T, 토큰당 활성화 파라미터 95B의 파인그레인드 MoE 구조.
- 풀 어텐션과 선형 어텐션을 결합한 하이브리드 아키텍처.
- 최대 100만 토큰 컨텍스트 윈도우, 최대 128K 출력 길이 지원.
- 코딩, 대규모 문서 분석, 멀티스텝 워크플로우 등 에이전틱 작업을 겨냥해 설계.

**긴 컨텍스트를 위한 아키텍처 혁신**

에이전틱 애플리케이션은 단일 프롬프트-응답이 아니라 시스템 지시, 도구 출력, 검색된 문서, 코드, 로그, 추론 과정이 누적되며 컨텍스트가 계속 길어진다. 이 때문에 어텐션 연산과 KV 캐시 메모리가 병목이 된다.

- 모델은 풀 어텐션 레이어와 선형 어텐션 레이어를 번갈아 사용한다.
- 풀 어텐션 레이어에서는 모든 토큰이 서로를 참조하고, 선형 어텐션 레이어에서는 커지는 KV 캐시 대신 크기가 고정된 순환 상태를 사용해 연산과 메모리를 100만 토큰까지도 일정하게 유지한다.
- 파인그레인드 MoE는 다수의 작은 전문가로 용량을 분산해 라우팅 효율과 전문화를 높이고, 학습된 라우터가 토큰마다 필요한 전문가만 활성화한다. 이 덕분에 서빙 비용은 전체 2.4T가 아닌 활성 파라미터 규모를 따라간다.
- 요청 단위로 추론 깊이를 low/high/xhigh 중에서 선택할 수 있는 내장 추론 컨트롤을 제공해, 복잡한 다단계 추론에는 깊게, 고처리량 문서 처리에는 얕게 설정할 수 있다.

- 컴포넌트별로 적합한 텔레메트리 도구(DCGM, NVSM, UFM, NetQ, NMX, BCM, Run:ai, NIM 등)를 매핑하는 의사결정 프레임워크를 제시한다.

- InfiniBand 클러스터 사례를 통해 실제 도구 선택과 알림 구성 과정을 단계별로 보여준다.

#### 시사점

- 모든 도구·지표를 무작정 수집하는 대신 실패 도메인별 필요 최소 도구 세트를 선정하면, 알림 피로(alert fatigue)를 줄이고 실제 장애 대응 속도를 높일 수 있다.
- 분산 학습처럼 동기화된 워크로드는 평균이 아닌 최악의 랭크(straggler) 성능에 좌우되므로, GPU 지표만으로는 놓치는 패브릭 수준의 미세 장애(gray failure)를 함께 봐야 한다.
- 관측성 성숙도를 대시보드 개수가 아니라 "장애 컴포넌트와 다음 조치를 얼마나 빨리 알 수 있는가"로 측정해야 한다는 실무 원칙을 제공한다.

#### 용어 설명

- **NCCL(NVIDIA Collective Communications Library)**: 여러 GPU 간 all-reduce 같은 집합 통신 연산을 처리하는 NVIDIA 라이브러리.
- **BSP(Bulk Synchronous Parallel)**: 모든 참여 노드가 동기화 지점을 기다려야 하는 병렬 처리 모델로, 느린 노드 하나가 전체 작업을 지연시킨다.
- **gray failure**: 하드웨어가 완전히 다운되지는 않았지만 성능이 저하된 상태로, 시스템이 "정상"으로 보고해 발견이 어려운 장애 유형.
- **BER(Bit Error Rate)**: 네트워크 링크에서 오류 비트 비율로, 값이 높아지면 재전송이 늘어 성능이 저하된다.
- **DCGM(Data Center GPU Manager)**: GPU 사용률, 전력, 온도, NVLink, XID/ECC 오류 등을 수집하는 NVIDIA GPU 관리 도구.
- **UFM(Unified Fabric Manager)**: InfiniBand 네트워크의 포트 상태, BER, 혼잡도, 라우팅을 모니터링하는 NVIDIA 도구.
- **SLI/SLO(Service-Level Indicator/Objective)**: 서비스 상태를 측정하는 지표(SLI)와 그 목표치(SLO)로, 알림 설계의 기준이 된다.

**컴포넌트-텔레메트리 도구 매핑**

DCGM, NVSM, UFM, NetQ, NMX, BCM, Run:ai를 각 컴포넌트에 매핑한 표를 기준으로, 부족한 영역을 없애는 최소 도구 세트를 고르는 것이 핵심이다.

- DCGM은 GPU 사용률·전력·온도·NVLink·XID/ECC를 Prometheus로 내보내는 데 적합하며, NVSM은 DGX급 노드의 전체 시스템 상태(드라이브, 전원 등)를 보완한다.
- 패브릭 종류에 따라 도구를 선택한다: InfiniBand는 UFM, Spectrum Ethernet/RoCE는 NetQ.
- NMX는 랙 스케일 NVLink에만 필요하며, 일반 멀티노드 NVLink 토폴로지는 DCGM으로 충분하다.
- BCM은 저수준 카운터의 원천이 아니라 클러스터·작업 집계 계층으로 취급한다.
- Run:ai와 NIM은 워크로드 스케줄링 공정성이나 추론 SLO가 실제 운영 요구사항이 될 때 도입한다.

불필요한 익스포터 추가는 관측성이 아니라 노이즈이며 알림 피로로 이어진다는 것이 이 글의 핵심 원칙이다.

**InfiniBand 클러스터에 프레임워크 적용**

DGX 클러스터(InfiniBand + BCM + Slurm) 사례를 예로 든다. 대상 도메인은 플랫폼, GPU, InfiniBand 패브릭, 클러스터/작업이며, NetQ·NMX·Run:ai·NIM은 초기 배포에서 제외한다.

- 모든 노드에 Redfish/IPMI(팬, PSU, 섀시, BMC 상태)
- 모든 GPU 노드에 DCGM(사용률, 전력, 온도, XID/ECC, NVLink)
- DGX 노드에 NVSM(시스템 상태 집계)
- InfiniBand 포트 상태·BER·혼잡도·라우팅에 UFM
- 작업·예약·통합 하드웨어 알림을 위한 BCM

DCGM만으로는 서두에서 언급한 BER 저하(하나의 느린 랭크가 전체 처리량을 좌우하는 tail-at-scale 문제)를 놓치고, UFM만으로는 GPU XID 폭증이나 노드 전원 장애를 놓친다. 두 도구를 결합해야 GPU 시간 낭비를 막는 도메인을 모두 커버할 수 있다.

**실행 가능한 알림 세트 구성**

수백 개 지표 대신 SLI/SLO에 연결된 짧은 top-k 알림 세트를 우선한다. UFM Telemetry는 수백 개 필드를 제공하지만, 문서화된 고빈도 필드부터 시작한다.

- 플랫폼: `SPD_FAN_*`, `PWR_*`, `TEMP_*` (Redfish/IPMI)
- GPU: `DCGM_FI_DEV_GPU_UTIL`, `DCGM_FI_DEV_MEM_COPY_UTIL`, `DCGM_FI_DEV_POWER_USAGE`, `DCGM_FI_DEV_XID_ERRORS`, NVSM GPU/시스템 상태
- InfiniBand: `PortXmitDataExtended`, `SymbolErrorCounterExtended`, `Effective_BER`, `Total_Raw_BER`, `Chip_Temp`

### [Make Long-Running NVIDIA TensorRT Engine Builds Observable and Cancelable in Python or C++](https://developer.nvidia.com/blog/make-long-running-nvidia-tensorrt-engine-builds-observable-and-cancelable-in-python-or-c/)

`TensorRT` `IProgressMonitor` `Python` `C++` `Engine Build` `Agentic AI`

> TensorRT의 IProgressMonitor로 엔진 빌드 진행률 표시와 취소를 구현하는 법

#### 요약

- TensorRT 엔진 빌드는 수 초~수십 분이 걸릴 수 있는데, 대부분의 통합 환경은 진행 상황을 보여주지 않고 중간에 중단할 방법도 없다.
- `IProgressMonitor`는 빌드 중 TensorRT가 호출하는 추상 클래스로, `phase_start`/`step_complete`/`phase_finish` 세 메서드를 오버라이드해 중첩된 진행률 트리와 취소 신호를 처리한다.
- Python(ResNet-50)과 C++(MNIST) 공식 샘플을 기반으로 터미널 진행률 바 렌더링, Ctrl-C/프로그래매틱 취소 경로, IDE·서비스·에이전트 런타임 연동 방법을 다룬다.
- `step_complete`의 반환값(Bool)만이 빌드를 취소할 수 있는 유일한 지점이며, 취소는 즉시가 아니라 다음 스텝 경계에서 반영된다.

#### 시사점

- 긴 빌드 시간 동안 아무 피드백 없이 대기하던 문제를 해결해, GPU 낭비와 멈춘 세션(stuck session)을 줄일 수 있다.
- AI 에이전트 워크플로우에서 빌드 진행 상황을 스트리밍하고 타임아웃 시 자동 취소하는 로직을 구현할 수 있어, 에이전트 런타임의 시간 예산 관리에 직접 활용 가능하다.
- IDE 확장, HTTP 서비스(FastAPI), 에이전트 툴콜 등 다양한 표면(surface)에 동일한 콜백 하나로 진행률과 취소 기능을 통합할 수 있다.

#### 용어 설명

- **TensorRT**: NVIDIA의 딥러닝 추론 최적화 및 런타임 라이브러리로, 모델을 최적화된 엔진으로 컴파일한다.
- **IProgressMonitor**: TensorRT 빌더가 엔진 빌드 진행 상황을 알려주기 위해 호출하는 콜백 인터페이스.
- **엔진 빌드(engine build)**: ONNX 등으로 정의된 신경망을 GPU에서 실행할 최적화된 TensorRT 엔진으로 컴파일하는 과정.
- **타이밍 캐시(timing cache)**: 이전 빌드에서 측정한 커널 성능 정보를 저장해 재빌드 속도를 높이는 캐시.
- **택틱 서치(tactic search)**: 각 레이어 연산에 가장 빠른 커널 구현(택틱)을 찾기 위해 여러 후보를 실측 비교하는 과정.
- **SIGINT**: Ctrl-C 입력 시 프로세스에 전달되는 인터럽트 신호.
- **Server-Sent Events (SSE)**: 서버가 클라이언트로 단방향 실시간 스트림을 push하는 HTTP 기반 기법.

#### 상세 내용

**IProgressMonitor의 구조**

TensorRT는 빌드 도중 `IProgressMonitor`를 상속한 사용자 클래스의 세 메서드를 호출한다.

- `phase_start(phase_name, parent_phase, num_steps)`: 새 진행률 단계(phase)를 등록. `parent_phase`가 있으면 다른 phase에 중첩된다.
- `step_complete(phase_name, step) -> bool`: 스텝 완료마다 호출되며, `False`를 반환하면 빌드가 취소된다.
- `phase_finish(phase_name)`: phase 종료 시 호출.

빌더는 내부적으로 여러 스레드에서 동일한 모니터 인스턴스를 호출하므로 구현은 반드시 스레드 안전(thread-safe)해야 한다. 모니터는 `config.progress_monitor = MyMonitor()`(Python) 또는 `config->setProgressMonitor(&myMonitor)`(C++) 한 줄로 빌더 설정에 연결한다.

Each row is indented to indicate nesting under its parent phase.](https://developer-blogs.nvidia.com/wp-content/uploads/2026/07/image-65.webp)

**Python 구현: 진행률 바와 취소 처리**

`RichProgressMonitor` 클래스는 `Lock`으로 보호되는 딕셔너리에 phase 상태를 저장하고, ANSI 이스케이프 코드(`\x1b[NA`로 커서 이동, `\x1b[2K`로 줄 지우기)로 중첩 진행률 바를 그린다.

- `phase_start`는 반환값이 없어 취소할 수 없다. 최초 취소 가능 지점은 해당 phase의 첫 `step_complete` 호출 시점이다.
- SIGINT 핸들러를 등록해 Ctrl-C 시 `monitor._cancelled = True`로 플래그를 세우면, 다음 스텝 경계에서 빌드가 중단된다.
- `build_serialized_network()`는 취소 시 `None`을 반환한다.
- 동일한 플래그는 IDE의 Stop 버튼, 에이전트 타임아웃, CI 취소 웹훅 등 시그널이 아닌 경로에서도 설정할 수 있다.

**C++ 구현**

C++ 버전도 동일한 세 메서드(`phaseStart`, `stepComplete`, `phaseFinish`)를 오버라이드하며, 뮤텍스로 상태를 보호한다. 취소 플래그는 다른 스레드나 시그널 핸들러에서 설정될 수 있으므로 `std::atomic<bool>`을 사용한다.

**실제 시스템에 연동하기**

터미널 렌더링 외에 세 가지 통합 패턴을 제시한다.

- **IDE 확장**: `_render()`을 Language Server Protocol의 `$/progress` 알림(또는 `window/showProgress`)으로 대체. phase마다 하나의 progress token이 대응된다.
- **FastAPI/HTTP 서비스**: 백그라운드 스레드에서 빌드를 실행하고 `_render()`이 `asyncio.Queue`에 항목을 넣어 SSE(Server-Sent Events)로 스트리밍. 취소는 `POST /builds/{id}/cancel`이 `monitor.requestCancel()`을 호출.
- **에이전트 툴콜**: phase 전환마다 `{"phase": ..., "step": ..., "total": ...}` 형태의 구조화된 청크를 툴콜 스트림에 내보내고, 에이전트 타임아웃이 초과되면 동일한 `requestCancel()`을 호출.

![Three-layer architecture diagram with the TensorRT Builder at the top, IProgressMonitor in the middle, and four application sinks below: terminal renderer, IDE extension, FastAPI service, and agent runtime. A dashed red arrow shows the cancel signal flowing from a sink back through the monitor to the builder.](https://developer-blogs.nvidia.com/wp-content/uploads/2026/07/image-68.webp)
*이미지 출처: [원문](https://developer.nvidia.com/blog/make-long-running-nvidia-tensorrt-engine-builds-observable-and-cancelable-in-python-or-c/)*

**주의해야 할 엣지 케이스**

- 터미널 렌더러가 붙어 있는 동안 `stdout`을 파일/파이프로 리다이렉트하면 이스케이프 코드가 로그를 오염시킨다.
- `phase_finish()`는 `num_steps`를 다 채우기 전에도 호출될 수 있다(에러 복구, 빌더 내부 단락 처리, 취소 시 등). `current_step == num_steps`를 가정하면 안 된다.
- 취소 지연은 유한하지만 0은 아니다. 긴 택틱 서치 스텝 중에는 수 초~수십 초까지 걸릴 수 있다.

**대상 독자**: TensorRT로 대형 모델 엔진을 빌드하는 개발자, 특히 빌드 진행 상황 표시나 타임아웃 취소가 필요한 IDE 플러그인·백엔드 서비스·AI 에이전트 런타임 개발자에게 유용하다.

### [Setting a World Record for MoE Pre-Training on NVIDIA GB300 NVL72](https://developer.nvidia.com/blog/setting-a-world-record-for-moe-pre-training-on-nvidia-gb300-nvl72/)

`GB300 NVL72` `Mixture of Experts` `NVLink` `Megatron Core` `DeepSeek-V3` `Pre-Training`

> GB300 NVL72, MoE 사전학습서 GPU당 1,648 TFLOPs 세계기록 수립

#### 요약

- MoE(Mixture of Experts) 모델은 토큰마다 일부 파라미터(전문가)만 활성화해 연산 효율이 높지만, 전문가 간 all-to-all 통신이 학습 성능의 병목이 됨
- NVIDIA GB300 NVL72는 5세대 NVLink로 랙 내 72개 Blackwell Ultra GPU를 130TB/s 논블로킹 대역폭으로 연결해 이 통신 병목을 해소
- DeepSeek-V3 671B 모델을 256개 GPU로 사전학습한 결과 GPU당 1,648 TFLOPs를 기록, 이전 세대 GB200 NVL72(606 TFLOPs) 대비 약 3배 향상
- Megatron Core 외 TorchTitan, JAX 등 오픈소스 프레임워크도 NVIDIA의 지속적 소프트웨어 최적화로 6개월 만에 각각 최대 6배, 10배 성능 향상

#### 시사점

- 같은 GPU 수로 더 높은 처리량을 내므로, 동일 인프라에서 더 큰 모델을 더 빠르게 학습하거나 더 많은 실험을 반복할 수 있음
- 성능 향상이 하드웨어 교체 없이 소프트웨어 최적화만으로도 지속적으로 발생함을 보여주며, 이는 기존 인프라 투자의 수명을 늘리는 효과가 있음
- 256→1,024 GPU로 확장해도 프레임워크별 97~98.5%의 GPU당 성능이 유지되어, 대규모 분산 사전학습에서 확장 효율성이 검증됨

#### 용어 설명

- **MoE (Mixture of Experts)**: 모델 파라미터를 여러 "전문가"로 나누고 토큰마다 일부만 선택적으로 활성화하는 구조로, 전체 파라미터 수 대비 연산 비용을 낮춤
- **All-to-all 통신**: MoE 레이어에서 각 GPU가 토큰을 다른 GPU의 전문가에게 보내고 결과를 모으는 통신 패턴으로, 매 레이어마다 발생해 성능에 큰 영향을 줌
- **NVLink**: GPU 간 메모리를 직접 읽고 쓸 수 있게 해주는 NVIDIA의 고대역폭·저지연 인터커넥트로, 랙 내부(scale-up) 연결에 사용됨
- **Scale-up / Scale-out**: scale-up은 랙 내부처럼 촘촘하게 연결된 도메인 확장을, scale-out은 랙과 랙을 네트워크로 연결하는 확장을 의미
- **TFLOPs**: 초당 조(10¹²) 단위 부동소수점 연산 수로, GPU가 실제로 처리하는 연산 성능을 나타내는 지표
- **BlueField DPU**: 네트워킹, 스토리지, 보안, 텔레메트리 등 인프라 작업을 호스트 CPU에서 분리해 처리하는 NVIDIA의 데이터 처리 장치
- **ConnectX-8 SuperNIC / Quantum-X800 InfiniBand / Spectrum-X Ethernet**: 랙을 넘어선(scale-out) GPU 간 통신을 담당하는 NVIDIA의 네트워킹 하드웨어

#### 상세 내용

**MoE 학습의 통신 병목**

Dense(밀집) 모델은 토큰마다 모든 파라미터를 사용해 파라미터가 늘수록 토큰당 연산량도 늘지만, MoE는 일부 파라미터만 활성화한다. DeepSeek-V3는 671B 파라미터 중 토큰당 약 37B만 활성화해, 훨씬 작은 모델 수준의 비용으로 프론티어급 성능을 낸다.

- 대신 전문가들이 다른 GPU에 분산돼 있어, 매 MoE 레이어마다 순전파·역전파 양쪽에서 all-to-all 통신으로 토큰을 보내고 결과를 모아야 함
- 이 통신은 학습의 critical path(임계 경로)에 있어 처리량이 연산력만큼이나 통신 성능에 좌우됨
- 매 레이어·매 스텝마다 발생하므로 작은 지연도 누적돼 연산 뒤로 숨길 수 없게 되고, GPU를 더 추가해도 처리량이 늘지 않는 상황이 발생

![MoE 학습 스텝 구조: 순전파, 역전파, 그래디언트 동기화, 옵티마이저 스텝. 레이어 내에서 attention은 텐서 병렬 all-reduce와 all-to-all 통신을 통해 전문가와 연결된다. 레이어별 통신은 critical path에 있고, 그래디언트 동기화는 스텝당 한 번 발생해 연산과 오버랩될 수 있다.](https://developer-blogs.nvidia.com/wp-content/uploads/2026/07/image-59.webp)
*이미지 출처: [원문](https://developer.nvidia.com/blog/setting-a-world-record-for-moe-pre-training-on-nvidia-gb300-nvl72/)*

이 때문에 사전학습에는 모든 GPU가 서로 통신할 수 있는 촘촘한 scale-up 도메인(높은 균일 대역폭, 낮은 지연, 전체 이분 대역폭 보장)이 필요하다. 하나의 도메인 규모를 넘어서는 학습에는 여러 도메인을 연결하는 scale-out 통신도 필요한데, 이는 빈도는 낮지만 연산 시간 안에 반드시 끝나야 하는 두 번째 과제다.

**GB300 NVL72: 통신 병목을 겨냥한 co-design**

GB300 NVL72는 실리콘, 인터커넥트, 네트워킹, 소프트웨어를 하나의 플랫폼으로 함께 설계한 랙 스케일 시스템이다.

- 5세대 NVLink가 랙 내 72개 Blackwell Ultra GPU를 GPU당 1.8TB/s, 랙 전체 130TB/s의 논블로킹 all-to-all 대역폭으로 연결해 모든 GPU가 한 홉(hop)으로 서로에게 닿음
- NVLink는 메모리 시맨틱 방식으로, GPU가 다른 GPU의 HBM(고대역폭 메모리)을 네이티브 load/store 연산으로 직접 읽고 쓰며, 스위치 내부에서 리덕션(reduction) 연산까지 처리 가능
- 랙을 넘어서는 확장은 GPU당 800Gbps의 ConnectX-8 SuperNIC과 Quantum-X800 InfiniBand 또는 Spectrum-X Ethernet으로 처리하며, 그래디언트 트래픽을 연산 뒤에 숨김

### [Inside NVIDIA Rubin GPU Architecture: Powering the Era of Agentic AI](https://developer.nvidia.com/blog/inside-nvidia-rubin-gpu-architecture-powering-the-era-of-agentic-ai/)

`Rubin GPU` `Vera Rubin` `NVFP4` `HBM4` `Mixture of Experts (MoE)` `NVLink`

> 에이전틱 AI 추론에 최적화된 NVIDIA Rubin GPU 아키텍처와 랙 스케일 설계 분석

#### 요약

- Rubin GPU는 Blackwell 대비 에너지당 최대 10배 높은 에이전틱 처리량을 목표로 설계됨
- Tensor Core, Transformer Engine, HBM4 메모리, NVLink 6를 통해 연산·메모리·통신 병목을 동시에 개선

- Vera Rubin NVL72 랙 아키텍처와 DSX MaxLPS로 전력 예산 내 GPU 밀도를 높임

#### 시사점

- 멀티스텝 추론·도구 호출·긴 컨텍스트를 요구하는 에이전틱 AI 서비스를 구축하는 개발자에게 실질적인 지연시간·처리량 개선을 제공

- 랙 단위 전력 최적화(DSX MaxLPS)로 동일 전력 예산에서 더 많은 GPU를 운용할 수 있어 AI 팩토리 설계 시 참고할 수치 제공

#### 용어 설명

- **Agentic AI**: 단일 응답이 아니라 추론·계획·도구 사용·검증을 여러 단계에 걸쳐 수행하는 AI 워크플로
- **MoE (Mixture-of-Experts)**: 입력마다 여러 전문가 네트워크 중 일부만 선택적으로 사용하는 모델 구조
- **NVFP4**: NVIDIA가 정의한 4비트 부동소수점 정밀도 포맷으로 추론 성능과 정확도 균형을 맞춘 형식
- **HBM4**: 고대역폭 메모리(HBM)의 4세대 규격, GPU와 함께 패키징되어 초고속 데이터 접근을 제공
- **TMA (Tensor Memory Accelerator)**: GPU 내 복잡한 데이터 레이아웃 간 이동을 가속하는 하드웨어 유닛
- **NVLink**: GPU 간 초고속 직접 연결 인터커넥트로, 다중 GPU를 하나의 컴퓨팅 도메인처럼 묶어줌
- **KV 캐시**: 트랜스포머 추론 중 이전 토큰들의 키-값 쌍을 저장해 재계산을 피하는 캐시

**Rubin GPU 칩 아키텍처**

### [NVIDIA Vera CPU: Olympus Cores Built for Maximum Single-Thread Performance in Agentic AI](https://developer.nvidia.com/blog/inside-nvidia-vera-cpu-olympus-cores-built-for-maximum-single-threaded-performance-in-agentic-ai/)

`Vera CPU` `Olympus Core` `Agentic AI` `NVLink-C2C` `SOCAMM2 LPDDR5X` `Confidential Computing`

> NVIDIA Vera CPU의 Olympus 코어, 에이전틱 AI 위한 단일 스레드 성능 극대화 설계

#### 요약

- Vera CPU는 에이전트 워크로드(불규칙한 제어 흐름, 긴 의존성 체인, 포인터 기반 데이터 구조)에 최적화된 Olympus 코어를 중심으로 설계됨
- Olympus는 프론트엔드(분기 예측), 미드코어(비순차 실행), 실행 엔진, 캐시 서브시스템으로 구성되며 IPC(사이클당 명령어 처리량) 극대화에 집중
- NVIDIA Spatial Multithreading, Scalable Coherency Fabric, SOCAMM2 LPDDR5X 메모리, 듀얼 소켓 확장, Confidential Computing 등을 결합해 AI 팩토리 규모의 성능·보안·확장성 확보
- x86 CPU 대비 에이전틱 워크로드에서 최대 1.8배 성능 향상 (SPEC CPU 2026 기준)

#### 시사점

- 에이전트 런타임, 툴 호출, RL(강화학습) 환경처럼 CPU 실행 경로가 병목이 되는 워크로드를 개발하는 인프라 엔지니어에게 직접적인 참고가 됨
- 소켓 전체가 가득 찬 상태에서도 예측 가능한 단일 스레드 성능이 보장되어, 다수의 동시 에이전트 샌드박스를 운영할 때 지연 시간 변동성을 줄일 수 있음
- 듀얼 소켓을 단일 NUMA 도메인으로 노출하는 설계로 대규모 CPU 워크로드의 소프트웨어 튜닝 복잡도가 낮아짐

#### 용어 설명

- **IPC (Instructions Per Cycle)**: CPU가 한 사이클에 처리하는 명령어 수. 높을수록 동일 클록에서 더 많은 작업 수행
- **SMT (Simultaneous/Spatial Multithreading)**: 하나의 물리 코어에서 두 개의 하드웨어 스레드를 동시에 처리하는 기술
- **NUMA (Non-Uniform Memory Access)**: 메모리 접근 속도가 프로세서 위치에 따라 달라지는 다중 소켓 시스템 구조
- **NVLink-C2C**: NVIDIA의 칩 간(Chip-to-Chip) 고대역폭 인터커넥트 기술
- **SCF (Scalable Coherency Fabric)**: 코어, 캐시, 메모리 컨트롤러, I/O를 연결하는 Vera CPU의 온다이 통신 백본
- **CXL (Compute Express Link)**: 메모리 확장·풀링을 지원하는 코히런트 인터커넥트 표준
- **Confidential Computing**: 사용 중인 데이터를 암호화·격리해 보호하는 보안 컴퓨팅 방식

#### 상세 내용

**에이전틱 AI가 요구하는 새로운 CPU 설계**

에이전트는 샌드박스에서 코드를 실행하고 툴을 호출하며 컨텍스트를 조회하는 등 실행 경로의 상당 부분을 CPU에서 처리한다. 이 때문에 기존 클라우드 CPU가 중시하던 코어 밀도·처리량 대신, 다음과 같은 요구사항이 부각된다.

- 소켓이 완전히 로드된 상태에서도 강한 단일 스레드 성능
- 다수의 실행 컨텍스트를 지원할 충분한 코어당 메모리 대역폭
- 동시성 상황에서도 예측 가능한 지연 시간
- 불규칙한 제어 흐름, 긴 의존성 체인, 포인터 기반 데이터 구조의 효율적 처리

**Olympus 코어 아키텍처**

Vera Rubin 플랫폼 전반(CPU, GPU, 네트워킹, 스토리지, 메모리, 소프트웨어)의 공동 설계를 통해 개발된 Olympus 코어는 4개 블록으로 구성된다.

![Diagram of the NVIDIA Olympus Core Architecture showing the front end, mid core, execution engine, and cache subsystem.](https://developer-blogs.nvidia.com/wp-content/uploads/2026/07/image-64.webp)
*이미지 출처: [원문](https://developer.nvidia.com/blog/inside-nvidia-vera-cpu-olympus-cores-built-for-maximum-single-threaded-performance-in-agentic-ai/)*

- **프론트엔드**: 신경망 기반 분기 예측기로 사이클당 최대 2개의 분기(taken branch) 처리, 10-wide 디코드 엔진으로 명령어 공급 강화
- **미드코어**: 넓은 리네임/할당 엔진과 대형 리오더 버퍼(reorder buffer)로 비순차 실행 심화, 메모리 리네이밍·값 예측 등으로 의존성 병목 완화
- **실행 엔진**: 정수·분기·벡터·부동소수점·암호화·로드/스토어 자원을 동적으로 스케줄링해 높은 IPC 달성 (주파수보다 IPC에 집중)
- **캐시 서브시스템**: 깊은 캐시 계층, 메모리 모호성 해소(disambiguation), 다수의 하드웨어 프리페치 엔진과 그래프 프리페처로 불규칙 메모리 접근 지연 감소

**멀티스레딩: NVIDIA Spatial Multithreading**

에이전트 워크로드는 버스티하고 이벤트 기반이며 백그라운드 시스템 활동과 뒤섞여 실행되는 특성이 있다. 기존 SMT는 두 스레드가 코어 자원을 두고 경쟁해 "노이지 네이버" 효과가 발생할 수 있다.

![NVIDIA Spatial Multithreading concept with two hardware threads sharing core resources.](https://developer-blogs.nvidia.com/wp-content/uploads/2026/07/image-47.webp)
*이미지 출처: [원문](https://developer.nvidia.com/blog/inside-nvidia-vera-cpu-olympus-cores-built-for-maximum-single-threaded-performance-in-agentic-ai/)*

Vera CPU의 NVIDIA Spatial Multithreading은 두 하드웨어 스레드 간 자원을 더 명확히 분할해, 필요 시 고성능 단일 스레드 코어처럼 동작하거나 두 개의 격리된 실행 컨텍스트로 동작할 수 있다. Vera CPU는 88개의 Olympus 코어와 176개의 SMT 스레드를 지원한다.

### [NVIDIA NVLink: The Scale-Up Network for AI Factories](https://developer.nvidia.com/blog/nvidia-nvlink-the-scale-up-network-for-ai-factories/)

`NVLink` `NVLink Fusion` `Vera Rubin` `MoE` `Spectrum-X` `InfiniBand`

> AI 팩토리 성능을 좌우하는 GPU 스케일업 네트워크 NVLink 6세대 소개

#### 요약

- AI 팩토리는 수많은 가속기가 하나의 연산 단위처럼 동작해야 하며, 이를 위한 고대역폭·저지연 GPU 간 연결이 스케일업 네트워킹이다.
- 6세대 NVLink는 Vera Rubin NVL72 기준 GPU당 3.6TB/s 양방향 대역폭, 랙 전체 260TB/s를 제공하며, 오프더셸프 이더넷 대비 지연은 3배 낮고 패킷 처리율은 10배 높다.
- MoE(전문가 혼합) 모델의 all-to-all 통신 특성상 스케일업 대역폭·지연이 추론 처리량에 직결되며, NVLink는 오프더셸프 이더넷 대비 최대 2.3배의 디코드 처리량을 보인다.
- 핫스왑 스위치 트레이, 동적 트래픽 재라우팅 등 랙 단위 복원력 기능과 CPU-GPU 연결용 NVLink-C2C, 커스텀 실리콘 연동용 NVLink Fusion도 함께 제공된다.

#### 시사점

- 대형 언어모델·MoE 추론/학습 인프라를 설계하는 개발자에게는 GPU 개수뿐 아니라 스케일업 네트워크 성능이 실질적인 처리량과 비용 효율(토큰당 비용, 와트당 토큰)을 결정한다는 점이 중요하다.
- NVLink Fusion을 통해 하이퍼스케일러나 반도체 기업이 자체 커스텀 실리콘(XPU)을 NVIDIA 생태계와 결합해 개발 기간을 단축할 수 있다.
- 소프트웨어 스택(Dynamo, TensorRT-LLM, NCCL, NIXL)이 하드웨어와 공동 설계되어 있어, 인프라 도입 시 이 생태계와의 호환성을 함께 고려해야 한다.

#### 용어 설명

- **NVLink**: NVIDIA가 만든 GPU 간 초고속 직접 연결 기술로, 여러 GPU를 하나의 연산 유닛처럼 묶어준다.
- **스케일업/스케일아웃 네트워킹**: 스케일업은 한 도메인 내 GPU들을 고대역폭으로 연결하는 것, 스케일아웃은 데이터센터 전역의 서버를 연결하는 것을 뜻한다.
- **MoE(Mixture-of-Experts)**: 입력마다 일부 "전문가" 서브 네트워크만 선택적으로 사용하는 모델 구조로, GPU 간 토큰 교환(all-to-all 통신)이 많이 발생한다.
- **SHARP**: 네트워크 장비 내부에서 리덕션 등 집합 연산(all-reduce 등)을 직접 처리해 GPU 부담을 줄이는 인네트워크 컴퓨트 기술이다.
- **NCCL**: GPU 간 고속 통신을 위한 NVIDIA의 오픈소스 라이브러리다.
- **NVLink-C2C**: GPU와 CPU 사이를 캐시 일관성(coherent) 있게 연결하는 NVLink 기술이다.
- **NVLink Fusion**: 타사의 커스텀 실리콘(XPU)을 NVLink 생태계에 연결할 수 있게 하는 IP·인터커넥트 기술이다.

#### 상세 내용

**스케일업 네트워킹이 AI 팩토리 경제성을 좌우하는 이유**

스케일아웃 네트워크(NVIDIA Quantum InfiniBand, Spectrum-X Ethernet)는 수천~수십만 GPU 규모의 클러스터를 데이터 병렬 학습용으로 연결한다. 반면 스케일업 네트워크는 하나의 도메인 안에서 GPU들을 고대역폭·저지연·공유 HBM(고대역폭 메모리)으로 연결하며, 지연에 민감한 통신이 대부분 이 영역에서 발생한다.

- MoE 모델 추론에서는 전문가 병렬화로 여러 GPU에 전문가를 분산 배치하는데, 이 과정에서 토큰을 각 전문가에 분배·처리·재수집·재정렬하는 집중적인 all-to-all 통신이 발생한다.
- 스케일업 대역폭이 낮거나 지연이 크면 전문가 병렬화로 얻은 이득이 통신 오버헤드로 상쇄된다.
- DeepSeek-R1, Qwen 235B, 시뮬레이션한 2T 파라미터 LLM 기준으로 NVLink는 오프더셸프 이더넷 대비 최대 2.3배의 디코드 처리량을 제공한다.

![NVLink 6와 오프더셸프 이더넷의 모델별 디코드 처리량 비교 막대그래프](https://developer-blogs.nvidia.com/wp-content/uploads/2026/07/image2-10.webp)
*이미지 출처: [원문](https://developer.nvidia.com/blog/nvidia-nvlink-the-scale-up-network-for-ai-factories/)*

**스케일업 기술을 평가하는 기준**

단순 대역폭 스펙만으로는 부족하며, 실제 팩토리 단위 관점의 평가가 필요하다.

- **전달 성능(Delivered Performance)**: all-to-all 대역폭, 종단 간 지연(모든 GPU의 HBM에서 다른 GPU의 HBM까지), 집합 연산용 인네트워크 컴퓨트, 완전 통합된 소프트웨어 스택이 함께 작용한다.
- **팩토리 복원력**: 장기간 무중단 운영, 지속적 상태 모니터링, 컴포넌트 단위 유지보수 지원 여부가 실제 처리량(goodput)을 결정한다.
- **플랫폼 성숙도와 공급망**: 검증된 대규모 배포 이력을 가진 성숙한 기술 스택을 쓰는 것이 리스크를 줄인다.

**NVLink: 성능, 복원력, 성숙도**

- **세계적 수준의 성능**: Vera Rubin NVL72 기준 GPU당 3.6TB/s 양방향 대역폭, 72-GPU 도메인에서 260TB/s의 랙 단위 대역폭을 제공한다. GPU 간 종단 간 전송 지연은 오프더셸프 이더넷 기반 대안 대비 3배 낮고, 패킷 처리율은 10배 높다.
- NVLink 스위치 트레이와 5,000개 케이블로 구성된 NVLink 스파인이 all-to-all 토폴로지를 형성해 모든 GPU가 균일한 지연·대역폭으로 통신한다. 트레이 1개당 4개의 NVLink 6 스위치 칩, 28.8TB/s 대역폭, 14.4TFLOPS FP8 인네트워크 컴퓨트를 갖춘다.
- Vera Rubin NVL72 랙 하나에서 260TB/s 집계 대역폭과 130TFLOPS의 인네트워크 컴퓨트(all-reduce 등 집합 연산 가속용)를 제공한다.
- NVLink 로드맵은 최대 1152 GPU 규모의 스케일업 도메인과 co-packaged optics(광통신 통합 패키징) 연결을 지원할 예정이다.

**속도와 지능형 복원력을 함께 갖춘 설계**

NVLink 6는 다음과 같은 지능형 복원력 기능을 지원한다.

- 컨트롤 플레인 복원력
- 부분적으로만 채워진 랙에서의 운영 지원

- 세밀한 링크 텔레메트리(모니터링·장애 원인 파악용)

**성숙한 기술, 빠른 출시 주기**

NVLink는 거의 10년간 대규모로 production 배포되어 왔으며, 수백만 개의 NVIDIA 칩이 NVLink 지원 시스템에 탑재됐다. 함께 제공되는 주요 소프트웨어 스택은 다음과 같다.

- **Dynamo**: 다중 노드 GPU 환경에서 생성형·추론 모델을 확장하는 오픈소스 프레임워크(분리형 서빙, 동적 GPU 할당, KV-cache 인지 라우팅, NIXL 기반 데이터 이동 지원).
- **TensorRT-LLM**: 최적화된 커널과 저정밀 포맷(NVFP4, FP8)을 활용한 고성능 LLM 추론용 오픈소스 라이브러리.
- **NIXL**: GPU/CPU 메모리, NVMe, 원격 스토리지 간 빠른 데이터 전송용 오픈소스 라이브러리.
- **NCCL**: 10년 이상 이어진 고속 GPU 통신용 오픈소스 라이브러리, SHARP 기반 인네트워크 리덕션 지원.
- **Fabric and Memory Management**: 주소 공간 관리 API, 확장 가능한 메모리 시맨틱, HBM 접근을 위한 메모리 일관성 지원.

**NVLink-C2C: CPU까지 확장되는 패브릭**

Vera Rubin NVL72의 Vera CPU와 NVLink-C2C를 결합하면 CPU-GPU 간 1.8TB/s의 코히런트(cache-coherent) 대역폭을 제공하며, 이는 PCIe Gen6 대비 7배다. 이를 통해 KV-cache 오프로드, 멀티모델 실행, 데이터 처리, 에이전틱 오케스트레이션 같은 워크로드의 프로그래밍이 단순해진다. Vera CPU는 88개의 NVIDIA 커스텀 Olympus 코어를 탑재하고 있다.

**NVLink Fusion: 처음부터 다시 만들지 않는 세미커스텀 XPU 인프라**

하이퍼스케일러와 AI 네이티브 기업들은 특화된 커스텀 실리콘을 만들지만, 스케일업 네트워크 통합·랙 스케일 설계·공급망 리스크 등에서 어려움을 겪는다. NVLink Fusion은 검증된 NVLink 스택과 생태계를 커스텀 실리콘에 연결할 수 있게 해, 개발·배포 복잡도를 줄이고 출시 시점을 앞당긴다.

**대상 독자**: 대규모 LLM/MoE 학습·추론 인프라를 설계·운영하는 인프라 엔지니어, 데이터센터 아키텍트, AI 플랫폼 팀에게 유용하다.

### [Integrate NVIDIA Omniverse RTX Sensor Simulation Into Existing Apps](https://developer.nvidia.com/blog/integrate-nvidia-omniverse-rtx-sensor-simulation-into-existing-apps/)

`Omniverse` `OpenUSD` `RTX` `Physical AI` `Sensor Simulation` `Robotics`

> ovrtx SDK로 기존 앱에 NVIDIA Omniverse RTX 센서 시뮬레이션 통합

#### 요약

- NVIDIA Agent Toolkit에 포함된 Omniverse 라이브러리 중 하나인 `ovrtx`는 카메라·라이다·레이더 등 센서 출력을 OpenUSD 콘텐츠에서 생성하는 경량 C/Python SDK로, GitHub에 프리릴리스 형태로 공개됨.
- 개발자는 렌더러 생성 → OpenUSD 로드 → RenderProduct/RenderVar 설정 → 애플리케이션 루프에서 렌더링 스텝 실행 → 결과를 CPU/GPU로 반환받는 5단계로 기존 앱 구조를 유지한 채 통합 가능.
- `ovstage`(공유 USD 런타임), `ovphysx`(물리), `ovstream`(스트리밍), `ovstorage`(저장) 등 다른 Omniverse 라이브러리와 조합해 물리 시뮬레이션, 브라우저 스트리밍, USD 콘텐츠 관리 등 기능을 확장 가능.
- PTC Onshape Render Studio(클라우드 CAD)와 SimReady Blender 워크플로 등 실제 통합 사례를 통해 애플리케이션 아키텍처와 UX를 유지하면서 RTX 렌더링을 도입하는 방법을 소개.

#### 시사점

- 자체 3D 뷰어, CAD, 로보틱스, 디지털 트윈 애플리케이션에 별도 Omniverse Kit 앱을 새로 만들지 않고도 RTX 기반 물리 정확 렌더링과 센서 시뮬레이션을 붙일 수 있음.
- 데이터 모델과 UI 제어권을 애플리케이션이 그대로 유지하면서 합성 데이터 생성(SDG), 인지 시스템 테스트, 설계 리뷰 등에 활용 가능.
- GPU 메모리에서 바로 PyTorch/Warp로 텐서를 넘길 수 있어 딥러닝 파이프라인과의 연동 오버헤드를 줄일 수 있음.

#### 용어 설명

- **OpenUSD**: 3D 장면 데이터를 표준화된 방식으로 표현하는 오픈소스 포맷/API로, NVIDIA Omniverse의 기반 데이터 레이어.
- **RTX 렌더러**: NVIDIA RTX GPU의 RT Core(광선 추적 가속)와 Tensor Core(AI 가속)를 활용해 실시간 물리 기반 렌더링을 수행하는 엔진.
- **RenderProduct/RenderVar**: USD 안에서 어떤 센서(카메라, 라이다 등)로부터 어떤 형태의 출력(색상, 깊이, 시맨틱 분할 등)을 생성할지 정의하는 설정 단위.
- **SimReady 에셋**: 물리 시뮬레이션에 바로 사용 가능하도록 준비된 3D 에셋.
- **DLPack**: 프레임워크 간(NumPy, PyTorch 등) GPU/CPU 텐서 데이터를 복사 없이 교환하기 위한 표준 인터페이스.
- **합성 데이터 생성(SDG)**: 실제 데이터 대신 시뮬레이션으로 학습·테스트용 데이터를 인공적으로 생성하는 기법.

#### 상세 내용

**배경: 라이브러리 우선 접근**

기존 CAD, Blender, PLM/PDM, 자체 시뮬레이션 스택 등 다양한 애플리케이션에 물리 AI 기능을 넣으려면 별도 앱을 새로 만들기보다 필요한 기능만 라이브러리로 가져다 쓰는 방식이 유리하다.

- `ovrtx`는 이 라이브러리 우선 전략을 RTX 센서 시뮬레이션/시각화 영역에 적용한 것.
- 2026 SIGGRAPH에서 NVIDIA Agent Toolkit에 Omniverse 라이브러리가 포함된다고 발표되었으며, `ovrtx`가 그 안에서 RTX 센서 시뮬레이션 레이어 역할을 담당.

![Diagram showing an existing application connected to OpenUSD scene data, ovrtx, and RTX-rendered camera, lidar, radar, or sensor outputs](https://developer-blogs.nvidia.com/wp-content/uploads/2026/06/app-workflow-openusd-scene-data-nvidia-ovrtx.webp)
*이미지 출처: [원문](https://developer.nvidia.com/blog/integrate-nvidia-omniverse-rtx-sensor-simulation-into-existing-apps/)*

**통합 5단계**

기존 애플리케이션 루프 안에 아래 순서로 `ovrtx`를 호출한다.

1. 렌더러 생성 및 설정
2. 기존 파이프라인의 OpenUSD 콘텐츠 로드(`open_usd`, `open_usd_from_string`, `add_usd_reference`)
3. 카메라·라이다·레이더·시맨틱 분할 등에 필요한 RenderProduct/RenderVar 정의
4. 앱 루프에서 `renderer.step()`으로 렌더링/센서 시뮬레이션 진행
5. 결과를 CPU 또는 GPU 텐서로 매핑해 표시·저장·분석·후속 처리에 사용

```
renderer = ovrtx.Renderer()
renderer.open_usd(app_scene_or_usd_layer)
render_products = {"/Render/Camera"}
while app.is_running():
    app.update_scene_state()
    products = renderer.step(render_products=render_products, delta_time=app.frame_delta_seconds)
```

**핵심 구성 요소**

- **Omniverse RTX Renderer**: RT Core와 Tensor Core를 활용해 카메라·라이다·레이더 등 센서 출력을 물리 기반 광 전달(light transport) 시뮬레이션으로 생성.
- **ovstage**: CPU/GPU 메모리에 걸쳐 트랜스폼, 재질, 계층 구조, 시뮬레이션 상태 등 OpenUSD 장면 데이터를 읽고 쓰는 공유 런타임. `ovphysx`가 갱신한 시뮬레이션 상태를 `ovrtx`가 별도 장면 표현 없이 바로 읽을 수 있게 함.
- **OpenUSD**: 씬 그래프 기반 표준 3D 데이터 포맷으로, 복잡한 지오메트리·측광 조명·OpenPBR 재질·카메라·센서를 정의.
- **RenderProducts/RenderVars**: 출력 유형, 해상도, 포맷 등을 USD 네이티브 방식으로 정의하며 프로그램 방식 또는 런타임 API로 설정 가능.

### [Q&A: How Capcom Brought Path Tracing to RE ENGINE Across PRAGMATA and Resident Evil Requiem](https://developer.nvidia.com/blog/qa-how-capcom-brought-path-tracing-to-re-engine-across-pragmata-and-resident-evil-requiem/)

`RE ENGINE` `Path Tracing` `NVIDIA RTX Kit` `DLSS 4` `Ray Reconstruction` `ReSTIR GI`

> Capcom가 RE ENGINE에 패스 트레이싱 도입, 두 게임의 실시간 라이팅 혁신

#### 요약

- Capcom RE ENGINE팀이 2년에 걸쳐 레퍼런스 패스 트레이서를 개발하고, 이를 DLSS에 최적화된 게임용 버전으로 축소해 *PRAGMATA*와 *Resident Evil Requiem*에 동시 적용.
- 기존에는 간접광에만 레이 트레이싱을 썼지만, 이제 직접광까지 패스 트레이싱으로 처리해 게임플레이와 컷신 간 시각적 격차를 크게 줄임.
- NVIDIA RTX Kit, DLSS 4 Ray Reconstruction으로 노이즈 제거와 실시간 성능을 확보하고, ReSTIR GI를 자체 재구현해 실내 조명 노이즈를 완화.
- 스트랜드 헤어에 실시간 광 투과 효과를 적용해 두 타이틀 캐릭터의 머리카락 표현력을 향상.

#### 시사점

- 오프라인 제작 수준의 라이팅 품질을 실시간 게임에서도 구현할 수 있음을 대형 상용 게임 사례로 입증.
- DLSS Ray Reconstruction 같은 신경망 디노이징 기술이 실제 프로덕션 파이프라인에 통합되는 구체적 방식을 확인 가능.
- 자체 엔진에 패스 트레이싱을 도입하려는 개발자에게 아트·기술 파이프라인 전환 과정과 최적화 트릭(ScreenSpaceAlphaTest 등)이 참고 자료가 됨.

#### 용어 설명

- **패스 트레이싱(Path Tracing)**: 빛의 경로를 물리적으로 시뮬레이션해 사실적인 조명·반사·그림자를 구현하는 렌더링 기법.
- **레이 트레이싱(Ray Tracing)**: 광선을 추적해 반사·그림자를 계산하는 기법으로, 패스 트레이싱보다 단순화된 형태.
- **DLSS Ray Reconstruction**: NVIDIA의 AI 기반 디노이징(노이즈 제거) 기술로, 레이/패스 트레이싱 결과를 더 빠르고 안정적으로 정제.
- **NVIDIA RTX Kit**: 패스 트레이싱, 지오메트리 처리, 신경망 디노이징을 포함한 NVIDIA의 렌더링 기술 모음.
- **NEE(Next Event Estimation)**: 광원에서 직접 샘플링해 노이즈를 줄이는 렌더링 샘플링 기법.
- **ReSTIR GI**: 적은 샘플로도 효율적인 전역 조명(글로벌 일루미네이션)을 계산하는 샘플링 알고리즘.
- **스트랜드 헤어(Strand Hair)**: 개별 머리카락 가닥 단위로 시뮬레이션하는 헤어 렌더링 기술.

#### 상세 내용

**도입 배경**

RE ENGINE은 오랫동안 레이 트레이싱에 투자해 왔지만, *Resident Evil Requiem*과 *PRAGMATA*는 어두운 분위기와 복잡한 재질, 자연스러운 반사가 핵심인 타이틀이다.

- 개발팀은 간접광과 반사가 환경 전반에 걸쳐 개별 조정 없이 자연스럽게 통합되길 원했다.
- NVIDIA 패스 트레이싱과 프레임 생성 기술의 발전으로, 오프라인 제작에서만 가능했던 렌더링 품질을 실시간 게임에 구현하는 것이 현실화됐다.

**개발 과정**

두 팀이 2년간 협업해 먼저 레퍼런스 패스 트레이서를 만들고, DCC(디지털 콘텐츠 제작 도구)의 패스 트레이서와 라이팅·바운스 결과를 비교 검증하며 다듬었다.

- 검증된 레퍼런스 버전을 DLSS Ray Reconstruction 디노이징에 맞춰 축소한 게임용 버전으로 재구성.
- 테크니컬 아티스트가 인게임 통합을 주도해 두 타이틀에 동시 적용 가능했다.
- 블러 필터 기반의 투명 램프쉐이드처럼 지원이 까다로운 요소는 팀 간 신속한 공유로 해결.

**레이 트레이싱과의 차이**

기존에는 간접광에만 레이 트레이싱을 썼지만, 이제는 직접광까지 패스 트레이싱으로 처리한다.

- 기존 그림자 맵 방식은 해상도 제한으로 컷신에서는 수동 조정으로 덜 티가 났지만, 게임플레이 중에는 품질 저하가 느껴졌다.
- 패스 트레이싱은 항상 활성화돼 게임플레이와 컷신 간 시각적 격차가 크게 줄었다.

**다양한 디바이스 지원**

RE ENGINE은 RayQuery 기반 레이 트레이싱을 사용해 언제든 검증 가능한 기반을 갖추고 있었다.

- DLSS Ray Reconstruction이 수작업 셰이더 기반 디노이징보다 빠르고 안정적인 결과를 제공.
- 손상된 지오메트리 영역의 반사·그림자 최적화를 위해 **ScreenSpaceAlphaTest**라는 경량 기법을 자체 개발. 매 레이 히트마다 비용이 큰 텍스처 조회 대신, 레이 히트 위치와 화면 공간 깊이를 비교해 AlphaTest 통과 여부를 판정한다.

**샘플링과 디노이징**

이미시브(발광체) 샘플의 경우 BSDF 샘플링만 쓰면 히트 시에만 기여도가 누적돼 노이즈가 심해진다.

- 이를 해결하기 위해 NEE 전용 샘플링 구조를 도입.
- IBL(이미지 기반 조명)이 지배적인 실내 공간의 노이즈를 줄이기 위해 ReSTIR GI를 활용하되, RTX Kit의 구현을 그대로 쓰지 않고 논문을 기반으로 직접 재구현했다.

### [Integrating Context-Aware Video AI Agents Into Enterprise Workflows](https://developer.nvidia.com/blog/integrating-context-aware-video-ai-agents-into-enterprise-workflows/)

`NVIDIA NemoClaw` `Video Search and Summarization (VSS)` `RAG Blueprint` `AI Agent` `Video Analytics`

> 비디오 분석 결과를 자동으로 티켓·업무 흐름으로 연결하는 NVIDIA 에이전트 파이프라인

#### 요약

- NVIDIA NemoClaw가 VSS(비디오 검색·요약)와 RAG Blueprint(사내 문서 검색)를 오케스트레이션해, 비디오 분석에 조직 지식을 결합한 구조화된 보고서를 생성
- 사용자 의도를 먼저 확인하는 HITL(사람 개입) 프롬프트로 분석 범위(시나리오, 관심 이벤트, 추적 객체, 참고 지식)를 지정한 뒤 처리 시작
- 생성된 보고서를 기반으로 Jira 티켓 자동 생성 등 후속 업무까지 자동 트리거
- Computacenter, VAST Data 등 파트너사가 예지보전·실시간 스트림 분석에 실제 적용 중

#### 시사점

- 비디오 분석이 정적 보고서에서 끝나지 않고, 조직의 다른 시스템(Jira, Slack, DB, 티켓 큐)과 연동되는 자동화된 액션으로 이어짐
- 개발자는 오픈소스 블루프린트(VSS, RAG)를 조합해 도메인 특화 에이전트를 구축할 수 있으며, NemoClaw가 오케스트레이션 계층 역할을 함
- 전체 파이프라인에서 오케스트레이션과 지식 검색이 차지하는 지연 시간은 미미(약 8%)해 실용적인 엔터프라이즈 배포가 가능

#### 용어 설명

- **NVIDIA NemoClaw**: 자율 에이전트를 만들기 위한 오픈 블루프린트 모음. 여러 서비스를 조율해 업무를 실행시키는 오케스트레이션 계층
- **NVIDIA Blueprint**: 엔터프라이즈 규모 에이전틱 AI 파이프라인을 위한 커스터마이즈 가능한 레퍼런스 워크플로 (마이크로서비스+모델+API 조합)
- **VSS (Video Search and Summarization)**: 스트리밍/저장 비디오를 수집해 캡션·메타데이터를 생성하고 의미 기반 검색, Q&A, 이벤트 요약을 지원하는 블루프린트
- **RAG (Retrieval-Augmented Generation) Blueprint**: 사내 문서(매뉴얼, 정책, 규정 등)를 GPU 가속 벡터 DB에 인덱싱해 의미 검색을 제공하는 블루프린트
- **HITL (Human-in-the-Loop)**: 처리 시작 전 사람이 개입해 분석 파라미터를 확인·입력하는 절차
- **LVS (Long Video Summary)**: 긴 비디오를 계층적으로 요약하는 비디오 이해 도구
- **frag (Knowledge Retrieval Tool)**: RAG Blueprint를 호출해 조직 특화 컨텍스트를 검색하는 에이전트 도구

#### 상세 내용

**NemoClaw와 NVIDIA Blueprints란**

NemoClaw는 도메인 특화된 상시 가동 에이전트를 안전하고 저비용으로 구축할 수 있게 하는 오픈 블루프린트 모음이다. 이 글에서 사용하는 주요 블루프린트는 두 가지다.

- VSS: 스트리밍/아카이브 비디오를 캡션·메타데이터로 변환하고 의미 검색·Q&A·이벤트 요약을 지원
- RAG Blueprint: 매뉴얼, 정책, SOP 등 사내 문서를 GPU 가속 벡터 스토어에 인덱싱

**VSS가 의도를 포착하고 지식을 검색해 보고서를 생성하는 방식**

VSS는 에이전트에 내장된 도구 세트를 통해 유도형(guided) 비디오 분석을 제공한다. 세 가지 도구가 함께 동작한다.

- LVS 비디오 이해 도구: HITL로 시나리오, 관심 이벤트, 추적 객체, 지식 검색 쿼리를 수집한 뒤 장시간 비디오를 계층적으로 요약
- 지식 검색(frag) 도구: RAG Blueprint를 호출해 조직 특화 컨텍스트(문서, 정책, 참고자료)를 검색. 임베딩·재순위화·벡터 검색은 RAG Blueprint 내부에서 처리
- 보고서 생성 도구: 비디오 분석과 검색된 컨텍스트를 결합해 타임스탬프·내러티브 분석·인용이 포함된 구조화된 보고서 생성

**아키텍처**

시스템은 4개 계층으로 구성된다.

- 오케스트레이션: NemoClaw 에이전트, `vss-generate-video-report-rag` 스킬, HITL 프롬프트
- VSS 에이전트: 비디오 I/O, 검색, 이해, LVS, 지식 검색, 보고서 생성 도구 (지식 검색은 별도 확장이 아닌 에이전트 내장 기능)
- RAG Blueprint: NVIDIA RAG API, Milvus 벡터 DB, NVIDIA Nemotron 재순위화 NIM, 인덱싱된 참고·조직 문서
- LLM 융합: VSS 요약 결과에 RAG로 검색된 컨텍스트를 결합·보강

**배포 방법 (요약)**

- 사전 요구사항: VRAM 24GB 이상 NVIDIA GPU, Docker Engine + Compose v2, NGC/NVIDIA Build API 키, 배포된 RAG Blueprint, NemoClaw 설치
- VSS 저장소 클론 후 NGC 인증 → `.env` 파일에 배포 모드, GPU 하드웨어 프로필, `VSS_AGENT_CONFIG_FILE`을 `config_rag.yml`로 설정(지식 검색 활성화), RAG 서버 URL·API 키·컬렉션명 입력
- Docker Compose로 VST, Redis, Elasticsearch, LVS, NIM, 에이전트 스택 배포 (NIM 로딩에 5~15분 소요)
- 각 서비스 헬스체크(`/health`, `/v1/ready` 등) 후, NemoClaw 인스톨러(`init_nemoclaw.sh`)로 샌드박스·네트워크 정책·스킬 설치, OpenClaw TUI로 종단간 워크플로 테스트

### [Scaling Agentic AI Factories Through Extreme Co-Design with NVIDIA BlueField](https://developer.nvidia.com/blog/scaling-agentic-ai-factories-through-extreme-co-design-with-nvidia-bluefield/)

`NVIDIA BlueField` `DOCA` `Agentic AI` `KV Cache` `Vera Rubin` `DPU`

> BlueField DPU가 에이전틱 AI 인프라를 오프로드·가속·격리해 GPU 효율을 높인다

#### 요약

- 에이전틱 AI는 모델 호출 외에 툴 호출, 메모리 조회, 정책 검사, 스토리지 접근 등 다수의 인프라 작업을 유발해 인프라 자체가 추론 파이프라인의 일부가 됨
- NVIDIA BlueField-4 DPU와 Vera BlueField-4 STX 스토리지 프로세서가 네트워킹, 스토리지, 보안, 텔레메트리, 제어 플레인 작업을 호스트 CPU에서 오프로드
- DOCA 소프트웨어가 이러한 가속 인프라 서비스를 프로그래밍 가능하게 만들어 KV 캐시 재사용, 테넌트 격리 등 다양한 요구에 대응
- Vera Rubin 플랫폼과 DSX 아키텍처 전반에서 BlueField가 GPU 컴퓨트, CPU 실행, 스토리지/컨텍스트 메모리, 보안 영역을 통합 관리

#### 시사점

- 호스트 CPU 자원을 인프라 작업에 뺏기지 않게 되어 GPU 활용률, 토큰당 비용, 와트당 토큰 수 등 실질적인 생산성 지표가 개선됨
- KV 캐시를 컴퓨트-스토리지 노드 간에 공유·재사용할 수 있어 긴 컨텍스트·멀티턴 에이전트 워크로드에서 반복 prefill과 지연을 줄일 수 있음
- 보안 처리를 실리콘 레벨로 분리함으로써 멀티테넌트 AI 팩토리에서 호스트 침해와 무관하게 격리·정책 집행이 가능해짐

#### 용어 설명

- **BlueField DPU (Data Processing Unit)**: 네트워킹·스토리지·보안 작업을 호스트 CPU 대신 처리하는 전용 인프라 프로세서
- **DOCA**: BlueField/ConnectX 가속 인프라를 프로그래밍하기 위한 NVIDIA 소프트웨어 플랫폼
- **KV 캐시**: LLM 추론 중 생성되는 어텐션 중간 상태 데이터로, 재사용 시 반복 연산(prefill)을 줄여줌
- **Prefill**: LLM이 프롬프트를 처리해 초기 KV 캐시를 생성하는 추론 단계
- **NVIDIA CMX**: GPU 메모리와 대규모 공유 스토리지 사이에서 컨텍스트(주로 KV 캐시)를 저장하는 AI 전용 스토리지 플랫폼
- **Vera CPU**: NVIDIA의 에이전트 실행·오케스트레이션용 CPU로, 툴 호출과 데이터 처리를 담당
- **Spectrum-X / ConnectX-9**: NVIDIA의 이더넷 기반 고속 네트워킹 인프라 및 SmartNIC 제품군

#### 상세 내용

**에이전틱 AI가 인프라를 추론의 일부로 만든다**

에이전틱 AI 워크플로우는 GPU, CPU, 메모리, 네트워크, 스토리지, 보안을 아우르는 분산 작업으로 확장된다.

- GPU는 모델 추론과 토큰 생성을 담당하고, CPU는 툴 실행·검색 결과 처리·프롬프트 준비·출력 검증 등 에이전트 런타임을 조율
- 프롬프트와 대화, 에이전트 워크플로우가 길어질수록 KV 캐시 상태를 여러 추론 단계와 요청 간에 유지·재사용해야 하며, GPU 메모리가 제한되면 캐시를 축출·재계산하거나 다른 메모리 계층으로 옮겨야 해 지연시간·처리량·비용에 트레이드오프 발생

**BlueField가 AI 팩토리의 운영체제 역할을 한다**

BlueField-4는 Rubin GPU 및 Vera CPU 전반에서 DPU로 동작하고, Vera BlueField-4 STX 스토리지 프로세서는 CMX 컨텍스트 메모리와 AI 네이티브 스토리지를 담당한다.

- BlueField는 보안 처리를 실리콘 내부, 호스트 워크로드 영역 바깥으로 옮겨 통제 경계를 강화하면서 CPU·GPU 자원은 AI 작업에 보존

### [Build a Multi-Camera 3D Tracking Application with NVIDIA DeepStream 9.1 Skills](https://developer.nvidia.com/blog/build-a-multi-camera-3d-tracking-application-with-nvidia-deepstream-9-1-skills/)

`DeepStream` `Multi-Camera 3D Tracking` `Computer Vision` `Camera Calibration` `Jetson` `Agentic AI`

> DeepStream 9.1의 에이전틱 스킬로 다중 카메라 3D 객체 추적을 손쉽게 구축

#### 요약

- NVIDIA DeepStream 9.1은 여러 카메라의 탐지 결과를 하나의 3D 좌표계로 융합해 객체의 일관된 ID를 유지하는 MV3DT(Multi-View 3D Tracking)와, 카메라 보정을 자동화하는 AMC(AutoMagicCalib)를 새로 도입했다.
- 코딩 에이전트(Claude Code, Codex 등)가 자연어 프롬프트만으로 설치·설정·실행을 처리하는 13개의 에이전틱 스킬이 제공된다.
- MV3DT는 각 카메라가 독립적으로 2D 탐지를 3D 월드 좌표로 역투영하고, MQTT로 트랙릿을 공유해 동일 객체에 단일 글로벌 ID를 부여한다.
- AMC는 체스보드 같은 물리적 보정 패턴 없이 기존 영상 속 이동 객체 궤적만으로 카메라의 내부·외부 파라미터를 추정해 보정 파일을 생성한다.

#### 시사점

- 창고 안전관리, 리테일 분석, 스마트빌딩 모니터링 등 넓은 공간에서 카메라 간 객체 추적이 끊기던 문제를 해결할 수 있다.
- 수동 카메라 보정 작업(체스보드 배치, 운영 중단)이 사라져 배포 시간과 오류가 크게 줄어든다.
- 자연어 프롬프트 기반 스킬 덕분에 파이프라인 구축에 필요한 스크립트·설정 파일 편집 지식 없이도 빠르게 데모부터 실제 배포까지 진행할 수 있다.

#### 용어 설명

- **MV3DT (Multi-View 3D Tracking)**: 여러 카메라의 탐지를 하나의 3D 좌표계로 합쳐 동일 객체에 일관된 ID를 부여하는 추적 기술.
- **AMC (AutoMagicCalib)**: 영상 속 객체 이동 궤적을 분석해 카메라 보정을 자동으로 수행하는 마이크로서비스.
- **투영 행렬 (Projection Matrix)**: 2D 이미지 좌표를 3D 월드 좌표로 변환하는 데 쓰이는 3×4 행렬.
- **MQTT**: 여러 카메라 노드 간 트랙릿(추적 조각) 데이터를 공유하는 경량 발행-구독(pub/sub) 메시징 프로토콜.
- **BEV (Bird's-Eye View)**: 객체의 이동 경로를 위에서 내려다본 2D 지도 형태로 보여주는 화면.
- **VGGT (Visual Geometry Grounded Transformer)**: 객체 이동이 적을 때도 정확한 보정을 돕는 학습 기반 모델.
- **Bundle Adjustment**: 여러 카메라의 파라미터를 동시에 미세 조정해 전체 재투영 오차를 최소화하는 과정.

#### 상세 내용

**MV3DT는 어떻게 카메라 간 객체를 추적하나**

각 카메라는 독립적으로 객체를 탐지·추적하며, 이를 공유 3D 좌표계에 투영해 전체 환경에서 고유하고 안정적인 ID를 유지한다.

![MV3DT 시스템 개요 아키텍처 다이어그램](https://developer-blogs.nvidia.com/wp-content/uploads/2026/07/image5-7.webp)
*이미지 출처: [원문](https://developer.nvidia.com/blog/build-a-multi-camera-3d-tracking-application-with-nvidia-deepstream-9-1-skills/)*

데이터는 다음과 같이 흐른다.

- **탐지**: DeepStream 파이프라인이 모든 카메라 스트림을 처리하며, 기본 제공 탐지 모델 3종 지원
  - PeopleNetTransformer: 트랜스포머 기반 보행자 탐지기 (기본값)
  - PeopleNet v2.6.3: `DetectNet_v2` 아키텍처 기반 고효율 탐지기
  - RT-DETR 2D: 보행자·운반차·지게차 등을 탐지하는 다중 클래스 탐지기(산업 환경에 적합)
- **단안 3D 인식**: 각 카메라가 YAML 보정 파일에 저장된 3×4 투영 행렬과 지면 평면 가정을 이용해 2D 바운딩박스를 3D 월드 좌표로 역투영
- **다중 뷰 연관**: MQTT로 트랙릿을 공유하고, 3D 월드 공간에서의 근접성을 기준으로 동일 인물의 트랙릿을 매칭해 단일 글로벌 ID 부여
- **출력**: OSD(화면 표시, 2D/3D 바운딩박스 오버레이), BEV(실시간 상단뷰 궤적 지도), Kafka 메시징(센서 ID·객체 ID·3D 바운딩박스를 담은 프레임별 protobuf 메타데이터)

**AutoMagicCalib으로 카메라 네트워크 보정하기**

기존 방식은 체크보드 같은 보정 패턴을 카메라 앞에 물리적으로 배치해야 해 운영 중단과 특수 장비가 필요했다. AMC는 기존 영상이나 스트림 속 이동 객체 궤적을 DeepStream으로 분석해 이 과정을 자동화한다.

![AutoMagicCalib UI 결과 페이지, BEV 지도 위 궤적 표시](https://developer-blogs.nvidia.com/wp-content/uploads/2026/07/image4-7.webp)
*이미지 출처: [원문](https://developer.nvidia.com/blog/build-a-multi-camera-3d-tracking-application-with-nvidia-deepstream-9-1-skills/)*

내부 보정 파이프라인은 5단계로 구성된다.

1. 카메라별 궤적 추출
2. 단일 뷰 보정 및 정류(rectification) — 초점 거리, 투영 행렬, 렌즈 왜곡 추정
3. 다중 뷰 트랙릿 매칭 — 사용자가 지정한 정렬점을 초기 앵커로 사용
4. 번들 조정 — 모든 카메라 파라미터를 전역적으로 동시 정제해 재투영 오차 최소화
5. (선택) VGGT 보정 — 객체 이동이 제한적일 때 학습 기반 모델로 정확도 보강

### [Develop Lightweight USD Runtimes Faster with AI Agents](https://developer.nvidia.com/blog/develop-lightweight-usd-runtimes-faster-with-ai-agents/)

`OpenUSD` `nanousd-labs` `AI Agents` `USD Core Specification` `Physical AI` `NVIDIA Omniverse`

> AI 에이전트가 USD 표준 명세서만으로 경량 USD 런타임을 직접 생성

#### 요약

- NVIDIA Omniverse Labs의 실험 프로젝트 nanousd-labs는 기존 OpenUSD 코드베이스를 수정하는 대신, AOUSD가 개발한 "USD Core Specification"(USD 데이터 모델의 구성·해석 규칙을 정의한 표준 명세)을 계약(contract)으로 삼아 AI 에이전트가 새 런타임을 직접 생성한다.
- nanousd는 C++로 작성되고 안정적인 C ABI(응용 프로그램 바이너리 인터페이스)로 노출되는 독립적인 USD 런타임 데이터 모델 구현체로, 렌더링은 하지 않고 파싱·구성·쿼리·저장 기능만 담당한다.
- 개발자는 두 가지 방식으로 시작할 수 있다: (1) nanousd를 바로 clone/build해 사용하거나, (2) 인간의 지시를 재사용 가능한 스킬로 코드화한 "skillgraph"를 통해 방법론 자체를 익히고 자신의 스택에 적용한다.
- 에이전트는 명세서를 섹션 단위로 읽고, 해당 동작을 구현하는 코드를 작성한 뒤, 같은 표준에서 파생된 테스트 스위트로 검증하는 과정을 반복하며, 엔지니어는 성능·아키텍처 관련 의사결정을 담당한다.

#### 시사점

- 메모리 사용량, ABI, 성능 특성이 특정 배포 환경(예: 로봇, 엣지 디바이스)에 맞춰진 맞춤형 USD 런타임을 처음부터 코드를 직접 짜지 않고도 빠르게 생성할 수 있다.
- 표준화된 명세가 있으면 "정답"의 기준이 명확해져, 에이전트가 생성한 코드나 기존 자산이 스펙을 준수하는지 자동으로 검증할 수 있다.
- 안정적인 C API 덕분에 백엔드(OpenUSD ↔ nanousd)를 교체해도 클라이언트 코드는 그대로 유지되어, 실험과 성능 비교가 쉬워진다.

#### 용어 설명

- **OpenUSD**: 3D 씬(장면) 정보를 CAD, 시뮬레이션, 실측 데이터 등 다양한 소스에서 공유·조합할 수 있게 하는 개방형 장면 기술 프레임워크.
- **USD Core Specification**: AOUSD(Alliance for OpenUSD)가 만든, USD 데이터가 레이어 스택 전반에서 어떻게 구성·해석되는지 정의하는 버전 관리되는 공식 표준.
- **ABI (Application Binary Interface)**: 컴파일된 코드가 서로 다른 언어·모듈 간에 호출·연동되는 방식을 정의하는 저수준 인터페이스 규약.
- **Prim**: USD 씬을 구성하는 개별 요소(객체)로, 계층 구조로 배치된다.
- **Instanceable**: 반복되는 프림(예: 바퀴)이 각각 전체 복사본을 갖는 대신 하나의 정의(프로토타입)를 공유하도록 지정하는 USD 기능.
- **skillgraph**: 명세 준수 코드를 생성하기 위한 지시·프롬프트·테스트를 재사용 가능한 구조로 정리한 nanousd-labs의 구성 요소.
- **Hydra**: 기존 OpenUSD 스택에서 사용되는 렌더링 프레임워크(본문에서 비교 대상으로 언급).

#### 상세 내용

**배경: 왜 새로운 접근이 필요한가**

기존에는 특정 메모리 사용량, ABI, 성능 특성이 필요한 팀도 대형 기존 코드베이스를 그대로 가져다 수정해야 했다. nanousd-labs는 이 대신 표준 명세서로부터 런타임을 직접 생성하는 새로운 경로를 제시한다.

![A photorealistic 3D rendering of a warehouse environment with shelving, lighting, and floor details, illustrating a physical AI deployment scenario where lightweight, purpose-built USD runtimes are required.](https://developer-blogs.nvidia.com/wp-content/uploads/2026/07/image-37.webp)
*이미지 출처: [원문](https://developer.nvidia.com/blog/develop-lightweight-usd-runtimes-faster-with-ai-agents/)*

**AI 에이전트가 명세서를 기반으로 코드를 만드는 방식**

- 에이전트는 USD Core Specification을 "계약"으로 취급해, 명세가 정의한 동작(behavior)을 만족하는 코드를 작성한다.
- 에이전트는 명세를 섹션별로 읽고, 각 동작을 구현한 뒤, 같은 표준에서 파생된 테스트 스위트로 결과를 검증하며 반복 수정한다.
- 씬 데이터의 구조화·해석·오버라이드 규칙이 모두 텍스트로 표현되어 있어, 에이전트가 이를 그대로 적용하고 검증할 수 있다.
- 파싱, 씬 구성, 레이어 간 값 해석 등 기계적인 스펙-투-코드 작업은 에이전트가 담당하고, 성능 트레이드오프와 아키텍처 결정은 엔지니어가 맡는다.

**nanousd-labs란 무엇인가**

nanousd는 USD Core Specification에서 직접 파생된 독립적인 USD 런타임 데이터 모델 구현체로, C++로 작성되고 어떤 언어에서든 호출 가능한 공개 C API를 제공한다.

![A layered architecture diagram with a wide green bar at the bottom labeled USD Core Specification. On the right, a separate block labeled Existing OpenUSD stacks showing Hydra, USD tooling, and DCCs. - nanousd는 렌더러가 아니라 데이터 레이어로, 파싱·구성·쿼리·저장까지만 담당하고 픽셀 렌더링 이전에 멈춘다.
- 기존 OpenUSD 스택(Hydra, USD 툴링, DCC 등)은 그대로 유지되며 영향을 받지 않는다.
- 명세는 메모리, 스레딩, ABI, 언어를 요구사항이 아닌 구현 선택 사항으로 남겨두며, nanousd는 현재 안정적인 C ABI를 1차 선택으로 삼고 있다.
- 클라이언트 코드는 고정된 C API에 맞춰 컴파일되고 런타임에 구현체를 로드하므로, 백엔드(OpenUSD 또는 nanousd)를 교체해도 클라이언트 코드는 그대로 유지된다.

**시작하는 두 가지 방법**

1. **nanousd 직접 clone/build**: `nanousd-python`(GPU 불필요, 헤드리스 실행 가능한 Python 패키지)을 `pip install -e ./nanousd-python`으로 설치해 기존 USD 스테이지를 바로 열고 탐색할 수 있다. 이후 에이전트에게 자연어로 지시하면(예: "창고 AMR을 위한 USD 스테이지를 작성하라") 스펙 준수 여부를 확인하며 자산을 생성하거나, 기존 자산(`robot.usda` 등)이 스펙을 준수하는지 검증할 수 있다.
2. **skillgraph 활용**: 약 10분짜리 튜토리얼을 통해 Core Specification을 충족하는 USD ASCII(USDA) 파서를 생성하는 스킬을 실행해보며 방법론 자체를 익힐 수 있다. 아직 명세 전체를 커버하지는 않으며, 여러 파트 간 정합성(multi-part cohesion) 확보가 향후 과제로 남아 있다.

**공식 예시**: 두 바퀴를 동일한 자산에 대한 instanceable 참조로 생성하도록 지시했을 때, 에이전트는 초기 초안에서 `instanceable` 플래그가 누락되어 바퀴가 각각 별도의 전체 복사본으로 구성된 것을 발견하고 스펙에 맞게 수정한 뒤, 하나의 프로토타입을 공유하도록 재구성한 결과를 보고했다.

**대상 독자**: 물리 AI(로봇, 시뮬레이션 등) 파이프라인을 구축하며 특정 메모리·성능·ABI 요구사항에 맞는 경량 USD 런타임이 필요한 개발자, 그리고 표준 명세 기반 AI 에이전트 코드 생성 방법론에 관심 있는 개발자에게 유용하다.

### [Building Faster Cryptography with Carryless Multiplication in NVIDIA CUDA 13.3](https://developer.nvidia.com/blog/building-faster-cryptography-with-carryless-multiplication-in-nvidia-cuda-13-3/)

`CUDA` `CUDA 13.3` `GHASH` `AES-GCM` `zero-knowledge proofs` `PTX`

> CUDA 13.3의 clmad 명령어로 GPU에서 암호학용 캐리리스 곱셈을 하드웨어 가속

#### 요약

- CUDA 13.3에서 Ampere(SM 80) 이상 GPU에 캐리리스 곱셈(carryless multiplication)을 하드웨어로 처리하는 새 PTX 명령어 `clmad`가 추가됨
- AES-GCM의 무결성 해시인 GHASH와 영지식 증명의 핵심 루프인 sum-check 프로토콜, 두 워크로드로 성능을 벤치마크
- B200에서 GHASH 처리량이 약 6.3TB/s(DRAM 읽기 대역폭에 근접)로, 기존 비트슬라이스 방식 대비 최대 18.8배 향상
- $GF(2^{128})$ 상의 sum-check는 기존 대비 4~13배 속도 향상

#### 시사점

- x86 CPU에는 15년 넘게 있었던 캐리리스 곱셈 하드웨어 가속이 처음으로 GPU에 도입되어, 이미 배포된 Ampere 이후 모든 시스템에서 즉시 활용 가능
- TLS·VPN·데이터센터 암호화의 기반인 AES-GCM뿐 아니라 CRC, Reed-Solomon, BCH 코드, 양자 안정화 코드, 후양자 암호, Binius 같은 이진체 기반 영지식 증명 시스템까지 광범위한 암호·부호이론 워크로드의 비용 구조를 바꿈
- GPU 파이프라인에 암호화를 통합하는 CUDA 개발자나 이진체 프로토콜을 연구하는 보안·프라이버시 연구자가 인라인 PTX 예제를 커널에 바로 적용 가능

#### 용어 설명

- **carryless multiplication (캐리리스 곱셈)**: 자리올림 없이 비트 단위로 곱하는 연산으로, 암호학의 이진체 연산에서 핵심적으로 쓰임
- **PTX**: NVIDIA GPU용 저수준 중간 명령어 세트로, CUDA 커널이 컴파일되는 대상
- **GF(2^n) (이진 확장체)**: n비트로 표현되는 유한체로, 덧셈은 XOR, 곱셈은 기약다항식으로 나눈 나머지로 정의됨
- **GHASH**: AES-GCM에서 데이터 무결성을 검증하는 인증 해시 계산 알고리즘
- **AES-GCM**: 인증과 암호화를 동시에 수행하는 AEAD(Authenticated Encryption with Associated Data) 암호 방식으로 TLS·VPN 등에 쓰임
- **sum-check protocol**: 검증자가 다변수 다항식의 합을 직접 계산하지 않고도 증명자의 계산 결과를 확인할 수 있게 하는 영지식 증명의 핵심 프로토콜
- **Karatsuba algorithm**: 큰 수의 곱셈을 더 작은 곱셈들로 분할해 계산량을 줄이는 알고리즘

#### 상세 내용

**이진 확장체(Binary Extension Fields)**

가장 작은 유한체 $GF(2)$는 한 비트로, 덧셈은 XOR, 곱셈은 AND다. 암호학에서는 여러 비트를 묶은 $GF(2^n)$(이진 확장체)을 사용하며, 이때 덧셈은 여전히 XOR이지만 곱셈은 각 비트 쌍의 곱을 XOR로 합친 뒤 기약다항식으로 나눈 나머지를 취해야 한다.

- 기존에는 이 연산을 AND/XOR 연산의 반복적인 시프트·마스킹으로 에뮬레이션해야 해 오버헤드가 컸음
- x86은 PCLMULQDQ 같은 하드웨어 지원이 있었지만 GPU에는 없어 비트슬라이스 회로 같은 대체 기법에 의존해야 했음

**하드웨어 지원: clmad 명령어**

CUDA 13.3은 `clmad`라는 새 PTX 캐리리스 곱셈-누산(multiply-accumulate) 명령어를 추가했다. x86의 PCLMULQDQ처럼 64비트 입력 두 개를 128비트 결과로 캐리리스 곱셈하며, `.hi`/`.lo` 변형으로 64비트 누산기를 더한 128비트 결과의 상/하위를 각각 계산한다.

- Ampere(`sm_80`) 이상 GPU에서 하드웨어 가속됨
- $GF(2^{128})$ 원소 곱셈은 Karatsuba 알고리즘으로 `clmad` 명령 6번에 처리 가능
- 256비트 결과를 다시 128비트 체로 되돌리려면 Barrett reduction(추가 CLMAD 호출 이용) 또는 시프트-XOR 기반 다항식 장제법 방식의 reduction이 필요

**GHASH 가속**

GHASH는 기약다항식 $X^{128} + X^7 + X^2 + X + 1$을 기준으로 $GF(2^{128})$ 상의 이진 곱셈에 크게 의존하기 때문에 `clmad`에 적합하다. 입력을 128비트 블록으로 나눠 누산기에 XOR한 뒤 해시 키(H, 제로 블록을 AES로 암호화해 도출)와 곱하는 과정을 반복한다.

![Line chart of throughput of GHASH (GB/s, 0–8000) for the B200 and RTX 5090 for increasing payload sizes from 0-2 GB of data, showing the CLMAD variant exhibits up to 18.8× higher throughput than the bitsliced vriant on the B200 and up to 2× higher throughput on the 5090.](https://developer-blogs.nvidia.com/wp-content/uploads/2026/07/image-40.webp)

- RTX 5090: `clmad` 기반 GHASH 최고 처리량 약 1,300GB/s, 비트슬라이스 대비 2배
- B200: 최고 처리량 약 6,335GB/s(DRAM 읽기 대역폭에 근접), 비트슬라이스 대비 최대 18.8배
- 비트슬라이스 기준에서는 SM 개수와 클럭이 낮아 B200이 오히려 RTX 5090보다 느렸지만, CLMAD 가속이 이를 뒤집음

**영지식 증명: sum-check 가속**

Sum-check 프로토콜은 검증자가 결과를 직접 재계산하지 않고도 $n$-변수 다항식의 불(boolean) 입력에 대한 합을 증명자가 알고 있음을 증명하게 해주는 여러 영지식 증명 시스템의 기반 primitive다. 각 라운드에서 증명자는 (1) 평가값들의 곱의 합을 계산하고, (2) $d$개 점에서 보간해 라운드용 단변수 다항식을 만들고, (3) 검증자가 고른 랜덤 점에서 다시 보간해 다음 라운드로 넘어가며, 이 과정에서 다수의 이진 확장체 곱셈이 필요하고 대부분 병렬화 가능하다.

- Irreducible사가 개발한 비트슬라이스 회로 기반 구현과 비교
- RTX 5090에서 3~4배, B200에서 최대 13배 성능 향상
- 다항식 크기와 구성(composition) 크기가 커질수록 성능 향상 폭도 소폭 증가

**대상 독자**: GPU 파이프라인에 암호화 기능을 통합하는 CUDA 개발자, 그리고 이진체 기반 영지식 증명 프로토콜을 연구·구현하는 보안/프라이버시 엔지니어에게 유용하다.

### [Lessons From the Leaderboard: What 5,000+ Kagglers Taught Us About Improving AI Reasoning](https://developer.nvidia.com/blog/lessons-from-the-leaderboard-what-5000-kagglers-taught-us-about-improving-ai-reasoning/)

`Nemotron` `Kaggle` `LoRA` `AI Reasoning` `Blackwell` `Fine-Tuning`

> Kaggle 5천여 명이 참가한 Nemotron 추론 챌린지에서 얻은 5가지 실전 교훈

#### 요약

- NVIDIA의 Nemotron Model Reasoning Challenge에 5,000명 이상, 4,000개 팀이 참가해 동일한 오픈 모델·벤치마크·인프라 조건에서 추론 정확도를 높이는 기법을 겨뤘다.
- 상위 팀들은 LoRA 어댑터 학습, 합성 chain-of-thought(단계별 추론 과정) 데이터 구축, 퍼즐 유형별 전용 솔버 개발 등 전체 엔지니어링 워크플로우로 접근했다.
- 인터넷 접속 불가, 추론 코드 수정 불가, Nemotron-3-Nano-30B에 rank 32 이하 LoRA 어댑터만 제출 가능 등 엄격한 제약 속에 진행됐으며, 모든 제출물은 동일한 NVIDIA RTX PRO 6000 Blackwell GPU 환경에서 평가됐다.
- 리더보드와 토론 스레드에서 도출된 5가지 교훈: 검증 가능한 추론 데이터 만들기, 토큰 예산에 맞춘 설계, 암기와 추론의 분리, 도구를 답 계산이 아닌 데이터 생성에 활용, 유형별 트레이드오프 측정.

#### 시사점

- 프롬프트나 학습 데이터에 chain-of-thought을 포함시킬 때, 단순히 양을 늘리기보다 각 단계가 검증 가능한지 확인하는 워크플로우가 실제 정확도 향상에 더 중요하다.
- 긴 프롬프트·검색 결과·로그·멀티스텝 추론 트레이스를 다루는 모든 시스템에서 반복 구조를 압축해 토큰 예산 내에서 모델이 실제 추론에 쓸 여유를 확보하는 전략이 유효하다.
- 단일 정확도 점수만 보면 특정 태스크 유형에서의 퇴보를 놓칠 수 있으므로, 프로덕션 평가 체계에서도 태스크 유형별 세분화된 검증이 필요하다.

#### 용어 설명

- **Chain-of-thought (CoT)**: 모델이 최종 답에 도달하기까지의 단계별 추론 과정을 보여주는 데이터/출력 방식.
- **LoRA (Low-Rank Adaptation)**: 대형 모델 전체를 재학습하지 않고 소량의 추가 파라미터만 학습해 효율적으로 미세조정하는 기법.
- **Nemotron**: NVIDIA가 공개한 오픈 소스 파운데이션 모델 계열.
- **SFT (Supervised Fine-Tuning)**: 정답이 있는 데이터로 모델을 지도 학습 방식으로 추가 학습시키는 과정.
- **CSP (Constraint Satisfaction Problem)**: 여러 제약 조건을 동시에 만족시키는 해를 찾는 문제 유형.
- **Private leaderboard**: 참가자에게 공개되지 않은 별도 데이터셋으로 최종 순위를 매기는 평가판.
- **Token budget**: 모델이 한 번의 응답에서 생성할 수 있는 최대 토큰(텍스트 단위) 수 제한.

#### 상세 내용

**챌린지 개요**

Nemotron Model Reasoning Challenge는 동일한 오픈 모델, 벤치마크, 인프라, 평가 기준에서 출발했을 때 추론 정확도를 개선하는 방법을 탐구하기 위해 기획됐다.

- 5,000명 이상, 4,000개 팀 참가, 1,000개 이상의 토론 게시물 생성
- 제출은 Nemotron-3-Nano-30B에 대한 rank 32 이하 LoRA 어댑터로 제한
- 평가 시 인터넷 접속 불가, 추론 코드 수정 불가
- 모든 팀은 Google Cloud G4 VM의 NVIDIA RTX PRO 6000 Blackwell GPU에서 동일하게 실행

**교훈 1. Chain-of-thought 데이터는 검증 가능해야 한다**

단순히 `prompt → final answer` 형태보다, `prompt → 솔버가 생성한 트레이스 → 검증/보정 → 학습` 워크플로우가 더 효과적이었다.

- 1위 팀 re는 합성 문제와 솔버 기반 트레이스를 생성해 SFT로 학습
- 2위 팀 vli도 유사하게 프롬프트 생성과 트레이스 생성 파일을 분리해 관리
- ATLAS 토론(Shehab Anwer)에서도 "검증된 트레이스가 무필터링된 규모보다 중요하다"는 점이 재확인됨

**교훈 2. 토큰 예산에 맞춰 추론을 설계한다**

긴 트레이스는 논리가 맞아도 토큰이 부족하면 실패한다. 반복 구조(긴 문자열, 표, 보일러플레이트)를 압축하면서 논리는 보존하는 것이 핵심이다.

- Tong Hui Kang의 비트 조작(bit-manipulation) 전략이 이후 여러 솔루션의 기반이 됨
- 1~3위 팀은 이를 HEX, 하이브리드 hex-binary 서명 등으로 확장해 트레이스를 압축

**교훈 3. 암기할 것과 풀어야 할 것을 분리한다**

재사용 가능한 패턴(스키마, 공식, 룩업 테이블)은 저장/조회하고, 모델은 매번 달라지는 부분만 풀도록 설계하면 효율이 높아진다.

- 1위 팀 re는 크립트애리즘(문자-숫자 치환 퍼즐) 패턴에 대한 서명 카탈로그를 활용
- 2위 팀 vli는 이를 "저장 대 연산" 분리로 설명
- 3위 팀 YS-L도 암기와 실행을 나누는 2단계 접근을 사용

**교훈 4. 도구는 최종 답이 아니라 더 나은 학습 데이터를 만드는 데 쓴다**

평가 시 외부 프로그램 실행이 불가했기에, 도구 활용은 학습 데이터 생성 단계(업스트림)에서 이뤄졌다. 정답은 맞지만 잘못된 추론 과정을 거친 트레이스, 모순을 숨긴 트레이스 등을 걸러내는 데 도구가 사용됐다.

- Mayur Pawar는 솔버 엔지니어링과 실행 가능한 CoT 감사(audit)로 잘못된 트레이스를 걸러냄
- StSTXion은 후보 선택, 제약 전파, 모순, 백트래킹 등 탐색 과정 자체를 학습 데이터로 사용

**교훈 5. 추론 트레이드오프를 유형별로 측정한다**

단일 종합 점수는 특정 태스크 유형에서의 퇴보(regression)를 가릴 수 있다. 태스크 유형별로 정확도와 실패 패턴을 나눠 추적해야 한다.

- EnDream은 카테고리별 오류 분석으로 포맷 성공과 실제 추론 품질을 구분해 병목을 드러냄
- Yurnero는 전체 학습 검증과 도메인별 공개 체크를 병행해 어떤 변화가 어떤 유형에 도움 되는지 파악
- Taha는 반복 제출 시 점수가 흔들릴 수 있다는 비결정성(non-determinism) 문제를 지적

**정리**

가장 강력한 접근법들은 다음을 결합했다: 검증 가능한 추론 트레이스 확보, 토큰 예산을 추론 문제의 일부로 취급, 구조가 명확한 태스크에는 전용 솔버 사용, 실제 신경 쓰는 실패 유형에 대한 검증, 리더보드 점수뿐 아니라 추론 행동 자체를 보존하는 학습 선택.

Nemotron이 모델·데이터셋·학습 레시피를 공개했기 때문에 커뮤니티가 서로의 접근을 검토하고 비교하며 지식을 공유할 수 있었다는 점도 챌린지의 핵심 가치로 강조된다.

**대상 독자**: LLM 파인튜닝, chain-of-thought 데이터 설계, 또는 제한된 토큰 예산 내에서 추론 성능을 최적화해야 하는 ML 엔지니어와 AI 애플리케이션 개발자에게 유용하다.

- NVIDIA TAO 에이전트 스킬을 이용하면 코딩 에이전트(Codex)가 데이터 오류 패칭, 학습 컨테이너 실행, 하이퍼파라미터 스윕까지 자동으로 수행한다.
- Woven Traffic Safety(WTS) 데이터셋 기준, LoRA 파인튜닝만으로 정확도가 54.41%→87.14%로 상승했고, TAO AutoML 스윕 후 93.35%까지 향상됐다.
- 자연어 프롬프트 단 두 번으로 하루 만에 도메인 특화 비전-언어 모델을 학습·평가·배포까지 완료할 수 있다.

#### 시사점

- 파인튜닝 파이프라인 구축에 걸리던 수일의 엔지니어링 작업을 자동화해 프로덕션 적용 속도를 크게 단축할 수 있다.
- LoRA는 풀 파라미터 SFT 대비 GPU 시간을 약 7배 절감해, 비용 효율적으로 도메인 특화 모델을 만들 수 있다.
- 교통안전 외에도 창고 모니터링, 자율주행 인지, 로봇 워크셀 등 다양한 비전 추론 태스크에 동일한 워크플로우를 그대로 적용할 수 있다.

#### 용어 설명

- **Cosmos 3**: NVIDIA의 오픈 물리 AI 월드 파운데이션 모델로, 이해·생성·시뮬레이션·행동을 하나의 모델로 통합한다.
- **MoT (Mixture-of-Transformers)**: 오토리그레시브(자기회귀) 추론 경로와 디퓨전(확산) 생성 경로를 결합한 듀얼 타워 아키텍처.
- **LoRA (Low-Rank Adaptation)**: 기본 모델 가중치는 고정하고 저랭크(rank) 행렬만 학습시켜 적은 자원으로 파인튜닝하는 기법.
- **NVIDIA TAO**: 비전 모델의 학습·평가·최적화·서빙을 자동화하는 에이전트 스킬 라이브러리.
- **AutoML**: 학습률, LoRA 랭크 등 하이퍼파라미터를 자동으로 탐색·최적화하는 기능.
- **NIM (NVIDIA Inference Microservice)**: 모델을 프로덕션에 바로 배포할 수 있도록 최적화된 컨테이너 형태의 추론 서비스.

#### 상세 내용

**Cosmos 3의 MoT 아키텍처**

Cosmos 3는 강건한 추론·계획을 담당하는 오토리그레시브 트랜스포머와, 미래 세계 상태·행동을 예측하는 디퓨전 트랜스포머를 결합했다. Super 64B, Nano 16B 등 여러 크기로 제공되며 VANTAGE-Bench(비디오 이해), PAI-Bench·Physics-IQ(월드 생성), RoboLab·RoboArena(행동 정책) 등 오픈 모델 벤치마크에서 1위를 기록 중이다.

- 오토리그레시브 경로의 key-value 상태(K_AR, V_AR)가 크로스 스트림 연결을 통해 디퓨전 경로의 Full Attention 블록으로 전달됨

**LoRA vs 풀 파라미터 SFT**

파운데이션 모델을 특정 도메인(카메라 각도, 엣지 케이스, 환경 등)에 맞추려면 포스트트레이닝이 필요하다.

- **Full-Parameter SFT**: 도메인 변화가 크거나 구조적 변경이 필요할 때 적합하지만, 모든 가중치를 업데이트하므로 연산 자원이 많이 들고 일반 지식 성능이 퇴화할 수 있음
- **LoRA**: 기본 가중치를 고정하고 저랭크 분해 행렬만 학습시켜 빠른 반복이 가능
- 이번 실험에서 LoRA는 풀 파라미터 SFT 대비 GPU 시간을 약 7배 절감해 하루 만의 포스트트레이닝을 가능하게 함

**TAO 에이전트 스킬로 자동화되는 워크플로우**

Cosmos 3 포스트트레이닝에는 두 가지 방법이 있다. 하나는 학습 레시피·데이터셋 포맷·설정 파일을 직접 다루는 오픈 프레임워크이고, 다른 하나는 코딩 에이전트가 워크플로우를 추론해 데이터 문제를 패치하고 학습 컨테이너를 실행하며 하이퍼파라미터를 스윕하는 TAO 에이전트 스킬이다.

- Cosmos 3는 멀티모달 이해·논리를 담당하는 Reasoner 타워와 비디오·행동 생성을 담당하는 Generator 타워로 분리되며, TAO 에이전트 스킬은 이 중 Reasoner 가중치만을 대상으로 포스트트레이닝을 수행하도록 자동 처리한다.

### [How to Run an Autoresearch Workflow with RL Agent Skills and NVIDIA NeMo](https://developer.nvidia.com/blog/how-to-run-an-autoresearch-workflow-with-rl-agent-skills-and-nvidia-nemo/)

`NVIDIA NeMo RL` `NVIDIA NeMo Gym` `Reinforcement Learning` `Codex` `Agent Skills` `NVIDIA Brev`

> 코딩 에이전트가 RL 실험 설계부터 실행·분석까지 자동화하는 워크플로

#### 요약

- Codex(GPT 5.5) 에이전트가 NVIDIA NeMo RL·NeMo Gym 스택을 스스로 구축하고, VLM(비전 언어 모델) RL 학습 스모크 테스트를 수행
- 새로운 NeMo Gym 시각 카운팅 환경을 처음부터 설계·구현해 Qwen3-VL-2B-Instruct 모델 정확도를 25.0%에서 96.9%로 향상
- 연구 논문(OAPL: 오프폴리시 RL 기법)을 읽고 구현 계획 수립, 코드 작성, 테스트, 10시간 검증 학습까지 자동 수행
- Brev-etiquette, Session-memory, Autoresearch 세 가지 에이전트 스킬을 활용해 장시간 세션의 맥락 유지와 재현성 확보

#### 시사점

- 반복적인 환경 설정·디버깅·실험 반복 작업을 에이전트에 위임함으로써 연구자는 가설 수립과 결과 해석 등 고부가가치 작업에 집중할 수 있음
- 논문을 코드로 자동 변환하는 paper-to-code 워크플로는 최신 RL 알고리즘의 검증 속도를 크게 높임
- 오픈소스 모델(NVIDIA Nemotron 등)을 기반으로 데이터·IP·배포·학습 과정을 직접 통제하면서 특정 도메인에 맞게 RL로 미세조정하는 파이프라인 구축이 가능

#### 용어 설명

- **Autoresearch**: Andrej Karpathy가 만든 오픈소스 프로젝트로, AI 에이전트가 ML 학습 워크플로를 자동화하도록 하는 접근 방식
- **NeMo RL / NeMo Gym**: NVIDIA NeMo 프레임워크의 강화학습 후처리(post-training) 라이브러리(NeMo RL)와, 모델이 상호작용하며 보상을 받는 학습 환경 라이브러리(NeMo Gym)
- **GRPO / DPO / SFT**: 각각 그룹 상대 정책 최적화, 직접 선호도 최적화, 지도 미세조정을 뜻하는 LLM 후처리 학습 기법들
- **Agent Skill**: 에이전트가 반복 실행하는 표준화된 운영 지침(예: 저장소 정리 규칙, 세션 기록 방식)을 담은 재사용 가능한 워크플로 모듈
- **OAPL (Optimal Advantage-based Policy Optimization with Lagged Inference)**: 학습·추론 정책 간 시차(lag)를 오류가 아닌 최적화 목표의 일부로 활용하는 오프폴리시 RL 기법
- **VLM (Vision Language Model)**: 이미지와 텍스트를 함께 이해하는 멀티모달 언어 모델
- **NVIDIA Brev**: GPU 인스턴스를 손쉽게 띄우고 관리할 수 있는 NVIDIA의 클라우드 개발 환경

#### 상세 내용

**전체 스택 자율 관리**

Codex는 리포지토리 점검, 런타임 구성, 빌드 문제 해결, 실험 실행·모니터링까지 사람의 개입 없이 수행한다.

- Brev 인스턴스(NVIDIA L40S 48GB GPU 1개)를 띄우고 VS Code로 원격 연결
- Codex IDE 확장을 설치하고 `/goal` 명령으로 지속 목표(persistent objective)를 설정
- NeMo RL 서브모듈 초기화, Hugging Face에서 Qwen3-VL-2B-Instruct 모델 다운로드, 대용량 캐시·체크포인트를 `/ephemeral` 볼륨으로 라우팅하는 등 의존성 문제를 자체 해결
- 전체 설정에 약 40분~1시간 소요되며, session-memory 스킬로 진행 상태를 저장해 네트워크 단절이나 VS Code 재시작 후에도 이어서 작업 가능

**목표 기반 자동연구(Autoresearch) 캠페인**

사람이 목표와 시간 예산만 제시하면, Codex가 베이스라인 측정→가설 수립→실험→분석까지의 루프를 관리한다.

- 먼저 NeMo Gym의 circle click 환경을 참고해 색깔별 별(star) 개수를 세는 새로운 "star count" 환경을 처음부터 설계

**자동연구 워크플로 운영 시 유의점**

- **맥락 소실(context drift)**: 장시간 세션에서 컨텍스트 압축이 반복되면 목표·스킬·중단 규칙을 잊을 수 있어 durable memory가 필요
- **로컬 정리 문제**: 로그·체크포인트·캐시가 파일시스템 곳곳에 흩어질 수 있어 머신별 운영 규칙(etiquette)을 명시해야 함
- **조타 이탈(steering drift)**: 중간 지시가 유용하지만 잘못하면 세션을 조기 종료시킬 수 있음
- **저신호 루프**: 적은 스텝·작은 배치로 학습해 의미 있는 신호를 얻지 못하는 비생산적 루프에 빠질 수 있어 사람의 개입이 필요
- 명시적인 시간·GPU 시간·실험 횟수 예산을 사전에 설정해 에이전트가 고가치 가설에 집중하도록 유도할 것을 권장

**대상 독자**: RL 연구·실험 자동화에 관심 있는 ML 엔지니어 및 연구자, 에이전트 기반 워크플로로 반복적인 실험 인프라 구축·논문 재현 작업을 줄이고 싶은 개발자에게 유용합니다.

### [NVIDIA Ising Decoding Cuts Color Code Logical Error Rates by Over 300x](https://developer.nvidia.com/blog/nvidia-ising-decoding-cuts-color-code-logical-error-rates-by-over-300x/)

`Quantum Error Correction` `Color Codes` `Ising Decoder` `cuQuantum` `cuStabilizer` `PyTorch`

> AI 기반 프리디코더로 컬러 코드 논리 오류율을 347배 이상 개선

#### 요약

- NVIDIA가 삼각형 컬러 코드(Color Code)용 AI 프리디코더 "Ising Decoder ColorCode 1 Fast"를 공개, 기존 최고 성능 디코더 Chromobius 대비 논리 오류율(LER)을 347.7배, 처리 속도를 7.3배 개선(d=31, 물리 오류율 0.3% 기준).
- 컬러 코드는 서피스 코드보다 논리 게이트 연산이 효율적이지만 디코딩이 훨씬 어려워 실용화가 지연되어 왔는데, 이번 성과로 실시간 활용 가능성이 열림.
- 3D CNN(합성곱 신경망) 기반 프리디코더가 지역화된 오류 신드롬을 처리해 기존 디코더의 정확도와 속도를 함께 끌어올림.
- 모델 가중치, 학습 아키텍처, 벤치마크, 레시피를 전부 오픈소스로 공개.

#### 시사점

- 그동안 디코딩 난이도 때문에 배제되었던 컬러 코드를 실용적인 오류 정정 방식으로 재고려할 수 있게 됨.
- QPU(양자 처리 장치) 개발자가 자사 노이즈 특성에 맞춘 디코더를 직접 학습·튜닝할 수 있어 하드웨어별 맞춤 최적화가 가능.
- 오픈 라이선스(OpenMDW 1.1)로 가중치와 학습 파이프라인이 공개되어 연구·상용 배포 모두에 활용 가능.

#### 용어 설명

- **QEC (Quantum Error Correction)**: 양자 비트의 오류를 검출·정정해 신뢰할 수 있는 연산을 가능하게 하는 기술.
- **LER (Logical Error Rate)**: 오류 정정 후에도 남는 논리적 오류의 발생 비율. 낮을수록 좋음.
- **QPU (Quantum Processing Unit)**: 양자 연산을 수행하는 하드웨어 프로세서.
- **Color Code / Surface Code**: 둘 다 위상학적(topological) 오류 정정 코드 계열이며, 서피스 코드는 메모리 효율이 좋고 컬러 코드는 논리 게이트 연산이 더 효율적임.
- **Chromobius**: 현재 널리 쓰이는 오픈소스 컬러 코드 디코더.
- **cuQuantum / cuStabilizer**: NVIDIA의 양자 시뮬레이션·안정자(stabilizer) 계산 가속 라이브러리.
- **CNN (Convolutional Neural Network)**: 이미지·공간 데이터 패턴 인식에 강한 신경망 구조로, 여기서는 오류 신드롬 패턴 인식에 사용.

#### 상세 내용

**배경: 왜 컬러 코드인가**

내결함성(fault-tolerant) 양자 컴퓨터를 만들려면 오류를 정정하는 논리 연산이 필요합니다. 서피스 코드는 격자 수술(lattice surgery)로 논리 연산을 하는 방법이 잘 알려져 있지만, 서피스 코드 외 다른 위상학적 코드에 비해서는 논리 계산 효율이 떨어집니다. QLDPC 코드는 메모리 효율은 가장 좋지만 논리 게이트 연산 방법이 아직 명확하지 않습니다.

- 컬러 코드는 모든 클리포드(Clifford) 게이트를 전이적(transversal)으로 수행할 수 있고 대칭적 구조 덕분에 격자 수술이 단순해 논리 게이트 연산 효율이 높음.
- 다만 메모리 유지에는 서피스 코드보다 더 많은 물리 큐비트가 필요.
- 디코딩 난이도가 높아 빠르고 정확한 디코더가 없어 실용화가 지연되어 왔음.

**Ising Decoding: 3D CNN 프리디코더**

Ising Decoding 학습 파이프라인은 QPU 개발자와 디코더 개발자가 삼각형 컬러 코드용 소형 3D CNN AI 프리디코더를 직접 학습할 수 있게 해줍니다.

- 공간·시간 양 방향으로 확장 가능해 지연 시간과 LER을 함께 개선.
- 국소적(local)이고 입력 크기·형상에 독립적이라, 병렬 공간-시간 블록 단위 디코딩 구조에 활용 가능해 양자 알고리즘 실행 중 실시간 오류 정정에 필수적.
- 사용자는 노이즈 모델, 삼각형 컬러 코드 거리(distance), 모델 깊이만 정의하면 됨. 깊이가 깊을수록 정확도는 높아짐.
- 학습 아키텍처는 cuQuantum 내 cuStabilizer 라이브러리와 PyTorch를 사용해 합성 학습 데이터를 생성하고 3D CNN을 학습.
- 약 20줄의 Python 코드로 컬러 코드 메모리 실험을 구축하고, Chromobius 디코더를 컴파일해 신드롬을 샘플링·디코딩한 뒤 LER을 계산하는 과정을 시연(예시: distance=5, 물리 오류율 0.3%에서 LER 약 3.6e-03, 라운드당 7.3e-04).

**정확도와 속도: 모델 선택**

Ising Decoder ColorCode 1 Fast는 17개 레이어, 수용 영역(receptive field) 13, 입력 볼륨 13x13x19(추론 시 임의 크기 입력 가능) 구조로 약 290만 개 파라미터를 가집니다. 크기가 작아 GPU에서 효율적으로 동작하지만, 더 큰 모델 대비 LER 개선폭은 상대적으로 작습니다.

This peaks at 347x LER improvement and 7.3x runtime improvement at d=31 for physical error rate of 0.3%.](https://developer-blogs.nvidia.com/wp-content/uploads/2026/07/image2-6.webp)

- 코드 거리(distance) 13 지점에서 LER과 종단간 실행 시간이 함께 개선되는 교차점이 발생.
- distance=31, 물리 오류율 0.3% 조건에서 LER 347배, 런타임 7.3배 개선이 정점.
- 벤치마크는 NVIDIA DGX GB300(Fast 모델 실행)과 NVIDIA Grace Neoverse-V2 CPU(Chromobius 실행) 기준.

**오픈소스 리소스**

NVIDIA Ising 모델 패밀리는 전면 공개되어 있습니다.

- **모델 가중치**: Ising Decoder ColorCode 1 Fast의 전체 파라미터 체크포인트를 Hugging Face에서 제공, OpenMDW 1.1 라이선스로 데이터 통제권을 유지하며 어디든 배포 가능.
- **학습 레시피**: cuQuantum, cuStabilizer로 합성 데이터를 실시간 생성하고 PyTorch로 학습하는 전체 파이프라인 공개. 자사 QPU 노이즈 특성에 맞춘 디코더 모델 제작 가능.
- Ising Decoding 학습 아키텍처와 쿡북은 Apache 2.0 라이선스로 GitHub 공개, Color Code 모델 아키텍처 논문도 제공.

**대상 독자**: 양자 오류 정정 디코더를 연구·개발하는 엔지니어, QPU 하드웨어 빌더, 그리고 GPU 가속 AI를 양자 컴퓨팅 인프라에 적용하려는 개발자에게 유용합니다.

### [Extreme Event Likelihoods with Guided Generative Models](https://developer.nvidia.com/blog/extreme-event-likelihoods-with-guided-generative-models/)

`Diffusion Model` `cBottle` `Earth2Studio` `Climate Emulator` `Importance Sampling` `NGC`

> 가이드 확산 모델로 희귀 기후 극한현상 확률을 효율적으로 추정하는 기법

#### 요약

- 저확률·고영향 사건(태풍 등) 확률 추정에 몬테카를로 샘플링은 비용이 크며, NVIDIA는 가이드 확산 모델과 odds ratio(오즈비) 보정을 결합해 이를 해결하는 방법을 제시
- NVIDIA cBottle 기반 확산 모델을 태풍 상태로 유도(guidance)한 뒤, 유도 분포와 비유도 분포 간 오즈비를 계산해 원래 기후 분포 하에서의 확률을 역산
- Earth2Studio의 CBottleTCGuidance 예제로 실제 워크플로 구현이 가능하며, 논문 실험에서 단순 몬테카를로 대비 표준오차를 25% 감소시킴
- 태풍 외에도 전력망, 항공우주, 금융 테일 리스크, 신소재 탐색 등 희귀 사건이 중요한 다른 도메인에도 적용 가능한 일반적 패턴

#### 시사점

- 값비싼 물리 기반 시뮬레이션을 대량 반복하지 않고도 희귀 기후 사건의 발생 확률을 더 적은 샘플로 추정할 수 있어, 재해 리스크 분석·보험 모델링·인프라 계획의 비용을 크게 낮출 수 있음
- 오픈소스 플랫폼(Earth2Studio)과 사전학습 체크포인트(NGC)로 제공되어 개발자가 바로 코드를 실행해 볼 수 있음
- "가이드 생성 + 오즈비 보정" 패턴은 기후과학을 넘어 로보틱스 엣지 케이스, 분자 시뮬레이션 등 희귀 이벤트가 지배하는 다양한 리스크 분석 문제에 재사용 가능

#### 용어 설명

- **확산 모델(Diffusion Model)**: 노이즈에서 점진적으로 데이터를 복원해 생성하는 생성형 AI 모델 구조
- **cBottle**: NVIDIA가 개발한 기후 조건부 확산 기반 날씨 상태 생성 모델
- **가이드 생성(Guided Generation)**: 확산 모델의 샘플링 과정을 특정 조건(예: 특정 지역의 태풍 발생)으로 유도하는 기법
- **오즈비(Odds Ratio)**: 유도된 분포와 원래(비유도) 분포에서 특정 샘플이 나올 확률의 비율로, 유도로 인해 얼마나 확률이 왜곡됐는지 보정하는 값
- **중요도 샘플링(Importance Sampling)**: 희귀 사건이 더 자주 나오도록 샘플링한 뒤, 가중치를 곱해 원래 분포에서의 확률을 추정하는 통계 기법
- **Earth2Studio**: AI 기반 기후·날씨 워크플로를 위한 NVIDIA의 오픈소스 추론 플랫폼

#### 상세 내용

**문제 배경: 희귀 기후 사건 추정의 비용 문제**

특정 해안 인근의 태풍처럼 국지적이고 드문 기상 현상은 전통적인 기후 시뮬레이션으로 신뢰할 만한 확률을 얻으려면 매우 큰 규모의 앙상블(반복 시뮬레이션 집합)이 필요하다.

- 이는 상륙 리스크 분석, 기후 귀속(attribution) 실험, 인프라 계획, 보험 모델링, 영향 연구 전반의 병목이 됨
- 확산 기반 기후 에뮬레이터는 사실적인 대기 상태를 생성하는 데 그치지 않고, 그 상태의 확률 추정에도 활용될 수 있음을 이 연구가 보여줌

**가이드 샘플링에서 오즈비 계산까지**

cBottle 태풍 가이드 워크플로는 사용자가 지정한 태풍 활동 조건(위치·시기)에 맞춰 대기 샘플을 생성한다. Earth2Studio 예제에서는 플로리다 인근(위도 27.0, 경도 -82.0), 허리케인 시즌(2005년 10월) 조건으로 가이드 텐서를 만든다.

- 생성된 대기 상태 $x$에 대해 유도 분포 확률 $p_{guided}(x)$와 비유도 분포 확률 $p_{unguided}(x)$을 비교
- 로그 오즈비: $\log o(x) = \log p_{unguided}(x) - \log p_{guided}(x)$
- 이 값을 지수화하면 중요도 가중치 $o(x)$가 되어, 유도된 샘플을 재가중함으로써 원래 분포에서의 확률을 추정하는 중요도 샘플링이 가능해짐: $P_{IS}(TC) \approx \frac{1}{K}\sum I_{TC}(x_i) o(x_i)$

**Earth2Studio에서의 실행**

CBottleTCGuidance 진단 모델을 사용하며, NGC에서 체크포인트를 자동 다운로드한다.

```python
from earth2studio.models.dx import CBottleTCGuidance
package = CBottleTCGuidance.load_default_package()
lat = torch.tensor([27.0], device=device)
lon = torch.tensor([-82.0], device=device)
times = [datetime(2005, 10, 11, 12)]
model = CBottleTCGuidance.load_model(package, seed=0).to(device)
guidance, coords = model.create_guidance_tensor(lat, lon, times)
guided_sample, guided_coords = model(guidance, coords)
```

생성된 `guided_sample`에서 10m 지상풍(u10m), 해수면 기압 등 변수를 추출해 시각화할 수 있다.

오즈비 계산은 생성 흐름의 발산(divergence)을 추정해야 하며 2차 도함수 연산이 필요하므로, 모델을 `allow_second_order_derivatives=True` 옵션으로 재로드한다.

```python
model = CBottleTCGuidance.load_model(
    package, seed=0, sampler_steps=2,
    allow_second_order_derivatives=True,
).to(device)
log_odds_ratio, forward_latents, latent_coords = model.calculate_odds_ratio(guidance, coords)
```

- 반환된 `log_odds_ratio`는 가이드가 샘플 확률을 얼마나 변화시켰는지를 나타냄
- 값이 음수이면 해당 샘플이 비유도 모델보다 유도 모델에서 훨씬 더 그럴듯하다는 의미
- 예제는 속도를 위해 `sampler_steps`를 줄였으며, 고품질 결과와 안정적인 오즈비 값을 위해서는 기본 샘플러 설정을 사용해야 함

**연구 성과와 향후 과제**

논문 실험에서 가이드 생성과 오즈비 진단을 결합한 중요도 샘플링은 단순 몬테카를로 샘플링 대비 표준오차를 25% 줄였다.

- 확산 샘플링, 특히 2차 도함수가 필요한 오즈비 계산은 연산 비용이 크며, 더 빠른 샘플러·증류(distillation)·저단계(few-step) 확산 기법 연구가 필요
- 태풍 외에 대기천(atmospheric river), 폭염, 강한 폭풍, 가뭄, 복합 극한현상 등에도 유사 기법 적용을 검토 중이며, 서로 다른 경계조건·기후 상태 간 사건 확률 비교를 통한 귀속 실험 확장 가능성도 언급

**대상 독자**: 기후·날씨 리스크 모델링, 생성형 AI 기반 확률 추정, 또는 희귀 이벤트 시뮬레이션(보험, 인프라, 금융 테일 리스크 등)에 관심 있는 개발자·연구자에게 유용하다.
