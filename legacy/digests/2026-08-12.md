# NVIDIA 블로그 요약 — 2026-08-12

### [NVIDIA JetPack 7.2.1 Adds Agentic Video Skills and T3000 Emulation](https://developer.nvidia.com/blog/nvidia-jetpack-7-2-1-adds-agentic-video-skills-and-t3000-emulation/)

`JetPack` `Jetson` `PyNvVideoCodec` `Video Codec SDK` `NVENC/NVDEC` `Jetson T3000`

> JetPack 7.2.1, 에이전틱 비디오 스킬과 T3000 성능 에뮬레이션 지원 추가

#### 요약

- JetPack 7.2.1이 Jetson에서 처음으로 PyNvVideoCodec 2.2를 지원, Python으로 GPU 하드웨어 가속 비디오 인코딩/디코딩이 가능해짐
- Video Codec SDK와 PyNvVideoCodec 위에 에이전틱 "Jetson video skills"(jetson-videosdk)를 도입해 프롬프트만으로 코덱 파이프라인 구성·검증을 자동화
- 스킬은 장치 능력 탐지, 인코더 레시피 생성, 성능/품질 벤치마크, 파이프라인 검증의 4가지 워크플로 제공
- JetPack 7.2.1로 Jetson T5000 모듈(Jetson Thor AGX 개발자 키트)에서 신규 발표된 Jetson T3000(865 FP4 TFLOPS) 성능을 에뮬레이션 가능

#### 시사점

- 코덱 설정에 필요한 저수준 지식 없이도 코딩 어시스턴트가 대상 장치에 맞는 최적 인코드/디코드 구성을 자동 선정하고 실측 근거(latency, throughput 등)를 제공해 개발 속도가 빨라짐
- PyNvVideoCodec은 GPU 상주 메모리(DLPack, CUDA 디바이스 버퍼)로 프레임을 주고받아 디코드→AI 추론 파이프라인에서 불필요한 CPU-GPU 복사를 줄일 수 있음
- 아직 실물이 없는 T3000 하드웨어용 애플리케이션을 T5000 개발자 키트로 미리 개발·검증할 수 있어 로보틱스/휴머노이드 개발 착수가 앞당겨짐

#### 용어 설명

- **JetPack**: NVIDIA Jetson 임베디드 보드에 설치되는 SDK/OS 패키지
- **Jetson**: 로봇, 엣지 AI 등에 쓰이는 NVIDIA의 임베디드 컴퓨팅 플랫폼
- **NVENC/NVDEC**: NVIDIA GPU에 내장된 하드웨어 비디오 인코더/디코더 엔진
- **Video Codec SDK**: NVENC/NVDEC를 직접 제어하는 저수준 C/C++ API
- **PyNvVideoCodec**: Video Codec SDK를 감싼 Python 라이브러리로, GPU 상주 프레임을 다룸
- **DLPack**: 프레임워크 간에 GPU 텐서를 복사 없이 공유하는 표준 프로토콜
- **Jetson T3000 / T5000**: 로보틱스·휴머노이드용 Jetson Thor 계열 모듈, T3000은 소형·저전력 버전

#### 상세 내용

**PyNvVideoCodec 2.2, Jetson 최초 지원**

기존 JetPack 7.1은 Jetson Thor에서 Video Codec SDK(C/C++)를 지원했다. JetPack 7.2.1은 여기에 더해 Python용 PyNvVideoCodec 2.2를 처음 지원한다.

- 프레임을 GPU 상주 디바이스 메모리로 생산·소비하며 DLPack, CUDA 디바이스 버퍼로 노출
- 멀티모드 프레임 샘플링, 백그라운드 스레드에서 미리 디코드하는 ThreadedDecoder를 지원해 디코드 지연과 추론 지연을 분리

**프롬프트에서 검증된 파이프라인까지**

"이 Jetson에서 저지연 용도로 H.264 1080p30 스트림을 몇 개 돌릴 수 있나?" 같은 질문은 코드 생성이나 스펙표만으로 답할 수 없고, 설치된 소프트웨어·타깃의 실제 코덱 능력·메모리 경로·실측 실행이 필요하다.

- Jetson video skills는 이를 자동화된 워크플로로 전환: 타깃 점검 → 지원되는 SDK 경로 선택 → 테스트된 설정 생성 → 실행 → 경고와 근거를 포함한 측정 결과 반환

**JetPack 7.2.1의 4가지 foundational skills (jetson-videosdk)**

1. **탐지·설정·능력 보고**: Jetson 플랫폼·설치 소프트웨어 식별, 인코드/디코드 코덱·포맷·메모리 경로·세션 능력을 실제 타깃에서 조회
2. **인코더 레시피 생성**: 저지연, 고정 품질, 제한 비트레이트, 해상도, 프레임레이트, 코덱 선택 등 목표를 실행 가능한 Video Codec SDK/PyNvVideoCodec 설정으로 변환
3. **성능·품질 벤치마크**: 처리량, 지연, 활용도, 비트레이트, 출력 품질을 반복 측정
4. **코덱 워크플로 검증**: 설정→레시피 선택→인코드/디코드→측정→결과물 전달을 연결하고, 재현에 필요한 설정·결과·경고·근거를 반환

SDK가 가속 비디오 primitive를 제공한다면, 스킬은 그 위에서 장치 인식 기반 구성과 검증을 더한다. 표기된 스펙과 실제 타깃에서 동작하는 구성을 구분하고, 재현성을 위해 레시피·입출력·측정값을 보존한다.

**PyNvVideoCodec + Jetson video skills로 AI 비디오 파이프라인 구축**

"이 비디오를 디코드하고 내 AI/컴퓨터 비전 처리를 적용한 뒤 코덱 단계가 성능 목표를 만족하는지 검증하라"는 프롬프트를 예로 든다.

- **1단계 (점검·구성)**: 코딩 어시스턴트가 스킬을 호출해 플랫폼·소프트웨어·코덱 능력을 확인하고 디코더, 출력 포맷, 메모리 경로, 버퍼링을 선택
- **2단계 (프레임워크 데이터로 디코드)**: PyNvVideoCodec 샘플이 백그라운드 스레드에서 프레임을 준비해 프레임워크 텐서로 전달, 애플리케이션 전용 코덱 버퍼 코드 불필요
- **3단계 (애플리케이션 흐름 완성)**: 전처리, 검출/분류, 블러링 등 프라이버시 필터, 시각화, 출력 처리를 코딩 어시스턴트가 확장 (모델·로직 선택은 개발자 몫)
- **4단계 (측정·검증)**: 스킬이 코덱 구성을 기록하고 실행 상태, 처리량, 지연, 활용도, 경고, 근거를 검증

**Jetson 비디오 인터페이스 선택**

Jetson은 여러 계층의 소프트웨어로 비디오를 다룬다. 파이프라인이 캡처·코덱·AI·전달 단계를 넘나들 때 이들을 조합할 수 있다.

| 인터페이스 | 사용 시점 | 파이프라인 내 가치 |
|---|---|---|
| GStreamer | 조합 가능한 멀티미디어 그래프가 필요할 때 | 캡처, 재생, 스트리밍, 트랜스코딩, 포맷 변환을 위한 하드웨어 가속 파이프라인 구축 |
| V4L2 | Linux 카메라/장치/포맷/버퍼를 직접 제어해야 할 때 | 명시적 포맷·버퍼·장치 제어로 가속 인코드/디코드에 접근 |
| Video Codec SDK | NVENC/NVDEC를 세밀하게 제어하는 C/C++ API가 필요할 때 | 품질·지연·처리량을 세밀히 제어하는 하드웨어 가속 인코드/디코드 |
| PyNvVideoCodec | 간단한 Python API와 AI 프레임워크 통합이 필요할 때 | AI 프레임워크와 쉽게 통합되는 Python 비디오 인코드/디코드/트랜스코드 워크플로 구축 |

**Jetson T3000 성능 에뮬레이션**

Jetson T3000은 865 FP4 TFLOPS를 소형·저전력 플랫폼에 담아 휴머노이드·로보틱스용 멀티모달 AI 추론에서 T5000에 준하는 성능을 제공하면서 크기·전력·비용을 줄인 모델이다.

- JetPack 7.2.1로 Jetson Thor AGX 개발자 키트의 T5000 모듈 위에서 T3000 성능을 에뮬레이션해 개발을 조기에 시작 가능
- 구현 세부사항은 Jetson Linux Developer Guide 참고

**대상 독자**: Jetson 기반 로보틱스·엣지 AI·비디오 분석 파이프라인을 구축하는 개발자, 특히 Python으로 GPU 가속 비디오 인코드/디코드를 AI 모델과 통합하려는 개발자와 T3000 출시 전 미리 성능을 검증하려는 로보틱스 개발자에게 유용하다.

### [NVIDIA Nemotron 3.5 Lightning Delivers Fast, Accurate Specialized Task Execution for Long-Running Agents](https://developer.nvidia.com/blog/nvidia-nemotron-3-5-lightning-delivers-fast-accurate-specialized-task-execution-for-long-running-agents/)

`Nemotron` `Mixture-of-Experts` `Agentic AI` `NVFP4` `NeMo Switchyard` `DGX Spark`

> 자율 에이전트 실행 계층을 위한 경량 30B MoE 오픈 모델 출시

#### 요약

- NVIDIA는 3B 활성 파라미터를 가진 30B 규모의 오픈 MoE(Mixture-of-Experts) 모델 Nemotron 3.5 Lightning을 공개했다.
- 도구 호출, 결과 검증, 서브에이전트 위임 등 상시 작동 에이전트의 고빈도 실행 작업에 특화되어 있으며, OpenClaw·Hermes Agent 등의 하네스와 NemoClaw 오픈소스 스택을 지원한다.
- 스펙큘레이티브 디코딩(speculative decoding), 하네스 최적화 학습, NVFP4 양자화 등을 통해 속도와 정확도를 동시에 확보했다.
- NVIDIA NeMo Switchyard라는 라우팅 라이브러리를 통해 대형 추론 모델(Nemotron 3 Ultra 등)과 Lightning 같은 경량 모델 간 작업을 자동 분배할 수 있다.

#### 시사점

- 모든 요청에 프런티어급 대형 모델을 쓰지 않고, 고빈도·저지연 작업은 경량 모델로 처리해 비용과 지연을 줄이는 "모델 시스템" 설계가 가능해진다.
- 가중치·학습 데이터·레시피가 OpenMDW-1.1 라이선스로 공개되어 있어, 개발자가 자체 LoRA/SFT 파인튜닝이나 강화학습으로 특정 워크로드에 맞게 커스터마이징할 수 있다.
- DGX Spark, Jetson, GeForce RTX 5090 등 로컬 환경부터 데이터센터까지 동일한 체크포인트로 배포 가능해 온디바이스 에이전틱 AI 구현의 문턱이 낮아진다.

#### 용어 설명

- **MoE (Mixture-of-Experts)**: 입력마다 전체 파라미터 중 일부 "전문가" 서브네트워크만 활성화해 연산량은 줄이면서 큰 모델 수준의 성능을 내는 구조.
- **Speculative decoding**: 작은 초안(draft) 모델이 여러 토큰을 미리 생성하면 본 모델이 이를 한꺼번에 검증해 토큰 생성 속도를 높이는 기법.
- **MTP (Multi-Token Prediction)**: 한 번에 여러 토큰을 예측하도록 모델을 학습시켜 추론 속도를 높이는 사전학습 기법.
- **NVFP4**: NVIDIA가 개발한 4비트 부동소수점 양자화 포맷으로, 모델 크기와 연산량을 줄이면서 정확도 손실을 최소화한다.
- **NeMo Switchyard**: 각 작업을 가장 적합한 모델(대형/소형, 오픈/폐쇄)로 자동 라우팅해주는 NVIDIA의 오케스트레이션 라이브러리.
- **PinchBench / Artificial Analysis Intelligence Index**: 에이전틱 작업 완료 속도·정확도, 코딩·추론·범용 지능 등을 측정하는 벤치마크 지표.
- **DGX Spark**: NVIDIA의 소형 데스크톱급 AI 개발 하드웨어.

#### 상세 내용

**Nemotron 3.5 Lightning의 설계 목적**

상시 작동하는 AI 에이전트는 대부분의 시간을 도구 호출, 결과 검증, 서브에이전트 위임 같은 고빈도 실행 작업에 소모한다. 이런 작업마다 프런티어급 추론 모델을 쓰면 비용과 지연이 커진다.

- Nemotron 3.5 Lightning은 30B 규모지만 활성 파라미터는 3B에 불과한 MoE 모델로, 라우터가 토큰별로 소수의 전문가만 호출해 대형 모델 수준의 성능을 소형 모델 수준의 연산 비용으로 제공한다.
- Nemotron 3 계열 중 가장 작은 모델이며, Nemotron 3 Super·Ultra와 동일한 스펙큘레이티브 디코딩(MTP) 기법, 그리고 인기 에이전트 하네스에 맞춘 학습(harness-optimized training)을 적용했다.
- Nemotron 3 Ultra 같은 프런티어 모델이 오케스트레이션과 복잡한 계획을 담당하고, Lightning은 고빈도 실행을 담당하는 "모델 시스템" 구조를 지향한다.

**커스터마이징**

소형 모델은 대형 모델보다 저렴하고 빠르게, 더 적은 하드웨어로도 파인튜닝할 수 있다.

- 가중치, 학습 데이터, 레시피가 OpenMDW-1.1 라이선스로 최대한 개방적으로 공개된다.
- NeMo Automodel과 NeMo Megatron Bridge로 LoRA 또는 풀 SFT(지도 미세조정) 파인튜닝이 가능하다.
- NeMo RL과 NeMo Gym으로 강화학습 및 환경 기반 평가·롤아웃을 수행할 수 있다.
- 코딩 에이전트 역량 학습에 쓰인 오픈 에이전틱 강화학습 데이터셋 "Nemotron-RL Agentic Terminal Pivot"도 함께 공개됐다.

**NeMo Switchyard를 통한 작업 라우팅**

git pull 실행, 도구 출력 검증, 결과 포맷팅 같은 일상적 호출이 장기 실행 에이전트의 토큰 예산 대부분을 차지한다.

- NeMo Switchyard는 Nemotron 3.5 Lightning을 다른 오픈·폐쇄 모델과 나란히 라우팅 대상으로 노출시켜, 각 요청이 이를 처리할 수 있는 가장 효율적인 모델로 가도록 한다.
- 계획(planning) 작업은 프런티어 모델로, 실행 작업은 Lightning으로 내려보내는 방식으로 토큰을 효율적으로 사용한다.

### [Route AI Agent Workloads Across Models with NVIDIA NeMo Switchyard](https://developer.nvidia.com/blog/route-ai-agent-workloads-across-models-with-nvidia-nemo-switchyard/)

`NVIDIA NeMo Switchyard` `Model Routing` `AI Agent` `LLM Orchestration` `Nemotron`

> 여러 LLM을 작업 특성에 맞게 자동 라우팅해 비용·품질 균형을 맞추는 오픈소스 도구

#### 요약

- NeMo Switchyard는 하나의 최상위 모델만 쓰는 대신, 작업 단계별로 가장 적합한 모델에게 요청을 분배하는 "모델 라우팅" 오픈소스 시스템이다.
- 요청 자체, 모델 상태(로짓 등), 시스템 신호(가격·지연·부하)를 종합해 어떤 모델로 보낼지 결정하며, 튜닝 없이 쓰는 라우터와 실제 워크로드 데이터로 학습하는 튜닝형 라우터를 모두 제공한다.
- LangChain 벤치마크에서는 프론티어 모델 대비 비용 74% 절감(프론티어 모델 호출은 전체의 7%만), 정확도는 약 6점 하락하는 트레이드오프를 보였다.
- Cognition의 Devin Desktop 적용 사례에서는 Opus 5와 Kimi K2.7 사이를 라우팅해 Opus 5 정확도 대비 2.8%p 차이(50.6%)로 평균 비용을 약 28% 절감했다.

#### 시사점

- 여러 LLM 공급사·모델을 하나의 애플리케이션 코드 변경 없이 유연하게 조합할 수 있어, 에이전트 개발 시 모델 종속성을 줄일 수 있다.
- 비용과 품질 사이의 트레이드오프를 자동화된 정책으로 관리할 수 있어, 대형 모델 남용으로 인한 불필요한 비용·지연을 줄일 수 있다.
- 오픈소스이며 OpenAI, Anthropic, Responses API 형식을 지원하는 게이트웨이 형태로 제공되어 기존 인프라에 통합하기 쉽다.

#### 용어 설명

- **Model Routing**: 요청마다 가장 적합한 AI 모델을 자동으로 선택해 보내는 기법.
- **LLM Gateway**: 여러 LLM 제공사의 API를 하나의 표준 인터페이스로 중계하는 서버.
- **Residual Stream**: 트랜스포머 모델 내부에서 레이어를 거치며 누적되는 중간 표현 값.
- **MLP (Multi-Layer Perceptron)**: 여러 층의 뉴런으로 구성된 기본적인 신경망 구조.
- **Terminal-Bench Hard**: 터미널 조작(컴퓨터 사용) 작업 능력을 평가하는 벤치마크.
- **Token/Tool Call**: 모델이 생성하는 텍스트 단위(토큰)와 외부 도구를 호출하는 동작(툴 콜).

#### 상세 내용

**왜 라우팅이 필요한가**

에이전트 작업은 단계마다 요구 능력이 다르다. 분류가 필요한 단계, 추론이 필요한 단계, 단순 반복 작업 단계가 섞여 있는데, 매번 가장 큰 모델을 쓰면 비용·지연이 커지고 작은 모델만 쓰면 복잡한 작업 품질이 떨어진다.

- Terminal-Bench Hard 벤치마크에서 전체 정확도는 DeepSeek V4가 가장 높지만, ML/RL 작업군은 Kimi K2.6이, 수학/과학 작업군은 Qwen3.5 397B A17B가 더 우수했다.
- 나머지 6개 작업군은 DeepSeek V4가 적합해, 작업군별로 다른 모델을 쓰는 것이 유리하다.

**라우팅 결정에 쓰이는 신호**

효과적인 라우팅은 세 가지 영역의 신호를 활용한다.

- **모델 능력**: 어떤 모델이 해당 작업을 정확히 풀 수 있는지
- **모델 비용 프로필**: 모델별 지연시간과 비용
- **인프라**: 안정적인 핸드오프를 위한 시스템 신호

신호는 요청 자체(분류기, 임베딩 모델), 모델 상태(로짓, 어텐션 행렬 등), 시스템(가격, 지연, 부하, 에러) 세 곳에서 얻을 수 있다. 요청 전체를 한 모델로 보낼지, 단계마다 다시 판단할지도 설계 시 고려해야 한다.

**NeMo Switchyard 아키텍처**

핵심은 공급사 독립적인 SDK인 NeMo switchyard-libsy다. 요청을 표현하고, 사용 가능한 모델들을 정의하며, 선택된 모델 호출을 관리한다.

- 각 모델은 의미상 이름(semantic name)을 가지며, 실제 공급사 엔드포인트·모델 ID와의 매핑은 별도 클라이언트가 담당해 라우팅 로직과 특정 공급사를 분리한다.
- 정책이 필요하면 에이전트 세션 전체에 걸쳐 라우팅 상태(이전 턴의 툴 결과, 선호 모델 결정 등)를 유지할 수 있고, 필요 없으면 상태 없이(stateless) 동작할 수도 있다.
- NeMo Switchyard 서버는 OpenAI, Anthropic, Responses API 요청을 받아 내부 형식으로 변환하고, 선택된 모델·판단 근거·토큰 사용량·지연시간·호출 결과를 기록해 LLM 게이트웨이처럼 동작한다.

**튜닝 없이 쓰는 라우터**

- **LLM classifier**: LLM을 심판(judge)으로 써서 후보 모델을 고르고, 이후 턴에서도 같은 모델과의 세션 친화도(affinity)를 유지해 반복 재분류를 피한다. 코딩·수학·헬스케어 등 도메인 특화 시스템에 적합하다.
- **Stage router**: 코딩 에이전트가 탐색·오류 복구 단계인지, 이미 안정적으로 구현 중인 단계인지에 따라 필요한 모델 능력 수준을 판단한다. 심각한 오류나 반복된 비생산적 작업은 고성능 모델로, 안정적인 코드 작성·수정(특히 테스트 통과 후)은 효율적인 모델로 보낸다.
- **Escalation router**: 저비용 모델로 대화를 시작하고, LLM 심판이 턴마다 진행 상황을 감시하다가 지속적인 어려움이 감지되면 더 강력한 모델로 전환한다.

**튜닝형 라우터: Prefill router**

학습 과정에서 LLM의 residual stream(내부 중간 표현)을 추출해 쿼리 복잡도를 추정한다. 공유 트렁크(shared-trunk) MLP가 이 신호를 각 후보 모델의 정확도 레이블에 매핑한다.

- 추론 시점에는 이 prefill 상태를 입력으로 받아, 각 후보 모델이 작업을 성공적으로 완료할 확률을 예측한다.
- 예측 정확도와 비용·지연 등 배포 제약을 함께 고려하는 정책을 적용해 최적의 트레이드오프를 가진 모델로 라우팅한다.
- 벤치마크(Pinchbench + ClawdQA)에서 학습된 prefill 라우터는 단일 모델(Gemma 4 26B, Nemotron Nano 3.5, Qwen 3.6 35B, Opus 4.8 등) 대비 더 나은 정확도-비용 프론티어를 그렸다.

NVIDIA는 Cognition, Nous Research, Ramp, LangChain, LiteLLM, Kong, Classmethod, Boomi, Cadence, Siemens 등과 협력해 NeMo Switchyard를 기존 개발 워크플로에 통합하고 있다.

#### 용어 설명

- **Dense 모델**: 매 토큰 처리 시 모델의 모든 파라미터를 활성화하는 구조로, 일부 전문가만 선택적으로 쓰는 MoE와 대비됨
- **MoE(Mixture of Experts)**: 입력마다 일부 "전문가" 서브네트워크만 선택해 연산하는 아키텍처로, 효율적이지만 라우팅에 따른 변동성이 있음
- **NVIDIA NIM**: 사전 최적화된 추론 컨테이너로, 런타임 설정을 자동 구성해 모델을 손쉽게 배포할 수 있게 해줌
- **KV 캐시**: 트랜스포머 추론 시 이전 토큰들의 키·값을 저장해 재계산을 줄이는 메모리 버퍼
- **NeMo AutoModel**: Hugging Face 체크포인트를 변환 없이 그대로 파인튜닝할 수 있는 NVIDIA의 학습 라이브러리
- **SGLang / vLLM**: LLM 서빙을 위한 오픈소스 추론 프레임워크
- **NemoClaw**: Muse Glimmer 같은 모델을 격리된 샌드박스 환경에서 구동해 장기 실행형 개인 비서 에이전트를 만들 수 있게 하는 에이전트 하네스

#### 상세 내용

**장기 실행 에이전트를 위한 설계**

### [Beyond VLAs: How World Action Models Reshape Robot Manipulation](https://developer.nvidia.com/blog/beyond-vlas-how-world-action-models-reshape-robot-manipulation/)

`VLA` `World Action Model` `Cosmos 3` `Robot Manipulation` `DROID` `Jetson Thor`

> 언어 이해 대신 물리 역학을 예측하는 월드 액션 모델이 로봇 정책의 새 표준을 제시

#### 요약

- VLA(Vision-Language-Action) 모델은 VLM(Vision-Language Model) 기반이라 언어·이미지 이해에는 강하지만 물체가 어떻게 움직이는지 같은 물리적 역학을 학습하지 못해 미학습 상황에서 일반화가 약함
- WAM(World Action Model)은 비디오 월드모델을 백본으로 삼아 행동과 미래 영상을 동시에 예측하며, 포스트트레이닝 이전부터 물리 사전지식을 보유
- NVIDIA Cosmos 3는 Mixture-of-Transformers(MoT) 구조의 옴니모달 월드 파운데이션 모델로, 대규모 이미지·비디오·행동 데이터로 학습되어 WAM 구축에 강력한 기반 제공
- DROID 로봇 플랫폼용으로 포스트트레이닝된 Cosmos3-Nano/Edge-Policy-DROID가 워크스테이션 서빙과 온디바이스 배포를 모두 지원

#### 시사점

- 근접 동일한 시연 데이터가 필요한 VLA와 달리, WAM은 다양한 상호작용 데이터 전부를 학습 신호로 활용할 수 있어 데이터 수집 비용이 낮아짐
- 물리 법칙은 객체나 장면에 무관하게 일반적이므로, 학습 분포 밖 환경·물체에서도 더 견고하게 동작함
- 이미 물리적 상호작용을 이해하는 백본에서 출발하므로 새로운 로봇 팔·그리퍼로 전환할 때 적은 시연 데이터로도 빠르게 적응 가능

#### 용어 설명

- **VLM (Vision-Language Model)**: 이미지와 텍스트를 함께 이해하도록 학습된 모델
- **VLA (Vision-Language-Action Model)**: VLM에 행동 생성 모듈을 붙여 로봇 정책으로 만든 모델
- **WAM (World Action Model)**: 비디오 월드모델을 백본으로 행동과 미래 세계 상태를 함께 예측하는 로봇 정책 모델
- **Cosmos 3**: NVIDIA의 옴니모달 월드 파운데이션 모델
- **MoT (Mixture-of-Transformers)**: 텍스트 같은 이산 토큰은 자기회귀 트랜스포머로, 이미지·비디오·행동 같은 연속 모달리티는 확산 트랜스포머로 처리하는 아키텍처
- **DROID**: Franka Panda 로봇팔과 Robotiq 그리퍼로 구성된 로봇 조작 플랫폼
- **포스트트레이닝(post-training)**: 사전학습된 모델을 특정 작업(로봇 정책 등)에 맞게 추가로 학습시키는 과정

#### 상세 내용

**오늘날 로봇 정책은 어떻게 만들어지나**

VLA 방식은 사전학습된 VLM에 행동 모듈을 붙여 언어 지시와 시각 정보를 로봇 동작으로 매핑한다. 하지만 VLM은 이미지를 설명하도록 최적화된 모델이라, 그리퍼가 컵을 쥐면 어떻게 되는지, 수건이 어떻게 접히는지 같은 물리적 역학은 학습하지 않는다.

- VLA는 의미(semantic) 이해에는 강하지만 미학습 물리 상황·환경으로의 일반화에는 약함

**WAM이 바꾸는 것**

WAM은 백본을 비디오 월드모델로 교체해 영상과 행동을 동시에 예측한다. NVIDIA 연구 논문 *World Action Models are Zero-shot Policies*는 이 방식이 VLA가 쉽게 얻지 못하는 특성을 준다고 설명한다.

- **다양한 데이터로 학습**: 근접 동일한 시연이 필요 없고, 밀고·쥐고·떨어뜨리는 모든 상호작용 데이터가 학습 신호가 됨
- **오픈월드 일반화**: 물체가 낙하하거나 미끄러지는 방식은 객체가 바뀌어도 동일하므로, 물리를 학습한 모델은 미학습 장면·동작에도 지식을 확장함
- **소수 시연으로 신규 로봇 적응**: 물리적 상호작용을 이미 이해하는 모델은 새로운 팔·그리퍼에 특화하는 데 적은 작업별 데이터만 필요

![Comparison of VLA and world action model architectures.](https://developer-blogs.nvidia.com/wp-content/uploads/2026/07/image-85.webp)
*이미지 출처: [원문](https://developer.nvidia.com/blog/beyond-vlas-how-world-action-models-reshape-robot-manipulation/)*

**Cosmos 3, WAM을 위한 강력한 기반**

Cosmos 3는 MoT 구조를 채택한 옴니모달 월드 파운데이션 모델이다. 자기회귀 트랜스포머가 텍스트 같은 이산 토큰을 추론하고, 이를 바탕으로 확산 트랜스포머가 이미지·비디오·오디오·행동 등 연속 모달리티를 반복적 디노이징으로 생성한다.

- 모델 규모: Cosmos Edge(4B), Cosmos Nano(16B), Cosmos 3 Super(64B) 세 가지
- 학습 데이터: 약 7.67억 개 이미지, 실세계 역학을 담은 3.48억 개 비디오, 로봇 조작·자율주행·카메라 모션·1인칭 모션을 아우르는 800만 개 행동 샘플

**월드모델에서 로봇 정책으로: Cosmos 3 Policy DROID 모델**

Cosmos3-Nano-Policy-DROID는 Cosmos 3 Nano에서 포스트트레이닝된 160억 파라미터 정책으로, DROID(Franka Panda 팔 + Robotiq 그리퍼)용이다. 온디바이스용으로는 40억 파라미터의 Cosmos3-Edge-Policy-DROID가 동일한 방식으로 학습되었다.

- 언어 지시와 멀티카메라 관측을 입력받아 로봇 행동 궤적을 생성
- 행동을 출력하면서 동시에 해당 행동이 실행됐을 때 카메라에 보일 영상도 예측("상상하며 행동")
- 포스트트레이닝 후에도 추론·영상 생성 등 옴니 아키텍처 전체 기능을 유지
- 동일한 레시피·데이터·연산량으로 학습한 두 DROID 정책을 비교한 결과, 멀티도메인 행동 데이터로 학습된 옴니 체크포인트에서 시작한 쪽이 RoboLab 성공률을 28.1%에서 36.8%로 끌어올려, 성능 향상이 스케일이 아닌 아키텍처 자체에서 비롯됨을 보여줌

![Robot gripper positioned above a table with a banana and red bowl.](https://developer-blogs.nvidia.com/wp-content/uploads/2026/07/image-86.webp)
*이미지 출처: [원문](https://developer.nvidia.com/blog/beyond-vlas-how-world-action-models-reshape-robot-manipulation/)*

**배포 고려사항**

WAM은 액션 헤드만 있는 것이 아니라 전체 생성형 월드모델을 포함하므로 컴팩트한 VLA보다 크지만, Cosmos 3는 서로 다른 배포 티어에 맞춰 제공된다.

- **워크스테이션 서빙 (Nano, 16B)**: Cosmos3-Nano-Policy는 로봇에 직접 탑재되지 않고 NVIDIA RTX PRO 6000 한 장에서 서빙되며, 로봇은 네트워크로 관측을 전송하고 행동 청크를 수신
- **온디바이스 (Edge, 4B)**: Cosmos 3 Edge는 임베디드 하드웨어에서 직접 실행되며, 640×360 해상도 관측을 처리하고 NVIDIA Jetson Thor에서 추론당 32개 행동을 생성해 15Hz 실시간 제어 달성. RTX PRO GPU, DGX, GeForce RTX GPU, Jetson(신형 Jetson T2000/T3000 포함) 등 다양한 엣지 컴퓨터 지원

**왜 Cosmos 3로 로봇 정책을 만드는가**

- **오픈 파운데이션**: 베이스 모델, 데이터셋, 포스트트레이닝 레시피, 학습된 가중치, 평가 도구, 서빙 스택 모두 상업적 사용이 가능한 라이선스로 공개
- **빠른 적응**: 강력한 물리 사전지식 덕분에 새 정책에 필요한 작업별 데이터가 줄어듦. LeRobotDataset 포맷으로 데이터를 변환한 뒤 공개된 레시피를 실행하면 됨
- **하나의 파운데이션, 다양한 로봇**: Franka, 듀얼암, UR, WidowX 등 각 embodiment는 별도의 포스트트레이닝이 필요하지만, 모두 동일한 사전학습 파운데이션에서 출발해 필요한 시연 수가 줄어듦

**대상 독자**: 로봇 조작 정책을 개발하는 로보틱스·ML 엔지니어, VLA 기반 정책의 물리적 일반화 한계를 겪고 있는 팀, Cosmos 3를 기반으로 자체 로봇 플랫폼용 정책을 포스트트레이닝하려는 개발자에게 유용하다.

### [Generate Trajectories, Reasoning Traces, and Auto-Labels with NVIDIA Alpamayo 2 Super](https://developer.nvidia.com/blog/generate-trajectories-reasoning-traces-and-auto-labels-with-nvidia-alpamayo-2-super/)

`Alpamayo 2 Super` `Vision-Language-Action Model` `Autonomous Vehicles` `NVIDIA Cosmos` `AlpaSim` `NVIDIA DRIVE`

> 자율주행 개발 전 단계를 하나로 묶는 오픈 340억 파라미터 추론 VLA 모델 공개

#### 요약

- NVIDIA가 자율주행(AV) 개발용 오픈 모델 Alpamayo 2 Super를 공개, 320억 파라미터 Cosmos 3 Super Reasoner와 20억 파라미터 확산 기반 Action Expert를 결합하고 강화학습으로 후처리 학습했다.
- 최대 7개 카메라의 360도 서라운드 입력을 받아 미래 궤적, Chain-of-Causation(CoC) 추론 트레이스, 고수준 메타 액션, 장면 질의응답(VQA), 추론 오토라벨을 동시에 생성한다.
- 오픈루프(사전 기록 데이터 대비 평가)와 클로즈드루프(AlpaSim을 통한 실제 반응형 시뮬레이션) 두 방식으로 평가했으며, LingoQA 벤치마크에서 37개 모델 중 1위(79.2점)를 기록했다.
- 모델 가중치는 Hugging Face, 추론 노트북은 GitHub에서 제공되며 OpenMDW-1.1 라이선스로 파인튜닝·파생 모델·상업적 재배포가 가능하다.

#### 시사점

- 궤적 생성, 의도 예측, 장면 이해, 데이터 라벨링에 각각 별도 모델을 쓰던 기존 방식 대신 하나의 파운데이션 모델을 오프라인 정책 교사, 평가 비평가, 데이터 엔진, 커스텀 태스크의 시작점으로 재사용할 수 있다.
- CoC 추론 트레이스로 모델이 왜 그런 판단을 했는지 들여다볼 수 있어, 실패 원인이 인지·추론·행동 생성 중 어디서 발생했는지 진단하기 쉬워진다.
- 수작업으로 몇 달 걸리던 장기 꼬리(long-tail) 주행 클립 라벨링을 오토라벨링으로 며칠 단위로 단축할 수 있고, 교사 모델을 증류해 NVIDIA DRIVE AGX Thor 같은 차량 내장 하드웨어에서 구동 가능한 경량 모델을 만들 수 있다.

#### 용어 설명

- **VLA (Vision-Language-Action) 모델**: 영상·언어·행동을 함께 처리해 주행 결정을 내리는 모델 유형.
- **Chain-of-Causation (CoC)**: 모델이 특정 주행 결정을 내린 이유를 설명하는 추론 트레이스.
- **오픈루프/클로즈드루프 평가**: 오픈루프는 고정된 기록 데이터와 비교하는 평가, 클로즈드루프는 시뮬레이터에서 예측 행동을 실제로 실행해 주변 반응까지 반영하는 평가.
- **minADE_6**: 예측 궤적과 실제 궤적 간 평균 거리 오차를 나타내는 지표(낮을수록 좋음).
- **IoU (Intersection-over-Union)**: 예측 영역(바운딩박스 등)과 정답 영역이 얼마나 겹치는지를 나타내는 지표(높을수록 좋음).
- **2D grounding**: 텍스트 답변에서 언급한 객체를 카메라 화면상의 2D 바운딩박스로 구체적으로 위치시키는 기능.
- **메타 액션(Meta-action)**: '양보', '차선 변경', '정지' 등 고수준 주행 의도를 요약한 출력.

### [How to Run Isolated Tenant Kubernetes Clusters on Shared GPU Infrastructure](https://developer.nvidia.com/blog/how-to-run-isolated-tenant-kubernetes-clusters-on-shared-gpu-infrastructure/)

`Kubernetes` `KAI Scheduler` `vCluster` `GPU Sharing` `Multi-tenancy` `NVIDIA GPU Operator`

> KAI Scheduler와 vCluster로 GPU 1장을 여러 팀이 격리된 클러스터처럼 공유

#### 요약

- 팀마다 별도 클러스터를 두면 자율성은 확보되지만 하드웨어가 쪼개져 낭비되고, 클러스터 하나를 공유하면 CRD 충돌·RBAC 중첩·GPU 예산 분배 문제가 생긴다.
- 이 글은 단일 물리 GPU 위에서 KAI Scheduler(GPU 분배·스케줄링)와 vCluster(팀별 가상 컨트롤 플레인)를 결합해, 팀별로 독립된 API 서버·RBAC·CRD를 제공하면서 실제로는 GPU 노드를 공유하는 패턴을 튜토리얼로 소개한다.
- NLP·Vision·Recommender 3개 팀이 각자 vCluster에서 GPU 워크로드를 배포하고, 각 팀은 자신의 파드만 볼 수 있으며 GPU는 0.33씩 균등 분배되어 실행된다.
- KAI Scheduler는 GPU를 누구에게 얼마나 배정할지 스케줄링만 담당하며, 하드웨어 수준의 메모리 격리는 보장하지 않는다(엄격한 격리가 필요하면 NVIDIA MIG 사용 권장).

#### 시사점

- GPU 인프라를 늘리지 않고도 "팀별 전용 클러스터" 같은 사용자 경험을 제공할 수 있어, 플랫폼팀이 GPU 조달 비용 없이 조직 확장에 대응할 수 있다.
- KAI Scheduler와 vCluster 모두 오픈소스이며 수백 대 규모 GPU 클러스터로도 동일한 패턴이 확장 가능해, 소규모 데모 환경에서 검증 후 프로덕션에 그대로 적용할 수 있다.
- CRD 버전 충돌이나 cluster-admin 권한 요구처럼 클러스터 공유 시 흔한 팀 간 마찰을 해결하는 실전 아키텍처 참고 자료가 된다.

#### 용어 설명

- **KAI Scheduler**: AI 워크로드를 위해 만들어진 GPU 자원 할당 전용 Kubernetes 스케줄러로, 팀별 쿼터와 그룹 스케줄링을 지원한다.
- **vCluster**: 하나의 물리 클러스터 위에 팀별로 완전히 독립된 가상 Kubernetes 컨트롤 플레인(API 서버, CRD, RBAC)을 만들어주는 도구.
- **CRD (Custom Resource Definition)**: Kubernetes API를 확장해 사용자 정의 리소스 타입을 등록하는 기능.
- **RBAC (Role-Based Access Control)**: 사용자·서비스별 권한을 역할 단위로 관리하는 접근 제어 방식.
- **GPU fraction / GPU sharing**: 하나의 물리 GPU를 여러 워크로드가 시간 분할(time-slicing) 방식으로 나눠 쓰는 것.
- **NVIDIA GPU Operator**: Kubernetes 클러스터에 GPU 드라이버, 디바이스 플러그인 등 GPU 사용에 필요한 구성요소를 자동 설치·관리하는 오퍼레이터.
- **MIG (Multi-Instance GPU)**: 지원 하드웨어에서 GPU를 물리적으로 여러 인스턴스로 분할해 하드웨어 수준 메모리 격리를 제공하는 NVIDIA 기술.

#### 상세 내용

**문제 배경**

- 팀마다 전용 클러스터를 주면 자율성은 얻지만 GPU가 팀 단위로 고정 할당되어 유휴 자원이 낭비된다.
- 반대로 클러스터 하나를 공유하면 팀이 늘수록 CRD 버전 충돌, RBAC 중첩, GPU 예산 분리 부재 같은 조율 비용이 커진다.

**아키텍처 개요**

- 물리 GPU 노드를 가진 단일 컨트롤 플레인 클러스터 위에, 팀마다 독립된 vCluster(API 서버·컨트롤러·데이터스토어·syncer·스케줄러 포함)를 올린다.
- 각 팀의 파드는 `schedulerName: kai-scheduler`, `gpu-fraction`, 팀별 큐(queue) 정보를 갖고 vCluster의 syncer를 거쳐 호스트 파드로 매핑되고, 실제 스케줄링은 KAI Scheduler가 담당한다.
- 호스트에서는 NVIDIA GPU Operator(CDI 모드)와 디바이스 플러그인이 GPU를 time-slicing 방식으로 노출해, 물리 GPU 1장을 3개 팀이 나눠 쓴다.

![Diagram of a single Nebius host cluster where three tenant virtual clusters each run their own API server and RBAC, use schedulerName kai-scheduler, request gpu-fraction 0.33 and bind to team-specific queues.](https://developer-blogs.nvidia.com/wp-content/uploads/2026/07/kai-scheduler-vcluster-architecture-1.webp)
*이미지 출처: [원문](https://developer.nvidia.com/blog/how-to-run-isolated-tenant-kubernetes-clusters-on-shared-gpu-infrastructure/)*

**튜토리얼 환경**

- NVIDIA Brev GPU 인스턴스(Nebius) 기준 L40S GPU 1장(VRAM 48GB), vCPU 40개, RAM 160GiB, Ubuntu 24.04.4, MicroK8s v1.36.2, KAI Scheduler v0.16.4, vCluster CLI 0.35.1로 구성.
- GKE/EKS/AKS 등 다른 환경에서도 NVIDIA GPU Operator와 CDI(Container Device Interface)만 갖추면 3단계(KAI Scheduler 설치)부터는 동일하게 진행 가능.

**설치 및 구성 단계**

- `kubectl`, `helm` 설치 후 MicroK8s에 `dns`, `hostpath-storage` 애드온을 활성화(vCluster는 PVC가 필요).
- NVIDIA GPU Operator를 확인/설치하고, KAI Scheduler를 Helm으로 설치(`global.gpuSharing=true`).
- KAI Scheduler의 Queue CRD로 조직 계층을 정의: 상위 큐 `ml-org`(총 GPU 쿼터 1)와 팀별 하위 큐 3개(`team-nlp`, `team-vision`, `team-recommender`)를 각각 `quota: 0.33`, `limit: 1`로 생성. `quota`는 보장된 최소치, `limit`은 최대치, `overQuotaWeight`는 잉여 자원 분배 비율을 의미한다.
- 팀별로 vCluster를 생성하되, `setOwner: false` 설정이 핵심이다. KAI Scheduler의 pod-grouper가 Job→Pod, Deployment→ReplicaSet→Pod 같은 소유 관계를 따라 워크로드를 자동 그룹핑하는데, vCluster의 owner 재작성을 끄지 않으면 이 관계가 가려지기 때문이다.

**워크로드 배포와 검증**

- 각 팀은 자기 vCluster에서 `kai.scheduler/queue`(팀 큐), `gpu-fraction: "0.33"`, `schedulerName: kai-scheduler`를 지정한 파드를 배포한다.
- 세 파드는 각기 다른 `vcluster-team-*` 네임스페이스에 있지만 실제로는 동일한 물리 노드에서 실행되며, 각 팀은 자신의 vCluster 안에서 자기 파드만 조회 가능하다.
- `kubectl describe queue`로 확인하면 세 팀 모두 `Allocated: nvidia.com/gpu: 330m`으로 GPU가 균등 분배된 것을 볼 수 있다.

**한계와 대안**

- KAI Scheduler는 어느 파드가 GPU를 얼마나 쓸지 "스케줄링"만 하며, GPU 공유 시 하드웨어 수준의 메모리 격리는 보장하지 않는다. GPU는 CUDA 컨텍스트 간에 커널 경계 단위로 time-slice 된다.
- 애플리케이션이 자체적으로 메모리 사용량을 지켜야 하며(예: vLLM의 `--gpu-memory-utilization`), 엄격한 하드웨어 격리가 필요하면 NVIDIA MIG를 사용해 물리적으로 GPU를 분할하고 이 역시 KAI Scheduler로 스케줄링할 수 있다.
- 이 글은 신뢰할 수 있는 내부 팀을 대상으로 노드를 공유하는 vCluster 방식을 사용했으며, 신뢰할 수 없는 테넌트에는 노드·네트워크·스토리지까지 분리하는 vCluster private nodes 방식으로 확장 가능하다.

**대상 독자**: 여러 팀이 제한된 GPU 자원을 공유해야 하는 플랫폼 엔지니어나 MLOps 담당자가, 하드웨어 추가 없이 팀별 독립 Kubernetes 환경을 구축하려 할 때 참고할 수 있다.

### [NVIDIA Vera Storage Benchmarks: Faster Encryption, Compression, Integrity Checking, and Recovery for AI-Native Storage](https://developer.nvidia.com/blog/nvidia-vera-storage-benchmarks-faster-encryption-compression-integrity-checking-and-recovery-for-ai-native-storage/)

#### 용어 설명

- **Vera CPU**: NVIDIA가 설계한 Olympus 코어 기반 Arm CPU로, Rubin GPU와 함께 사용되며 스토리지 프로세싱에도 활용됨.

- **KV 캐시(key-value cache)**: LLM 추론 시 재사용되는 중간 연산 결과를 저장해 반복 계산을 줄이는 캐시.

### [Co-Designing AI Model Attention for Fast, Interactive Long-Context Inference](https://developer.nvidia.com/blog/co-designing-ai-model-attention-for-fast-interactive-long-context-inference/)

`Attention` `LLM Inference` `GQA` `FlashAttention` `Tensor Parallelism` `NVIDIA GPU`

> 어텐션 구조를 GPU 실행 방식에 맞게 설계하는 4가지 co-design 가이드라인

#### 요약

- 긴 컨텍스트·에이전틱 워크로드가 늘면서 어텐션이 추론 시간의 대부분(4K에서 128K 토큰으로 갈수록 18%→85%)을 차지하게 되어, 어텐션 설계 방식이 추론 성능을 좌우함
- Group size, head dimension, sequence length가 prefill(계산 바운드)과 decode(메모리 바운드)에 미치는 영향을 GEMM 형태 분석과 실측 데이터로 규명
- Tensor Parallelism은 KV head 수(KH)를 넘어서면 KV 캐시가 중복되어 비효율이 발생하므로, KH 수에 맞춘 병렬화 전략(TP, ADP, KVP, Wide EP, Helix Parallelism)이 필요
- 이를 4가지 실전 가이드라인(group size 확대, head dimension 128/256, KV 상태 축소, KH 기반 병렬화)으로 정리

#### 시사점

- 모델 아키텍처 설계 단계에서 GPU 실행 특성을 고려하면 하드웨어 교체 없이 추론 처리량과 응답성을 동시에 개선할 수 있음
- GQA의 group size, head dimension, KV 캐시 관리 방식을 결정할 때 참고할 수 있는 정량적 기준을 제공
- 대규모 모델을 서빙하는 개발자는 KV head 수에 따라 TP 대신 ADP/KVP, Wide EP, Helix Parallelism 등 대안적 병렬화 전략을 고려해야 함

#### 용어 설명

- **Attention (어텐션)**: 트랜스포머 모델이 입력 토큰 간의 관련성을 계산하는 핵심 연산
- **Prefill / Decode**: prefill은 입력 프롬프트 전체를 한 번에 처리하는 단계(계산 바운드), decode는 토큰을 하나씩 생성하는 단계(메모리 바운드)
- **GQA (Grouped Query Attention) / MHA / MQA**: 여러 query head가 하나의 KV head를 공유하는 정도에 따라 나뉘는 어텐션 변형(MHA는 공유 없음, MQA는 모든 head가 공유)
- **FlashAttention**: 어텐션 행렬 전체를 메모리에 올리지 않고 타일 단위로 스트리밍 계산해 속도를 높이는 커널 기법
- **Roofline model / Arithmetic Intensity**: GPU 성능이 연산량과 메모리 대역폭 중 무엇에 의해 제한되는지 판단하는 모델과 그 지표(FLOPs/byte)
- **Tensor Parallelism (TP)**: 모델의 head(또는 레이어)를 여러 GPU에 나눠 분산 처리하는 병렬화 기법
- **KV cache**: 디코딩 중 재사용을 위해 저장해두는 key/value 텐서로, 길어질수록 메모리 대역폭 부담이 커짐

#### 상세 내용

**Prefill과 Decode는 서로 다른 문제**

Prefill은 프롬프트 전체를 한 번에 처리해 큰 GEMM-M(=ISL×G)을 만들어 계산 바운드가 되고, decode는 토큰을 하나씩 생성해 작은 GEMM-M(=G)을 만들어 KV 캐시 읽기에 의한 메모리 바운드가 된다.

- Speculative decoding은 GEMM-M을 키워 decode를 계산 바운드 쪽으로 이동시킬 수 있음
- Prefix caching 환경(에이전틱/멀티턴)에서는 짧은 ISL이라도 긴 prefix cache에 어텐션하면 prefill이 decode처럼 동작

![DeepSeek-R1 prefill time breakdown](https://developer-blogs.nvidia.com/wp-content/uploads/2026/07/attention-prefill-time-ai-model.webp)
*이미지 출처: [원문](https://developer.nvidia.com/blog/co-designing-ai-model-attention-for-fast-interactive-long-context-inference/)*

**Arithmetic Intensity로 보는 compute/memory bound**

Roofline 모델에서 arithmetic intensity(총 FLOPs / 총 메모리 접근 바이트)가 ridge point보다 높으면 compute-bound, 낮으면 memory-bound다.

- Prefill은 ridge point보다 위에 있어 compute-bound
- Decode는 ridge point 아래에 있어 memory-bound (speculative decoding으로 ridge에 가까워질 수 있음)

![Roofline plot](https://developer-blogs.nvidia.com/wp-content/uploads/2026/07/roofline-plot-prefill-decode.webp)
*이미지 출처: [원문](https://developer.nvidia.com/blog/co-designing-ai-model-attention-for-fast-interactive-long-context-inference/)*

**FlashAttention 커널 동작**

FlashAttention은 Q, K, V 타일을 HBM에서 SRAM으로 스트리밍하며 세 단계를 한 번에 처리한다.

- BMM1: query와 key를 곱해 score 계산 (Tensor Core)
- Online softmax: running max/sum으로 정규화 (special-function unit)
- BMM2: value에 가중합 적용 (Tensor Core)

![FlashAttention dataflow](https://developer-blogs.nvidia.com/wp-content/uploads/2026/07/flashattention-overview.webp)
*이미지 출처: [원문](https://developer.nvidia.com/blog/co-designing-ai-model-attention-for-fast-interactive-long-context-inference/)*

**Group Size(G): decode 효율을 좌우**

Prefill에서는 G가 커져도 arithmetic intensity가 2×ISL에 수렴해 성능에 거의 영향이 없다(G를 1→64로 바꿔도 runtime 변화 1% 미만). 반면 decode는 arithmetic intensity가 대략 2×G로 G에 비례해, G를 두 배로 늘리면 decode 성능도 크게 개선된다(G를 1→8로 늘리면 8배 향상).

- NVIDIA Nemotron 3는 KV head 2개의 GQA를 채택해 decode 효율을 높임
- G가 커질수록 KVSL=32K 커널은 flash-decoding reduction 등 고정 오버헤드로 인해 개선폭이 완만해짐

![Runtime versus G](https://developer-blogs.nvidia.com/wp-content/uploads/2026/07/normalized-runtime-versus-g.webp)
*이미지 출처: [원문](https://developer.nvidia.com/blog/co-designing-ai-model-attention-for-fast-interactive-long-context-inference/)*

**가이드라인 1**: decode 효율을 위해 G를 최대한 높게 선택한다. prefill은 G에 둔감하다.

**Head Dimension(Hsz): 128 또는 256이 최적**

Hsz는 FLOPs와 byte를 동일 비율로 늘리므로 arithmetic intensity 자체는 바뀌지 않지만, GPU 타일 정렬 문제로 runtime에는 영향을 준다.

- Matmul과 메모리 접근은 128바이트 단위로 이뤄져, Hsz=64는 128 타일 비용을 그대로 지불하고 Hsz≥512는 TMEM(tensor memory) 용량 한계에 근접
- Softmax 비용은 Hsz와 무관(query×key 행렬 크기에만 의존)해서, Hsz가 커질수록 prefill에서 softmax 비중이 상대적으로 줄어듦
- Decode는 memory-bound이므로 Hsz가 커지면 KV 바이트가 늘어 runtime도 비례해서 증가(약간 sublinear)

![Runtime versus Hsz](https://developer-blogs.nvidia.com/wp-content/uploads/2026/07/normalized-runtime-versus-hsz.webp)
*이미지 출처: [원문](https://developer.nvidia.com/blog/co-designing-ai-model-attention-for-fast-interactive-long-context-inference/)*

**가이드라인 2**: Hsz는 128 또는 256을 사용한다. GPU 타일과 128바이트 전송 단위에 맞고 TMEM 예산 안에 들어간다.

**Sequence Length: prefill은 제곱, decode는 선형**

Prefill은 모든 토큰이 서로 어텐션하므로 ISL²로 계산량이 늘어 arithmetic intensity가 ISL에 비례해 상승(계속 compute-bound). Decode는 매 스텝 전체 KV 캐시를 읽으므로 KVSL에 선형 비례해 늘어난다(계속 memory-bound).

- ISL이 2배가 되면 prefill runtime은 대략 4배로 증가
- KVSL이 2배가 되면 decode runtime은 대략 2배로 증가
- 짧은 길이에서는 고정 오버헤드 때문에 이상적인 배율보다 낮게 나타남

![Runtime versus sequence length](https://developer-blogs.nvidia.com/wp-content/uploads/2026/07/normalized-runtime-versus-sequence-length.webp)
*이미지 출처: [원문](https://developer.nvidia.com/blog/co-designing-ai-model-attention-for-fast-interactive-long-context-inference/)*

**가이드라인 3**: KV-cache 압축, sparse/sliding-window attention, 또는 일부 레이어만 전역 KV를 유지하는 하이브리드 구조(Nemotron 3 등)로 실질적인 KV 상태를 줄인다.

**Tensor Parallelism과 KV head 수**

TP는 어텐션 head를 GPU마다 나눠 QH/TP query head와 KH/TP KV head를 할당하며, 토큰이 아닌 head를 분할한다. 단, KV head는 GPU 수만큼 균등 분할되어야 하며, TP가 KH를 넘으면 하나의 KV head를 여러 랭크가 복제해서 갖게 되어 메모리·대역폭 낭비가 발생한다.

- KV head가 적은 모델(예: Nemotron 3의 2개)은 TP를 금방 소진하므로, Attention Data Parallelism(ADP)이나 KV Parallelism(KVP)으로 어텐션을 확장하고 FFN은 Expert Parallelism(EP)으로 분리
- TensorRT-LLM은 이를 Wide EP(ADP+EP), Helix Parallelism(KVP+EP)으로 구현

![Attention sharding strategies](https://developer-blogs.nvidia.com/wp-content/uploads/2026/07/atention-sharding-strategies.webp)
*이미지 출처: [원문](https://developer.nvidia.com/blog/co-designing-ai-model-attention-for-fast-interactive-long-context-inference/)*

**가이드라인 4**: KH가 병렬화 전략을 결정하게 한다. TP ≤ KH를 유지하고, KV head가 적은 모델은 ADP/KVP + EP(Wide EP, Helix Parallelism)로 확장한다.

**대상 독자**: 긴 컨텍스트·에이전틱 LLM을 GPU에서 서빙하는 ML 인프라 엔지니어, 그리고 모델 아키텍처(GQA 설정, head dimension, 병렬화 전략)를 설계하는 모델 개발자에게 유용하다.

`NVIDIA Video Codec SDK` `NVENC` `NVDEC` `AV1` `MV-HEVC` `CUDA`

> NVENC·NVDEC 최신 기능으로 인코딩 품질과 트랜스코딩 성능을 대폭 개선

#### 요약

- AV1 인코딩에 최대 31개 B-frame을 지원하는 계층적 참조 구조와 UHQ 튜닝-반복 인코딩 결합 기능 추가
- H.264/HEVC 매크로블록 단위 디코드 통계, GOP 인식 기반 프레임 단위 시크(seek) 기능 도입
- NVDEC와 NVENC가 동일 GPU 메모리(`CUarray`)를 공유해 복사 과정을 없앤 제로카피 트랜스코딩 샘플 신규 제공
- 모듈형 큐 기반 트랜스코더 파이프라인 재설계 및 공식 Docker 개발 환경 제공

#### 시사점

- 비디오 분석 파이프라인에서 CPU 비트스트림 파싱 없이 GPU에서 직접 모션 벡터·QP값을 얻어 장면 전환 감지, 객체 추적, 화질 모니터링을 구현할 수 있음
- 제로카피 트랜스코딩으로 SM(스트리밍 멀티프로세서) 사용률과 GPU 메모리 사용량이 줄어, 동일 GPU에서 더 많은 동시 트랜스코딩 세션 처리 가능
- 프레임 정확 시크 API로 AI 학습 데이터 준비, 영상 편집, 콘텐츠 검토 등에서 필요한 프레임만 빠르게 추출 가능

#### 용어 설명

- **NVENC / NVDEC**: NVIDIA GPU에 내장된 전용 하드웨어 비디오 인코더/디코더
- **B-frame**: 이전·이후 프레임을 모두 참조해 압축하는 프레임 유형으로, 활용도가 높을수록 압축 효율이 좋아짐
- **GOP (Group of Pictures)**: IDR(완전 독립) 프레임부터 다음 IDR 전까지의 프레임 묶음, 디코딩·시크의 기본 단위
- **QP (Quantization Parameter)**: 압축 시 손실 정도를 나타내는 값으로 화질과 비트레이트를 좌우
- **CUarray**: CUDA에서 GPU 메모리에 텍스처/이미지 형태로 데이터를 저장하는 자료구조
- **MV-HEVC**: 좌우 두 시점(뷰)을 하나의 HEVC 비트스트림에 담아 3D/스테레오 영상을 표현하는 확장 규격
- **SM (Streaming Multiprocessor)**: GPU 내 실제 연산을 수행하는 코어 단위 블록

#### 상세 내용

**AV1 계층적 참조 모드 (Hierarchical Reference Mode)**

B-frame을 참조로 사용하면 화질이 개선되는데, 이 모드는 B-frame을 트리 구조로 배치해 효과를 극대화한다. 리프 노드는 참조되지 않는 B-frame, 루트는 중간 B-frame이다.

- NVENC의 B-frame 최대 개수를 7개에서 31개로 확장
- AV1에서 1, 3, 7, 15, 31개 B-frame 구조 지원 (H.264/HEVC는 추후 드라이버에서 지원 예정)
- 성능 저하 없이 적용 가능하지만 비디오 메모리 사용량은 증가
- 7개 이상 B-frame에서 가장 효과적

**UHQ 튜닝 정보와 반복 인코딩 결합**

반복 인코딩(iterative encoding, SDK 12.1 도입)은 동일 프레임을 여러 파라미터로 재인코딩할 수 있게 해준다. UHQ 튜닝 정보(SDK 12.2 도입)는 룩어헤드 레벨과 시간적 필터링을 결합해 품질-성능 균형을 맞춘다.

- 시간적 필터링: 모션 추정으로 인접 프레임의 유사 패치를 찾아 노이즈 제거, 평균 4~5% 코딩 이득
- 룩어헤드 레벨: 미래 프레임을 분석해 비트 할당 최적화, 4단계 레벨 지원
- 13.1부터 이 두 기능이 반복 인코딩과 함께 사용 가능

**매크로블록 단위 디코드 통계**

H.264/HEVC 콘텐츠의 16×16 블록마다 luma QP, 코딩 유닛 타입(Intra/Inter/Skip/PCM), 최대 2개의 모션 벡터를 하드웨어 디코드 과정에서 별도 CPU 부하 없이 추출한다.

- `cuvidGetDecoderCaps()`로 지원 여부 확인 → 디코더 생성 시 통계 수집 활성화 → `cuvidMapVideoFrame()`으로 GPU 상주 통계 버퍼 획득
- 모션 벡터로 장면 전환/객체 추적/샷 경계 분석, QP로 화질 모니터링, 매크로블록 타입으로 콘텐츠 분류 가능
- 샘플 `AppDec -dumpstats` 제공

**프레임 정확 시크(Frame-Accurate Seek)**

AI 추론 파이프라인이나 영상 편집처럼 특정 프레임만 필요한 워크로드를 위한 GOP 인식 기반 시크 아키텍처가 추가됐다.

- 목표 프레임 N 요청 시 가장 가까운 IDR 프레임을 찾아 그곳부터 디코드 시작, `CUVID_PKT_DISCONTINUITY`로 디코더 상태 초기화
- 참조되지 않는 프레임은 스킵, 참조 프레임은 디코드는 하되 매핑/후처리는 생략, N번 프레임만 전체 파이프라인 실행
- `NvVideoDecoder` 클래스가 배열 인덱싱처럼 간단한 인터페이스 제공

주요 기능:
- 코덱·비트 심도·크로마 포맷별 디코더 인스턴스를 LRU 방식으로 캐싱해 재생성 오버헤드 최소화
- 비시크(non-seekable) 스트림(엘리멘터리 스트림, 네트워크 스트림, 파이프) 자동 감지 및 대응

- Open GOP 스트림에서도 가장 가까운 IDR로 정확히 시크

**MV-HEVC 스테레오스코픽 개선**

3D 영상 지원이 강화됐다. 디코드 시 view-ID/레이어 메타데이터(`nuh_layer_id`)를 제공해 좌우 뷰를 정확히 구분하고, 서드파티 인코더가 만든 MV-HEVC 비트스트림 호환성도 향상됐다. 인코드 측에서는 FFmpeg로 HEVC 3D 메타데이터를 올바르게 생성할 수 있고, Split Frame Encoding(SFE)으로 여러 인코더가 하나의 고해상도 3D/XR 프레임을 분담 처리해 속도를 높인다.

**재설계된 트랜스코더 파이프라인**

기존 트랜스코딩 샘플은 빠르지만 모놀리식 구조라 수정하려면 전체 파이프라인 이해가 필요했다. 13.1은 파이프라인 단계별로 전용 CPU 스레드를 할당하고, 스레드 간 통신은 명시적 크기의 입출력 큐로 처리하는 프로듀서-컨슈머 구조로 재설계됐다.

- `AppTrans` 핵심 파이프라인: Decode(NVDEC) → Compute(CUDA) → Encode(NVENC) → Output 4개 독립 스레드로 분리
- 신규 샘플 `AppTransZeroCopy`: 지연시간 최소화에 최적화된 1:1 제로카피 순수 트랜스코딩 애플리케이션
- 기존 `AppTransPerf`(처리량 벤치마크), `AppTrans`(1:1 트랜스코딩), `AppTransOneToN`(1:N 스케일링)도 함께 제공

**`CUarray` 기반 제로카피 트랜스코딩**

기존 파이프라인은 디코더 출력 → 애플리케이션 접근 가능 서페이스 변환 → 인코더 입력 버퍼로 복사 → 인코더 내부 포맷 재변환의 다단계 복사 과정을 거친다. `AppTransZeroCopy`는 이 복사 체인을 없앤다.

동작 방식 4단계:
1. `cuArray3DCreate`와 `CUDA_ARRAY3D_VIDEO_ENCODE_DECODE` 플래그로 NVDEC·NVENC가 공유할 `CUarray` 풀을 사전 할당
2. 동일 `CUarray`를 디코더 측에서는 `SetExternalOutputArrays()`로, 인코더 측에서는 `nvEncRegisterResource`(`NV_ENC_INPUT_RESOURCE_TYPE_CUDAARRAY`)로 이중 등록
3. 디코드·인코드·출력 3개 스레드가 토큰 기반 흐름 제어로 `CUarray` 소유권을 관리하며 파이프라인 실행
4. NVDEC와 NVENC가 동일 CUDA 스트림을 공유해 CPU-GPU 동기화 없이도 순서 보장

장점: 중간 변환 커널 제거로 SM 사용률 감소, 버퍼 통합으로 GPU 메모리 사용량 감소, 이를 통한 동시 세션 처리량 증가.

### [Run High-Performance Core Math at Scale with NVIDIA nvmath-python](https://developer.nvidia.com/blog/run-high-performance-core-math-at-scale-with-nvidia-nvmath-python/)

`nvmath-python` `CUDA-X` `cuBLAS` `cuFFT` `numba-cuda` `Python`

> Python에서 CUDA-X 수학 라이브러리 성능을 CPU~멀티GPU까지 활용

#### 요약

- nvmath-python v1.0이 정식 출시되어, cuFFT·cuBLASLt·cuDSS·cuSPARSE·cuTENSOR·cuBLASMp 등 CUDA-X 및 NVPL 수학 라이브러리를 Python에서 그대로 사용할 수 있게 함.
- NumPy·CuPy·PyTorch 등 기존 배열 라이브러리와 함께 동작하며, CPU/GPU/분산 멀티노드 환경을 입력 데이터 위치에 따라 자동 선택.
- 범용(generic) API와 특화(specialized) API를 구분 제공하고, 상태 저장(stateful) API로 플래닝·오토튜닝 비용을 여러 실행에 걸쳐 상각 가능.
- numba-cuda와 연동해 커스텀 FFT 콜백이나 GPU 커널 내에서 nvmath-python의 디바이스 API(FFT, GEMM, 솔버, RNG)를 직접 호출 가능.

#### 시사점

- 저수준 C/C++ 인터페이스 없이 Python만으로 GPU 가속 수학 연산을 구현할 수 있어 과학 컴퓨팅·딥러닝 워크로드 개발 생산성이 높아짐.
- 커널 퓨전(fusion)과 오토튜닝을 통해 별도 최적화 없이도 유의미한 성능 향상을 얻을 수 있음.
- 기존 NumPy/CuPy 코드베이스를 크게 바꾸지 않고 CPU→GPU, 단일→분산 환경으로 점진적 확장이 가능.

#### 용어 설명

- **CUDA-X**: NVIDIA GPU용으로 최적화된 라이브러리·툴 모음(cuBLAS, cuFFT 등 포함).
- **GEMM**: 일반 행렬 곱셈(General Matrix Multiply) 연산.
- **커널 퓨전(kernel fusion)**: 여러 연산을 하나의 GPU 커널로 합쳐 중간 결과 저장/전송 비용을 줄이는 기법.
- **오토튜닝(autotuning)**: 여러 커널 구현 중 실측 성능을 비교해 최적의 것을 자동 선택하는 과정.
- **stateful/stateless API**: 매번 새로 계산 준비를 하는 방식(stateless)과 준비 결과를 재사용하는 방식(stateful) API.
- **JIT 컴파일**: 코드를 실행 시점에 즉석으로 컴파일하는 방식(numba-cuda가 사용).
- **UST(universal sparse tensor)**: 사용자가 도메인 특화 언어로 자신만의 희소 행렬 포맷을 정의할 수 있게 하는 기능.

#### 상세 내용

**설치와 유연성**

- pip, conda, uv, pixi 등 원하는 패키지 매니저로 설치 가능하며, 필요한 의존성만 골라 CI/CD나 CPU 전용 환경에서도 최소 설치가 가능.
- CPU 백엔드, 디바이스 API, 분산 API 지원 여부와 NumPy/CuPy/PyTorch 등 사용할 배열 라이브러리를 선택할 수 있음.
- 설치 명령 예시: `pip install nvmath-python[cu13]`

**기존 배열 라이브러리와의 관계**

- nvmath-python은 인덱싱·슬라이싱 같은 범용 배열 기능을 대체하지 않고, 핵심 수치 연산(core numerical operations)에 집중.
- NumPy 배열을 입력하면 NumPy 배열이 결과로 나오는 식으로 기존 워크플로우에 자연스럽게 통합됨.

**메모리·실행 공간 선택**

- cuBLAS·cuFFT 같은 GPU 라이브러리, NVPL(Grace/ARM)·Intel MKL(x86) 같은 CPU 라이브러리, cuBLASMp·cuSOLVERMp·cuFFTMp 같은 분산 라이브러리를 백엔드로 지원.
- `fft` 같은 연산의 실행 공간은 입력 텐서가 CPU/GPU 중 어디에 있는지에 따라 자동으로 결정되며, `execution` 인자로 직접 지정도 가능.
- 로깅 기능으로 연산이 어느 메모리·실행 공간에서 이루어졌는지 확인할 수 있어 불필요한 데이터 전송을 점검할 수 있음.

**범용 API vs 특화 API**

- 범용(generic) API는 CPU/GPU, 다양한 오퍼랜드 타입에 걸쳐 일관된 사용성을 제공하지만 설정 옵션은 공통 부분으로 제한됨.
- 특화(specialized, `advanced` 서브모듈) API는 GPU의 조밀(dense) 오퍼랜드 등 좁은 범위에 특화되어 하드웨어 효율을 극대화하는 세밀한 설정을 제공.
- 성능이 중요한 병목 구간에는 특화 API를, 성능이 중요하지 않은 작업에는 범용 API를 사용하는 것을 권장.

**복합 연산과 커널 퓨전**

- $\mathbf{D}=\alpha\mathbf{A}\cdot\mathbf{B}+\beta\mathbf{C}$처럼 산술 강도(arithmetic intensity)가 낮은 연산을 여러 커널 호출로 나누어 처리하면 비효율적.
- cuBLASLt 기반의 즉석 커널 퓨전(JIT kernel fusion)을 이용한 `matmul`은 단일 커널로 처리해 CuPy 조합 대비 큰 성능 향상을 보임.

![Significant performance speedup of fused kernels compared to unfused in low arithmetic intensity composite operations.](https://developer-blogs.nvidia.com/wp-content/uploads/2026/07/image-81.webp)

**Stateful API로 준비 비용 상각**

- 함수 호출형(stateless) API는 매번 플래닝·오토튜닝을 반복해 비용이 발생하지만, 클래스 기반(stateful) API는 플랜을 재사용해 반복 실행 시 이 비용을 상각 가능.
- 예시 코드는 `Matmul` 객체로 planning → autotuning → execute 세 단계를 분리해 배치 행렬 곱셈을 반복 수행.
- 오토튜닝된 플랜은 디스크에 직렬화해 다른 세션이나 동일 하드웨어의 여러 시스템에 재사용 가능.

![Stateless APIs add a constant overhead to each operation. Stateful APIs quickly amortize one-time initial costs](https://developer-blogs.nvidia.com/wp-content/uploads/2026/07/image-82.webp)

- 오토튜닝 효과는 하드웨어에 따라 다르며, 테스트 결과 NVIDIA RTX A6000에서는 최대 256%의 속도 향상을 보인 반면 NVIDIA B200은 기본 휴리스틱만으로 이미 최고 성능에 근접.

![Bar chart showing the percentage speedup from autotuning on two GPUs: NVIDIA RTX A6000 shows over 250% speedup, while B200 shows minimal gains for this example (indicating that the heuristics do a great job).](https://developer-blogs.nvidia.com/wp-content/uploads/2026/07/image-83.webp)
*이미지 출처: [원문](https://developer.nvidia.com/blog/run-high-performance-core-math-at-scale-with-nvidia-nvmath-python/)*

**커스텀 커널과의 통합**

- numba-cuda와 연동해 사용자 정의 Python 함수를 JIT 컴파일 후 nvmath-python 연산에 콜백(prolog/epilog)으로 삽입 가능.
- 예시로 이미지에 가우시안 필터를 적용하는 코드를 제시: 이미지를 R2C FFT → 주파수 영역에서 필터 곱 → C2R 역FFT로 처리하며, 필터 곱 연산을 커스텀 epilog로 컴파일해 FFT에 융합.

- 두 번째 시나리오는 numba-cuda로 작성한 GPU 커널 내부에서 nvmath-python의 디바이스 API(FFT, GEMM, LU/Cholesky/QR 직접 솔버, RNG)를 호출하는 것. 예시로 몬테카를로 주가 시뮬레이션(Geometric Brownian Motion)을 위한 커스텀 커널을 제시하며, nvmath-python의 RNG로 정규분포 난수를 생성해 numba-cuda 코드에서 경로를 계산.

**대상 독자**: 과학 계산·딥러닝·금융공학 등에서 Python으로 GPU 가속 수학 연산을 구현하려는 개발자, 특히 CUDA-X 라이브러리를 C/C++ 없이 활용하거나 커스텀 CUDA 커널과 결합하려는 개발자에게 유용하다.

### [Four Ways to Deploy More Secure AI Agents](https://developer.nvidia.com/blog/four-ways-to-deploy-more-secure-ai-agents/)

`AI Agent` `AI Red Team` `Cybersecurity` `LLM` `Prompt Injection` `Agentic AI`

> NVIDIA 레드팀이 밝힌 AI 에이전트 4대 취약점과 방어책

#### 요약

- NVIDIA AI Red Team이 6개월간 다양한 AI 에이전트를 평가한 결과, 접근 제어 부재·임의 코드 실행 허용·네트워크 아웃바운드 미제어·평문 시크릿 노출이라는 공통된 취약점을 발견했다.
- 사회공학, 점진적 유도(frog-boiling/Crescendo), 정상 워크플로 위장(패키지 설치 등) 세 가지 기법으로 프롬프트 기반 방어(시스템 프롬프트, LLM-as-a-judge)를 손쉽게 우회할 수 있었다.
- 프롬프트 기반 방어는 LLM의 확률적 특성을 그대로 물려받아 신뢰할 수 없으며, 모델의 제어 영역 밖에서 강제되는 결정론적(deterministic) 아키텍처 통제만이 실효성을 보였다.
- 접근 제어, 샌드박스화된 코드 실행, 기본 차단(default-deny) 네트워크 아웃바운드, 시크릿 격리 등을 권장 통제로 제시했다.

#### 시사점

- AI 에이전트를 사내 도구·데이터에 연결할 때 프롬프트 지시만으로는 보안을 담보할 수 없으며, OS·네트워크·시크릿 관리 계층에서 별도의 강제 통제가 필요하다.
- 코딩 에이전트에 Bash 등 명령 실행 도구를 부여할 경우 이는 사실상 임의 코드 실행 권한과 동일하다는 점을 설계 단계부터 인지해야 한다.
- 에이전트를 실제 서비스에 배포하려는 개발자는 최소 권한 원칙, 샌드박스, 시크릿 매니저, 아웃바운드 화이트리스트를 기본 아키텍처 요소로 반영해야 한다.

#### 용어 설명

- **AI Red Team**: 시스템의 취약점을 찾기 위해 공격자 관점에서 모의 공격을 수행하는 보안 조직/활동.
- **LLM-as-a-judge**: 한 LLM의 출력(예: 실행할 명령어)을 다른 LLM이 검토·승인하게 하는 방어 패턴.
- **RCE (Remote Code Execution)**: 공격자가 원격에서 임의의 코드를 실행할 수 있게 되는 취약점.
- **프롬프트 인젝션(Prompt Injection)**: 모델에 입력되는 텍스트에 악의적 지시를 숨겨 의도치 않은 동작을 유도하는 공격.
- **네트워크 이그레스(Network Egress)**: 내부 시스템에서 외부로 나가는 아웃바운드 네트워크 트래픽.
- **Crescendo 공격 (Frog-boiling)**: 여러 차례의 대화를 통해 점진적으로 신뢰를 쌓아가며 원하는 악의적 행동을 유도하는 공격 기법.
- **allowlist(허용목록)**: 명시적으로 허용된 항목만 통과시키고 나머지는 모두 차단하는 방식.

#### 상세 내용

**주요 실패 패턴 4가지**

NVIDIA AI Red Team은 채팅 연동형 에이전트를 중심으로 다양한 프레임워크의 AI 에이전트를 평가했다. 프레임워크와 무관하게 반복적으로 관찰된 취약점은 다음과 같다.

- 에이전트 접근 통제 부재: 사내망의 인증된 사용자라면 누구나 다른 사용자 명의의 자격 증명을 가진 에이전트에 접근 가능
- 임의 코드 실행을 가능케 하는 도구(예: Bash 셸)
- 네트워크 아웃바운드 미제어로 인한 데이터 유출·리버스 셸 경로
- 평문(plaintext) 형태로 에이전트에 노출된 시크릿

**접근 제어(Access Control)**

가장 흔한 실패는 에이전트 자체에 대한 접근 통제 부재였다. 개별 사용자의 자격 증명을 보유한 에이전트가 내부망의 모든 인증된 사용자에게 열려 있는 경우가 많았고, 이는 자격 증명 수집·오남용으로 이어졌다.

- 권장: 명시적으로 승인된 사용자만 에이전트와 상호작용하도록 제한
- 권장: 에이전트 권한을 호출 사용자의 권한과 일치시키는 최소 권한 원칙 적용

**코드 실행 제한**

많은 하네스가 범용성을 위해 Bash 셸이나 명령 실행 도구를 노출한다. 모델 출력이 명령 실행을 제어하는 구조에서는 공격자가 직접 입력이나 간접 프롬프트 인젝션으로 해당 출력에 영향을 미쳐 임의 명령을 실행시킬 수 있다.

- `pytest`, `npm install` 같은 개발 워크플로용 명령을 허용하도록 설계된 LLM-as-a-judge는 공격자가 조작한 입력이 섞이면 사실상 임의 명령 실행을 승인하는 구조가 된다.
- Python 스크립트 작성·실행이나 원격 패키지 설치를 요청하는 것만으로 리버스 셸을 포함한 완전한 RCE를 획득한 사례도 있었다.
- 명령줄 도구가 없어도 파일 읽기/쓰기 도구만으로 `~/.bashrc`, `.gitconfig`, `hooks.json`, `MCP.json`, 스킬 파일 등에 쓰기가 가능하면, 다른 프로세스가 해당 파일을 실행할 때 코드 실행으로 이어질 수 있다.

- 권장: 명령줄 도구는 가급적 피하고, 필요 시 엄격한 최소 권한 허용목록과 격리된 실행 환경, 강력한 네트워크 아웃바운드 통제를 함께 적용
- 권장: 비실행 워크스페이스 외부로의 쓰기를 OS 레벨에서 차단
- 권장: 파일명 등 외부 데이터를 명령줄에 전달할 때 경로 순회(path traversal)나 명령 인젝션을 막기 위해 반드시 정제·정규화

**네트워크 아웃바운드 기본 차단**

아웃바운드 네트워크 연결은 데이터 유출과 리버스 셸/SOCKS 같은 직접 연결 생성을 가능하게 한다. 네트워크 이그레스 통제가 적절히 적용된 환경에서는 모든 상호작용이 에이전트 프로세스를 거쳐야 했고, 이는 공격 속도를 늦추고 성공률을 떨어뜨렸다.

- 권장: 작업에 필요한 최소한의 엔드포인트만 허용하는 기본 차단(default-deny) 정책 적용
- 권장: 에이전트가 접하는 모든 네트워크 경계에서, 에이전트가 접근할 수 없는 환경 통제로 강제

**시크릿 격리**

에이전트는 플랫폼 토큰, API 키, VCS(버전관리시스템) 접근 토큰, 때로는 OAuth 리프레시 토큰까지 필요로 한다. 환경 변수로 시크릿을 주입하는 방식은 컨테이너 안에서 오직 자신의 코드만 실행될 때만 안전하며, 명령 실행 권한을 가진 에이전트와 환경을 공유하면 `env`, `printenv`, `/proc/self/environ` 등으로 직접 노출된다.

- git 저장소, `.env` 파일, bash 히스토리, `.netrc` 파일, OAuth 2.0 리프레시 토큰, 실행 환경의 환경 변수 등에서 토큰이 관찰됨
- 네트워크·파일시스템 통제로 직접 유출을 막아도, "frog-boiling" 방식으로 채팅 인터페이스를 통해 시크릿을 유도해낼 수 있었음

- 권장: 시크릿은 전용 시크릿 매니저에 저장하고 필요할 때만 프로세스 메모리로 가져오기
- 권장: 짧은 수명의 범위 제한 토큰을 사용하고 작업 완료 즉시 폐기

**결정론적 통제를 첫 방어선으로**

시스템 프롬프트로 위험 행동을 금지하거나 LLM-as-a-judge로 이중 검증하는 방식은 모두 LLM 자체의 확률적·불안정한 속성을 물려받는다. 아래 세 가지 기법이 이러한 방어를 일관되게 무력화시켰다.

- **사회공학**: "디버깅 중"이거나 "관리자"라는 맥락을 제시하는 것만으로 에이전트가 요청에 순응하는 경우가 많았다. 한 Slack 연동 에이전트는 리버스 셸을 직접 작성·실행하기도 했다.

![Dark-mode Slack screenshot showing an agent acknowledge a sanctioned red-team request, then create and execute a reverse-shell script.](https://developer-blogs.nvidia.com/wp-content/uploads/2026/07/image-80.webp)
*이미지 출처: [원문](https://developer.nvidia.com/blog/four-ways-to-deploy-more-secure-ai-agents/)*

- **Frog-boiling(Crescendo 공격)**: 여러 차례 대화를 통해 신뢰를 쌓고, 정상 워크플로 실행 중 발생한 오류의 "원인"이 시크릿과 관련되어 있다고 설득해 결국 시크릿을 노출시키도록 유도
- **정상 워크플로 위장**: 코딩 에이전트가 일상적으로 수행하는 패키지 설치 요청(예: `pip install git+https://…`)에 악성 패키지를 심어, 설치 과정에서 임의 코드가 실행되도록 유도

**권장 통제 목록**

동일한 결론은, LLM과 같은 제어 영역에 있는 방어(특히 프롬프트 기반)는 반복적으로 우회된다는 것이다. 통제는 모델의 제어 영역 밖에서 강제되어야 한다.

- 에이전트 접근 통제: 인증된 특정 사용자만 상호작용 허용
- 임의 명령 실행은 Docker, NVIDIA OpenShell, VM 등 강화된 샌드박스 환경에서만, 환경/설정 파일 자체 수정 불가하도록 제한
- 기본 차단 네트워크 아웃바운드, 작업에 필요한 특정 리소스만 최소 권한으로 허용
- 시크릿은 저장 상태(at rest)나 환경에 노출 금지, 시크릿 매니저와 온디맨드 접근, 가능하면 토큰 브로커를 통한 최소 권한·임시 토큰 사용
- 패키지 설치는 검증된 저장소에서만 허용, 임의 URL/VCS 기반 설치 기본 차단
- 도구·MCP·스킬 등은 최소 권한으로, 실행·쓰기·네트워크 접근 기능은 특히 면밀히 검토
- 영구 저장소도 최소 권한 원칙 적용, 볼륨 마운트는 가급적 피하고 쓰기 가능한 경로를 실행 경로에 마운트하지 않기
- LLM-as-a-judge 등에는 최신/프론티어 모델을 사용해 적대적 조작에 대한 견고성 확보

**대상 독자**: 사내 시스템·데이터에 연결되는 AI 에이전트(코딩 어시스턴트, 채팅 봇 등)를 설계·배포하는 개발자와 보안 엔지니어에게 유용하며, 특히 명령 실행 도구나 자격 증명을 다루는 에이전트 아키텍처를 검토할 때 참고할 수 있다.

### [NVIDIA Exemplar Cloud: Lessons for Unlocking Full Performance on AI Infrastructure](https://developer.nvidia.com/blog/nvidia-exemplar-cloud-lessons-for-unlocking-full-performance-on-ai-infrastructure/)

`NVIDIA GB200 NVL72` `NCCL` `H100` `NUMA` `ConnectX-8` `Exemplar Cloud`

> 동일 스펙 AI 클러스터도 설정 차이로 성능 8~12% 격차 발생, 4가지 실전 사례로 원인 진단

#### 요약

- 동일한 NVIDIA H100·GB200 NVL72·GB300 NVL72 시스템으로 구성된 클러스터라도 커널, 하이퍼바이저, BIOS, NCCL 설정 차이가 누적되면 NVIDIA 레퍼런스 아키텍처(RA) 대비 8~12%의 학습 처리량 격차가 발생한다.
- 이 격차는 NVIDIA Exemplar Cloud 인증에 필요한 95% 성능 기준을 통과하지 못하게 만드는 주요 원인이다.
- 글은 SMMU/가상화, CPU 전력·NUMA 배치, NCCL 큐페어 동시성, 컨테이너 내 환경변수 누락이라는 4개 계층에서 실제 파트너 클러스터 디버깅 사례를 다룬다.
- 각 사례마다 `perf`, Nsight Systems, `nccl-tests`로 포착한 구체적 신호와 이를 해결한 튜닝 방법을 제시한다.

#### 시사점

- 인프라 엔지니어와 성능 아키텍트는 공식 RA 검증 이전에 이 글의 진단 패턴을 자신의 클러스터에 선제적으로 적용해 값비싼 대규모 디버깅 세션을 줄일 수 있다.
- 하드웨어 스펙이 동일해도 소프트웨어/설정 계층의 미세한 차이가 실제 학습 성능에 큰 영향을 준다는 점을 구체적 수치로 확인할 수 있다.
- 컨테이너 환경에서는 호스트에서 정상으로 보이는 설정도 컨테이너 내부에 전파되지 않을 수 있으므로, 반드시 실제 실행 환경(컨테이너·런처·Slurm 할당) 내부에서 점검해야 한다.

#### 용어 설명

- **NCCL(NVIDIA Collective Communications Library)**: GPU 간 집합 통신(AllGather, ReduceScatter 등)을 처리하는 NVIDIA 라이브러리.
- **SMMU(System Memory Management Unit)**: Arm 아키텍처에서 가상화 시 메모리 매핑을 관리하는 하드웨어 유닛.
- **NUMA(Non-Uniform Memory Access)**: CPU와 메모리가 여러 노드로 분리되어 접근 속도가 노드별로 다른 시스템 구조.
- **VCMDQ(Virtual Command Queue)**: 게스트 VM이 SMMU 무효화 명령을 VM 종료(exit) 없이 하드웨어에 직접 전달할 수 있게 하는 기능.
- **QPS(Queue Pairs per Connection)**: InfiniBand/RoCE 네트워크 연결당 사용하는 큐페어 개수를 설정하는 NCCL 파라미터.
- **AllGather / ReduceScatter**: 분산 학습에서 GPU 간 데이터를 모으거나 나눠 합산하는 집합 통신 연산.
- **Exemplar Cloud**: NVIDIA가 클라우드 파트너의 클러스터 성능을 RA 대비 95% 이상으로 검증하는 프로그램.

#### 상세 내용

**사례 1: GB200 NVL72, 가상머신에서 FP8 사전학습이 12% 느림**

DeepSeek-V3 MoE(Mixture-of-Experts) FP8 사전학습을 VM에서 돌렸을 때 베어메탈 RA보다 반복(iteration) 시간이 12~14% 느렸다. Llama 3 70B 같은 dense 모델은 RA 대비 3% 이내 차이였지만, 작은 커널을 많이 호출하는 DeepSeek-V3 MoE에서만 격차가 두드러졌다.

- `perf record -a -g` 30초 캡처에서 `arm_smmu_cmdq_issue_cmdlist` 함수가 CPU 사이클의 24%를 차지.
- 이 함수는 Arm SMMU 커맨드 큐에 무효화(invalidation) 명령을 제출하는 함수로, 가상화 환경에서 게스트의 맵/언맵 작업마다 호스트로 트랩되어 단일 큐로 직렬화되며 병목이 발생.

![Linux perf icicle graph showing arm_smmu_cmdq_issue_cmdlist consuming ~24% of CPU time via memory-unmapping and TLB-flush paths during a virtualized DeepSeek-V3 workload, indicating significant Arm SMMU command-queue overhead.](https://developer-blogs.nvidia.com/wp-content/uploads/2026/07/image7-3.webp)
*이미지 출처: [원문](https://developer.nvidia.com/blog/nvidia-exemplar-cloud-lessons-for-unlocking-full-performance-on-ai-infrastructure/)*

- **해결책**: 호스트 커널에서 CMDQV/VCMDQ를 활성화하고 게스트에 노출. `tegra241-cmdqv` 드라이버가 포함된 커널과 이를 지원하는 하이퍼바이저(최신 QEMU/libvirt의 `cmdqv` IOMMU 속성)가 필요.
- 적용 후 `arm_smmu_cmdq_issue_cmdlist`가 상위 프레임에서 사라지고 dTLB 미스율이 베어메탈 수준으로 회복, 격차가 RA 허용 범위 내로 줄어듦.

**사례 2: H100 클러스터, CPU 경합과 NUMA 오배치로 12% 손실**

동일한 NCCL 버전과 NeMo 컨테이너를 사용한 H100 SXM5 클러스터가 Llama 3 70B 사전학습에서 RA보다 12% 느렸다. 커널 문제가 아닌 사용자 공간과 BIOS 설정 문제였다.

- `turbostat -i 1` 확인 결과, 3.8GHz 터보를 지원하는 SKU임에도 바쁜 코어와 유휴 코어 모두 3.0GHz에 고정, C-state가 C6가 아닌 C1에 머물러 있었음.
- `numastat` 확인 결과 학습 프로세스 메모리 접근의 약 18%가 원격 NUMA 노드로 향함.

원인은 두 가지였다.

- BIOS에서 C-state가 C1로 제한되어 있어 유휴 코어가 패키지 전력을 계속 소모, 바쁜 코어가 터보 클럭에 도달할 전력 여유가 없었음. C6로 전환을 허용하자 약 4% 성능 회복.
- 하이퍼바이저의 하우스키핑 스레드가 학습 프로세스의 데이터 로더 워커와 동일한 물리 코어에 배치되어 50~100ms 단위의 간헐적 지연 발생. `cpuset`으로 하이퍼바이저/호스트 서비스(코어 0-7, 56-63)와 학습 프로세스를 분리하여 해결.

결과적으로 12% 격차가 3%로 축소되었으며, 잔여 격차는 다음 사례(NCCL 튜닝)에서 다룬다.

**사례 3: GB300 NVL72 + ConnectX-8, 1.6Tbps 패브릭 저활용**

ConnectX-8 SuperNIC(노드당 1.6Tbps)를 탑재한 GB300 NVL72 클러스터가 Nemotron-4 15B 사전학습에서 31% 성능 격차를 보였다. 단일 노드는 정상이었지만 512 GPU 규모에서 AllGather/ReduceScatter 시간이 노출(exposed)되는 것으로 확인되어 컴퓨트가 아닌 집합 통신 경로가 원인으로 지목됐다.

- `NCCL_IB_QPS_PER_CONNECTION`을 기본값 1에서 4로 변경.
- RA 클러스터 기준 반복 시간이 약 1.09초에서 0.83초로 개선. AllGather 시간은 약 375ms→262ms, ReduceScatter는 약 389ms→273ms로 감소.

![Nsight Systems timelines comparing unoptimized (1.09 s) vs. optimized (0.76 s) iterations; red boxes highlight long AllGather/ReduceScatter regions in the top trace, green boxes show shorter collectives with better overlap at QPS=4 in the bottom.](https://developer-blogs.nvidia.com/wp-content/uploads/2026/07/image2-11.webp)
*이미지 출처: [원문](https://developer.nvidia.com/blog/nvidia-exemplar-cloud-lessons-for-unlocking-full-performance-on-ai-infrastructure/)*

- 비교군(0.76초)은 다른 NCCL 버전을 사용해 잔여 차이가 일부 존재했으나, NCCL 버전 변경은 Exemplar 튜닝 범위 밖이라 배포된 버전을 유지하는 것을 권장.
- **교훈**: QPS를 무조건 높이면 안 된다. 이는 패브릭·워크로드에 따라 달라지는 값이며, 실제 메시지 크기에서 테스트하고 대상 패브릭에서 값을 스윕한 뒤 학습 워크로드로 검증해야 한다.

**사례 4: 컨테이너까지 전달되지 않은 환경변수**

가상화된 B200 배포에서 호스트의 `nccl-tests`는 정상이었지만 학습 처리량이 RA 대비 13~53% 낮았다. `enroot` 컨테이너 내부에서 AllGather/ReduceScatter가 2~4배 느렸다.

- 원인: VM에는 `NCCL_TOPO_FILE`이 설정되어 있었지만, 이 변수와 토폴로지 파일(`/etc/nccl/topo.xml`) 모두 `enroot` 컨테이너에 마운트/전파되지 않아 NCCL이 자동 감지 모드로 폴백.
- **해결책**: `--mount type=bind,source=/etc/nccl/topo.xml,target=/etc/nccl/topo.xml`로 토폴로지 파일을 컨테이너에 바인드 마운트.
- **교훈**: 벤치마크를 실행할 실제 컨테이너·런처·Slurm 할당 내부에서 점검해야 한다. `echo $NCCL_TOPO_FILE && cat $NCCL_TOPO_FILE`을 잡 컨테이너 내부에서 실행하는 것이 가장 빠른 점검법이며, 경로가 잘못되면 NCCL이 오류 없이 조용히 실패해 진단이 까다롭다.

**사전 점검(Preflight) 체크리스트**

본격적인 워크로드 튜닝 전에 확인해야 할 항목들을 정리했다.

- GPU/하드웨어 상태: 클럭, 전력, 온도, NVLink 대역폭 (`nvidia-smi`, DCGM)
- Grace/VM 준비 상태: CMDQV 지원, 게스트 페이지 크기, IOMMU 패스스루 (`perf`, `dmesg`, 커널 설정)
- CPU 전력·배치: 터보 클럭, `cpuset` 격리, NUMA/PCT 바인딩 (`turbostat`, `numactl`)
- 런타임 토폴로지: 토폴로지 파일, NCCL 환경변수, 컨테이너 내 HCA 가시성 (`env`, `NCCL_DEBUG=INFO`)
- 패브릭 집합 통신: 워크로드 메시지 크기에서의 AllGather/ReduceScatter 동작 (`nccl-tests`)
- 워크로드 튜닝: 파이프라인 병렬화, 마이크로배치 크기, 통신 오버랩 (플랫폼 이슈 해결 후 진행)

**대상 독자**: 클라우드에서 대규모 GPU 클러스터를 운영하며 NVIDIA 레퍼런스 아키텍처 대비 성능 검증(Exemplar Cloud 인증 등)을 진행하는 인프라 엔지니어, 성능 아키텍트, MLOps 담당자에게 유용하다.

### [How to Self-Host a Validated AI Coding Assistant with NVIDIA NeMo Guardrails](https://developer.nvidia.com/blog/how-to-self-host-a-validated-ai-coding-assistant-with-nvidia-nemo-guardrails/)

`NVIDIA NIM` `NeMo Guardrails` `StarCoder2` `CI/CD` `Slopsquatting` `Prometheus`

> NeMo Guardrails·CI 검증·메트릭으로 자체 호스팅 AI 코딩 어시스턴트를 안전하게 운영

#### 요약

- 자체 GPU에서 StarCoder2-7B를 NVIDIA NIM으로 배포해 소스 코드 유출 없이 코드 완성 서비스 제공
- NeMo Guardrails가 인증·결제·암호화 등 "인간 전용" 경로 요청을 모델 도달 전에 차단
- CI 단계에서 환각(가짜) 패키지, 시크릿 유출, 라이선스 위반을 자동 검증
- 커밋 트레일러와 Prometheus/Grafana 메트릭으로 AI 지원 변경의 결함률·롤백률을 추적

#### 시사점

- 모델을 통제 지점(control plane)에서 제외하고 정책·검증·측정을 기존에 신뢰하는 시스템(CI, 모니터링)에 맡겨 이해 가능하고 감사 가능한 구조를 유지할 수 있음
- 규제·소버린·소스 민감 환경에서도 AI 코딩 어시스턴트를 도입할 수 있는 실전 청사진 제공
- 각 계층(서빙, 가드레일, CI, 추적성, 메트릭)을 독립적으로 도입할 수 있어 대규모 마이그레이션 없이 점진적 채택 가능

#### 용어 설명

- **NIM (NVIDIA Inference Microservice)**: OpenAI 호환 API를 제공하는 컨테이너 형태의 NVIDIA 모델 추론 서비스
- **NeMo Guardrails**: LLM 요청·응답에 정책 기반 검증(가드레일)을 적용하는 NVIDIA 오픈소스 프레임워크
- **StarCoder2-7B**: 코드 생성에 특화된 70억 파라미터 오픈소스 LLM
- **Slopsquatting**: AI가 지어낸 존재하지 않는 패키지명을 공격자가 실제 레지스트리에 등록해 악성코드를 배포하는 공급망 공격
- **SAST**: 소스 코드를 실행하지 않고 취약점을 분석하는 정적 애플리케이션 보안 테스트
- **SBOM/VEX**: 소프트웨어 구성요소 목록(SBOM)과 알려진 취약점의 실제 영향 여부를 기록한 문서(VEX)
- **Escape rate**: 코드 결함이 리뷰를 통과해 실제 프로덕션까지 도달한 비율

**전체 아키텍처**

개발자 IDE → NeMo Guardrails 프록시 → StarCoder2 NIM → CI 검증 → 리뷰/머지 → Prometheus/Grafana 메트릭이 다시 가드레일 정책을 조정하는 순환 구조다.

- 모델은 코드를 제안할 뿐, 정책 집행·의존성 검증·추적성·성과 측정은 모두 모델 밖의 신뢰된 시스템에서 담당
- 문제 발생 시 가드레일 정책, 의존성 스캔 결과, 프로덕션 메트릭 등 원인을 개별적으로 점검 가능

**1단계: StarCoder2를 NIM으로 배포**

NGC 카탈로그의 특정 버전을 고정해 `docker run`으로 StarCoder2-7B NIM 컨테이너를 GPU(최소 24GB, A10/L4/L40S/A100 등)에서 실행한다. BF16로 동작하며 H100/H200이 최고 처리량을 내지만 필수는 아니다.

- `/v1/health/ready`, `/v1/completions` 엔드포인트로 동작 확인
- 파일럿은 단일 GPU 호스트로 한 팀만 접근 허용, 확장 시 서비스 메시/로드밸런서와 시크릿 매니저 사용

**2단계: IDE에 NIM 연결**

Continue, Cursor, Cline 등 OpenAI 호환 base URL을 지원하는 IDE 어시스턴트에 로컬 NIM 엔드포인트(`http://localhost:8000/v1`)를 등록한다. IDE 어댑터만 교체 가능하게 하면 모델·정책·CI·메트릭 계층은 그대로 유지된다.

**3단계: NeMo Guardrails로 검증 계층 추가**

`nemoguardrails` 패키지로 정책 설정을 작성해 IDE와 NIM 사이에 프록시(포트 8100)를 둔다. `self_check_input` 액션이 요청이 인증·결제·암호화·특정 보안 경로(`src/security/`, `src/auth/`, `src/payments/`)를 건드리는지 판단해 해당 시 즉시 거부한다.

- 거부 시 모델은 호출되지 않고 "이 경로는 AI 사용 정책상 인간 전용입니다" 메시지 반환
- 초기에는 인증/인가/결제/암호화/배포 매니페스트/장애대응 자동화 등을 보수적으로 인간 전용 경로로 설정 권장

**4단계: CI 검증 게이트 추가**

`ai-assisted` 라벨이 붙은 PR에만 동작하는 워크플로를 추가해 단위 테스트, SAST(Semgrep), 시크릿 스캔(gitleaks), 환각 의존성(slopsquatting) 스캔, 라이선스 스캔을 순차 실행한다.

- 가장 중요한 단계는 slopsquatting 스캔: 모델이 지어낸 패키지명을 공격자가 실제 레지스트리에 등록해 악성코드를 유포하는 공급망 위협을 방지
- 관련 도구: **dep-hallucinator**(PyPI/npm/Maven/crates.io/Go, SBOM 출력), **slopgate**(PR diff 인식, SARIF 업로드), **XBOM**(CVE+slopsquatting+SBOM 통합)
- 라이선스 검증은 `pip-licenses`로 GPL/AGPL/LGPL/SSPL 등 카피레프트 계열 차단
- 에어갭 환경에서는 매니페스트 diff + 레지스트리 조회 기반의 자체 스크립트(약 40줄)로 대체 가능하나 유지보수 도구의 대체재는 아님
- StarCoder2 NIM 컨테이너 자체는 서명된 SBOM/VEX를 이미 제공하므로 이 게이트는 애플리케이션 의존성만 커버

**5단계: AI 지원 작업을 추적 가능하게 만들기**

`prepare-commit-msg` 훅으로 `AI_ASSISTANT` 환경변수가 설정된 경우 커밋 메시지에 `AI-Assistant`, `AI-Scope` 트레일러를 자동 추가한다. 목적은 특정 개발자를 추적하는 것이 아니라, AI 지원 변경이 리뷰 지연·롤백률·결함률에서 기준선과 다른지 측정하기 위함이다.

**6단계: 결과 메트릭 연결**

승인율만으로는 부족하므로 결함 escape rate, 롤백 빈도, 리뷰 지연시간, 인시던트 건수를 AI 지원 vs. 기준선으로 나눠 측정한다.

**선택: NeMo Framework로 도메인 적응**

기본 StarCoder2는 내부 API를 모르기 때문에 환각을 일으킬 수 있다. NVIDIA ChipNeMo 연구처럼 지속 사전학습(continued pretraining), 지도 미세조정, 검색 커스터마이징을 통해 내부 도메인에 맞게 모델을 개선할 수 있으며, 결과물은 NIM으로 패키징해 1단계에 그대로 대체 투입 가능하다.

**7단계: 전체 루프 검증**

허용 경로 요청 → 정상 완성, 인증 파일 수정 요청 → 정책 거부, 가짜 패키지명 PR → slopsquatting 스캔 실패, 정상 AI 지원 PR → 라벨·트레일러 확인, PR 되돌리기 → 롤백 카운터 증가, 5단계 스모크 테스트로 파이프라인을 검증한다.

**대상 독자**: 규제·소버린·소스 민감 환경에서 AI 코딩 어시스턴트를 안전하게 도입해야 하는 플랫폼 엔지니어, DevOps/보안 담당자에게 유용하다.

### [NVIDIA Ising Enables Fully Automated Quantum Computer Calibration with Enhanced In-Context Learning](https://developer.nvidia.com/blog/nvidia-ising-enables-fully-automated-quantum-computer-calibration-with-enhanced-in-context-learning/)

`Quantum Computing` `VLM` `Ising` `NVFP4` `DGX Spark` `In-Context Learning`

> 양자 컴퓨터 자동 캘리브레이션용 오픈소스 VLM, NVFP4로 로컬 배포까지 지원

#### 요약

- NVIDIA Ising Calibration 1.5는 양자 프로세서(QPU)의 진단 결과를 해석해 캘리브레이션(보정) 방법을 판단하는 오픈소스 비전 언어 모델(VLM)로, 사전 학습 예시 없이도 낯선 진단 결과를 분석할 수 있다.
- 이전 버전 대비 BF16 정밀도에서 크기가 11.4% 작아졌고, 관련 실험 예시를 활용하는 인컨텍스트 러닝(ICL) 성능이 86.68% 향상됐다.
- 초전도 큐비트, 양자점, 이온, 중성원자, 헬륨 위 전자 등 다양한 큐비트 방식의 파트너 제공 데이터로 학습됐으며, QCalEval 벤치마크로 성능을 평가한다.
- 처음으로 NVFP4 양자화 버전이 제공되어 단일 GPU나 NVIDIA DGX Spark에서도 실행 가능해졌다.

#### 시사점

- 양자 컴퓨팅 연구자가 클로즈드 소스 대형 모델 없이도 오픈 가중치 모델로 QPU 캘리브레이션을 자동화하는 에이전트 워크플로를 구축할 수 있다.
- NVFP4 양자화로 데이터센터급 GPU 없이도 로컬 랩 환경(단일 GPU, DGX Spark)에서 정확도 손실을 최소화하며 배포할 수 있어 진입 장벽이 낮아진다.
- 가중치, 데이터, 벤치마크, 배포 레시피가 모두 공개되어 특정 QPU에 맞춘 파인튜닝과 커스터마이징이 가능하다.

#### 용어 설명

- **QPU(Quantum Processing Unit)**: 양자 연산을 수행하는 하드웨어, 양자 컴퓨터의 핵심 칩.
- **VLM(Vision Language Model)**: 이미지와 텍스트를 함께 이해하고 처리하는 AI 모델.
- **캘리브레이션(Calibration)**: QPU가 정상 작동하도록 각종 파라미터를 진단·보정하는 작업.
- **NVFP4**: NVIDIA의 4비트 부동소수점 양자화 포맷으로, 모델 크기와 연산량을 줄여 저사양 하드웨어에서도 실행 가능하게 한다.
- **인컨텍스트 러닝(In-Context Learning, ICL)**: 모델이 별도 재학습 없이 프롬프트에 포함된 예시를 참고해 답을 추론하는 방식.
- **제로샷(Zero-shot)**: 사전 예시 없이 결과를 독립적으로 분석하는 방식.
- **QCalEval**: 양자 캘리브레이션 플롯 이해 능력을 측정하는 벤치마크.

#### 상세 내용

**모델 학습 방식**

Ising Calibration 1.5는 초전도 큐비트, 양자점, 이온, 중성원자, 헬륨 위 전자 등 다양한 큐비트 방식을 다루는 파트너들이 제공한 실제 데이터로 학습됐다.

- 캘리브레이션 및 제어에 특화된 여러 실험 데이터를 통합해 다양한 QPU 환경에 대응하도록 설계됐다.

**성능 평가: QCalEval 벤치마크**

QCalEval은 모델이 실험 결과 해석, 결과 분류, 유의성 평가, 피팅 품질 및 핵심 특징 평가, 다음 단계 제안 능력을 얼마나 잘 수행하는지 측정한다.

- 평가는 제로샷(사전 예시 없이 독립적으로 분석)과 ICL(관련 샘플을 참고해 분석) 두 가지로 진행된다.
- 제로샷에서는 비교 가능한 크기의 오픈 모델 중 최고 성능 대비 평균 10% 더 우수했다.
- ICL에서는 이전 버전 대비 86.5% 향상됐다.

### [Six Agent Harness Capabilities for Higher Model Performance](https://developer.nvidia.com/blog/six-agent-harness-capabilities-for-higher-model-performance/)

`AI Agent` `NOOA` `Agentic AI` `SWE-bench` `Cybersecurity` `Open Source`

> NVIDIA의 오픈소스 에이전트 프레임워크 NOOA, 하네스 설계로 성능·비용 동시 개선

#### 요약

- NVIDIA Labs가 공개한 오픈소스 연구 프리뷰 NOOA(NVIDIA Labs Object-Oriented Agents)는 에이전트를 단일 Python 클래스로 정의하는 프레임워크다.
- 타입이 지정된 입출력, 객체 참조 전달, 코드로서의 행동 등 6가지 인터페이스 설계 아이디어로 모델 성능을 끌어올린다.
- SWE-bench Verified(82.2%), CyberGym L1(86.8%), ARC-AGI-3(85.1% RHAE) 등 여러 벤치마크에서 벤치마크 특화 프롬프트 없이 높은 점수를 기록했다.
- 동일 정확도 기준 토큰 사용량을 절반 수준으로 줄이고, 컨텍스트 압축(compaction) 없이도 캐시 효율을 유지한다.

#### 시사점

- 에이전트를 일반 Python 코드처럼 diff, 코드리뷰, 유닛테스트, 버전관리할 수 있어 기존 소프트웨어 개발 워크플로를 그대로 적용할 수 있다.
- 하네스(harness) 설계만으로도 동일 모델에서 두 자릿수 퍼센트 포인트의 벤치마크 성능 차이와 큰 토큰 비용 차이를 만들 수 있음을 보여준다.
- 코드/취약점 검증처럼 결정론적 검증이 필요한 워크플로에서, 모델 추론과 강제된 검증 로직을 하나의 타입 객체 안에 통합할 수 있다.

#### 용어 설명

- **Harness(하네스)**: 모델을 감싸는 실행 구조로, 컨텍스트 구성·행동 실행·상태 관리·종료 판단 등을 담당하는 아키텍처.
- **SWE-bench Verified**: 실제 GitHub 이슈 해결 능력을 평가하는 소프트웨어 엔지니어링 벤치마크.
- **CyberGym L1**: 실제 취약점 재발견 능력을 측정하는 사이버보안 벤치마크.
- **ARC-AGI-3**: 미지의 규칙을 가진 그리드 게임에서 관찰과 행동만으로 규칙을 파악해야 하는 일반 추론 벤치마크.
- **RHAE**: ARC-AGI-3에서 사용하는 평가 점수 지표.
- **Pass by reference(참조 전달)**: 도구 실행 결과를 텍스트로 직렬화해 컨텍스트에 넣는 대신, 살아있는 Python 객체로 다루는 방식.
- **Context compaction(컨텍스트 압축)**: 대화 기록이 길어질 때 이를 요약해 컨텍스트 창에 맞추는 작업.

#### 상세 내용

**에이전트는 하나의 Python 객체다**

NOOA는 프롬프트 템플릿, 도구 스키마, 콜백 코드, 워크플로 그래프로 흩어져 있던 에이전트 개발 요소를 단일 Python 클래스로 통합한다.

- 클래스의 메서드는 에이전트의 능력(capability), 필드는 상태(state), docstring은 프롬프트 역할을 한다.
- 메서드 본문이 생략 부호(`...`)면 런타임에 LLM이 그 내용을 채워 실행하고, 일반적인 본문이 있으면 결정론적 Python 코드로 그대로 실행된다.
- 타입 애너테이션은 강제되는 계약(contract)으로 작동한다.

```python
class SupportAgent(Agent):
    """You are a support agent for a customer service system."""
    order_db: OrderDB
    def is_refund_eligible(self, order: Order) -> bool:
        """Return whether an order is eligible for a refund."""
        return order.delivered and order.days_since_delivery <= 30
    @strategy(PredictStrategy())
    async def classify(self, message: str) -> TicketKind:
        """Classify the customer message into the best ticket kind."""
        ...
```

이 덕분에 에이전트 개발이 일반 소프트웨어 개발과 동일해져, 사람과 AI 코딩 에이전트 모두 기존 도구(diff, 코드리뷰, 테스트, 추적, 버전관리, 리팩터링)를 그대로 사용할 수 있다.

**여섯 가지 핵심 인터페이스 아이디어**

NOOA 아키텍처는 모델 성능을 좌우하는 여섯 가지 설계 원칙을 제시한다.

- **Typed input/output**: 자유 텍스트가 아닌 타입 지정 인자와 검증된 반환값 사용
- **Pass by reference**: 직렬화된 덤프 대신 실제 Python 객체의 제한된 미리보기(bounded preview)를 모델이 보게 함
- **Code as action**: 모델이 제어 흐름과 인라인 메서드 호출이 포함된 Python 코드를 작성해 행동
- **Programmable loop engineering**: 오케스트레이션 루프도 개발자와 모델 모두가 작성 가능한 일반 Python 코드
- **Explicit object state**: 지속적이고 타입이 지정된 상태가 대화 기록이 아닌 에이전트 객체에 존재
- **Model-callable harness APIs**: 컨텍스트 블록과 이벤트 히스토리를 모델이 직접 조회·관리할 수 있는 API로 노출

**에이전트가 직접 큐레이션하는 장기 메모리**

NOOA는 백그라운드 자동 요약 파이프라인 대신, 모델이 직접 도구를 호출해 기록을 쓰고 조회하고 수정하는 방식의 장기 메모리 서브시스템을 갖췄다.

- 현재 턴과 관련된 "즉흥적 기억(spontaneous memories)"은 자동으로 컨텍스트에 표면화된다.
- 기록은 타입, 중요도, 태그를 가지며 "지지한다", "모순된다", "파생되었다" 같은 타입 관계로 연결되어 단순 로그가 아닌 지식 그래프를 형성한다.
- 백그라운드 **reflection** 작업이 중복 병합, 관련 기록 연결, 에피소드의 통찰 추출, 무의미해진 정보 정리를 수행한다.
- 모든 데이터는 사람이 읽을 수 있는 단일 SQLite 파일에 저장되어 팀이 검사·백업·리뷰할 수 있고, 여러 에이전트가 소유권을 유지하며 저장소를 공유할 수도 있다.
- ARC-AGI-3 평가에서 이 메모리 시스템은 파일 기반 노트 대비 RHAE를 +11.8점 개선했다.

**벤치마크 결과: 같은 모델에서 더 높은 성능**

- **소프트웨어 엔지니어링**: SWE-bench Verified에서 GPT-5.5로 **82.2%**(제출 당시 리더보드 SOTA 79.2%보다 높음), Opus 4.6으로 79.8%를 253줄짜리 범용 에이전트(벤치마크 특화 프롬프트 없음)로 달성.
- **사이버보안**: CyberGym L1에서 GPT-5.5로 **86.8%**를 기록해 오픈소스 에이전트 중 최고 점수이자 대다수 폐쇄형 시스템을 앞섬. 네트워크 접근을 차단하고 규칙 기반 "치트 체크"를 모든 실행 경로에 적용해, 공개된 취약점 검색이 아닌 코드 자체에 대한 추론으로 얻은 결과임을 확인.
- **일반 추론**: ARC-AGI-3에서 GPT-5.5 단일 에이전트가 평균 RHAE 50.2%(스킬: 가설 기반 베이스라인 대비 +8.5점, 메모리: 파일 기반 노트 대비 +11.8점), GPT-5.6-sol로 **85.1%**를 게임당 20달러 미만($17.85, $13.3)으로 달성해 점수-비용 파레토 프론티어를 확장.

**동일 성능, 절반의 토큰, 컨텍스트 압축 불필요**

GPT-5.5 기준 NOOA는 SWE-bench Verified에서 82.2%를 달성하는 데 29회의 LLM 호출과 약 110만 토큰만 사용한다.

- 비교 대상 하네스는 78.2%를 얻는 데 66회 호출과 220만 토큰이 필요했고, 78.6%를 얻는 데는 29회 호출과 130만 토큰이 필요했다.
- 이는 두 가지 메커니즘에서 비롯된다. 첫째, **pass by reference** 방식으로 도구 결과가 텍스트로 컨텍스트를 왕복하지 않고 실행 환경 안의 살아있는 Python 변수로 존재하며, 모델은 타입이 지정된 제한된 미리보기만 본다.
- 둘째, 이 특성 덕분에 NOOA는 프론티어 모델로 SWE-Bench를 풀 때 컨텍스트 압축이 필요 없다. 세션의 중간값 프롬프트 토큰은 200~400k 창(window) 대비 22~72k에서 정점을 찍으며, 트랜스크립트가 계속 추가만 되는(append-only) 형태로 캐시 유효성을 유지해 요약 과정 없이 프리필(prefill) 캐시 적중이 전체 작업에 걸쳐 누적된다.

**ARC-AGI-3에서 게임당 20달러 미만으로 85.1% RHAE 달성**

ARC-AGI-3는 에이전트가 규칙, 목표, 조작법을 모르는 그리드 게임에 배치되어 행동을 통해 이를 발견해야 하는 벤치마크다.

- NOOA 예시는 여섯 개의 전문화된 에이전트가 공유되는 실행 가능한 세계 모델(world model)을 중심으로 조율하는 동반 아키텍처 DreamTeam을 단일 에이전트와 45줄짜리 스킬로 축소한 버전이다.
- 게임은 별도 하네스 프로세스에서 실행되며 append-only 파일을 통해 상태와 행동을 주고받는다.
- 스킬은 에이전트가 관찰된 상태를 인코딩하고 다음 상태를 예측하는 Python 프로그램 집합으로 세계 모델을 구축하도록 지시한다. 매 턴마다 에이전트는 예측과 실제 결과를 비교(retrodict)하고 불일치 시 모델과 가설을 수정한다.
- 2시간 제한의 경쟁 모드에서 GPT-5.5 플릿은 평균 RHAE 50.2%를 기록했고, 세계 모델링 스킬이 가설 기반 베이스라인 대비 +8.5점, 메모리 서브시스템이 파일 기반 노트 대비 +11.8점 기여했다.
- GPT-5.6-sol 플릿은 게임당 약 $13.3로 **85.1%**를 달성했으며(25개 게임 중 19개 완전 해결), 두 플릿 모두 게임당 20달러 미만을 유지했다.

**취약점 탐지에 적용한 사례**

취약점 탐지는 에이전트 프레임워크에게 까다로운 시험대다. 후보 버그를 찾아낸 뒤, 이를 실제로 크래시를 유발하는 입력으로 증명해야 하며, 증명 단계는 크래시가 정확히 일치하고 재현 가능해야만 유효하다.

- NVIDIA 내부 연구에서는 검증 파이프라인을 단일 NOOA 객체로 구현했다. 모델은 에이전트 자신의 메서드를 호출하는 Python 코드를 작성·실행해, 탐색과 검증을 고정된 도구 메뉴가 아닌 한곳에 유지한다.
- 세 개의 결정론적 게이트(gate)가 있다: 검증기(verifier)의 원시 출력을 크래시 여부 판정으로 변환, 크래시가 보고된 취약점과 일치하는지 확인, 입력을 재실행해 재현되는지 확인.
- 게이트가 자유 형식 텍스트가 아닌 일반 타입 메서드이기 때문에, 코드가 승인해야만 발견이 인정되고 전체 실행 과정이 하나의 트레이스로 검사·테스트 가능하다.
- CyberGym L1(실제 취약점 재발견 벤치마크)에서 이 NOOA 기반 연구 하네스는 커머디티(범용) 모델과 네트워크 접근 없이 86.8%의 작업을 해결했다.

**오픈 에이전트 생태계를 위한 연구 프리뷰**

NVIDIA는 프레임워크, 캐패빌리티 테스트, 벤치마크 에이전트, 평가 방법론을 공개했다. 투명하고 타입이 지정된, 검사 가능한 에이전트와 사람이 읽을 수 있는 단일 상태 저장소, 조회 가능한 이벤트 히스토리를 통해 팀은 기존 보안 검토, 접근 제어, 관측성(observability) 관행을 그대로 적용해 구축할 수 있다. NOOA는 기존 하네스를 대체하는 것이 아니라 실험적으로 열려 있는 표면으로 제공되며, 기술 보고서를 통해 누구나 채택·검증·개선할 수 있도록 문서화되어 있다.

**대상 독자**: AI 에이전트 프레임워크를 직접 설계·개선하려는 개발자, 소프트웨어 엔지니어링·보안·추론 벤치마크에서 토큰 비용 대비 성능을 최적화하려는 엔지니어, 그리고 오픈소스 에이전트 아키텍처를 실험해보고 싶은 연구자에게 유용하다.

### [NVIDIA Nemotron 3 Ultra Leads Open Models on Accuracy and Efficiency in Agentic RTL Coding](https://developer.nvidia.com/blog/nvidia-nemotron-3-ultra-leads-open-models-on-accuracy-and-efficiency-in-agentic-rtl-coding/)

`Nemotron 3 Ultra` `RTL` `ACE-RTL` `EDA` `Agentic AI` `Mixture-of-Experts`

> Nemotron 3 Ultra, ACE-RTL 에이전트와 결합해 반도체 RTL 코딩에서 최고 정확도·효율 달성

#### 요약

- ACE-RTL 에이전트(생성-테스트-반성 반복 워크플로)와 Nemotron 3 Ultra를 결합해 CVDP 벤치마크의 9개 RTL 작업 카테고리에서 평균 97.1% 통과율 달성
- 디버깅/버그 수정(cid016) 과제에서 Nemotron 3 Ultra는 단독 65.7%에서 ACE-RTL 적용 시 100.0%로 향상
- 동일한 정확도를 GLM 5.2 대비 약 28%, Kimi K2.6 대비 약 71% 적은 토큰으로 달성
- Nemotron 3 Ultra는 RTL 코드 생성뿐 아니라 수정·디버깅 작업까지 포함한 합성 데이터 생성(SDG) 파이프라인으로 학습됨

#### 시사점

- 반도체 설계 엔지니어는 명세서 이해, 코드 재사용, 시뮬레이션 결과 해석, 버그 수정까지 이어지는 반복적 작업을 AI 에이전트에 위임할 수 있는 실질적 수준에 도달
- 토큰 효율이 높아 같은 컴퓨팅 예산으로 더 많은 RTL 작업을 처리하거나 더 빠른 반복 속도를 얻을 수 있음
- Cadence, Siemens, Synopsys 등 기존 EDA(전자설계자동화) 툴체인에 바로 연동 가능해 검증·사인오프 워크플로에 도입 장벽이 낮음

#### 용어 설명

- **RTL(Register Transfer Level)**: 디지털 회로의 동작을 신호와 레지스터 단위로 기술하는 하드웨어 설계 언어 수준
- **EDA(Electronic Design Automation)**: 반도체 회로 설계·검증을 자동화하는 소프트웨어 도구군
- **CVDP 벤치마크**: 실제 하드웨어 설계 상황을 반영한 Verilog(RTL 설계용 언어) 문제 평가 기준
- **ACE-RTL**: 생성기·리플렉터·코디네이터로 구성돼 RTL 코드를 반복적으로 생성·검증·수정하는 에이전트 프레임워크
- **Mixture-of-Experts(MoE)**: 전체 파라미터 중 일부만 활성화해 연산하는 신경망 구조로, 대형 모델을 효율적으로 운용
- **Mamba-Attention 하이브리드**: 상태공간모델(Mamba)과 어텐션을 결합해 긴 문맥 처리 시 연산 비용을 줄이는 아키텍처
- **QoR(Quality of Result)**: 칩 설계 결과물의 품질(속도, 면적, 전력 등)을 나타내는 지표

#### 상세 내용

**CVDP 벤치마크와 RTL 작업의 특성**

CVDP(Comprehensive Verilog Design Problems)는 RTL 코드 완성, 자연어 명세→코드 변환, 코드 수정, 모듈 재사용, 린팅/QoR 개선, 테스트벤치 자극/체커 생성, 어서션 생성, 디버깅 등 9개 카테고리로 구성된다. 짧고 독립적인 프롬프트 위주였던 기존 벤치마크와 달리 실제 하드웨어 설계 업무를 더 잘 반영한다.

RTL 코딩은 명세 이해, 기존 모듈 재사용·수정, 시뮬레이션 실패 해석, 디버깅까지 이어지는 본질적으로 에이전트적(agentic) 작업이며, 엔지니어들도 컴파일러·시뮬레이터·린트 도구·파형 검사 등과 반복적으로 상호작용하며 문제를 해결한다.

**ACE-RTL 에이전트 구조**

ACE-RTL은 생성기(generator), 리플렉터(reflector), 코디네이터(coordinator) 세 요소로 구성된다.

- 생성기: RTL 코드를 생성·수정
- 리플렉터: 시뮬레이션 피드백을 분석해 근본 원인을 파악하고 수정 방향 제시
- 코디네이터: 반복 과정 전반의 디버깅 컨텍스트를 관리해 이전 실패를 반영한 다음 시도를 유도

Nemotron 3 Ultra는 총 550B 파라미터 중 55B가 활성화되는 Mixture-of-Experts 기반 하이브리드 Mamba-Attention 모델로, 장기 실행 에이전트를 위해 설계됐다. 20조 개의 텍스트 토큰으로 사전학습됐고 컨텍스트 길이는 100만 토큰까지 확장됐다.

- MoE 구조: 활성 파라미터당 정확도 향상
- 다른 오픈 모델 대비 최대 5배 높은 처리량, 30% 낮은 비용

RTL 워크플로에서는 명세서, 모듈 코드, 생성된 RTL, 시뮬레이터 출력, 어서션 실패, 이전 수정 시도 등으로 에이전트 컨텍스트가 빠르게 늘어나기 때문에 효율적인 장문 컨텍스트 추론이 실용성에 직결된다.

**RTL 작업을 위한 학습 방법**

Nemotron 3 Ultra의 RTL 능력은 ACE-RTL 논문에서 제안된 합성 데이터 생성(SDG) 파이프라인에서 비롯됐다. 공개 저장소에서 선별한 고품질 RTL 시드 설계를 기반으로, 오픈 LLM이 이를 명세→코드 예제로 변환한다.

- 핵심은 작업 다양성: 명세→RTL 생성 외에도 코드 편집, 디버깅 작업까지 포함
- 편집 작업: 원본 시드 RTL을 정답으로, 단순화된 버전을 입력으로 사용
- 디버깅 작업: 유한상태기계(FSM) 전이 오류, 핸드셰이크/타이밍 위반 등 실제 발생하는 오류를 시드 설계에 주입하고, 관찰된 실패 동작 등 진단 정보를 명세에 포함
- 모든 샘플은 문법 검사, 벤치마크 오염 제거, LLM 심사(judge) 기반 루브릭 채점을 거쳐 필터링

이런 편집·디버깅 작업 학습은 에이전트 워크플로에서 모델이 이전 코드, 실패한 테스트, 도구 피드백을 바탕으로 추론해야 하는 실제 상황과 직결된다.

**EDA 파트너 연동**

Nemotron 3 Ultra는 오픈 모델로서 기존 EDA 툴에 바로 통합 가능하다.

- Cadence: ChipStack AI SuperAgent와 결합해 RTL 생성, 테스트벤치 작성, 회귀 테스트 오케스트레이션, 디버깅을 조정하는 에이전트 오케스트레이션 제공. InnoStack, ViraStack, AuraStack 등 다른 Super Agent 제품군에도 적용
- Siemens: Questa One Agentic Toolkit, Fuse EDA AI Agent와 연동해 최대 5~10배 높은 토큰 효율의 장기 실행 자가검증 에이전트 지원
- Synopsys: AgentEngineer의 멀티 에이전트 시스템을 통해 연속적·추적 가능한 검증 피드백 루프 제공, Openshell Sandbox로 수 주 걸리던 수동 검증을 수 시간으로 단축

**대상 독자**: 반도체 RTL 설계·검증 엔지니어, EDA 툴체인에 AI 에이전트를 통합하려는 개발자, 오픈 LLM 기반 코딩 에이전트의 효율성·정확도 비교에 관심 있는 개발자에게 유용하다.

### [Advancing Semiconductor Innovation Across Materials Engineering and Manufacturing](https://developer.nvidia.com/blog/advancing-semiconductor-innovation-across-materials-engineering-and-manufacturing/)

`CUDA-X` `PhysicsNeMo` `Omniverse` `DFT` `Digital Twin` `Semiconductor Manufacturing`

> NVIDIA와 Applied Materials가 원자 단위 소재 발견부터 팹 최적화까지 시뮬레이션으로 연결

#### 요약

- NVIDIA와 Applied Materials가 원자 단위 소재 설계, 공정(챔버) 개발, 팹(공장) 운영 최적화를 하나로 잇는 엔드투엔드 디지털 개발 모델을 구축
- Ginestra 플랫폼에 NVIDIA cuDSS를 결합해 소재 결함-성능 예측 시뮬레이션을 CPU 대비 최대 10배 가속
- cuEST로 DFT(밀도범함수이론) 기반 전자구조 계산을 가속해, 5일 걸리던 시뮬레이션을 단일 GPU로 약 2시간(약 55배)만에 처리
- ACE+ 플랫폼과 PhysicsNeMo로 챔버 다중물리 시뮬레이션을 최대 35배 가속하고, Omniverse로 팹 전체의 실시간 디지털 트윈 구현

#### 시사점

- GPU 가속 시뮬레이션으로 실험 없이도 방대한 소재·공정 조합을 가상 탐색할 수 있어, 반도체 소재·공정 개발 주기가 크게 단축됨
- 원자 스케일부터 공장 스케일까지 시뮬레이션이 연결되면서, 개발자는 각 CUDA-X 라이브러리(cuDSS, cuEST)를 활용해 도메인별 시뮬레이션 코드를 GPU로 손쉽게 가속할 수 있는 참고 사례를 얻을 수 있음

#### 용어 설명

- **CUDA-X**: NVIDIA GPU에서 다양한 과학·공학 계산을 가속하는 라이브러리 모음
- **cuDSS (CUDA Direct Sparse Solver)**: 희소 선형대수(대부분 값이 0인 행렬 연산) 계산을 GPU로 가속하는 라이브러리
- **cuEST (CUDA Electronic Structure Theory)**: 양자화학의 전자구조 계산(분자·물질의 전자 배치를 수학적으로 푸는 작업)을 GPU로 가속하는 라이브러리
- **DFT (Density Functional Theory, 밀도범함수이론)**: 물질의 전자구조를 계산해 물성을 예측하는 양자역학 기반 표준 계산 방법
- **GAA (Gate-All-Around) 트랜지스터**: 게이트가 채널을 사방에서 감싸는 차세대 반도체 트랜지스터 구조
- **NVIDIA PhysicsNeMo**: 시뮬레이션 데이터를 실시간 디지털 트윈으로 변환하는 물리 AI 프레임워크
- **NVIDIA Omniverse**: 데이터·모델·워크플로를 연결해 물리적으로 정확한 디지털 트윈을 구축하는 플랫폼

### [ModelExpress: Distributing Model Artifacts at the Speed of Light](https://developer.nvidia.com/blog/modelexpress-distributing-model-artifacts-at-the-speed-of-light/)

`ModelExpress` `NIXL` `RDMA` `vLLM` `DeepSeek-V4-Pro` `RL-post-training`

> 모델 가중치를 GPU 간 P2P RDMA로 직접 전송해 서빙 콜드스타트를 대폭 단축

#### 요약

- NVIDIA ModelExpress(MX)는 모델 로딩 시 원격 스토리지 대신 이미 GPU에 적재된 동일 가중치를 가진 다른 서빙 레플리카를 찾아 P2P RDMA로 직접 전송한다.
- DeepSeek-V4 Pro(806GiB) 기준 가중치 및 JIT 커널 캐시 전송이 10초 이내에 끝나 전체 시작 시간이 8분에서 1분 44초로 줄었다.
- 첫 워커는 오브젝트 스토리지 스트리밍, 로컬 GDS(GPUDirect Storage), 클러스터 공유 캐시 등으로 부트스트랩하고, 이후 워커들은 이미 서빙 중인 피어로부터 GPU-to-GPU로 가중치를 받아온다.
- 동일한 P2P 전송 방식을 JIT 컴파일된 커널 캐시 공유와 RL(강화학습) 후속 학습 시의 가중치 업데이트 배포에도 확장 적용했다.

#### 시사점

- 대형 모델(수백 GB~TB급) 서빙 환경에서 오토스케일링, 롤링 업데이트, 콜드스타트 시 반복되는 가중치 이동 비용을 획기적으로 줄일 수 있다.
- vLLM, SGLang과 네이티브 통합되며 Dynamo, llm-d 등 서빙 프레임워크에서 활용 가능해 실제 인프라에 적용 가능성이 높다.
- RL 후속학습 파이프라인에서 트레이너와 롤아웃 워커 간 가중치 동기화 지연을 줄여 학습 루프 전체 속도를 높일 수 있다.

#### 용어 설명

- **NIXL**: NVIDIA Inference Xfer Library. GPU 간 고속 데이터 전송을 담당하는 라이브러리로 다양한 네트워크 백엔드를 지원한다.
- **RDMA (Remote Direct Memory Access)**: CPU 개입 없이 네트워크를 통해 메모리 간 데이터를 직접 주고받는 기술로 매우 빠른 전송이 가능하다.
- **GDS (GPUDirect Storage)**: 로컬 스토리지에서 호스트 메모리를 거치지 않고 GPU 메모리로 데이터를 직접 읽어오는 기술.
- **Model Streamer**: 체크포인트 파일을 로컬 디스크에 내려받지 않고 CPU 버퍼를 통해 GPU로 스트리밍하는 로더.
- **TP (Tensor Parallel)**: 하나의 모델을 여러 GPU에 텐서 단위로 분할해 병렬로 연산하는 방식.
- **JIT 컴파일 / CUDA Graph**: 추론 엔진이 첫 실행 시 특정 모델·GPU에 맞춰 커널을 즉석 컴파일하고 실행 그래프를 캡처하는 과정으로, 시간이 오래 걸릴 수 있다.
- **RL post-training**: 사전 학습된 모델을 강화학습으로 추가 튜닝하는 과정으로, 매 스텝마다 가중치가 갱신된다.

#### 상세 내용

**ModelExpress의 핵심 아이디어**

모델을 로드하기 전에 "호환되는 가중치 사본이 이미 어딘가에 있는가"를 먼저 확인하는 방식이다. 매 레플리카를 독립적인 콜드스타트로 취급하지 않고, 가장 빠른 소스와 전송 경로를 자동으로 선택한다.

- 서빙 중인 피어가 GPU에 호환 가중치를 갖고 있으면 NIXL을 통한 P2P RDMA로 GPU-to-GPU 직접 전송
- 피어가 없으면 오브젝트 스토리지에서 디스크를 거치지 않고 스트리밍하는 방식으로 부트스트랩

![ModelExpress 개요. 제어 플레인은 Redis 또는 Kubernetes 메타데이터로 호환 소스를 탐색하고, 데이터 플레인은 우선순위 체인에 따라 전송한다.](https://developer-blogs.nvidia.com/wp-content/uploads/2026/07/image2-14.webp)
*이미지 출처: [원문](https://developer.nvidia.com/blog/modelexpress-distributing-model-artifacts-at-the-speed-of-light/)*

**첫 워커 부트스트랩 (스토리지 → GPU)**

- **오브젝트 스토리지**: Model Streamer가 멀티스레드로 safetensors 텐서 범위를 동시에 가져와 CPU 스테이징 버퍼를 거쳐 GPU로 파이프라이닝한다. 로컬 디스크에 내려받지 않아 중간 다운로드/재적재 과정이 사라진다.
- **클러스터 공유 캐시**: 10개 레플리카가 동시에 806GiB DeepSeek-V4 Pro를 받으면 약 8TiB 트래픽이 발생하는데, MX Model Cache Service는 메타데이터 스토어에서 원자적 클레임으로 다운로더 하나만 선정하고 나머지는 캐시를 재사용해 외부 다운로드 비용을 한 번만 지불한다.
- **로컬 스토리지 + GDS**: GDS가 지원되면 NIXL의 멀티스레드 GDS 백엔드로 호스트 메모리를 거치지 않고 로컬 파일을 GPU 메모리로 직접 읽는다. 자동 감지 후 미지원 시 다른 경로로 폴백한다.
- **로컬 스토리지 + Model Streamer**: GDS가 없을 때는 OS 스레드가 safetensors를 CPU 버퍼로 동시에 읽으면서 완료된 텐서는 GPU로 옮기고 디스크 I/O와 GPU 배치를 오버랩한다.

**이후 워커: 서빙 피어로부터 P2P 전송**

이미 서빙 중인 레플리카는 가중치가 GPU에 상주하고 후처리·레이아웃까지 끝난 상태다. MX는 이를 소스로 삼아 GPU-to-GPU 직접 전송하며, 새 레플리카는 로딩 완료 후 다시 소스 풀에 합류해 팬아웃 방식으로 확장된다.

- 제어 플레인(Redis, Kubernetes CRD, k8s-service)이 호환 피어를 탐색하고 전송 메타데이터를 교환
- 데이터 플레인은 NIXL을 기본 전송 엔진으로 사용하며 InfiniBand, RoCE, NVLink, EFA 등 다양한 네트워크 백엔드 지원
- 모델·런타임 설정에서 계산된 `mx_source_id`로 텐서 레이아웃이 일치하는 피어만 대상으로 함

**NIXL 메모리 등록 오버헤드 최적화**

RDMA 전송 전 GPU 메모리는 `ibv_reg_mr` 호출로 등록해 원격 키(rkey)를 받아야 하는데, 텐서가 수만 개면 이 등록 과정 자체가 부담이 된다.

- **Pool registration**: 텐서 단위가 아닌 `cudaMalloc` 할당 단위로 한 번만 등록해 등록 횟수를 80~99% 절감
- **VMM arena registration**: `CUDAPluggableAllocator`로 모든 로드 시점 할당을 16TiB 단일 가상주소 아레나에 모으고, 로드가 끝나면 사용된 범위 전체를 dmabuf 기반 메모리 영역 하나로 등록. 등록 호출이 텐서당 1회에서 전체 1회로 감소

**런타임 경로 선택과 안전한 폴백**

시작 시 사용 가능한 기능을 프로빙해 우선순위대로 시도한다: `P2P RDMA → ModelStreamer → GDS → 기본 로더(호스트 스테이징 POSIX I/O)`.

- 전송 시작 전 실패는 자동으로 다음 경로로 폴스루
- 가중치가 이미 일부 적재된 후 실패하면 모델을 재초기화해 부분 기록된 가중치가 서빙되지 않도록 방지
- P2P는 전송 시작 전 메타데이터 실패에 한해 다른 피어로 재시도

**JIT 커널 캐시 상속**

가중치 로딩이 끝나도 첫 forward pass에서 torch.compile, Triton, DeepGEMM, TileLang 등의 커널을 JIT 컴파일하고 CUDA Graph를 캡처하는 과정이 수 분씩 걸릴 수 있다. MX가 가중치 로딩을 줄이면 오히려 이 컴파일 비용이 시작 시간의 주요 병목이 된다.

![ModelExpress가 가중치 로딩 지연을 제거한 후 JIT 커널 컴파일이 DeepSeek-V4-Pro 시작 시간의 주요 병목이 되는 것을 보여주는 누적 막대 그래프](https://developer-blogs.nvidia.com/wp-content/uploads/2026/07/image8-1.webp)

MX의 Artifact Transfer API는 파일 기반 커널 캐시(Triton, DeepGEMM, TileLang, CuTe DSL, FlashInfer 등)를 NIXL의 CPU-to-CPU RDMA 경로로 등록된 호스트 메모리 버퍼 간에 직접 전송하고 검증 후 대상 엔진의 캐시 디렉터리에 설치한다. Kubernetes의 공유 RWX 볼륨이 필요 없고, 아티팩트 전용 `mx_source_id`로 비호환 레플리카 간 재사용을 방지한다.

**RL 후속학습에서의 가중치 갱신**

RL 후속학습에서는 트레이너가 매 스텝 정책을 갱신하고, 롤아웃 워커는 다음 세대 생성 전에 갱신된 가중치를 받아야 한다. MX는 이를 수신자 주도(receiver-driven) 방식으로 처리한다.

1. **Publish**: 각 트레이너 랭크가 보유한 텐서/샤드와 shape, dtype, 배치, 파라미터 매핑 메타데이터를 MX에 알림
2. **Discover**: 롤아웃 워커가 요청한 가중치 버전과 사용 가능한 소스를 MX를 통해 조회
3. **Plan**: 수신자가 자신의 목표 레이아웃에 맞춰 필요한 텐서/범위와 소스를 매핑
4. **Pull, convert, load**: 수신자가 해당 소스에 대해 원사이드(one-sided) 읽기를 수행

![트레이너 랭크가 제어 플레인에 텐서 소유권을 알려 소스를 탐색하게 하고, 롤아웃 워커가 NIXL을 통해 트레이너 랭크로부터 직접 갱신된 가중치를 가져오는 ModelExpress RL refit 흐름을 보여주는 다이어그램](https://developer-blogs.nvidia.com/wp-content/uploads/2026/07/image7-4.webp)
*이미지 출처: [원문](https://developer.nvidia.com/blog/modelexpress-distributing-model-artifacts-at-the-speed-of-light/)*

MX는 이 수신자 주도 refit의 핵심 빌딩 블록을 제공하며, 여러 고객이 실제 통합을 검증 중이다. Fireworks/Cursor, Cognition 등이 사용하는 델타 가중치 diff refit(크로스 클러스터 가중치 전송) 기법도 테스트하고 있다.

**대상 독자**: 대형 언어모델을 자체 GPU 클러스터에서 서빙·오토스케일링하거나 RL 기반 후속학습 파이프라인을 운영하는 인프라/ML 엔지니어에게 유용하다.

### [Debugging Ray Tracing Applications Using NVIDIA OptiX Toolkit](https://developer.nvidia.com/blog/debugging-ray-tracing-applications-using-nvidia-optix-toolkit/)

`NVIDIA OptiX` `Ray Tracing` `CUDA` `GPU Debugging` `OptiX Toolkit`

> OptiX Toolkit로 GPU 레이 트레이싱 앱의 에러 체크와 디버그 출력을 표준화

#### 요약

- NVIDIA OptiX Toolkit(OTK)은 OptiX 기반 레이 트레이싱 앱 개발에 흔히 필요한 디버깅 유틸리티를 제공하는 GitHub 저장소로, BSD 3-clause 라이선스로 자유롭게 수정 가능하다.
- `OTK_ERROR_CHECK` 매크로로 OptiX·CUDA 드라이버/런타임 API의 에러 코드를 일관되게 검사할 수 있다.
- `DebugLocation` 구조체와 `debugInfoDump` 함수로 GPU에서 특정 픽셀(런치 인덱스)에 대해서만 타겟팅된 디버그 출력을 할 수 있다.
- 예제 프로그램 DemandPbrtScene에서 이 디버깅 기능들이 ImGui 기반 UI와 함께 실제 적용된 모습을 보여준다.

#### 시사점

- 수천 개의 스레드가 동시에 실행되는 GPU 코드에서 `printf` 디버깅은 출력이 넘쳐 원인을 찾기 어려운데, OTK는 원하는 픽셀/스레드에서만 정보를 출력하도록 제한해 이 문제를 해결한다.
- 에러 체크 매크로를 인라인 함수로 위임하는 구조 덕분에 디버거에서 브레이크포인트를 걸어 에러 발생 시점을 바로 잡아낼 수 있다.
- OptiX·CUDA를 함께 쓰는 프로젝트에서 API별로 제각각이던 에러 처리 코드를 하나의 매크로/헤더 패턴으로 통일할 수 있다.

#### 용어 설명

- **NVIDIA OptiX**: GPU에서 레이 트레이싱을 수행하기 위한 NVIDIA의 애플리케이션 프레임워크.
- **OptiX Toolkit (OTK)**: OptiX 개발에 필요한 재사용 가능한 유틸리티를 모아둔 GitHub 저장소.
- **OptixResult**: OptiX API 함수가 반환하는 에러 코드 열거형 타입.
- **CUDA driver API / runtime API**: NVIDIA GPU를 제어하는 두 가지 수준의 CUDA 프로그래밍 인터페이스.
- **launch index**: GPU에 커널을 실행(launch)할 때 각 스레드를 식별하는 좌표(픽셀 위치 등).
- **pbrt**: 물리 기반 렌더링(physically based rendering) 연구용 오픈소스 렌더러 및 그 씬 파일 포맷.
- **ImGui**: C++용 즉시 모드(immediate mode) GUI 라이브러리.

#### 상세 내용

**OptiX 로깅과 검증(Validation)**

OptiX 디바이스 컨텍스트를 생성할 때 로그 콜백과 검증 모드를 설정할 수 있다.

- 검증 모드를 `OPTIX_DEVICE_CONTEXT_VALIDATION_MODE_ALL`로 설정하면 API 입력값을 자동으로 검사한다.
- 검증 오류는 사람이 읽을 수 있는 메시지로 로그에 출력되며, `OPTIX_ERROR_INVALID_VALUE` 같은 에러의 1차 확인 지점이 된다.
- 검증에는 추가 비용이 들기 때문에 디버그/테스트 빌드에서는 활성화하고 릴리스 빌드에서는 끄는 것이 권장된다.

**에러 코드를 일관되게 체크하는 방법**

OptiX, CUDA 드라이버 API, CUDA 런타임 API 모두 비슷한 패턴(0이 아니면 에러, 에러 이름 문자열, 사람이 읽을 메시지)을 갖는다. 매번 수동으로 처리하면 번거롭고 실수하기 쉬워, OTK는 이를 매크로로 표준화한다.

- `OTK_ERROR_CHECK( expr )`: 에러 시 예외를 던짐
- `OTK_ERROR_CHECK_NOTHROW( expr )`: 에러 시 `std::cerr`에 메시지만 출력하고 계속 진행
- 매크로는 최소한만 사용되고 실제 작업은 인라인 함수(`checkError`, `makeErrorString`, `getErrorName`, `getErrorMessage`)에 위임되므로, 디버거로 해당 함수에 브레이크포인트를 걸 수 있다.
- 에러 메시지 형식: `file(line): expr failed with error nnn (name): message`
- API별 헤더가 따로 제공된다.

| 헤더 | API |
|---|---|
| `<OptiXToolkit/Error/cuErrorCheck.h>` | CUDA driver API |
| `<OptiXToolkit/Error/cudaErrorCheck.h>` | CUDA runtime API |
| `<OptiXToolkit/Error/optixErrorCheck.h>` | OptiX API |

사용 예시:
```
OTK_ERROR_CHECK( cudaSetDevice( m_deviceIndex ) );
OTK_ERROR_CHECK( cuCtxGetCurrent( &m_cudaContext ) );
OTK_ERROR_CHECK( cuStreamCreate( &m_stream, CU_STREAM_DEFAULT ) );
OTK_ERROR_CHECK( optixInit() );
```

**타겟팅된 디바이스 측 디버그 출력**

GPU 코드 디버깅에는 두 가지 흔한 방법이 있지만 각각 한계가 있다.

- CUDA 디버거로 디버그 빌드를 검사: 디버그 빌드는 너무 느려 인터랙티브 앱에서 쓰기 어렵다.
- 릴리스 빌드에서 `printf` 사용: 동시에 실행되는 수많은 스레드 때문에 출력이 흘러넘치고, 문제가 특정 인터랙션 이후에만 발생하면 그 전의 출력은 노이즈가 된다.

이를 해결하기 위해 `<OptiXToolkit/ShaderUtil/DebugLocation.h>`가 제공하는 `DebugLocation` 구조체를 사용한다.

```
struct DebugLocation
{
    bool  enabled;
    bool  dumpSuppressed;
    bool  debugIndexSet;
    uint3 debugIndex;
};
```

디버그 출력은 다음 조건을 모두 만족할 때만 발생한다.

- `enabled`가 true
- `dumpSuppressed`가 false
- `debugIndexSet`가 true이고, 현재 런치 인덱스가 `debugIndex`와 일치

이 구조체를 OptiX 파이프라인의 launch parameter에 포함시키면 실행 중 인터랙티브하게 디버그 출력을 제어할 수 있다.

**`debugInfoDump` 함수와 콜백**

```
template <typename Callback>
static __forceinline__ __device__
bool debugInfoDump( const DebugLocation& debug, const Callback &callback )
```

콜백 구조체는 `setColor`(디버그 위치를 화면에 시각적으로 표시)와 `dump`(원하는 정보를 출력) 두 메서드를 구현해야 한다.

- 디버그 위치는 빨간 픽셀이 검은색 1픽셀 테두리, 흰색 1픽셀 테두리로 둘러싸여 고대비로 표시된다.
- 컬러 버퍼가 아닌 출력 대상이라면 RGB 값을 원하는 방식으로 매핑해 시각화할 수 있다.

**원샷(one-shot) 모드**

출력 폭주를 막기 위해 사용자가 원할 때 한 번만 덤프하는 절차를 제안한다.

1. `DebugLocation` 메커니즘 활성화 후 평소대로 launch
2. 사용자가 디버그 위치를 선택하면 `dumpSuppressed=true`, `debugIndexSet=true`, `debugIndex` 설정 → 이후 launch는 위치만 표시하고 덤프는 안 함
3. 사용자가 앱을 조작해 원하는 상태로 만든 뒤 `dumpSuppressed=false`로 설정하고 launch하면 그 시점에만 덤프 출력, 이후 다시 `true`로 되돌림

**DemandPbrtScene 예제**
